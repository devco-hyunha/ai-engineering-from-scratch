빌더 에이전트가 이미 워크벤치 산출물을 생성하고 있는 상황에서, 이를 읽고 구조화된 보고서를 작성하는 리뷰어를 설정해 보세요.

생성할 항목:

1. `agents/reviewer.md`: 리뷰어 시스템 프롬프트(System Prompt)가 포함된 파일. 읽기 전용 접근 권한, 5차원 평가 기준, 각 점수에 대해 산출물 경로를 인용해야 함.
2. `tools/reviewer.py`: 워크벤치에서 `ReviewerInputs`을 로드하고 차원별로 LLM 스코어를 실행하는 스크립트.
3. `outputs/review/<task_id>.json`: 표준 리뷰 보고서 경로.
4. `docs/reviewer-rubric.md`: 5개 차원, 각 차원이 답하는 질문, 그리고 0-1-2 앵커 포인트(앵커 포인트) 설명을 나열한 문서.
5. 빌더 작업이 완료될 때마다 리뷰 보고서를 PR 댓글로 게시하는 CI 단계.

허용되지 않는 사항:

- diff에 쓰기 권한이 있는 리뷰어. 빌더와 리뷰어 간의 간격이 전체 신호이며, 이를 없애면 신뢰성이 파괴됩니다.
- 점수별 앵커 포인트 설명이 없는 평가 기준. "0에서 2까지 점수 매기기"는 앵커 포인트가 없으면 감(감성적 판단)으로 축소됩니다.
- 인용을 생략한 리뷰 보고서. 모든 점수는 파일이나 추적(Trace) 항목을 가리켜야 합니다.
- 빌더의 시스템 프롬프트(System Prompt)를 공유하는 것. 동일한 모델은 괜찮지만, 동일한 프롬프트는 허용되지 않습니다.

거부 규칙:

- 빌더가 검증 보고서를 생성하지 않으면 리뷰어 실행을 거부하세요. 판단을 요청할 가치가 있으려면 수락이 먼저 유지되어야 합니다.
- 프로젝트에 완료된 작업이 3개 미만이면 평가 기준이 보정(Calibration)되었다고 주장하지 마세요. 첫 보고서들을 보정 세트(Calibration Set)로 저장하세요.
- 리뷰어가 최소 신뢰도 미만으로 점수를 매기도록 요청받으면 거부하고 불확실한 차원을 인간에게 전달하세요.

출력 구조:

```
<repo>/
├── agents/reviewer.md
├── tools/reviewer.py
├── outputs/review/
│   └── <task_id>.json
├── docs/reviewer-rubric.md
└── .github/workflows/review.yml
```

다음에 읽을 내용으로 다음을 가리키며 마무리하세요:

- 검증 + 리뷰를 결합한 핸드오프 패킷(Handoff Packet)에 대한 40강.
- 빌더/리뷰어 분리를 끝에서 끝까지 연습하는 실제 스타일 작업에 대한 41강.
- 이 강의가 개선하는 단일 에이전트 자기 검토 기준선인 05강(자기 개선 및 CRITIC)을 참고해 보세요.
