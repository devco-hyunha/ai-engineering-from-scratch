# 에이전트 관측 가능성: Langfuse, Phoenix, Opik

> 2026년, 세 개의 오픈소스 에이전트 관측 가능성 플랫폼이 시장을 주도하고 있습니다. Langfuse (MIT) — 월간 600만+ 설치, 추적 + 프롬프트 관리 + 평가 + 세션 재생. Arize Phoenix (Elastic 2.0) — 에이전트 특화 심층 평가, RAG 관련성, OpenInference 자동 계측. Comet Opik (Apache 2.0) — 자동 프롬프트 최적화, 가드레일, LLM 판정 환각 감지.

**유형:** Learn
**언어:** Python (stdlib)
**선수 요건:** 14단계 · 23강 (OTel GenAI)
**시간:** 약 45분

## 학습 목표

- 세 개의 주요 오픈소스 에이전트 관측 가능성 플랫폼과 그 라이선스를 나열해 보세요.
- 각 플랫폼이 가장 강점을 가진 부분을 구분해 보세요: Langfuse (프롬프트 관리 + 세션), Phoenix (RAG + 자동 계측), Opik (최적화 + 가드레일).
- 2026년까지 조직의 89%가 에이전트 관측 가능성을 도입했다고 보고하는 이유를 설명해 보세요.
- LLM 판정 평가를 포함하는 stdlib 추적 대시보드 파이프라인을 구현해 보세요.

## 문제점

OTel GenAI (23강)는 스키마를 제공합니다. 스팬을 수집하고, 평가를 실행하며, 프롬프트 버전을 저장하고, 회귀를 드러내는 플랫폼이 여전히 필요합니다. 세 후보는 각각 라이프사이클의 다른 부분을 강조합니다.

## 개념

### Langfuse (MIT)

- 월간 SDK 설치 600만+, GitHub 스타 19k+.
- 기능: 추적, 버전 관리 및 플레이그라운드를 포함한 프롬프트 관리, 평가 (LLM-as-judge, 사용자 피드백, 커스텀), 세션 재생.
- 2025년 6월: 이전 상용 모듈 (LLM-as-a-judge, 주석 큐, 프롬프트 실험, Playground)이 MIT 라이선스로 오픈소스화되었습니다.
- 가장 강점: 긴밀한 프롬프트 관리 루프를 갖춘 엔드투엔드 관측 가능성.

### Arize Phoenix (Elastic License 2.0)

- 더 깊은 에이전트 특화 평가: 추적 클러스터링, 이상 감지, RAG를 위한 검색 관련성.
- 네이티브 OpenInference 자동 계측.
- 프로덕션 환경에서는 관리형 Arize AX와 함께 사용.
- 프롬프트 버전 관리 없음 — 더 넓은 플랫폼과 함께 드리프트/행동 회귀 도구로 포지셔닝됨.
- 가장 강력한 부분: RAG 관련성, 행동 드리프트, 이상 탐지.

### Comet Opik (Apache 2.0)

- A/B 실험을 통한 자동화된 프롬프트 최적화.
- 가드레일 (PII 마스킹, 주제적 제약).
- LLM-판정자 환각(Hallucination) 탐지.
- Comet 자체 측정 기준 벤치마크: Opik은 로깅 + 평가에 23.44초, Langfuse는 327.15초 소요 (~14배 차이) — 벤더 벤치마크는 방향성 참고용으로만 사용하세요.
- 가장 강력한 부분: 최적화 루프, 자동화된 실험, 가드레일 강제 적용.

### 산업 데이터

Maxim (2026 현장 분석)에 따르면: 조직의 89%가 에이전트 관측성(Observability)을 구축하고 있으며, 품질 문제가 프로덕션의 가장 큰 장벽입니다 (응답자의 32%가 이를 지적).

### 하나 선택하기

| 필요 사항 | 선택 |
|------|------|
| 프롬프트 관리 포함 올인원 | Langfuse |
| 심층 RAG 평가 + 드리프트 | Phoenix |
| 자동화된 최적화 + 가드레일 | Opik |
| 오픈 라이선스, ELv2 없음 | Langfuse (MIT) 또는 Opik (Apache 2.0) |
| Datadog / New Relic 통합 | 모두 가능 — 모두 OTel로 내보냅니다 |

### 이 패턴이 잘못되는 지점

- **평가 전략 없음.** 평가 없이 추적하는 것은 비싼 로깅일 뿐입니다.
- **그라운딩(Grounding) 없는 자체 제작 LLM-판정자.** CRITIC 패턴 (05강)이 적용됩니다 — 판정자는 사실 검증을 위해 외부 도구가 필요합니다.
- **추적과 연결되지 않은 프롬프트 버전.** 프로덕션에서 성능이 저하되면, 원인을 유발한 프롬프트로 바이섹트(bisect)할 수 없습니다.

## 구현하기

`code/main.py`은 표준 라이브러리 추적 수집기 + LLM-판정자 평가기를 구현합니다:

- GenAI 형태의 스판(span)을 수집하세요.
- 세션별로 그룹화하고, 실패한 실행 (가드레일 트리핑, 낮은 신뢰도 평가)을 태깅하세요.
- 루브릭(rubric)으로 에이전트 응답을 점수화하는 스크립트화된 LLM-판정자.
- 대시보드 형태의 요약: 실패율, 주요 실패 원인, 평가 점수 분포.

실행하세요:

```
python3 code/main.py
```

출력: Langfuse/Phoenix/Opik이 보여주는 것과 일치하는 세션별 평가 점수 및 실패 분류입니다.

## 사용하기

- **Langfuse**는 셀프 호스팅 또는 클라우드; OTel 또는 SDK로 연결하세요.
- **Arize Phoenix**는 자체 호스팅; OpenInference를 자동 계측합니다.
- **Comet Opik**는 자체 호스팅 또는 클라우드; 자동화된 최적화 루프를 제공합니다.
- **Datadog LLM Observability**는 이미 Datadog을 사용하는 혼합 Ops+ML 팀에 적합합니다.

## 연습 문제

1. 1주간의 OTel 추적(trace)을 Langfuse 클라우드(무료 티어)로 내보내 보세요. 어떤 세션이 실패했나요? 왜 실패했나요?
2. 당신의 도메인에 대한 LLM 심사위원(rubric) 기준표(사실적 정확성, 톤, 범위 준수)를 작성해 보세요. 50개의 추적(trace)에서 테스트해 보세요.
3. Langfuse의 프롬프트 버전 관리와 Phoenix의 추적(trace) 클러스터링을 비교해 보세요. 어떤 것이 더 빨리 문제를 알려주나요?
4. Opik의 가드레일(guardrail) 문서를 읽어 보세요. PII 마스킹 가드레일(guardrail)을 에이전트 실행 중 하나에 연결해 보세요.
5. 당신의 코퍼스를 사용하여 세 가지를 벤치마킹해 보세요. 벤더가 공개한 수치는 무시하고, 직접 측정해 보세요.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| 추적(Tracing) | "스팬 수집기" | OTel / SDK 스팬(span)을 수집하고 세션별로 인덱싱합니다 |
| 프롬프트 관리 | "프롬프트 CMS" | 추적(trace)에 연결된 버전 관리된 프롬프트 |
| LLM-as-judge | "자동화된 평가" | 별도의 LLM이 기준표(rubric)에 따라 에이전트 출력에 점수를 매깁니다 |
| 세션 재생 | "추적(trace) 재생" | 디버깅을 위해 과거 실행을 단계별로 진행합니다 |
| RAG 관련성 | "검색 품질" | 검색된 컨텍스트가 쿼리와 일치하는지 여부 |
| 추적(trace) 클러스터링 | "행동 그룹화" | 드리프트(drift) 감지를 위해 유사한 실행을 클러스터링합니다 |
| 가드레일(guardrail) 적용 | "로그 시점의 정책" | 기록된 콘텐츠에 대한 PII/유해성/범위 검사 |
