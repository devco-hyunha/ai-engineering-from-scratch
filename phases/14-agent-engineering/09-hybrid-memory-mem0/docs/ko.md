# 하이브리드 메모리: 벡터 + 그래프 + KV

> 하이브리드 메모리는 세 개의 스토어를 병렬로 실행합니다. 벡터는 시맨틱 유사성, KV는 빠른 팩트 조회, 그래프는 엔티티-관계 추론을 담당하며, 검색 시 이들을 융합하는 스코어링 계층이 있습니다. 이는 외부 메모리를 위한 널리 사용되는 프로덕션 패턴입니다. Mem0 (Chhikara et al., 2025)는 이를 구현한 참고 구현체 중 하나입니다.

**유형:** Build
**언어:** Python (stdlib)
**선수 요건:** 14단계 · 07강 (MemGPT), 14단계 · 08강 (Letta Blocks)
**시간:** 약 75분

## 학습 목표

- 단일 스토어(벡터만, 그래프만, KV만)가 에이전트 메모리에 왜 불충분한지 설명해 보세요.
- Mem0의 세 병렬 스토어를 나열하고, 각각이 무엇을 최적화하는지 설명해 보세요.
- Mem0의 융합 스코어링(관련성, 중요성, 최신성)을 설명하고, 왜 이것이 가중 합산이며 계층 구조가 아닌지 설명해 보세요.
- 세 스토어에 모두 기록하는 `add()`과 결과를 융합하는 `search()`을 사용하여 stdlib에 장난감 3-스토어 메모리를 구현해 보세요.

## 문제점

세 가지 쿼리 클래스 중 하나에 대해 단일 스토어는 부적합합니다:

- **시맨틱 유사성** — "지난주에 에이전트 드리프트에 대해 무엇을 논의했나요?" 벡터가 승리합니다. KV와 그래프는 놓칩니다.
- **팩트 조회** — "사용자의 전화번호는 무엇인가요?" KV가 승리합니다. 벡터는 낭비적이고, 그래프는 과잉입니다.
- **관계 추론** — "어떤 고객들이 동일한 청구 엔티티를 공유하나요?" 그래프가 승리합니다. 벡터와 KV는 답할 수 없습니다.

프로덕션 에이전트는 한 세션에서 세 가지를 모두 요청합니다. 단일 스토어 메모리는 그중 두 가지에 대해 항상 부적합합니다. Mem0의 기여는 이 세 가지를 단일 `add`/`search` 인터페이스 뒤에 연결하고, 이들을 융합하는 스코어링 함수를 제공하는 것입니다.

## 개념

### 병렬로 실행되는 세 스토어

Mem0 (arXiv:2504.19413, 2025년 4월)의 `add(text, user_id, metadata)`:

1. 텍스트에서 후보 팩트를 추출합니다(LLM 주도 단계).
2. 시맨틱 검색을 위해 각 팩트를 벡터 스토어(임베딩)에 기록합니다.
3. O(1) 조회를 위해 각 팩트를 (user_id, fact_type, entity)를 키로 하는 KV 스토어에 기록합니다.
4. 관계 쿼리를 위해 각 팩트를 타입이 지정된 간선으로 그래프 스토어(Mem0g)에 기록합니다.

`search(query, user_id)`에서:

1. 벡터 스토어는 임베딩 코사인을 기준으로 상위 k개를 반환합니다.
2. KV 스토어는 쿼리에서 파생된 (user_id, type, entity)를 키로 하는 직접 조회 결과를 반환합니다.
3. 그래프 스토어는 쿼리 엔티티에서 도달 가능한 하위 그래프를 반환합니다.
4. 스코어링 레이어가 세 가지를 융합합니다.

### 융합 스코어링

```
score = w_relevance * relevance(q, record)
      + w_importance * importance(record)
      + w_recency * recency(record)
```

- **관련성** — 벡터 코사인, KV 정확 일치, 그래프 경로 가중치.
- **중요성** — 작성 시 태그를 지정하거나 학습된 값 (일부 사실은 더 중요합니다: 이름, ID, 정책).
- **최근성** — 마지막 작성 또는 읽기 이후 시간에 대한 지수 감쇠.

가중치는 제품별로 조정됩니다. 채팅 에이전트에는 `w_recency`을 높게, 컴플라이언스 에이전트에는 `w_importance`을 높게, 검색 에이전트에는 `w_relevance`을 높게 설정합니다.

### Mem0g와 시간적 추론

Mem0g는 충돌 감지기를 추가합니다. 새로운 사실이 기존 엣지와 모순될 때, 기존 엣지는 무효로 표시되지만 삭제되지는 않습니다. 시간적 쿼리("3월에 사용자의 도시는 어디였나요?")는 시간 기준 유효 하위 그래프를 탐색합니다.

이것은 Letta의 무효화 패턴이 일반화한 컴플라이언스 등급의 동작입니다.

### 벤치마크 수치

Mem0 논문은 (2025년) 다음을 보고합니다:

- **LoCoMo** (장기 대화 기억): 91.6
- **LongMemEval** (장기 일화 기억): 93.4
- **BEAM 1M** (1M 토큰 기억 벤치마크): 64.1

비교 기준선(전체 컨텍스트 128k LLM, 평면 벡터 스토어, 평면 KV)은 모두 10점 이상 뒤집니다. 벤치마크만으로는 선택을 정당화할 수 없습니다. 운영 형태가 정당화합니다. 하지만 수치들은 융합 설계가 반올림 오차가 아님을 보여줍니다.

### 범위 분류 체계

Mem0는 기억을 범위로 분리합니다:

- **사용자 기억** — 세션을 넘어 지속되며, `user_id`을 키로 합니다.
- **세션 기억** — 하나의 스레드 내에서 지속됩니다.
- **에이전트 기억** — 에이전트별 인스턴스 상태입니다.

모든 쓰기는 하나의 범위를 선택합니다. 검색은 범위별 가중치를 사용하여 범위를 넘어 쿼리할 수 있습니다. 범위를 고려하지 않고 혼합하면 "어시스턴트가 Alice에게 Bob의 프로젝트를 알려주었다"는 사고가 발생합니다.

### 이 패턴이 잘못된 곳

- **임베딩 드리프트.** 첫 100개 쿼리에서는 결과가 정상적으로 보이지만, 코퍼스가 커짐에 따라 벡터 결과가 저하됩니다. 가장 많이 사용된 상위 N개 레코드를 주기적으로 재임베딩하세요.
- **KV 스키마 크리프.** `(user_id, type, entity)`는 단순해 보이지만, 모든 팀이 자체 `type`을 추가하면 복잡해집니다. 타입 집합을 분기별로 감사하세요.
- **그래프 폭발.** 잡음이 많은 추출기가 메시지당 50개의 엣지를 추가합니다. `add` 호출당 그래프 쓰기를 제한하고, 신뢰도가 낮은 엣지는 제거하세요.

## 구현하기

`code/main.py`은 stdlib에서 3-스토어 패턴을 구현합니다:

- `VectorStore` — 임베딩 대체 수단으로서 단순한 토큰 겹침 유사도.
- `KVStore` — `(user_id, fact_type, entity)`을 키로 사용하는 dict.
- `GraphStore` — 타입이 지정된 엣지 (주체, 관계, 객체, 유효성).
- `Mem0` — `add()`, `search()`, 융합 점수화 및 범위 인식 검색을 포함하는 최상위 퍼사드.
- 다중 사용자, 다중 세션 대화에 대한 상세적인 추적 예시.

실행하세요:

```
python3 code/main.py
```

출력에는 세 개의 별도 리콜 경로와 융합된 top-k가 표시됩니다. `main()` 상단에서 점수 가중치를 바꾸고 순위가 변하는 것을 확인하세요.

## 사용하기

- **Mem0 (Apache 2.0)** — 프로덕션 준비 완료. Postgres + Qdrant + Neo4j로 셀프 호스팅하거나 관리형 클라우드를 사용하세요.
- **Letta** — core/recall/archival의 3계층 구조; 자체 벡터 및 그래프 백엔드를 가져오세요.
- **Zep** — 시간적 KG와 팩트 추출을 제공하는 상용 대안.
- **커스텀 빌드** — 추출기(컴플라이언스)나 융합 가중치(최근성이 지배하는 음성 에이전트)에 대한 정확한 제어 필요 시.

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| 하이브리드 메모리 | "벡터 + 그래프 + KV" | 병렬로 기록된 세 개의 저장소, 검색 시 융합 |
