작업 클래스(예상 소요 시간, 단계 수, 트리거 유형, 지연 시간 예산)가 주어지면 런타임 형태를 선택합니다.

결정:

1. 30초 미만, 사용자가 대기 -> **요청-응답**.
2. 점진적 UX 또는 음성 -> **스트리밍**.
3. 수 분에서 수 시간, 사용자가 대기하지 않음 -> **큐 기반**.
4. 외부 이벤트에 반응 -> **이벤트 주도**.
5. 주기적인 유지 관리 -> **cron**.
6. 재시작 비용이 높은 경우 -> **내구성 있는 실행(Durable Execution)**을 추가합니다.

생성물:

1. 스택 내의 형태 스캐폴드.
2. 관측 가능성: OTel GenAI 스팬(23강), 백엔드 연결(24강).
3. 큐의 경우: DLQ + 재시도 정책 + 큐 깊이 지표.
4. 이벤트의 경우: 명시적 구독자 레지스트리 + 재생 경로.
5. cron의 경우: 겹치는 실행을 방지하기 위한 잠금 파일 또는 분산 잠금.
6. 내구성 있는 실행의 경우: 체크포인터 백엔드 + 재개 의미론.

허용 불가 조건:

- 5분 작업에 동기식 HTTP. 사용자가 연결을 끊고 워커가 쌓입니다.
- DLQ 없는 큐 기반. 실패한 작업이 사라집니다.
- 추적 내보내기 없는 백그라운드 작업. 사용자가 불평할 때까지 실패가 보이지 않습니다.
- "내구성 있는 상태는 없고, 그냥 재시도하겠습니다." 긴 기간은 체크포인팅이 필요합니다.

거부 규칙:

- 제품에 SLA + 재생 요구 사항이 있는 경우, 스웜 토폴로지 + 비내구성 런타임을 거부합니다.
- 작업이 컴플라이언스에 묶여 있는 경우, 감사 추적 없는 이벤트 주도 방식을 거부합니다.
- 사용자가 cron + 잠금 없음인 경우, 거부합니다. 겹치는 cron 실행은 최선인 경우 중복 작업이며, 최악인 경우 데이터 손상입니다.

출력: 런타임 스캐폴드 + 관측 가능성 훅 + SLA, 재시도 정책, 체크포인터 선택이 포함된 README. "다음에 읽을 내용"으로 23강(OTel), 24강(관측 가능성), 또는 24강(호스팅된 장기 실행을 위한 관리형 에이전트)을 가리키며 마무리합니다.
