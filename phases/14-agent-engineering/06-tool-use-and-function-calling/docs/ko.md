# 도구 사용 및 함수 호출

> Toolformer (Schick et al., 2023)는 자기 지도 도구 주석을 시작했습니다. Berkeley Function Calling Leaderboard V4 (Patil et al., 2025)는 2026년 기준을 설정합니다: 에이전트형 40%, 다중 턴 30%, 라이브 10%, 비라이브 10%, 환각 10%. 단일 턴은 해결되었습니다. 메모리, 동적 의사결정, 장기 도구 체인은 해결되지 않았습니다.

**유형:** Build
**언어:** Python (stdlib)
**선수 요건:** 14단계 · 01강 (에이전트 루프), 13단계 · 01강 (함수 호출 심층 분석)
**시간:** 약 60분

## 학습 목표

- Toolformer의 자기 지도 학습 신호를 설명해 보세요: 실행이 다음 토큰의 손실을 줄일 때만 도구 주석을 유지합니다.
- BFCL V4의 다섯 가지 평가 범주와 각각이 측정하는 내용을 나열해 보세요.
- 스키마 검증, 인자 강제 변환, 실행 샌드박싱을 갖춘 stdlib 도구 레지스트리를 구현해 보세요.
- 2026년 세 가지 미해결 문제를 진단해 보세요: 장기 도구 체이닝, 동적 의사결정, 메모리.

## 문제점

초기 도구 사용은 모델이 올바른 함수 호출을 예측할 수 있는지를 물었습니다. 현대의 도구 사용은 모델이 메모리를 활용하고, 부분 관측 가능성을 고려하고, 도구 실패로부터 복구하며, 존재하지 않는 도구를 환각하지 않으면서 40단계에 걸쳐 도구를 체이닝할 수 있는지를 묻습니다.

Toolformer는 기준선을 확립했습니다: 모델은 자기 지도를 통해 언제 도구를 호출해야 하는지 학습할 수 있습니다. BFCL V4는 2026년 평가 목표를 정의합니다. 두 기준선 사이의 간격은 프로덕션 에이전트가 활동하는 영역입니다.

## 개념

### Toolformer (Schick et al., NeurIPS 2023)

아이디어: 모델이 자신의 사전 학습 코퍼스에 후보 API 호출을 주석하도록 허용합니다. 각 후보를 실행합니다. 도구 결과를 포함하는 것이 다음 토큰의 손실을 줄이는 경우에만 주석을 유지합니다. 필터링된 코퍼스로 미세 조정합니다.

대상 도구: 계산기, QA 시스템, 검색 엔진, 번역기, 캘린더. 자기 지도 신호는 도구가 텍스트 예측을 돕는지에 대한 것일 뿐이며, 인간 라벨은 없습니다.

확장 결과: 도구 사용은 확장 규모에서 나타납니다. 작은 모델은 도구 주석으로 인해 성능이 저하되지만, 큰 모델은 이득을 봅니다. 2026년 프론티어 모델은 도구 사용이 내장되어 있는 반면, 대부분의 7B 모델은 신뢰성을 위해 명시적인 도구 사용 미세 조정이 필요한 이유입니다.

### 버클리 함수 호출 리더보드 V4 (Patil et al., ICML 2025)

BFCL은 2026년 사실상의 평가 기준입니다. V4 구성:

- **에이전트 (40%)** — 전체 에이전트 궤적: 메모리, 다중 턴, 동적 결정.
- **다중 턴 (30%)** — 도구 체인을 포함한 대화형 대화.
- **라이브 (10%)** — 사용자가 제출한 실제 프롬프트 (더 어려운 분포).
- **비라이브 (10%)** — 합성 테스트 케이스.
- **환각 (10%)** — 도구를 호출하지 않아야 할 때를 감지.

V3는 상태 기반 평가를 도입했습니다: 도구 시퀀스 후, 도구 호출의 AST를 일치시키는 대신 API의 실제 상태 (예: "파일이 생성되었나요?")를 확인합니다. V4는 웹 검색, 메모리 및 형식 민감도 카테고리를 추가했습니다.

2026년 주요 발견: 단일 턴 함수 호출은 거의 해결되었습니다. 실패는 메모리 (턴 간 컨텍스트 유지), 동적 결정 (이전 결과에 기반한 도구 선택), 장기 체인 (20+ 단계 후 드리프트), 환각 감지 (도구가 적합하지 않을 때 호출을 거부하는 것)에 집중됩니다.

### 도구 스키마

모든 제공업체에는 스키마가 있습니다. 세부 사항이 다르지만 동일한 형태를 공유합니다:

```
name: string
description: string (what it does, when to use it)
input_schema: JSON Schema (properties, required, types, enums)
```

Anthropic은 `input_schema`를 직접 사용합니다. OpenAI는 `function.parameters`를 사용합니다. 둘 다 JSON Schema를 허용합니다. 설명은 핵심적입니다 — 모델은 올바른 도구를 선택하기 위해 설명을 읽습니다. 나쁜 도구 설명은 잘못된 도구 선택 실패의 #1 근본 원인입니다.

### 인수 검증

도구 호출을 신뢰하지 마세요. 검증하세요:

1. **타입 강제 변환.** 모델이 스키마가 int인 곳에 문자열 "5"를 반환할 수 있습니다. 모호하지 않으면 강제 변환하고, 모호하면 거부하세요.
2. **Enum 검증.** 스키마가 `status in {"open", "closed"}`인데 모델이 `"in_progress"`를 방출하면, 설명적인 오류와 함께 거부하세요.
3. **필수 필드.** 필수 필드가 누락되면 -> 즉시 오류 관측을 모델에 보내고, 크래시를 일으키지 마세요.
4. **형식 검증.** 날짜, 이메일, URL — 정규식이 아닌 구체적인 파서로 검증하세요.

모든 검증 실패는 모델이 올바른 형태로 재시도할 수 있도록 구조화된 관측 결과를 반환해야 합니다.

### 병렬 도구 호출

최신 제공자는 하나의 어시스턴트 턴에서 병렬 도구 호출을 지원합니다. 루프는 다음과 같습니다:

1. 모델이 서로 다른 `tool_use_id`를 가진 3개의 도구 호출을 생성합니다.
2. 런타임이 이를 실행합니다 (독립적인 경우 병렬로 실행).
3. 각 결과는 `tool_use_id`에 의해 상관된 `tool_result` 블록으로 반환됩니다.

엔지니어링 규칙: 상관 ID는 핵심적인 요소로 취급하세요. 이를 바꾸면 잘못된 도구와 잘못된 결과의 라우팅이 발생합니다.

### 샌드박스화

도구 실행은 샌드박스 경계입니다. 상세 내용은 09강을 참조하세요. 짧은 버전: 모든 도구는 읽기/쓰기 표면, 네트워크 접근, 시간 초과, 메모리 상한을 지정해야 합니다. 일반적인 `run_shell(cmd)`는 위험 신호이며, 구체적인 `git_status()`가 더 안전합니다.

```figure
tool-routing
```

## 구현하기

`code/main.py`는 프로덕션 형태의 도구 레지스트리를 구현합니다:

- JSON Schema 하위 집합 검증기 (표준 라이브러리만 사용).
- 설명, 입력 스키마, 시간 초과 및 실행기를 포함한 도구 등록.
- 인수 강제 변환 및 열거형 검증.
- 상관 ID를 사용한 병렬 도구 디스패치.
- 구조화된 문자열로서의 오류 관측 결과.

실행해 보세요:

```
python3 code/main.py
```

추적은 하나의 턴에서 세 개의 도구를 호출하는 미니 에이전트를 보여주며, 의도적으로 형식이 잘못된 호출은 모델이 처리할 수 있는 설명적인 오류와 함께 거부됩니다.

## 사용하기

각 제공자는 자체 도구 스키마를 가지고 있습니다 — Anthropic, OpenAI, Gemini, Bedrock. 다중 제공자가 필요하다면 번역 레이어 (OpenAI Agents SDK, Vercel AI SDK, LangChain 도구 어댑터)를 사용하세요. BFCL은 참조 벤치마크입니다 — 도구 사용이 제품의 중심이라면 출시 전에 에이전트에 대해 실행해 보세요.

## 출시하기

`outputs/skill-tool-registry.md`는 주어진 작업 도메인에 대한 도구 카탈로그, 스키마 및 레지스트리를 생성합니다. 설명 품질 검사를 포함합니다 (각 도구의 설명이 모델에게 언제 사용해야 하는지 알려주는가?).

## 연습 문제

1. 모델이 다른 도구를 명시적으로 거부할 수 있도록 하는 "no-op" 도구를 추가하세요. BFCL 유사 환각 테스트로 측정해 보세요.
2. int를 문자열로 취급하거나 float를 문자열로 취급하는 인자 강제 변환을 구현해 보세요. 강제 변환이 실제 버그를 숨기기 시작하는 지점은 어디인가요?
3. 도구별 시간 제한과 서킷 브레이커(연속 3회 실패 후 60초 동안 도구 사용 거부)를 추가해 보세요. 이 변경이 모델의 복구 방식에 어떤 영향을 미치나요?
4. BFCL V4 설명을 읽어 보세요. 한 카테고리(예: "multi-turn")를 선택하여 에이전트를 통해 10개의 예제 프롬프트를 실행해 보세요. 통과율을 보고하세요.
5. 표준 라이브러리 검증기를 Pydantic이나 Zod로 이식해 보세요. Pydantic/Zod가 장난감 검증기가 놓친 것을 잡아낸 것은 무엇인가요?
