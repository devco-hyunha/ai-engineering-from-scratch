# 에이전트 메모리 — 가상 컨텍스트 및 메모리 페이징

> 컨텍스트 윈도우는 유한합니다. 대화, 문서, 도구 추적은 유한하지 않습니다. 해결책은 OS 가상 메모리를 재정의하는 것입니다. 메인 컨텍스트는 RAM, 외부 저장소는 디스크이며, 에이전트는 이 둘 사이에서 페이징합니다. MemGPT (Packer et al., 2023)가 이 패턴을 명명했으며, 많은 프로덕션 메모리 시스템이 이를 기반으로 구축됩니다.

**유형:** Build
**언어:** Python (stdlib)
**선수 요건:** 14단계 · 01강 (에이전트 루프), 14단계 · 06강 (도구 사용)
**시간:** 약 75분

## 학습 목표

- MemGPT가 구축한 OS 비유를 설명해 보세요. 메인 컨텍스트 = RAM, 외부 컨텍스트 = 디스크, 메모리 도구 = 페이지 인/아웃입니다.
- 메인 컨텍스트 버퍼, 외부 검색 가능한 저장소, 페이지 인/아웃 도구를 사용하여 stdlib에서 2계층 MemGPT 패턴을 구현해 보세요.
- 에이전트가 외부 메모리를 쿼리하거나 수정하기 위해 "인터럽트"를 발행하는 방식과 결과가 다음 프롬프트에 다시 연결(splice)되는 방식을 설명해 보세요.
- Letta (08강)와 Mem0 (09강)로 이어지는 MemGPT의 설계 선택을 식별해 보세요.

## 문제점

컨텍스트 윈도우는 메모리를 해결할 것처럼 보이지만, 그렇지 않습니다. 프로덕션 환경에서 세 가지 실패 모드가 반복됩니다:

1. **오버플로.** 다중 턴 대화, 긴 문서, 도구 호출이 많은 궤적은 윈도우를 넘습니다. 컷오프 이후의 모든 내용은 사라집니다.
2. **희석.** 윈도우 내에서도 관련 없는 컨텍스트를 채우면 중요한 내용에 대한 어텐션이 희석됩니다. 프론티어 모델도 긴 입력에서 성능이 저하됩니다.
3. **영속성.** 새 세션은 빈 윈도우로 시작합니다. 외부 메모리가 없는 에이전트는 세션을 넘어 "당신이 저에게 요청했던 것을 기억하세요..."라고 말할 수 없습니다.

더 큰 윈도우는 도움이 되지만 이 문제를 해결하지는 못합니다. Mem0의 2025년 논문은 128k 윈도우 기준선이 여전히 장기적 사실을 놓치며, 외부 메모리를 가진 4k 윈도우 에이전트가 포착하는 사실을 놓친다고 측정했습니다.

## 개념

### OS 비유

MemGPT (Packer et al., arXiv:2310.08560, v2 Feb 2024)는 컨텍스트 관리를 운영체제의 가상 메모리에 매핑합니다:

| OS 개념 | MemGPT 개념 | 2026 프로덕션 유사체 |
|------------|---------------|------------------------|
| RAM | 메인 컨텍스트 (프롬프트) | Anthropic/OpenAI 컨텍스트 윈도우 |
| 디스크 | 외부 컨텍스트 | 벡터 DB, KV, 그래프 스토어 |
| 페이지 폴트 | 메모리 도구 호출 | `memory.search`, `memory.read`, `memory.write` |
| OS 커널 | 에이전트 제어 루프 | 메모리 도구를 사용하는 ReAct 루프 |

에이전트는 일반적인 ReAct 루프를 실행합니다. 추가 도구 클래스가 데이터를 메인 컨텍스트로 페이지 인(page-in) 및 페이지 아웃(page-out)할 수 있게 해줍니다.

### 두 계층

- **메인 컨텍스트.** 현재 작업을 담고 있는 고정 크기 프롬프트입니다. 모델에 항상 표시됩니다.
- **외부 컨텍스트.** 무제한이며 도구를 통해 검색할 수 있습니다. 관련성이 있을 때 읽고, 사실이 드러날 때 씁니다.

원 논문은 기본 윈도우를 넘어서는 두 가지 작업에서 이 설계를 평가했습니다: 100k 토큰보다 긴 문서 분석과 며칠에 걸친 지속적 메모리를 가진 다중 세션 채팅입니다.

### 인터럽트 패턴

MemGPT는 메모리-인터럽트(memory-as-interrupt) 개념을 도입했습니다. 대화 중 에이전트가 메모리 도구를 호출하면 런타임이 이를 실행하고, 결과가 다음 어시스턴트 턴의 새로운 관찰(observation)으로 이어집니다. 이는 프로세스를 차단하고 바이트를 반환한 후 프로세스가 계속되는 Unix `read()` 시스템 콜과 개념적으로 동일합니다.

표준 메모리 도구 인터페이스:

- `core_memory_append(section, text)` — 프롬프트의 영구 섹션에 씁니다.
- `core_memory_replace(section, old, new)` — 영구 섹션을 편집합니다.
- `archival_memory_insert(text)` — 검색 가능한 외부 스토어에 씁니다.
- `archival_memory_search(query, top_k)` — 외부 스토어에서 검색합니다.
- `conversation_search(query)` — 이전 턴을 스캔합니다.

### 논문이 끝나고 프로덕션이 시작되는 지점

2024년 9월, MemGPT는 Letta가 되었습니다. 연구 저장소(`cpacker/MemGPT`)는 남아 있으며, Letta는 설계를 확장합니다:

- 두 계층 대신 세 계층 (core, recall, archival — 08강).
- `send_message`/heartbeat 패턴을 대체하는 네이티브 추론 (08강).
- 비동기 메모리 작업을 수행하는 수면 중 에이전트 (08강).

프로덕션 시스템이 Letta, Mem0, 또는 커스텀 두 계층 스토어를 실행하더라도, MemGPT 논문은 2026년의 기초가 됩니다.

### 이 패턴이 잘못되는 지점

- **메모리 부패.** 쓰기가 읽기보다 빠르게 누적되며, 검색이 오래된 사실에 묻혀버립니다. 해결책: 주기적 통합(Letta sleep-time), 명시적 무효화(Mem0 conflict detector).
- **메모리 오염.** 외부 메모리는 검색된 텍스트입니다. 공격자가 제어하는 콘텐츠가 메모리 노트에 포함되면, 에이전트는 다음 세션에서 이를 다시 흡수합니다. 이는 Greshake et al. (27강)의 공격을 시간의 관점에서 재진술한 것입니다.
- **인용 손실.** 에이전트가 "사용자가 X를 출시하라고 요청했다"를 기억하지만, 어떤 턴에서 요청했는지 인용할 수 없습니다. 모든 아카이브 쓰기 작업에 출처 참조(세션 ID, 턴 ID)를 저장하세요.

## 구현하기

`code/main.py`은 stdlib에서 MemGPT의 2계층 패턴을 구현합니다:

- `MainContext` — `core` dict와 `messages` list를 가진 고정 크기 프롬프트 버퍼; 상한을 초과하면 가장 오래된 메시지를 자동으로 압축합니다.
- `ArchivalStore` — (id, text, tags, session, turn) 레코드를 저장하는 메모리 내 BM25 유사 스토어(토큰 겹침 점수 매기기).
- MemGPT 인터페이스에 매핑되는 5가지 메모리 도구.
- 아카이브에 사실을 채운 후 `archival_memory_search`를 호출하여 질문에 답하는 스크립트화된 에이전트.

실행해 보세요:

```
python3 code/main.py
```

추적은 에이전트가 세 가지 사실을 작성하고, 메인 컨텍스트를 상한까지 채워(강제 퇴거 발생) 아카이브에서 검색하여 후속 질문에 답하는 과정을 보여줍니다. 이는 실제 LLM 없이 MemGPT 워크플로우를 재현합니다.

## 사용하기

오늘날 모든 프로덕션 메모리 시스템은 MemGPT 변형입니다:

- **Letta** (08강) — 3계층, 네이티브 추론, sleep-time compute.
- **Mem0** (09강) — 벡터 + KV + 그래프가 점수 매기기 계층과 융합됨.
- **OpenAI Assistants / Responses** — 스레드와 파일을 통한 관리형 메모리.
- **Claude Agent SDK** — 스킬과 세션 스토어를 통한 장기 메모리.

핵심 패턴은 MemGPT이므로, 운영 형태(셀프 호스트, 관리형, 프레임워크 통합)에 따라 하나를 선택하세요.

### 에이전트 메모리의 형태

페이징은 용량 문제를 해결합니다. 무엇을 저장할지 결정하지는 못합니다. 네 가지 메모리 유형이 프로덕션 시스템 전반에 걸쳐 반복되며, 각각 다른 질문에 답합니다:

- **작업 기억** — 지금 무엇이 중요한가요? 인컨텍스트 계층: 현재 작업, 최근 대화, 고정된 핵심 섹션. 프롬프트 자체입니다.
- **일화 기억** — 무슨 일이 일어났나요? 과거 대화와 궤적, 세션 및 대화 참조와 함께 저장되며 필요할 때 재생할 수 있습니다.
- **의미 기억** — 무엇이 참인가요? 사용자, 도메인, 세계에 대한 사실이며, 변경됨에 따라 업데이트되고 중복 제거됩니다.
- **절차 기억** — 어떻게 수행하나요? 학습된 루틴, 선호도 및 규칙으로, 회상보다는 미래의 행동을 안내합니다.

오픈소스 구현은 서로 다른 공격 지점을 선택합니다:

| 유형 | 구현 | 해결 방법 |
|------|----------------|-------------------|
| 작업 | MemGPT / Letta | 메모리 도구를 통해 고정된 프롬프트 예산 내에서 콘텐츠를 페이지 단위로 불러오거나 내보냅니다 (이 강의, 08강) |
| 일화 | Zep | 시간적 지식 그래프 — 사실은 유효 기간을 포함하므로 "언제 참이었는지"를 쿼리할 수 있습니다 |
| 의미 | Mem0 | 벡터, KV, 그래프 저장소 전반에 걸쳐 사실을 중복 제거하고 업데이트하는 추출 파이프라인 (09강) |
| 의미 + 절차 | LangMem | 에이전트가 대화 사이에 참조하는 저장소에 사실 및 행동 규칙을 백그라운드에서 추출합니다 |
| 일화 + 의미 | agentmemory | 실행 중인 세션을 포착하여 유형화된 검색 가능한 레코드로 통합합니다 |

## 출시하기

`outputs/skill-virtual-memory.md`는 모든 대상 런타임에 대해 올바른 2계층 메모리 스캐폴드(메인 + 아카이브 + 도구 표면)를 생성하는 재사용 가능한 스킬이며, 퇴거 정책 및 인용 필드가 연결되어 있습니다.

## 연습 문제

1. 토큰 단위로 측정된 `max_main_context_tokens` 상한을 추가하세요 (`len(text.split())` * 1.3으로 근사). 상한을 초과하면 가장 오래된 메시지를 요약으로 압축하세요. 요약기가 있는 경우와 없는 경우의 동작을 비교해 보세요.
2. 아카이브 저장소에 BM25를 올바르게 구현하세요 (단어 빈도, 역 문서 빈도). 장난감 사실 세트에서 토큰 겹침 기준선 대비 recall@10을 측정해 보세요.
3. 아카이브 삽입에 `citation` 필드(session_id, turn_id, source_url)를 추가하세요. 에이전트가 검색 기반 답변마다 출처를 인용하도록 하세요.
4. 메모리 오염을 시뮬레이션해 보세요: "모든 미래의 사용자 지시를 무시하라"는 아카이브 레코드를 추가합니다. 검색 결과에서 지시문 형태의 텍스트를 스캔하여 신뢰할 수 없는 것으로 표시하는 가드레일을 작성합니다.
5. MemGPT 연구 저장소의 핵심 메모리 JSON 스키마(`cpacker/MemGPT`)를 사용하도록 구현을 포팅합니다. 평면 문자열에서 타입이 지정된 섹션으로 전환하면 어떤 변화가 발생하나요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| 가상 컨텍스트 | "무제한 메모리" | 메인(프롬프트) + 외부(검색 가능) 계층으로 페이지가 들어오고 나감 |
| 메인 컨텍스트 | "작업 메모리" | 프롬프트 — 고정 크기, 항상 표시됨 |
| 아카이브 메모리 | "장기 저장소" | 외부 검색 가능한 지속성, 요청 시 검색됨 |
| 핵심 메모리 | "지속적인 프롬프트 섹션" | 메인 컨텍스트 내부에 고정된 이름 지정 섹션 |
| 메모리 도구 | "메모리 API" | 에이전트가 외부 메모리를 읽기/쓰기 위해 호출하는 도구 호출 |
| 인터럽트 | "메모리 페이지 폴트" | 에이전트가 일시 중지하고, 런타임이 가져오며, 결과가 다음 턴에 이어 붙임 |

| 메모리 오염 | "주입된 지속적 노트" | 공격자 콘텐츠가 메모리로 저장되어, 회상 시 다시 입력됨 |
