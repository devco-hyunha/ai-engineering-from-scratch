# Anthropic의 워크플로 패턴: 복잡한 것보다 단순한 것

> Schluntz와 Zhang (Anthropic, 2024년 12월)는 워크플로(사전 정의된 경로)와 에이전트(동적 도구 사용)를 구분합니다. 다섯 가지 워크플로 패턴이 대부분의 경우를 커버합니다. 직접 API 호출부터 시작하세요. 단계를 예측할 수 없을 때만 에이전트를 추가하세요.

**유형:** Learn + Build
**언어:** Python (stdlib)
**선수 요건:** 14단계 · 01강 (에이전트 루프)
**시간:** 약 60분

## 학습 목표

- Anthropic의 다섯 가지 워크플로 패턴을 나열하세요: 프롬프트 체이닝, 라우팅, 병렬화, 오케스트레이터-워커, 평가자-최적화자.
- 에이전트 대 워크플로 구분과 각각의 엔지니어링 비용을 설명하세요.
- 워크플로를 에이전트보다 선택해야 하는 경우(그리고 그 반대)를 식별하세요.
- 스크립트된 LLM을 사용하여 stdlib로 다섯 가지 패턴을 모두 구현하세요.

## 문제점

팀들은 단일 함수 호출로 해결할 수 있는 문제에 다중 에이전트 프레임워크를 도입합니다. 비용은 실재합니다: 프레임워크는 프롬프트를 가리고, 제어 흐름을 숨기며, premature complexity를 유발하는 레이어를 추가합니다. Schluntz와 Zhang의 2024년 12월 게시물은 가장 많이 인용된 업계의 반론입니다: 단순하게 시작하고, 비용이 정당화될 때만 복잡성을 추가하세요.

## 개념

### 워크플로 대 에이전트

- **워크플로.** 사전 정의된 코드 경로를 통해 LLM과 도구를 오케스트레이션합니다. 엔지니어가 그래프를 소유합니다.
- **에이전트.** LLM이 자신의 도구를 동적으로 지시하고 스스로 단계를 수행합니다. 모델이 그래프를 소유합니다.

둘 다 장점이 있습니다. 워크플로는 더 저렴하고, 빠르며, 디버깅이 쉽습니다. 에이전트는 개방형 문제를 해결할 수 있지만, 실패 모드를 추론하기는 더 어렵습니다.

### 증강된 LLM

다섯 가지 패턴의 기반: 세 가지 기능이 연결된 단일 LLM — 검색(retrieval), 도구(actions), 메모리(persistence). 모든 API 호출이 이를 사용할 수 있습니다.

### 다섯 가지 패턴

1. **프롬프트 체이닝.** 호출 1의 출력이 호출 2의 입력이 됩니다. 작업이 깔끔한 선형 분해로 나뉠 때 사용하세요. 단계 사이에 선택적인 프로그래밍 게이트를 두세요.

2. **라우팅.** 분류기 LLM이 어떤 다운스트림 LLM이나 도구를 호출할지 선택합니다. 범주적으로 다른 입력이 다른 처리를 필요로 할 때 사용하세요 (1단계 지원 vs 환불 vs 버그 vs 영업).

3. **병렬화.** N개의 LLM 호출을 동시에 실행하고 결과를 집계합니다. 두 가지 형태가 있습니다: 섹셔닝(다른 청크)과 투표(동일한 프롬프트, N번 실행, 다수결/합성).

4. **오케스트레이터-워커.** 오케스트레이터 LLM가 어떤 워커(이것도 LLM)를 실행할지 동적으로 결정하고 그 출력을 합성합니다. 에이전트 루프와 유사하지만, 오케스트레이터는 무한히 루프하지 않습니다.

5. **평가자-최적화자.** 하나의 LLM이 답변을 제안하고, 다른 LLM이 이를 평가합니다. 평가자가 통과할 때까지 반복합니다. 이는 Self-Refine (05강)의 일반화된 형태입니다.

### 워크플로우가 에이전트를 이기는 경우

- **예측 가능한 작업.** 단계를 열거할 수 있다면, 그렇게 해야 합니다.
- **비용 제한 작업.** 워크플로우는 단계 수가 제한되어 있으며, 에이전트는 폭주할 수 있습니다.
- **컴플라이언스 제한 작업.** 감사자는 궤적에서 추론하는 것이 아니라 그래프를 읽고 싶어 합니다.

### 에이전트가 워크플로우를 이기는 경우

- **개방형 연구.** 다음 단계가 마지막 단계의 반환값에 의존할 때.
- **가변 길이 작업.** 단계 수가 알려지지 않은 몇 분에서 몇 시간의 작업.
- **신규 도메인.** 올바른 워크플로우를 아직 모를 때 — 먼저 탐색하고, 나중에 코디파이(codify)하세요.

### 컨텍스트 엔지니어링의 동반자

## 구현하기

`code/main.py`는 `ScriptedLLM`에 대해 모든 5가지 워크플로우 패턴을 구현합니다:

- `prompt_chain(input, steps)` — 순차적.
- `route(input, classifier, handlers)` — 분류 + 디스패치.
- `parallel_vote(prompt, n, aggregator)` — N번 실행, 집계.
- `orchestrator_workers(task, workers)` — 오케스트레이터가 워커를 선택.
- `evaluator_optimizer(task, proposer, evaluator, max_iter)` — 통과할 때까지 루프.

실행하세요:

```
python3 code/main.py
```

각 패턴은 자체 추적을 출력합니다. 패턴당 총 코드 줄 수는 약 10~15줄이며, 프레임워크의 비용은 수천 줄 단위로 측정됩니다.

## 사용하기

- 대부분의 작업에는 직접 API 호출을 사용하세요.
- 패턴이 실제로 내구성 있는 상태(LangGraph), 액터 모델 동시성(AutoGen v0.4), 또는 역할 템플릿(CrewAI)을 필요로 할 때만 프레임워크를 사용하세요.
- Claude Code 하네스 형태를 재구축하지 않고 원한다면 Claude Agent SDK를 선택하세요.

## 연습 문제

1. 신뢰 임계값을 사용하여 라우팅을 구현하세요. 임계값 미만 -> 인간에게 에스컬레이션하세요. 티어 1 지원 사용 사례에서 임계값은 어디에 위치해야 합니까?
2. `parallel_vote`에 타임아웃을 추가하세요. 한 호출이 멈추면 어떻게 됩니까? 누락된 투표는 어떻게 집계합니까?
3. `evaluator_optimizer`를 밴딧으로 만드세요. 반복 과정에서 상위 2개 출력을 유지하여 늦게 나온 좋은 결과가 늦게 나온 나쁜 결과에 의해 덮어써지지 않도록 하세요.
4. 프롬프트 체이닝과 라우팅을 결합하세요. 라우터가 세 개의 체인 중 하나를 선택합니다. 단일 대형 프롬프트 대안과 토큰 비용을 비교 측정하세요.
5. 프로덕션 기능 중 하나를 선택하세요. 워크플로우 그래프를 그리세요. 단계를 세어 보세요. 에이전트가 실제로 여기서 더 나은 성능을 내겠습니까?
