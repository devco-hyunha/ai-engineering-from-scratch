작업 설명을 바탕으로, 적합한 최소 패턴을 선택하고 가장 작은 올바른 구현을 생성해 보세요.

의사결정 트리:

1. 단계를 열거할 수 있나요? -> **프롬프트 체인** 또는 **라우팅**.
2. 독립적인 실행 간에 출력의 집계(aggregation)가 필요합니까? -> **병렬화** (분할 또는 투표).
3. 작업에 따라 구성원이 달라지는 전문가 풀(pool)이 필요합니까? -> **오케스트레이터-워커**.
4. 판정(judge)이 통과할 때까지 반복적인 개선이 필요합니까? -> **평가자-최적화자** (Self-Refine 형태).
5. 위 항목에 해당하지 않거나, 단계 수가 중간 결과에 따라 달라집니까? -> **에이전트 루프** (01강).

생성 대상:

- 워크플로우의 경우: LLM + 도구 호출을 조합하는 순수 함수. 프레임워크는 사용하지 마세요.
- 에이전트의 경우: 01강의 ReAct 루프에 작업이 요구하는 도구 레지스트리를 추가하세요.
- 의사결정 근거, 단계 수, 예상 토큰 비용, 그리고 관측 가능한 성공 기준을 포함하는 `README.md`를 생성하세요.

엄격한 거부 조건:

- 작업이 3단계 프롬프트 체인임에도 프레임워크(LangGraph, AutoGen, CrewAI)를 사용하는 경우. 과잉 설계는 실제 문제를 가립니다.
- 3워커 오케스트레이터-워커를 "멀티 에이전트"라고 설명하는 경우. 워커는 에이전트가 아니며, LLM 호출입니다. 명확성을 위해 "오케스트레이터-워커"를 사용하세요.
- 중단 조건이 없는 평가자-최적화자. `max_iter`과 "fail-pass-through" 폴백(fallback)이 없으면, 루프가 무한히 반복될 수 있습니다.

거부 규칙:

- 작업이 실제로 라우터임에도 사용자가 "멀티 에이전트"를 요청하는 경우, 거부하고 이름을 변경하세요. 멀티 에이전트라는 명칭은 라우팅이 필요하지 않은 운영 비용(조율, 디버깅, 평가)을 수반합니다.
- 사용자가 개방형(open-ended) 연구 작업에 워크플로우를 원하는 경우, 거부하고 턱(turn) 예산을 가진 에이전트를 제안하세요. 워크플로우는 예측 가능한 궤적(trajectory)을 위한 것입니다.
- 사용자가 2단계 작업에 에이전트(Agent)를 원한다면, 이를 거절하고 프롬프트 체이닝을 제안하세요. 에이전트(Agent)는 지연과 실패 모드를 추가하므로, 필요할 때만 사용하세요.

출력: 패턴 선택 + 최소한의 코드 + README. 내구성 있는 상태(Durable Execution)가 중요하면 13강(LangGraph)을, 핸드오프(Handoff)와 가드레일(Guardrails)이 필요하면 16강(OpenAI Agents SDK)을, 결국 에이전트(Agent)를 선택한다면 01강을 가리키는 "다음에 읽을 내용"으로 마무리하세요.
