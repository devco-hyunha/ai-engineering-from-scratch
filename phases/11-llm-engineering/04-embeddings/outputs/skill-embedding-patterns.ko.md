# 임베딩 패턴

모든 임베딩 워크플로우는 이 계약을 따릅니다:

```
text -> embed(text) -> vector (float array)
similarity(vector_a, vector_b) -> score (float)
```

임베딩 모델과 유사성 지표는 중요한 단 두 가지 결정 사항입니다. 나머지는 모두 단순한 구현 작업입니다.

## 임베딩을 사용하는 경우

- 문서 간 시맨틱 검색 (키워드가 아닌 의미를 찾음)
- 유사한 항목 클러스터링 (지원 티켓, 제품 리뷰, 버그 리포트)
- 최근접 이웃 분류 (레이블이 지정된 예시와의 유사성을 통해 새 항목에 레이블을 부여)
- 추천 시스템 (사용자가 좋아한 항목과 유사한 항목을 찾음)
- 중복 제거 (유사성 임계값을 사용하여 거의 중복된 콘텐츠를 찾음)

## 임베딩을 사용하지 말아야 하는 경우

- 정확한 키워드 매칭 (전문 검색을 사용하세요)
- 구조화된 쿼리 (SQL, 필터를 사용하세요)
- 수동 레이블링이 더 빠른 작은 데이터셋 (<100개 항목)
- 정확도보다 설명 가능성이 더 중요한 작업 (임베딩은 투명하지 않음)

## 모델 선택

제약 조건에 따라 선택하세요:

- **API가 필요하고 최고의 가치**: OpenAI text-embedding-3-small (1536d, $0.02/1M 토큰)
- **최대 정확도 필요**: Voyage-3 (1024d, $0.06/1M 토큰, 가장 높은 MTEB)
- **로컬/프라이빗 필요**: BGE-M3 (1024d, 무료, 다국어 지원, GPU 권장)
- **빠른 로컬 프로토타이핑 필요**: all-MiniLM-L6-v2 (384d, 무료, CPU에서 실행)
- **다국어 지원 필요**: Cohere embed-v3 (1024d) 또는 BGE-M3 (둘 다 강력한 다국어 지원)

규칙: 인덱싱과 쿼리 간에 임베딩 모델을 혼합하지 마세요. 서로 다른 모델의 벡터는 호환되지 않는 공간에 존재합니다.

## 청킹 규칙

1. 청크당 256-512 토큰을 목표로 하며 50 토큰 겹침을 사용하세요
2. 가능하면 문장 중간에서 분할하지 마세요
3. 모든 청크에 메타데이터(소스 파일, 섹션 제목, 위치)를 포함하세요
4. 구조화된 문서(Markdown, HTML)의 경우, 먼저 헤딩 경계에서 분할합니다
5. 알려진 답을 검색하고 검색 결과를 확인하여 청크 품질을 테스트해 보세요

## 유사도 지표 선택

- **코사인 유사도(Cosine Similarity)**: 기본 선택, 가변 길이 텍스트를 처리하며 정규화됨
- **내적(Dot Product)**: 벡터가 이미 단위 정규화되어 있을 때 사용(OpenAI 모델은 정규화됨), 약간 더 빠름
- **유클리드 거리(Euclidean Distance)**: 클러스터링에 사용, 절대 위치가 중요할 때

벡터가 정규화되면 세 가지 지표 모두 동일한 순위를 제공합니다. 선택은 정규화되지 않은 벡터에만 영향을 미칩니다.

## 저장소 최적화

세 가지 수준의 압축, 누적 가능:

1. **Matryoshka 절단(Matryoshka Truncation)**: 차원 감소(1536 -> 256 = 6배 절약, 정확도 손실 3-5%)
2. **Float16 양자화(Quantization)**: 차원당 저장 공간을 절반으로 줄임(2배 절약, 정확도 손실 <1%)
3. **Binary 양자화(Quantization)**: 차원당 1비트(32배 절약, 정확도 손실 5-10%, 재채점(rescoring)과 함께 사용)

프로덕션 패턴: 전체 코퍼스에 대해 binary 검색을 수행하고, 상위 1000개는 float32 벡터로 재채점(rescoring)합니다.

## 검색 후 재랭킹(Retrieve-then-rerank)

최고의 정확도를 위한 2단계 파이프라인:

1. Bi-encoder가 상위 100개 후보를 검색(빠름, 사전 계산된 임베딩 사용)
2. Cross-encoder가 상위 10개로 재랭킹(느림, 각 쿼리-문서 쌍을 처리)

이 방식은 단일 단계 검색보다 정확도 지표에서 10-15% 더 좋습니다. 지연 시간보다 정확도가 더 중요할 때 사용하세요.

## 공통 실수

- 인덱싱과 쿼리 시 서로 다른 임베딩 모델을 사용
- 청크 대신 전체 문서를 임베딩(임베딩이 모든 것의 평균이 됨)
- 코사인 유사도(Cosine Similarity) 전에 벡터를 정규화하지 않음(대부분의 모델은 사전 정규화하지만, 확인하세요)
- 청크 겹침(chunk overlap)을 무시(경계에서 분할된 문장은 컨텍스트를 잃음)
- 원본 텍스트 없이 벡터만 저장(검색에는 둘 다 필요함)
- 모델이 변경될 때 재임베딩하지 않음(이전 벡터는 호환되지 않음)
- 정확도만으로 차원을 선택(저장소와 지연 시간은 차원에 선형적으로 비례)

## 임베딩 디버깅

검색 결과가 부진한 경우:

1. 쿼리 임베딩이 비영(zero) 벡터가 아닌지 확인하세요 (빈 입력이나 공백 입력은 영 벡터를 생성합니다)
2. 알려진 관련 문서의 유사도 점수를 수동으로 확인하세요
3. 문서 어휘와 일치하도록 쿼리를 재구성해 보세요
4. 청크 경계를 검사하여 관련 내용이 청크 간에 분할되지 않았는지 확인하세요
5. 코사인, 내적, 유클리드 등 다양한 지표로 top-k 결과를 비교하여 정규화 문제를 발견하세요
6. 문서에서 문장을 복사한 자명하게 일치하는 쿼리로 테스트하여 파이프라인이 작동하는지 확인하세요

## 프로덕션 파라미터

- 청크 크기: 256-512 토큰
- 청크 겹침: 50 토큰 (청크 크기의 10-20%)
- Top-k 검색: 직접 사용 시 5-10, 리랭킹 시 50-100
- 유사도 임계값: 코사인 유사도 기준 0.7 이상 (이보다 낮으면 결과는 일반적으로 관련성이 낮습니다)
- 배치 임베딩: 처리량 향상을 위해 API 호출당 100-500개 텍스트를 처리하세요
- 인덱스 재구축: 모델이 변경되거나 문서가 크게 업데이트될 때 임베딩을 다시 수행하세요
