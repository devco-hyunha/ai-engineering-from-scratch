# RAG 파이프라인 패턴

모든 RAG 시스템은 이 패턴을 따릅니다:

```
documents -> chunk -> embed -> store
query -> embed -> search(top_k) -> build_prompt -> generate
```

인덱싱은 문서당 한 번만 수행됩니다. 쿼리링은 모든 사용자 요청마다 수행됩니다.

## RAG를 사용할 때

- LLM이 비공개 문서나 최신 문서에 접근해야 할 때
- 미세 조정이 너무 비싸거나 업데이트 속도가 너무 느릴 때
- 답변에 출처를 인용해야 할 때
- 지식 베이스가 자주 변경될 때

## RAG를 사용하지 말아야 할 때

- 답변이 LLM이 이미 알고 있는 일반 지식일 때
- 작업이 사실 확인이 아닌 창의적인 작업(글쓰기, 브레인스토밍)일 때
- 모델이 특정 추론 스타일을 채택해야 할 때 (미세 조정을 사용하세요)

## 구현 체크리스트

1. 문서를 256-512 토큰 세그먼트로 청킹하고 50 토큰 겹침을 적용하세요
2. 일관된 임베딩 모델을 사용하여 각 청크를 임베딩하세요
3. 임베딩을 원본 텍스트와 함께 벡터 데이터베이스에 저장하세요
4. 쿼리 시, 동일한 모델로 사용자의 질문을 임베딩하세요
5. 코사인 유사도를 통해 가장 유사한 top-k (5-10) 청크를 검색하세요
6. 프롬프트를 구축하세요: 시스템 지시문 + 검색된 컨텍스트 + 사용자 질문
7. 검색된 컨텍스트에 기반하여 답변을 생성하세요
8. 출처 참조와 함께 답변을 반환하세요

## 공통 실수

- 인덱싱과 쿼리링에 서로 다른 임베딩 모델을 사용하는 것 (벡터가 호환되지 않습니다)
- 청크가 너무 작아 컨텍스트가 손실되거나 너무 커서 관련성이 희석되는 것
- 청크 간 겹침을 포함하지 않는 것 (문장이 경계에서 분할됩니다)
- 문서가 변경될 때 재인덱싱을 잊는 것
- 连贯적인 답변을 생성하지 않고 검색된 청크를 사용자에게 반환하는 것
- 사실적 RAG 쿼리에 temperature=0을 설정하지 않는 것 (온도가 높을수록 환각이 더 심해집니다)

## 검색 디버깅

올바른 청크가 검색되지 않는다면:
1. 쿼리 임베딩을 출력하고 0이 아닌지 확인해 보세요
2. 알려진 관련 청크에 대해 코사인 유사도를 수동으로 확인해 보세요
3. 문서 어휘와 일치하도록 쿼리를 다시 표현해 보세요
4. 인덱스 생성 시점과 쿼리 시점의 임베딩 모델이 일치하는지 확인해 보세요
5. 청킹 과정에서 관련 내용이 손실되었는지 확인해 보세요

## 프로덕션 파라미터

- 청크 크기: 256-512 토큰
- 중복: 50 토큰 (청크 크기의 10-20%)
- Top-k: 대부분의 사용 사례에서 5-10
- 온도: 사실적 답변의 경우 0
- 임베딩 모델: text-embedding-3-small (비용 효율적) 또는 text-embedding-3-large (높은 정확도)
