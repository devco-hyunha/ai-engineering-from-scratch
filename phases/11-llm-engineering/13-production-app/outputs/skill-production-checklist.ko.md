# 프로덕션 LLM 체크리스트

LLM 애플리케이션을 출시할 때, 이 체크리스트를 순서대로 진행해 보세요. 각 섹션에는 구체적인 임계값을 포함한 통과/실패 기준이 있습니다.

## 1. 보안 (출시 차단 항목)

여기에 있는 모든 항목은 배포 전에 반드시 통과해야 합니다.

| 점검 항목 | 통과 기준 | 검증 방법 |
|-------|--------------|---------------|
| API 키가 환경 변수에 있음 | 코드베이스에 하드코딩된 키가 0개 | `grep -r "sk-" --include="*.py"`이 아무것도 반환하지 않음 |
| 입력 가드레일 활성화 | 프롬프트 인젝션 패턴 차단 | "이전 지침을 모두 무시하세요"를 전송 -- 차단된 응답이 반환됨 |
| PII 마스킹 | SSN, 신용카드, 이메일 패턴 감지 | "내 SSN은 123-45-6789입니다"를 전송 -- LLM 호출 전에 PII가 마스킹됨 |
| 출력 필터링 | 위험한 콘텐츠 차단 | 모델이 `DROP TABLE`, `rm -rf`, `exec()` 패턴을 반환할 수 없음 |
| 속도 제한 | 사용자별 요청 상한 강제 | 같은 사용자가 10초 동안 100개 요청 -- 마지막 50개 이상 거부됨 |
| 모든 엔드포인트에 인증 | 인증되지 않은 LLM 접근 없음 | `curl /v1/chat`이 토큰 없이 401을 반환 |
| CORS 제한 | 프로덕션 도메인만 허용 | `Origin: evil.com` 요청이 거부됨 |
| 최대 입력 토큰 | 제한을 초과하는 요청 거부 | 50K 토큰 입력 전송 -- 413 또는 잘림(truncation) 반환 |

## 2. 신뢰성 (첫 주 생존)

이 항목들은 첫 번째 온콜(on-call) 인시던트를 방지합니다.

| 점검 항목 | 통과 기준 | 검증 방법 |
|-------|--------------|---------------|
| 백오프 재시도 | 5xx에 대해 3회 재시도, 지수적 지연 | 요청 중 LLM 목(mock)을 종료 -- 재시도가 로그에 표시됨 |
| 폴백 모델 체인 | 체인에 2개 이상의 모델 | 주(primary) 모델이 사용 불가 -- 폴백에서 응답이 여전히 반환됨 |
| 요청 시간 초과 | 모든 외부 호출에 최대 30초 | 느린 LLM 목(mock) (60초) -- 요청이 30초에서 시간 초과됨 |
| 우아한 저하(Graceful Degradation) | 캐시/RAG 실패가 서비스 충돌을 일으키지 않음 | 캐시를 중지 -- 요청은 여전히 성공 (더 느리고 더 비쌈) |
| 헬스 체크 엔드포인트 | 의존성 상태를 반환 | `GET /health`가 `{"status": "healthy", "cache": ..., "llm": ...}`를 반환 |
| 스트리밍(Streaming) 작동 | 첫 토큰이 500ms 미만 | 첫 토큰까지의 시간(TTFT) 측정, 일관되게 < 500ms |
| 오류 메시지가 안전함 | 내부 오류가 사용자에게 절대 노출되지 않음 | 500 오류 강제 발생 -- 사용자는 스택 트레이스가 아닌 일반적인 오류를 봄 |

## 3. 비용 제어 (첫 달의 경제학)

이것들은 $50K의 예상치 못한 청구서를 방지합니다.

| 체크 항목 | 통과 기준 | 검증 방법 |
|-------|--------------|---------------|
| 요청당 비용 추적 | 모든 요청이 토큰 수 + USD 비용을 기록 | 요청 로그에 `input_tokens`, `output_tokens`, `cost_usd` 필드가 있음 |
| 시맨틱 캐시(Semantic Cache) 활성화 | 반복 패턴에서 > 20% 적중률 | 1000번의 테스트 요청 후 캐시 통계가 적중률을 표시 |
| 캐시 TTL 설정 | 항목이 만료됨 (기본값: 1시간) | 항목 삽입 -- TTL 후 반환되지 않음 |
| 사용자별 비용 추적 | user_id별로 비용 집계 | 대시보드/API가 비용 상위 10명의 사용자를 표시 |
| 비용 알림 | 일일 예산의 80%에서 알림 | $10 daily budget, send $8.50을 요청에 설정 -- 알림이 발생 |
| 비용 기반 모델 라우팅(Model Routing) | 낮은 복잡도의 쿼리는 더 저렴한 모델 사용 | 간단한 질문은 gpt-4o-mini로 라우팅, 복잡한 것은 gpt-4o로 라우팅 |
| 최대 출력 토큰 설정 | 응답이 템플릿별로 상한됨 | max_output_tokens=512인 템플릿 -- 응답이 이를 절대 초과하지 않음 |

**비용 추정 공식:**
```
Monthly LLM cost = DAU x queries_per_user x 30 x (1 - cache_hit_rate) x (avg_input_tokens x input_price + avg_output_tokens x output_price) / 1,000,000
```

**규모별 벤치마크 임계값:**

| DAU | 요청당 목표 비용 | 월간 예산 |
|-----|-------------------|----------------|
| 1K | < $0.005 | < $750 |
| 10K | < $0.003 | < $4,500 |
| 100K | < $0.001 | < $15,000 |

## 4. 관측 가능성(Observability) (프로덕션에서의 디버깅)

볼 수 없는 것은 고칠 수 없습니다.

| 체크 항목 | 통과 기준 | 검증 방법 |
|-------|--------------|---------------|
| 구조화된 JSON 로깅 | 모든 요청이 JSON 로그 라인을 생성 | 로그에 포함: request_id, user_id, model, tokens, latency_ms, cost |
| 요청 추적 | 컴포넌트 타이밍을 포함한 엔드투엔드 추적 | 단일 요청이 다음을 표시합니다: 가드레일 (5ms) + 캐시 (2ms) + llm (3200ms) + 평가 (1ms) |
| 지연 시간 추적 | P50, P95, P99 측정 | 1000개 요청 후: P50 < 2s, P99 < 10s |
| 오류율 모니터링 | 오류가 집계되고 분류됨 | 대시보드가 다음을 표시합니다: API 오류 0.5%, 가드레일 차단 0.1%, 시간 초과 0.01% |
| 캐시 지표 | 적중률, 미스율, 항목 수 표시 | `GET /v1/cache/stats`이 현재 수치 반환 |
| A/B 테스트 지표 | 변형별 품질 지표 로깅 | 각 요청이 prompt_template + 버전을 비교를 위해 로깅 |
| 평가 로깅 | 요청별 품질 신호 기록 | 응답 길이, 지연 시간, 모델, 템플릿 버전이 오프라인 분석을 위해 저장됨 |

## 5. 프롬프트 관리

프롬프트는 코드입니다. 코드처럼 취급하세요.

| 체크 항목 | 통과 기준 | 검증 방법 |
|-------|--------------|---------------|
| 버전 관리 템플릿 | 모든 템플릿에 이름 + 버전 문자열이 있음 | 템플릿 변경이 새 버전을 생성하고, 이전 버전은 보존됨 |
| A/B 테스트 지원 | 결정적 사용자 해시로 트래픽 분할 | 실험 내에서 동일한 사용자는 항상 동일한 변형을 봅니다 |
| 롤백 기능 | 1분 미만으로 이전 버전으로 되돌리기 | 실험 구성 변경 -- 트래픽이 즉시 이동 |
| 템플릿 검증 | 렌더링 전에 변수 검증 | 템플릿에 변수가 누락되면 KeyError가 아닌 명확한 오류가 발생 |
| 시스템 프롬프트 분리 | 시스템 및 사용자 메시지가 별도 필드에 있음 | 시스템 프롬프트가 사용자 메시지에 연결(concatenate)되지 않음 |

## 6. 확장성 준비

출시 시에는 필요하지 않습니다. 10배 확장 시 필요합니다.

| 체크 항목 | 통과 기준 | 검증 방법 |
|-------|--------------|---------------|
| 비동기 LLM 호출 | API 호출에서 스레드 블로킹 없음 | 50개 동시 요청 -- 서버 CPU가 < 30% 유지 |
| 연결 풀링 | HTTP 연결 재사용 | 네트워크 추적에서 LLM 제공자와의 지속 연결 표시 |
| 수평 확장 | 상태 비저장 서버 설계 | 로드 밸런서 뒤의 2개 인스턴스 -- 모든 요청 성공 |
| 큐 지원 | 실시간이 아닌 작업은 큐로 이동 | 요약 요청이 job_id를 반환하고, 결과는 폴링으로 이용 가능 |
| 테스트한 부하 | 동시 사용자 100명, 오류율 < 5% | `wrk` 또는 `locust` 테스트가 목표 동시성에서 통과 |

## 신규 프로젝트의 구현 순서

1. **1일차:** API 서버 + 프롬프트 템플릿 + 재시도 포함 단일 LLM 호출
2. **2일차:** 입력 가드레일 + 출력 가드레일 + 오류 처리
3. **3일차:** 시맨틱 캐시 + 요청별 비용 추적
4. **4일차:** 스트리밍 (SSE) + 헬스 체크 엔드포인트
5. **5일차:** 구조화된 로깅 + 요청 추적 + 평가 로깅
6. **2주차:** A/B 테스트 + 프롬프트 버전 관리 + 롤백
7. **3주차:** 대체 모델 체인 + 우아한 저하(Graceful Degradation)
8. **4주차:** 부하 테스트 + 비동기 최적화 + 수평 확장

## 빠른 진단

프로덕션에서 문제가 발생하면 이 순서로 점검하세요:

1. **사용자가 오류를 호소하나요?** 헬스 엔드포인트를 확인한 후, 로그에서 오류율을 확인하고, LLM 제공업체의 상태 페이지를 점검하세요
2. **응답이 느린가요?** P99 지연 시간을 확인한 후, 캐시 적중률을 확인하고, 추적(trace)에서 LLM 응답 시간을 점검하세요
3. **비용이 급증하나요?** 요청당 비용 추세를 확인한 후, 캐시 적중률을 확인하고, 비용이 높은 상위 사용자를 확인한 후, 토큰 수를 증가시킨 프롬프트 템플릿 변경을 찾아보세요
4. **품질이 떨어졌나요?** 새로운 프롬프트 버전이 배포되었는지, RAG 검색 정확도가 변경되었는지, 모델 제공업체가 기본 모델 버전을 변경했는지 확인하세요
5. **보안 사고가 발생했나요?** 가드레일 차단율(급격한 감소 = 가드레일 비활성화)을 확인하고, 요청 로그에서 이상한 패턴을 점검한 후, API 키를 즉시 회전하세요
