# 프롬프트 패턴 선택 가이드

LLM 기반 기능을 구축할 때, 프롬프트를 작성하기 전에 프롬프트 패턴을 선택하세요. 패턴이 구조를 결정합니다. 내용은 그 구조에 채워 넣습니다.

## 패턴 의사결정 매트릭스

| 작업 유형 | 주요 패턴 | 보조 패턴 | 온도 | 소수 예시 필요 여부 |
|-----------|----------------|-------------------|-------------|-----------------|
| 데이터 추출 | 템플릿 채우기 | 소수 예시 | 0.0 | 예 (2-3개 예시) |
| 분류 | 소수 예시 | 가드레일 | 0.0 | 예 (3-5개 예시) |
| 요약 | 페르소나 + 템플릿 | 청중 맞춤 | 0.3 | 아니오 |
| 코드 생성 | 페르소나 | 사고의 연쇄 | 0.0 | 선택적 |
| 창의적 글쓰기 | 페르소나 | 비평 | 0.7-1.0 | 아니오 |
| 다단계 추론 | 사고의 연쇄 | 분해 | 0.3 | 선택적 |
| 질문 답변 | 페르소나 + 가드레일 | 경계 | 0.3 | 아니오 |
| 프롬프트 생성 | 메타 프롬프트 | 비평 | 0.7 | 예 (1-2개 예시) |
| 콘텐츠 Moderation | 가드레일 + 경계 | 소수 예시 | 0.0 | 예 (5개 이상 예시) |
| 번역/적응 | 청중 맞춤 | 소수 예시 | 0.3 | 예 (2-3개 예시) |

## 각 패턴을 사용할 때

**페르소나 패턴**: 모든 프롬프트의 기본으로 사용하세요. 유일한 질문은 역할을 얼마나 구체적으로 만들지입니다. 일반적인 작업에는 넓은 역할이 충분합니다. 도메인 특화 작업에는 역할이 도메인, 경력 수준, 컨텍스트를 명시해야 합니다.

**소수 예시 패턴**: 출력 형식이 내용보다 중요할 때 사용하세요. 모델이 특정 JSON 형식, CSV 형식, 분류 레이블을 생성해야 한다면, 지시문보다 예시가 더 효과적입니다. 경험칙: 단순한 형식에는 2-3개 예시, 복잡하거나 모호한 형식에는 5개 이상 예시를 사용하세요.

**Chain-of-Thought 패턴**: 수학, 논리, 다단계 분석 및 모델이 "작업 과정을 보여줘야" 하는 모든 작업에 사용하세요. 추론 작업에서 정확도를 10-40% 향상시킵니다 (Wei et al., 2022). 단순한 사실 조회나 추출에는 사용하지 마세요. 토큰을 낭비합니다.

**Template Fill 패턴**: 모든 출력이 동일한 형태를 가져야 하는 구조화된 추출에 사용하세요. temperature=0.00강 누락된 필드에 대한 명시적인 "N/A" 처리와 함께 사용할 때 가장 잘 작동합니다.

**Critique 패턴**: 속도보다 품질이 중요할 때 사용하세요. 모델이 생성, 비판, 개선 과정을 거칩니다. 토큰 비용이 대략 두 배로 증가하지만 정확도와 완전성이 크게 향상됩니다. 고위험 출력(보고서, 추천, 공개 콘텐츠)에 가장 적합합니다.

**Guardrail 패턴**: 모든 사용자-facing 시스템에 사용하세요. 항상 포함해야 하는 요소는 범위 경계, 범위 밖 요청에 대한 거부 동작, 그리고 명시적인 "모르겠습니다" 처리입니다. 애플리케이션 측의 입력 검증과 결합하세요.

**Meta-Prompt 패턴**: 새로운 작업을 위한 프롬프트를 생성할 때 사용하세요. 프롬프트를 처음부터 작성하는 대신, 작업을 설명하고 모델이 프롬프트를 작성하게 하세요. 그 후 테스트하고 반복하세요. 초기 프롬프트 개발 시간을 절약합니다.

**Decomposition 패턴**: 분할 정복(divide-and-conquer)의 이점을 얻는 복잡한 문제에 사용하세요. 모델이 문제를 부분으로 나누고, 각각을 해결한 후 결합합니다. 3-7개의 하위 문제가 있는 작업에 가장 효과적입니다.

**Audience Adaptation 패턴**: 동일한 콘텐츠가 다른 청중을 위해 제공되어야 할 때 사용하세요. 청중을 명시적으로 지정하세요. 모델이 컨텍스트로부터 추측하도록 의존하지 마세요.

**Boundary 패턴**: 특정 유형의 질문에 절대 답변해서는 안 되는 프로덕션 시스템에 사용하세요. 가드레일보다 더 강력합니다. 정확한 거부 메시지와 함께 하드 스코프(hard scope)를 정의하기 때문입니다. 컴플라이언스 민감 도메인에 필수적입니다.

## 모델 간 호환성

GPT-4o, Claude 3.5 Sonnet, Gemini 1.5 Pro, Llama 3 전반에서 일관되게 작동하는 정도에 따라 패턴을 순위를 매겼습니다:

| 패턴 | 모델 간 일관성 | 비고 |
|---------|------------------------|-------|
| Few-Shot | 매우 높음 | 예시가 모든 모델에 잘 전달됩니다 |
| Template Fill | 매우 높음 | 명시적인 구조는 편차가 거의 없습니다 |
| Chain-of-Thought | 높음 | 주요 모델 모두 "단계별 사고"를 지원 |
| Persona | 높음 | 모든 모델에서 작동하지만, 모델별로 역할의 구체성 수준에 대한 반응이 다름 |
| Guardrail | 중간 | Claude는 가드레일을 가장 엄격하게 따름; GPT-4o는 긴 대화에서 가끔 이탈 |
| Critique | 중간 | 자기 비판의 품질이 모델에 따라 크게 다름 |
| Meta-Prompt | 중간 | GPT-4o와 Claude는 서로 다른 프롬프트 스타일을 생성 |
| Boundary | 낮음~중간 | 거부 행동이 다양함; 모델별로 테스트 |

## 공통 실수

1. **모든 것에 Chain-of-Thought 사용**: CoT는 토큰과 지연 시간을 추가합니다. 추론 단계가 필요할 때만 사용하세요.
2. **너무 많은 제약 조건**: 5~7개 이상의 제약 조건이 있으면 모델이 일부 조건을 무시하기 시작합니다. 가장 중요한 3가지를 우선시하세요.
3. **모순되는 페르소나 + 제약 조건**: "당신은 창의적인 작가입니다" + "절대 은유를 사용하지 마세요"는 모델을 혼란스럽게 만듭니다.
4. **온도 지정 없음**: 결정적 출력이 필요한데 온도를 기본값(보통 1.0)으로 방치합니다.
5. **모델 간 프롬프트 복사-붙여넣기**: 항상 테스트하세요. GPT-4o에 맞춰 조정된 프롬프트는 Claude에서 성능이 떨어질 수 있으며, 그 반대도 마찬가지입니다.
6. **시스템 메시지 무시**: 모든 것을 사용자 메시지에 넣는 대신, 지속되는 규칙을 위해 시스템 메시지를 사용하지 않습니다.
7. **부정적 제약 조건에 과도하게 의존**: "X, Y, Z, A, B, C를 하지 마세요"는 "W만 하세요"보다 효과가 적습니다. 긍정적 프레이밍은 모델에 명확한 목표를 제공합니다.

## 신뢰성 목표

| 사용 사례 | 패턴 조합 | 예상 정확도 | 토큰 비용 |
|----------|-------------------|-------------------|------------|
| 프로덕션 추출 | Template + Few-Shot | 95%+ | 낮음 (500-1K) |
| 사용자 대상 Q&A | Persona + Guardrail + Boundary | 90%+ | 중간 (1-2K) |
| 코드 생성 | Persona + Chain-of-Thought | 85%+ | 중간 (1-3K) |
| 콘텐츠 생성 | Persona + Critique | 90%+ 품질 | 높음 (2-4K, 이중 패스) |
| 분류 | Few-Shot + Guardrail | 95%+ | 낮음 (300-800) |
| 복잡한 분석 | Decomposition + Chain-of-Thought | 85%+ | 높음 (3-5K) |
