# 비동기 및 Hogwild! 추론

> 추론적 디코딩(Speculative Decoding)(10단계 · 15강)는 하나의 시퀀스 내에서 토큰을 병렬화합니다. 다중 에이전트 프레임워크는 전체 시퀀스 간에 병렬화하지만 명시적인 조정(투표, 하위 작업 분할)을 강제합니다. Hogwild! 추론(Rodionov et al., arXiv:2504.06261)은 다른 접근법을 취합니다: 동일한 LLM의 N개 인스턴스를 공유 키-값 캐시에 대해 병렬로 실행하는 것입니다. 각 워커는 다른 모든 워커가 생성한 토큰을 즉시 볼 수 있습니다. 최신 추론 모델(QwQ, DeepSeek-R1)은 미세 조정 없이도 그 공유 캐시를 통해 자체적으로 조정할 수 있습니다. 이 접근법은 실험적이지만, 추론적 디코딩과 직교하는 추론 병렬화의 완전히 새로운 축을 열립니다. 이 강의는 stdlib Python으로 두 워커 Hogwild! 시뮬레이터를 구현하고, 공유 캐시 협업이 기존 모델의 추론 능력에서 어떻게 자연스럽게 발생하는지 설명합니다.

**유형:** Build
**언어:** Python (stdlib)
**선수 요건:** 10단계 · 12강 (추론 최적화), 10단계 · 15강 (추론적 디코딩)
**시간:** 약 60분

## 학습 목표

- 세 가지 일반적인 병렬 LLM 토폴로지(투표, 하위 작업, Hogwild!)를 설명하고, 각각이 해결하려는 문제를 지정하세요.
- Hogwild!의 핵심 설정을 서술하세요: 여러 워커, 하나의 공유 KV 캐시, 자체 프롬프트를 통한 자연스러운 조정.
- 워커 수 `N`, 작업 수준 병렬성 `p`, 조정 오버헤드 `c`의 함수로서 Hogwild!의 실제 시간(speedup)을 계산하세요.
- 장난감 문제(toy problem)에 대해 두 워커 Hogwild! 시뮬레이터를 구현하고, 자연스럽게 발생하는 작업 분할을 관찰하세요.

## 문제점

최신 LLM은 긴 추론 체인을 생성하여 어려운 문제를 해결합니다. 5000개 토큰의 단계별 논리는 흔하며, 깊은 수학 문제에서는 수만 개 토큰이 발생합니다. 70B 모델에서 초당 35개 토큰 디코딩 시 5만 개 토큰은 24분입니다. 모델이 대화형(interactive)이 아닙니다.

추론적 디코딩(Speculative Decoding)(10단계 · 15강)은 하나의 시퀀스 내에서 병렬화하여 3-5배의 속도 향상을 제공합니다. 그 이상에서는 자기회귀(Autoregressive) 디코딩의 순차적 의존성이 하드 한계입니다. 각 새 토큰은 모든 이전 토큰에 의존합니다.

명백한 질문: 시퀀스 간 병렬화가 가능할까요? 동일한 모델의 여러 복사본을 같은 문제에 실행하고, 서로 협력하며, 작업을 분담할 수 있을까요?

선행 연구: 투표 앙상블(N개의 모델을 실행하고 다수결로 답을 선택), 사고의 나무(Tree-of-Thought, 추론 경로를 분기하고 재결합), 다중 에이전트 프레임워크(각 에이전트에 하위 작업을 할당하고 조정자 사용) 등이 있습니다. 이들은 특정 작업 도메인에서 도움이 됩니다. 또한 모두 명시적인 조정 메커니즘(투표 규칙, 분기 및 가지치기 로직, 에이전트 간 메시지 프로토콜)을 도입합니다.

Hogwild! 추론은 다른 접근법을 취합니다. N개의 워커가 단일 KV 캐시를 공유합니다. 각 워커는 다른 워커가 생성한 토큰을 즉시, 마치 자신의 컨텍스트인 것처럼 볼 수 있습니다. 워커들은 훈련이나 미세 조정 없이도 작업 분담 방법을 파악합니다. 현대적인 추론 모델(QwQ, DeepSeek-R1, Claude 계열 추론 모드)은 공유 캐시를 읽고 "워커 2가 기본 케이스를 이미 처리했으므로, 나는 귀납 단계에 집중하겠다"와 같은 식으로 말할 수 있습니다.

속도 향상은 작업량에 따라 달라지며, 2026년 4월 현재 실험적인 상태입니다. 하지만 이 아이디어는 추론 병렬화의 새로운 축을 열기 때문에 알아둘 가치가 있습니다.

## 개념

### 설정

N개의 워커 프로세스를 초기화하고, 모두 동일한 LLM을 실행합니다. 워커별 KV 캐시 대신 하나의 공유 캐시를 유지합니다. 워커 `i`가 토큰 `t_j`를 생성하면, 해당 토큰은 다음 위치에 공유 캐시에 기록됩니다. 워커 `k`가 다음 단계를 수행할 때, 캐시의 현재 상태(N개 워커가 지금까지 생성한 모든 내용을 포함)를 읽습니다.

단계 시간 동안 워커들은 토큰 기록을 위해 경쟁합니다. 워커별 위치 인덱스는 없으며, 캐시는 단일 성장 시퀀스입니다. 순서는 기록 도착 시간에 의해 결정됩니다.

### 조정이 발생하는 이유

워커들은 프롬프트를 공유합니다. 일반적으로 "당신은 이 문제를 함께 작업하는 N개 인스턴스 중 하나입니다. 각 인스턴스는 공유 메모리를 읽고 다른 인스턴스가 작성한 내용을 볼 수 있습니다. 중복 작업을 피하세요"와 같은 형태입니다. 프롬프트와 공유 캐시만으로도 충분합니다. 추론 모델은 캐시를 읽고, 문제의 어떤 부분이 이미 시도되었는지 파악하며, (항상은 아니지만) 자주 미탐색 부분으로 전환합니다.

Hogwild! 논문(Rodionov et al., 2025)은 다음과 같은 관찰을 보고합니다:

- 워커는 계획을 수립하고 캐시를 통해 다른 워커에게 이를 전달합니다.
- 워커는 다른 워커의 추론에서 오류를 발견하고 이를 지적합니다.
- 워커는 계획이 실패하면 적응하여 대안을 제안합니다.
- 중복성을 확인하라는 프롬프트를 받으면, 워커는 이를 감지하고 방향을 전환합니다.

이 모든 과정에는 미세 조정(Fine-tuning)이 필요하지 않습니다. 이러한 융현적 행동은 모델이 이미 가지고 있는 추론 능력에서 비롯됩니다.

### 명명

논문 이름은 Hogwild! SGD (Recht et al., 2011)를 비유한 것으로, 이는 비동기 업데이트 옵티마이저입니다. 비유하자면, SGD의 비동기 워커는 모두 공유 매개변수 벡터에 기록하며, Hogwild! 추론(Inference)의 워커는 모두 공유 KV 캐시에 기록합니다. 둘 다 동기화 보장보다는 경험적 수렴에 의존합니다.

### RoPE가 이를 다루기 쉽게 만듭니다

회전 위치 임베딩(RoPE, Su et al. 2021)은 Q 및 K 벡터에서의 회전을 통해 위치 정보를 인코딩합니다. 위치는 고정된 오프셋이 아닌 회전으로 표현되므로, 토큰의 위치가 이동해도 KV 캐시 항목을 재계산할 필요가 없습니다. 워커 `i`가 위치 `p`에서 공유 캐시에 기록할 때, 해당 위치를 읽는 다른 워커는 캐시된 항목을 직접 사용할 수 있습니다. 즉, 재회전이 필요하지 않습니다.

학습된 위치나 절대 위치 모델에서는 Hogwild!가 모든 동시 쓰기 시 캐시 무효화를 수행해야 합니다. RoPE는 캐시가 안정적으로 유지되도록 합니다.

### 실제 시간 계산

`T_serial`을 한 워커가 문제를 단독으로 해결하는 시간이라고 합시다. `p`은 작업 단위 병렬화 가능 비율이라고 합시다. `c`는 단계별 조정 오버헤드(확장된 캐시 읽기, 무엇을 쓸지 결정)라고 합시다.

단일 워커 시간: `T_serial`.
N-워커 Hogwild! 시간, 조정이 무료인 경우: `T_serial * ((1 - p) + p / N)`. 고전적인 Amdahl 법칙입니다.
조정 오버헤드가 있는 경우: `T_serial * ((1 - p) + p / N) + c * steps_per_worker`.

워커가 생산적이려면 `c`가 단계별 디코딩 시간에 비해 작아야 합니다. 5k+ 토큰을 생성하는 추론 모델에서는 워커가 수백 토큰의 조정 오버헤드를 감당하고도 순이익을 얻을 수 있습니다. 짧은 채팅 작업에서는 조정이 지배적이므로 Hogwild!가 순차 처리보다 더 나쁜 성능을 보입니다.

### 구체적인 예

추론 문제: 10k 토큰의 사고의 연쇄 (CoT)(Chain of Thought). 문제가 `p = 0.7`개의 병렬화 가능한 내용(서로 다른 증명 전략, 서로 다른 사례 분석)과 워커당 `c = 200`개의 조정 오버헤드 토큰을 가진다고 가정해 보세요. `N = 4`개의 워커를 사용할 경우:

- 순차적 시간: 10000 디코딩 단계.
- Hogwild! 시간: 10000 * (0.3 + 0.7 / 4) + 200 * 4 = 10000 * 0.475 + 800 = 5550 디코딩 단계.
- 속도 향상: 10000 / 5550 = 1.8배.

이는 미미한 수준입니다. 하지만 더 긴 추론 문제(50k 토큰)에서는 조정 오버헤드가 상각(amortize)되어 속도 향상이 2.5-3배까지 올라갑니다. Hogwild!는 다중 스레드 코드를 자연스럽게 작성할 수 있는 언어에서의 스레드 수준 병렬화(thread-level parallelism)에 해당하는 추론 방식입니다.

### Hogwild!를 사용할 때

- 독립적인 하위 목표(sub-goal)로 병렬화할 수 있는 긴 추론 문제(수천 토큰).
- 단계별로 생각하는 방식으로 학습된 추론 모델. 비추론 모델은 자체적으로 잘 조정되지 않습니다.
- 공유 캐시(shared cache)와 N개의 워커 프로세스를 수용할 수 있는 충분한 VRAM을 갖춘 단일 노드(single-node) 배포. 캐시는 공유되지만, 각 워커는 자체 활성화 메모리(activation memory)를 가집니다.

### 사용하지 말아야 할 때

- 짧은 대화형 채팅. 조정 오버헤드가 지배적입니다.
- 병렬화되지 않는 작업(단일 선형 증명, 단일 컴파일레이션). N=1이 최대입니다.
- 비추론 모델. 조정이 발생하지 않습니다.
- 다중 노드(multi-node) 배포. 공유 캐시는 워커 간 매우 빠른 동기화가 필요합니다. 노드 내(intra-node)는 괜찮지만, 노드 간(cross-node)은 지연(latency) 재앙입니다.

### 실험적 상태

2026년 4월 기준으로, Hogwild!는 오픈소스 PyTorch 구현이 있는 연구 방법입니다. 생산 환경 채택은 이루어지지 않았습니다. 세 가지 장애물:

1. 동시 프로세스(concurrent processes) 간 공유 KV 캐시(KV Cache) 관리는 비자명한(non-trivial) 엔지니어링입니다.
2. emergent coordination은 작업에 따라 달라지며, 벤치마크는 아직 구축 중입니다.
3. 속도 향상은 추론적 디코딩(Speculative Decoding)이 이미 제공하는 것에 비해 미미하며, 두 가지를 결합할 수 있지만 결합된 엔지니어링은 또 다른 레이어입니다.

알아둘 가치가 있습니다. 실험해 볼 가치가 있습니다. 제품에 베팅할 가치는 아직 없습니다.

## 구현하기

`code/main.py`는 Hogwild! 시뮬레이터를 구현합니다:

- 두 개의 워커 프로세스는 각각 결정론적인 "LLM"이며, 알려진 확률로 여러 토큰 카테고리(work-token, observe-token, coordinate-token) 중 하나를 생성합니다.
- 두 워커가 읽고 쓰는 공유 캐시(단순한 토큰 목록)가 있습니다.
- 간단한 조정 로직: 한 워커가 다른 워커가 특정 카테고리에서 충분한 work-token을 이미 생성한 것을 확인하면, 다른 카테고리를 선택합니다.

시뮬레이터는 고정된 스텝 예산으로 실행되며 다음을 보고합니다:

- 생성된 work-token의 총 개수.
- 총 벽 시간(wall time, 워커 스텝 수).
- 단일 워커 대비 유효 속도 향상.
- 어떤 워커가 어떤 토큰을 기록했는지 추적한 내역.

### 1단계: 공유 캐시

두 워커가 추가하는 목록입니다. 실제 구현에서는 단순한 잠금(Python `threading.Lock`)을 사용하며, 여기서는 카운터로 시뮬레이션합니다.

### 2단계: 워커 루프

각 워커는 매 스텝마다 다음을 수행합니다:

- 현재 공유 캐시를 읽습니다.
- 이미 존재하는 토큰을 기반으로 기록할 토큰 카테고리를 결정합니다.
- 토큰 하나를 기록합니다.

### 3단계: 조정 휴리스틱

카테고리 X가 캐시에 이미 K개의 토큰을 가지고 있고 워커의 의도된 카테고리가 X라면, 워커는 카테고리 Y로 전환합니다. 이는 "이 부분이 이미 다루어졌으니 다른 것을 하라"는 추론 모델의 동작을 대체하는 장난감 수준의 구현입니다.

### 4단계: 측정된 속도 향상

N=1 워커와 N=2 워커로 시뮬레이터를 실행하고, 동일한 총 스텝 예산을 사용합니다. 생성된 work-token을 세어 보세요. 조정 기반 작업 분업으로 인해 N=2는 work-token을 약 1.5-1.8배 더 생성해야 합니다.

### 5단계: 조정 스트레스 테스트

조정 휴리스틱의 민감도를 낮추고 다시 실행하세요. 좋은 조정이 없으면 N=2가 동일한 토큰을 중복 생성하여 속도 향상이 1 미만으로 떨어지는 것을 관찰할 수 있습니다. 이는 논문에서 관찰한 바와 일치합니다: 워커가 스스로 조정할 수 있는 추론 능력이 있어야 이 기법이 작동합니다.

## 사용하기

2026년 4월 기준 Hogwild!의 프로덕션 통합은 연구용 수준입니다. Yandex/HSE/IST의 참조 구현은 PyTorch 기반이며, DeepSeek-R1 및 QwQ 모델의 단일 노드 다중 프로세스 환경을 대상으로 합니다.

실용적인 채택 경로:

1. 추론 작업 워크로드를 프로파일링하세요. 탐색적 토큰(다중 전략, 사례 분석, 검색)과 선형 토큰의 비율을 측정하세요.
2. 탐색이 지배적이면, 두 워커 Hogwild! 실험을 수행하세요. 월타임(wall-time) 개선량을 측정하세요.
3. 개선량이 1.3배 미만이라면, 조정 지배(coordination-dominated) 영역에 속합니다. 단일 워커로 되돌리세요.
4. 개선량이 1.5배 이상이라면, N=4로 확장하고 다시 측정하세요. 수익 감소는 일반적으로 N=4~8 부근에서 발생합니다.

추론적 디코딩(Speculative Decoding)과 결합하세요: 각 Hogwild! 워커는 독립적으로 스펙 디코딩을 사용할 수 있습니다. 두 속도 향상은 (대략적으로) 곱해져, 3배 스펙 디코딩과 1.8배 Hogwild!가 단순한 단일 워커 디코딩 대비 효과적인 5.4배 성능을 달성합니다.

## 출시하기

이 강의는 `outputs/skill-parallel-inference-router.md`를 생성합니다. 추론 워크로드 프로파일(토큰 예산, 작업 병렬화 프로파일, 모델 계열, 배포 대상)이 주어지면, 투표(voting), tree-of-thought, 다중 에이전트, Hogwild!, 추론적 디코딩 전략 간에 라우팅합니다.

## 연습 문제

1. `code/main.py`를 기본 설정으로 실행하세요. N=2 Hogwild! 구성이 동일한 월타임에서 N=1 기준선보다 더 많은 작업 토큰을 생성함을 확인하세요.

2. 조정 휴리스틱의 강도를 낮추세요(`coordination_weight=0.1` 설정). 다시 실행하세요. 속도 향상이 붕괴됨을 보이세요. 이유를 설명하세요: 워커들이 조정할 수 없을 때 노력의 중복이 발생합니다.

3. `p=0.8, c=500` 및 N=4 워커를 사용하는 50k 토큰 추론 작업에 대한 예상 Hogwild! 속도 향상을 계산하세요. `p=0.3, c=200` 및 N=4를 사용하는 1k 토큰 채팅 작업에 대해서도 동일하게 수행하세요. 왜 하나는 이득이고 다른 하나는 손실인가요?

4. Hogwild! 논문의 섹션 4(예비 평가)를 읽으세요. 저자들이 보고하는 두 가지 실패 모드를 식별하세요. 더 나은 조정 프롬프트가 각각을 어떻게 완화할 수 있는지 설명하세요.

5. 토이(toy)에서 Hogwild!와 추론적 디코딩을 결합하세요: 각 워커는 내부적으로 2-토큰 스펙 디코딩을 사용합니다. 곱셈적 속도 향상을 보고하세요. 두 워커가 모두 동일한 공유 캐시 접두어를 확장하려고 할 때 어떤 장부(bookkeeping) 문제가 발생하나요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| Hogwild! | "병렬 워커, 공유 캐시" | 하나의 공유 KV 캐시를 사용하는 동일한 LLM의 N개 인스턴스가 동시에 실행되는 방식; 자기 프롬프트를 통한 창발적 조정 |
| 공유 KV 캐시 | "조정 매체" | 모든 워커가 읽고 쓰는 단일 확장 KV 버퍼; 워커 간 즉각적인 토큰 가시성을 가능하게 함 |
| 창발적 조정 | "학습 불필요" | 추론 가능한 LLM은 공유 캐시를 읽고 미세 조정이나 명시적 프로토콜 없이 작업을 분배할 수 있음 |
| 조정 오버헤드 (c) | "방향 설정에 사용된 토큰" | 확장된 캐시를 읽고 무엇을 할지 결정하는 데 드는 워커별 비용; 총 디코딩 시간 대비 작아야 함 |
| 병렬화 가능 비율 (p) | "병렬로 실행할 수 있는 부분" | 작업 수준 병렬화: 본질적으로 순차적이지 않은 전체 작업의 비율 |
| RoPE가 Hogwild!를 가능하게 함 | "회전 위치는 이동 불변" | 위치가 회전이기 때문에, 공유 캐시에 기록할 때 이전 토큰을 재계산할 필요가 없음 |
| 투표 앙상블 | "N개 실행, 다수 선택" | 가장 단순한 병렬 추론 토폴로지; 분류에는 유용하지만, 장문 추론에는 덜 유용 |
| Tree of thought | "분기 및 가지치기" | 여러 분기를 탐색하고 가지치기하는 추론 전략; 명시적 조정 로직 |
| 다중 에이전트 프레임워크 | "하위 작업 할당" | 각 에이전트가 역할을 부여받음; 조정자가 오케스트레이션; 무거운 프로토콜 오버헤드 |
