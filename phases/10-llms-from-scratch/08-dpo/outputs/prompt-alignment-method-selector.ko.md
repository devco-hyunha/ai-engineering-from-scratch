# 정렬 방법 선택기

언어 모델의 정렬 방법을 선택할 때, 이 프레임워크를 사용하여 데이터, 컴퓨팅 자원, 품질 요구 사항을 평가한 후, 제약 조건에 가장 잘 맞는 방법을 선택해 보세요.

## 입력 요구 사항

다음 정보를 제공하세요:
- **기본 모델** (예: Llama 3 8B, Mistral 7B, Qwen 2.5 72B)
- **시작점** (기본 모델, 또는 이미 SFT가 적용된 모델인가요?)
- **사용 가능한 데이터** (지시문 쌍, 선호 쌍, 비쌍 평가 데이터, 또는 없음)
- **컴퓨팅 예산** (GPU 시간, GPU 수)
- **품질 목표** (프로토타입에 충분, 오픈소스와 경쟁 가능, 최신 기술 수준)
- **기간** (일, 주, 월)

## 의사 결정 매트릭스

### 빠른 선택

| 상황 | 권장 방법 | 이유 |
|---------------|-------------------|-----|
| 선호 데이터 없음, 지시문 쌍만 있음 | SFT만 | 선호 신호 없이는 정렬할 수 없음 |
| 선호 쌍 5,000개 미만, 컴퓨팅 자원 제한 | DPO | 더 단순한 파이프라인, 소규모 데이터에 잘 작동 |
| 비쌍 피드백 (좋아요/싫어요만) | KTO | 쌍 비교 없이 작동하는 유일한 방법 |
| 단일 학습 실행에서 정렬 원함 | ORPO | SFT + 정렬 결합, 참조 모델 불필요 |
| 메모리 제한 (참조 모델 로드 불가) | SimPO | 참조 모델 불필요 |
| 대규모, 다목적 정렬 | RLHF (PPO) | 분리된 보상 모델이 복잡한 선호를 포착 |
| 온라인 데이터를 활용한 반복적 정렬 | RLHF (PPO) | 생성, 평가, 재학습을 반복하는 루프 가능 |
| RLHF 후 정제 | DPO | RLHF 모델을 타겟 선호에 대해 미세 조정 |

### 상세 비교

| 방법 | 데이터 요구 사항 | 메모리 내 모델 수 | 학습 루프 | 안정성 | 최적 규모 |
|--------|-----------------|-----------------|----------------|-----------|------------|
| SFT | 지시문 쌍 (10K+) | 1 | 1 | 높음 | 모든 규모 |
| RLHF | 선호 쌍 (20K+) | 3-4 | 3 | 낮음 | 대형 (70B+) |
| DPO | 선호 쌍 (5K+) | 2 | 2 (SFT + DPO) | 높음 | 소형-중형 (7B-70B) |
| KTO | 비쌍 평가 (5K+) | 2 | 2 (SFT + KTO) | 높음 | 모든 크기 |
| ORPO | 선호 쌍 (10K+) | 1 | 1 | 높음 | 소형-중형 |
| SimPO | 선호 쌍 (5K+) | 1 | 2 (SFT + SimPO) | 높음 | 소형-중형 |

## 방법별 구성

### SFT

- **중지 시점**: 1-3 에포크(Epoch) 후 또는 검증 손실(Loss)이 더 이상 감소하지 않을 때
- **핵심 하이퍼파라미터(Hyperparameter)**: 학습률(Learning Rate) (1e-5 ~ 5e-5, 더 큰 모델일수록 낮게 설정)
- **중요한 세부 사항**: 손실(Loss) 계산 시 지시문 토큰(Token)을 마스킹(Masking)하세요
- **주의 사항**: 3 에포크(Epoch) 이상은 암기(Memorization)를 유발합니다. 사전 학습 데이터의 2-5%를 혼합하세요

### RLHF (PPO)

- **사용 시점**: 20K+ 비교 쌍이 있고, 다중 목표 정렬(Alignment)이 필요하거나, 반복적인 온라인 학습을 원할 때
- **핵심 하이퍼파라미터(Hyperparameter)**: KL 계수 (0.01-0.05), PPO 클리핑(Clip) 비율 (0.1-0.3), 학습률(Learning Rate) (5e-6 ~ 3e-5)
- **중요한 세부 사항**: 보상 모델은 정책 모델보다 크기가 같거나 커야 합니다
- **주의 사항**: PPO는 불안정합니다. KL 발산(Divergence) 및 보상 곡선을 지속적으로 모니터링하세요

### DPO

- **사용 시점**: 선호 쌍이 있고, RLHF보다 더 단순한 파이프라인을 원할 때
- **핵심 하이퍼파라미터(Hyperparameter)**: Beta (0.1-0.5; 낮을수록 참조 모델로부터의 편차가 더 허용됨)
- **중요한 세부 사항**: 참조 모델은 SFT 체크포인트(Checkpoint)의 고정된(Frozen) 사본이어야 합니다
- **주의 사항**: Beta에 매우 민감합니다. [0.05, 0.1, 0.2, 0.5] 범위에서 스윕(Sweep)을 수행하세요

### KTO

- **사용 시점**: 쌍 비교 없이 "좋음" 또는 "나쁨" 레이블만 있을 때
- **핵심 하이퍼파라미터(Hyperparameter)**: Beta (DPO와 동일), 손실 회피 배수 (나쁜 응답에 대해 1.5배)
- **중요한 세부 사항**: 좋은 예시와 나쁜 예시가 대략적으로 균형을 이루어야 합니다 (40-60% 분할)
- **주의 사항**: 쌍이 없으면 기울기(Gradient) 신호가 약해집니다. DPO보다 더 많은 데이터가 필요할 수 있습니다

### ORPO

- **사용 시점**: SFT를 완전히 생략하고 기본 모델에서 정렬된 모델로 바로 전환할 때
- **핵심 하이퍼파라미터**: Lambda (선호 항과 SFT 항의 가중치)
- **중요한 세부 사항**: 하나의 데이터셋에 지시문 레이블과 선호 쌍이 모두 필요합니다
- **주의 사항**: 결합된 목적 함수는 균형 잡기 어려울 수 있습니다. SFT 손실이 지배적이면 정렬이 약해집니다

### SimPO

- **사용 시점**: 참조 모델을 유지할 수 없는 메모리 제약 환경
- **핵심 하이퍼파라미터**: Beta, gamma (길이 정규화 지수)
- **중요한 세부 사항**: 길이 정규화는 모델이 짧은 응답을 선호하는 것을 방지합니다
- **주의 사항**: 참조 모델 앵커가 없으면 모델이 더 크게 드리프트할 수 있습니다. 주의 깊게 모니터링하세요

## 파이프라인 템플릿

### 템플릿 1: 빠른 프로토타입 (1-2일)

```
Base Model -> SFT (1 epoch, 10K examples) -> DPO (3 epochs, 5K pairs)
```

컴퓨팅: A100에서 7B 모델에 약 4 GPU-시간
품질: 확실한 지시문 따르기, 기본 선호 정렬

### 템플릿 2: 생산 품질 (1-2주)

```
Base Model -> SFT (2 epochs, 50K examples) -> DPO (5 epochs, 20K pairs) -> Eval -> Iterate
```

컴퓨팅: 7B에 약 40 GPU-시간, 70B에 약 200 GPU-시간
품질: 오픈소스 RLHF 모델과 경쟁력 있는 수준

### 템플릿 3: 최신 기술 (1-3개월)

```
Base Model -> SFT (2 epochs, 100K+ examples) -> RLHF (PPO, 50K+ pairs) -> DPO (targeted refinement) -> Eval -> Iterate
```

컴퓨팅: 70B에 약 500+ GPU-시간
품질: 프론티어 모델 정렬에 근접

### 템플릿 4: 최소 데이터 (1-2일)

```
Base Model -> SFT (1 epoch, 5K examples) -> KTO (unpaired thumbs up/down from users)
```

컴퓨팅: 7B에 약 2 GPU-시간
품질: 최소한의 데이터 수집 오버헤드로 SFT 전용보다 더 좋음

## 평가 프로토콜

정렬 후, 다음 차원에서 평가하세요:

1. **선호 승률**: 정렬된 모델과 SFT 모델을 200개 이상의 테스트 프롬프트에서 인간 판정단으로 비교하세요. 목표: 승률 > 60%.
2. **벤치마크 유지**: MMLU, HumanEval 또는 도메인 특화 벤치마크. SFT 기준선에서 > 5% 감소하지 않아야 합니다.
3. **MT-Bench 또는 AlpacaEval**: 표준 정렬 품질 벤치마크. 공개된 기준선과 비교하세요.
4. **안전 평가**: 적대적 프롬프트, 제일브레이크, 유해 요청 범주에 대해 테스트하세요.
5. **응답 다양성**: 100개 프롬프트에 대한 응답의 엔트로피를 측정하세요. 낮은 엔트로피는 모드 붕괴를 의미합니다.

## 공통 실패 모드

| 증상 | 원인 | 방법별 수정 |
|---------|-------|-------------------|
| 장황하고 패딩된 응답 | 보상 모델 / 암시적 보상이 길이를 선호 | DPO: beta 증가. RLHF: 길이 페널티 추가. SimPO: gamma 조정. |
| 모델이 모든 것에 동의함 | 선호 데이터의 편향으로 인한 아첨(Sycophancy) | 올바른 응답이 사용자와 의견이 다른 선호 쌍 추가 |
| 무해한 요청을 거절함 | 안전 데이터에 대한 과잉 정렬 | 안전 예제 비율 감소, 더 많은 무해한 거절 쌍 추가 |
| 출력은 SFT와 거의 동일함 | Beta가 너무 높음 (DPO/KTO) 또는 KL 계수가 너무 높음 (PPO) | Beta / KL 계수 낮추기; 모델이 학습하지 못하고 있음 |
| 학습 손실이 진동함 | 학습률이 너무 높거나 데이터가 부족함 | lr을 2-3배 감소; 선호 데이터 증가 |
