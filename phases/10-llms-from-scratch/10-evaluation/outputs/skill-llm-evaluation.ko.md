# LLM 평가 전략

LLM 시스템을 평가할 때, 이 의사 결정 프레임워크를 적용하여 올바른 접근 방식을 선택해 보세요.

## 각 평가 유형을 사용할 때

**벤치마크 (MMLU, HumanEval, SWE-bench):** 초기 모델 선택을 수행 중입니다. 10개의 후보 모델을 3개로 좁혀야 합니다. 벤치마크는 비용 없이 대략적인 순위를 제공합니다. 벤치마크를 최종 평가로 사용하지 마세요.

**커스텀 평가:** 프로덕션 환경용으로 구축 중입니다. 특정 실패 모드와 함께 특정 작업이 있습니다. 커스텀 평가는 실제 세계의 성능을 예측하는 유일한 평가입니다. 프로토타입에는 최소 50개의 테스트 케이스, 프로덕션에는 200개 이상을 사용하세요.

**LLM-as-judge:** 작업이 개방형입니다 (요약, 작성, 대화). 정확 일치 및 토큰 겹침 지표는 너무 경직되어 있습니다. LLM-as-judge는 판정당 약 $0.01의 비용이 들며, 인간의 판단과 약 80% 일치합니다. 모호한 프롬프트가 아닌 평가 기준(rubric)을 항상 사용하세요.

**인간 평가:** 위험도가 높고 자동화된 지표들이 일치하지 않습니다. 인간 평가는 기준 진실(ground truth)이지만 판정당 $0.10-$2.00의 비용이 듭니다. 모호한 사례와 자동화된 지표의 주기적 보정을 위해 예약해 두세요.

**쌍대 비교(pairwise comparisons)를 통한 ELO:** 동일한 작업에서 여러 모델을 비교 중입니다. 쌍대 비교는 절대 점수보다 더 신뢰할 수 있습니다. 인간(및 LLM 판정자)은 상대적 판단을 더 잘하기 때문입니다.

## 채점 함수 선택

- **정확 일치**: 분류, 엔티티 추출, 알려진 답이 있는 구조화된 출력
- **토큰 F1**: 부분 점수가 중요한 추출 작업
- **ROUGE-L**: 요약, 번역
- **BLEU**: 기계 번역
- **LLM-as-judge**: 개방형 생성, 대화 품질, 유용성
- **실행 기반**: 코드 생성 (코드를 실행하여 테스트가 통과하는지 확인)
- **스키마 준수**: 구조화된 출력 (JSON이 스키마와 일치합니까?)

## 평가 설계에서의 위험 신호

- 평가 세트가 50개 미만인 경우: 결과가 통계적으로 의미가 없습니다
- 엣지 케이스가 없는 경우: 해피 패스 성능만 측정하고 있으며, 이는 실제 환경보다 항상 높습니다
- 단일 지표만 사용하는 경우: 서로 다른 지표는 서로 다른 이야기를 전달하므로, 최소 두 가지 지표를 사용하세요
- 버전 관리가 없는 경우: 버전화된 평가 세트 없이는 개선 사항을 추적할 수 없습니다
- 평가 세트 오염: 미세 조정 데이터나 소수 예시(Few-Shot) 프롬프트에 평가 예제를 포함하지 마세요
- 하나의 모델만 테스트하는 경우: 비교를 위해 기준선(단순한 휴리스틱이라도)이 필요합니다

## 평가 파이프라인 체크리스트

1. 작업을 정확하게 정의하세요 ("질문에 답하기"가 아니라 "지원 티켓을 5개 범주로 분류하기"처럼)
2. 해피 패스, 엣지 케이스, 알려진 회귀 테스트를 포함하여 테스트 케이스를 만드세요
3. 작업 유형에 적합한 2-3개의 채점 함수를 선택하세요
4. 프로덕션 요구 사항에 기반하여 통과/실패 임계값을 설정하세요
5. 실행을 자동화하세요: 한 명령으로 전체 테스트 스위트를 실행할 수 있어야 합니다
6. 모든 것을 버전화하세요: 테스트 케이스, 채점 함수, 프롬프트, 모델 버전
7. 모든 변경 사항에 대해 실행하세요: 프롬프트 업데이트, 모델 교체, 코드 배포
8. 추세를 추적하세요: 단일 점수는 잡음이고, 추세선은 신호입니다
9. 분기별로 인간 판단과 보정(Calibration)하세요
10. 프로덕션 실패가 발견될 때마다 회귀 테스트 케이스를 추가하세요
