# 서버리스 LLM의 콜드 스타트 완화

> 20 GB 모델 이미지는 콜드 상태에서 서빙 상태로 전환하는 데 7B 모델은 5-10분, 70B 모델은 20분 이상 소요됩니다. 진정한 서버리스 환경에서는 이것이 워밍업이 아니라 장애입니다. 완화 전략은 다섯 가지 계층에서 작동합니다: 사전 시드된 노드 이미지 (AWS의 Bottlerocket, 이중 볼륨 아키텍처), 모델 스트리밍 (NVIDIA Run:ai Model Streamer, vLLM 내장), GPU 메모리 스냅샷 (Modal 체크포인트, 최대 10배 빠른 재시작), 웜 풀 (`min_workers=1`), 계층적 로딩 (ServerlessLLM의 NVMe→DRAM→HBM 파이프라인, 지연 시간 10-200배 감소), 그리고 KV 캐시 (GB)가 아닌 입력 토큰 (KB)을 이동하는 라이브 마이그레이션. Modal은 2-4초의 콜드 스타트를 하한선으로 공개하며, Baseten은 기본 5-10초, 사전 워밍업으로 1초 미만입니다. 이 강의에서는 다섯 계층을 측정하고, 예산을 책정하고, 스택하는 방법을 배울 수 있습니다.

**유형:** Learn
**언어:** Python (stdlib, toy cold-start path simulator)
**선수 요건:** 17단계 · 02강 (추론 플랫폼 경제학), 17단계 · 03강 (GPU 자동 확장)
**시간:** 약 60분

## 학습 목표

- 콜드 스타트 완화의 다섯 계층을 나열하고 각 계층에서 하나의 도구 또는 패턴을 지정해 보세요.
- 70B 모델의 총 콜드 스타트 시간을 (노드 프로비저닝) + (가중치 다운로드) + (가중치를 HBM에 로드) + (엔진 초기화)의 합으로 계산해 보세요.
- 라이브 마이그레이션이 KV 캐시 (GB)가 아닌 입력 토큰 (KB)을 전송하는 이유와 그 페널티 (재계산)를 설명해 보세요.
- 웜 풀의 트레이드오프 (유휴 GPU 비용을 지불하거나 콜드 스타트 꼬리를 수용)와 `min_workers > 0`이 필수적이 되는 SLA 임계값을 지정해 보세요.

## 문제점

서버리스 LLM 엔드포인트가 밤새 제로로 축소됩니다. 오전 8시에 트래픽이 급증합니다. 첫 요청은 다음이 완료될 때까지 대기합니다:

1. Karpenter가 GPU 노드를 프로비저닝합니다: 45-60초.
2. 컨테이너가 가중치를 포함한 30 GB 이미지를 가져옵니다: 120-300초.
3. 엔진이 가중치를 HBM에 로드합니다: 모델 크기와 저장 속도에 따라 45-120초.
4. vLLM 또는 TRT-LLM이 CUDA 그래프, KV 캐시 풀, 토크나이저를 초기화합니다: 10-30초.

총 소요 시간: 토큰이 하나 돌아오기까지 약 220-510초 (대략 3-8분)입니다. SLA는 2초입니다. 워름 풀(warm-pool)(`min_workers=1`)을 출시하면 문제가 사라진 것처럼 보이지만, 이제 24x7로 유휴 GPU 하나에 비용을 지불해야 합니다. 서비스가 5개의 제품 각각에 워름 복제본(replica) 하나를 가지고 있다면, 사용자가 단 한 번도 호출하지 않았더라도 5 × 24 × 30 = 월 3,600 GPU-hours가 됩니다.

콜드 스타트(cold-start) 완화는 서버리스(serverless) 경제성을 유지하면서 상시(always-on) 실행의 지연 시간을 근사하는 방법입니다.

## 개념

### 레이어 1 — 사전 시드(seed)된 노드 이미지 (Bottlerocket)

AWS에서는 Bottlerocket의 이중 볼륨(dual-volume) 아키텍처가 OS와 데이터를 분리합니다. 컨테이너 이미지를 미리 당겨(pull) 데이터 볼륨을 스냅샷하고, `EC2NodeClass`에서 스냅샷 ID를 참조하세요. 새 노드는 가중치가 이미 로컬 NVMe에 있는 상태로 부팅됩니다 — 단계 2와 3의 일부가 사라집니다. Karpenter와 네이티브로 작동합니다. 일반적인 절감 효과: 대형 모델의 경우 콜드 스타트당 2-4분입니다.

GCP에서의 동등한 방법: 미리 구워(baked) 넣은 컨테이너 레이어가 포함된 커스텀 VM 이미지. Azure에서의 동등한 방법: 동일한 패턴의 관리형 디스크 스냅샷.

### 레이어 2 — 모델 스트리밍 (Run:ai Model Streamer)

첫 요청에 응답하기 전에 전체 파일을 로드하는 대신, GPU 메모리로 가중치를 레이어별로 스트리밍하고 첫 번째 트랜스포머 블록이 상주(resident)하는 즉시 처리를 시작하세요. NVIDIA Run:ai Model Streamer는 vLLM 2026에 네이티브로 탑재되어 출시됩니다. S3, GCS 및 로컬 NVMe와 작동합니다. I/O와 컴퓨팅 설정을 겹쳐(lap) 대형 모델의 가중치 로드 시간을 대략 절반으로 줄입니다.

### 레이어 3 — GPU 메모리 스냅샷 (Modal)

Modal은 첫 로드 후 GPU 상태(가중치, CUDA 그래프, KV 캐시 영역)의 체크포인트를 찍습니다. 이후 재시작은 HBM으로 직접 역직렬화(deserialize)합니다 — 재초기화보다 10배 빠릅니다. 이는 "2초 만에 워름 GPU를 부팅하는" 것에 가장 가까운 방법입니다. 트레이드오프(trade-off): 스냅샷은 GPU 토폴로지별이므로, Karpenter가 다른 SKU로 마이그레이션하면 체크포인트를 다시 찍어야 합니다.

### 레이어 4 — 워름 풀 (min_workers=1)

가장 단순한 완화 방법: 복제본(replica) 하나를 항상 준비 상태로 유지하세요. 비용은 24x7로 GPU 시간당 요금입니다. 소형 모델에서는 산술이 가혹합니다(30초 콜드 스타트를 피하기 위해 $0.85-$1.50/hr를 지불)하고, 대형 모델에서는 관대합니다(5분 콜드 스타트를 피하기 위해 $4/hr를 지불). 워름 풀이 필수적이게 되는 SLA 임계값: 일반적으로 70B+ 모델에서 TTFT P99 < 60s입니다.

### 5계층 — 계층적 로딩 (ServerlessLLM)

ServerlessLLM은 스토리지를 계층 구조로 취급합니다: NVMe (빠르지만 용량이 큼), DRAM (중간 용량, 계층화됨), HBM (용량은 작지만 즉각적임). 가중치는 DRAM에 사전 로드되며, HBM에는 필요 시 로드합니다. 논문에서는 단순한 디스크-투-HBM 방식 대비 콜드 로드 시 10-200배의 지연 시간 감소가 보고되었습니다. 프로덕션 도입은 초기 단계이지만 vLLM과의 통합이 존재합니다.

### 6계층 — 라이브 마이그레이션 (보너스 패턴)

노드가 사용 불가능해지면 (스팟 인스턴스 강제 종료, 노드 드레인), 전통적인 패턴은 다른 복제본을 콜드 스타트하고 요청 큐를 드레인하는 것입니다. 라이브 마이그레이션은 입력 토큰 (킬로바이트 단위)을 모델이 로드된 대상 노드로 이동하고, 대상 노드에서 KV 캐시를 재계산합니다. 네트워크를 통해 GB 단위의 KV 캐시를 전송하는 것보다 재계산이 더 저렴합니다. 분산 서빙 배포에 적용 가능합니다.

### 웜 풀 계산

P99 TTFT SLA가 2초인 서비스의 경우, "웜 풀 사용 여부"가 문제가 아니라 "웜 복제본의 개수와, 어떤 경로가 이를 사용하는지"가 문제입니다.

- 고가치 인터랙티브 경로 (라이브 채팅, 음성 에이전트): `min_workers=1-2`.
- 백그라운드 배치 경로 (야간 분류): 스케일 투 제로 허용, 5-10분 콜드 스타트 허용.
- 프리미엄 티어: 전용 용량으로 테넌트당 `min_workers`.

### 최적화 전에 측정하기

신규 노드에서 70B 모델의 콜드 스타트 구조 (예시):

| 단계 | 시간 | 완화 전략 |
|-------|------|-----------|
| 노드 프로비저닝 | 50초 | Bottlerocket + 사전 시드 이미지, 웜 풀 |
| 이미지 풀 | 180초 | 사전 시드 데이터 볼륨 (제거) |
| 가중치를 HBM으로 | 75초 | 모델 스트리머 (절감); GPU 스냅샷 (제거) |
| 엔진 초기화 | 20초 | 지속성 CUDA 그래프 캐시 |
| 첫 번째 순방향 | 3초 | 최소 고유 지연 |
| **총 콜드** | **328초** | |
| **완화 전략 적용 총 시간** | **~15초** | 22배 감소 |

### 기억해야 할 수치

- Modal 콜드 스타트: 2-4초 (GPU 스냅샷 사용 시).
- Baseten 기본 콜드 스타트: 5-10초; 사전 웜업 시 1초 미만.
- Raw 70B 콜드 스타트: 3-8분.
- Run:ai Model Streamer: 가중치 로드 속도 약 2배 향상.
- ServerlessLLM의 계층적 로딩: 지연 시간 10-200배 감소 (논문 수치).

## 연습 문제

1. `code/main.py`를 실행하세요. SLO 위반으로 인한 추가 요청 드롭 비용보다 웜 레플리카가 더 저렴한 손익분기 요청률을 계산하세요.
2. P99 TTFT SLA가 3초인 13B 모델을 배포합니다. 이를 달성하는 최소 완화 전략 스택(가장 적은 계층 수)을 선택하세요.
3. Bottlerocket의 사전 시딩은 이미지 풀을 제거하지만, 가중치는 여전히 스냅샷에서 HBM으로 로드됩니다. 스냅샷 기반 NVMe가 7 GB/s로 읽을 때 70B 모델의 월클록 시간을 계산하세요.
4. 서버리스 제공자가 GPU 스냅샷(Modal)을 제공하지만 팀이 "스냅샷이 PII를 유출한다"며 거부합니다. 양쪽 입장을 논증하세요 — 현실적인 위험은 무엇이며, 완화 전략(임시 스냅샷, 암호화, 네임스페이스 격리)은 무엇인가요?
5. 계층적 웜 풀 정책을 설계하세요: 유료 사용자, 트라이얼 사용자, 배치 워크로드에 대해 각각 몇 개의 웜 레플리카를 유지해야 할까요? 수학적 근거를 보여주세요.

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|----------------|------------------------|
| 콜드 스타트 | "큰 지연" | 새 레플리카에서 요청부터 첫 토큰까지 걸리는 시간 |
| 웜 풀 | "항상 켜진 최소 상태" | `min_workers >= 1`가 적어도 하나의 레플리카를 준비 상태로 유지하는 것 |
| 사전 시딩 이미지 | "구워진 AMI" | 컨테이너 가중치가 사전에 상주하는 노드 이미지 |
| Bottlerocket | "AWS 노드 OS" | 이중 볼륨 스냅샷을 지원하는 AWS 컨테이너 최적화 OS |
| 모델 스트리머 | "스트리밍 로드" | 가중치 I/O와 컴퓨팅 설정을 겹치게 처리 |
| GPU 스냅샷 | "HBM 체크포인트" | 로드 후 GPU 상태를 직렬화하고 재시작 시 역직렬화 |
| 계층적 로딩 | "NVMe + DRAM + HBM" | 저장소 계층 구조; 필요에 따라 로드 |
| 라이브 마이그레이션 | "토큰 이동" | 입력(KB)을 전송하고 목적지에서 KV를 재계산 |
| `min_workers` | "warm replicas" | 서버리스 최소 유지 개수 |
| Scale-to-zero | "full serverless" | 유휴 상태일 때 비용 없음; 완전한 콜드 스타트 비용을 감수 |
