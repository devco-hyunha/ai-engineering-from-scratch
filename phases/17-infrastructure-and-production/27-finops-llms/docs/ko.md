# LLM을 위한 FinOps — 단위 경제학과 멀티 테넌트 귀속

> 전통적인 FinOps는 LLM 지출에 적용하면 한계가 있습니다. 비용은 리소스 가동 시간이 아닌 토큰 트랜잭션이며, 태그는 매핑되지 않습니다. API 호출은 자산이 아니라 트랜잭션이기 때문입니다. 엔지니어링 결정(프롬프트 설계, 컨텍스트 윈도우, 출력 길이)은 곧 재무적 결정입니다. 2026년 플레이북은 첫날부터 계측해야 할 세 가지 귀속 차원을 제시합니다. 좌석 가격 및 확장성을 위한 사용자별 귀속(`user_id`), 제품 표면 비용 및 우선순위 결정을 위한 작업별 귀속(`task_id` + `route`), 단위 경제학 및 갱신 결정을 위한 테넌트별 귀속(`tenant_id`)입니다. 프롬프트, 도구, 메모리, 응답의 네 가지 토큰 계층이 있으며, 단일 버킷으로 관리하면 지출이 숨겨집니다. 멀티 테넌트 제품을 위한 강제 실행 사다리: 테넌트별 속도 제한(예상 피크의 2-3배, 명확한 429 + retry-after 헤더); 일일 지출 상한(계약 상한의 1.5-3배; 속도 제한 강화 및 알림 트리거); 지출 z-점수가 4를 초과할 때의 킬 스위치(자동 일시 중지 + 온콜 페이지). 귀속 패턴: 태그 및 집계, 텔레메트리 조인(trace-ID → 청구; 가장 높은 정확도), 샘플링 및 외삽, 모델 기반 할당, 이벤트 소싱, 실시간 스트리밍. 단위 지표: 해결된 쿼리당 비용, 생성된 아티팩트당 비용 — $/M 토큰이 아닙니다. 소급 태그는 항상 놓치므로, 요청 생성 시점에 계측해야 합니다.

**유형:** Learn
**언어:** Python (표준 라이브러리, 킬 스위치가 포함된 장난감 비용 귀속 시뮬레이터)
**선수 요건:** 17단계 · 13강 (관측 가능성), 17단계 · 14강 (캐싱)
**시간:** 약 60분

## 학습 목표

- 전통적인 FinOps(태그 + 계층)가 LLM 지출에 적용하면 왜 한계가 있는지 설명하고, 세 가지 새로운 귀속 차원을 나열해 보세요.
- 네 가지 토큰 계층(프롬프트, 도구, 메모리, 응답)을 나열하고, 단일 버킷 청구가 왜 비용을 숨기는지 설명해 보세요.
- 멀티 테넌트 제품을 위한 강제 실행 사다리(속도 제한 → 지출 상한 → 킬 스위치)를 설계해 보세요.
- $/M 토큰 대신 단위 지표(해결된 쿼리당 비용 / 아티팩트당 비용)를 선택해 보세요.

## 문제점

청구서는 $40,000라고 표시합니다. 다음을 알 수 없습니다:
- 어떤 테넌트가 그 비용을 사용했는지.
- 어떤 제품 기능이 그 비용을 유발했는지.
- 개별 사용자가 남용했는지 여부.
- 프롬프트 팽창, 도구 호출, 또는 메모리 증폭이 원인인지 여부.

제공자 측의 태깅 및 집계는 태그가 명세 항목에 전파되는 클라우드 리소스(EC2, S3)에 효과적입니다. LLM API 호출은 자동으로 태깅되지 않으므로, 호출 지점에서 사용자/작업/테넌트를 명시하고 이를 전달해야 합니다. 소급 귀속은 항상 예외 상황을 놓칩니다.

## 개념

### 세 가지 귀속 차원

**사용자별** (`user_id`): 누가 무엇을 비용화하는지. 좌석 가격 책정, 확장 논의, 파워 유저 식별에 활용됩니다.

**작업별** (`task_id` + `route`): 어떤 제품 표면이 무엇을 비용화하는지. 기능 우선순위 결정, 고비용 기능 제거 결정에 활용됩니다.

**테넌트별** (`tenant_id`): 어떤 고객이 수익적인지. 단위 경제학, 갱신 가격, 티어 임계값에 활용됩니다.

첫날부터 호출 지점에서 세 가지를 모두 계측하세요. 소급 적용은 항상 더 나쁜 결과를 낳습니다.

### 네 가지 토큰 계층

| 계층 | 예시 | 총합의 전형적인 비율 |
|-------|---------|---------------------|
| 프롬프트 | 시스템 + 사용자 입력 | 40-60% |
| 도구 | 도구 호출 결과가 피드백됨 | 20-40% (에이전트 워크로드) |
| 메모리 | 이전 대화 / 검색된 문서 | 10-30% |
| 응답 | 모델 출력 | 10-30% |

네 가지를 모두 한 버킷에 합치면 최적화가 불가능해집니다. 귀속 스키마에서 이들을 분리하세요.

### 강제 적용 사다리

1. **속도 제한**을 테넌트별로 설정하세요. 예상 피크의 2-3배로 설정합니다. `Retry-After`와 함께 429를 반환하세요. 테넌트는 마찰을 느끼게 되며, 예상치 못한 청구서가 발생하지 않습니다.

2. **일일 지출 상한**을 테넌트별로 설정하세요. 계약된 상한의 1.5-3배로 설정합니다. 트리거: 속도 제한 강화 + 고객 성공 팀에 알림.

3. 테넌트 기준 대비 지출 z-점수가 4를 초과하면 **킬 스위치**를 발동하세요. 테넌트를 자동 일시 중지하고, 온콜(on-call)을 호출하며, 운영 및 고객 성공 팀으로 에스컬레이션하세요.

### 귀속 패턴

- **태깅 및 집계**: 메타데이터 헤더를 태깅하고 나중에 집계합니다. 단순하지만 대략적입니다.
- **텔레메트리 조인**: 추적(traces)을 추적 ID를 통해 청구와 조인합니다. 가장 높은 정확도를 가집니다. 성숙한 팀들이 사용하는 방식입니다.
- **샘플링 및 외삽**: 5-10%를 샘플링하고 곱합니다. 대략적인 지출에는 비용 효율적이지만, 꼬리(tails)를 놓칩니다.
- **모델 기반 할당**: 비용 동인을 추론하기 위해 회귀 분석을 사용합니다. 태그가 없는 레거시 데이터에 적합합니다.
- **이벤트 소싱**: 스트림(Kafka / Kinesis)에서 이벤트로 비용을 처리합니다. 실시간입니다.
- **실시간 스트리밍**: 대시보드가 초당 단위(sub-second)로 업데이트됩니다.

### X당 비용은 단위 지표입니다

$/M 토큰은 벤더 용어입니다. 제품 지표는 다음과 같습니다:

- 해결된 지원 티켓당 비용.
- 생성된 기사당 비용.
- 성공한 에이전트 작업당 비용.
- 사용자 세션 분당 비용.

비용을 제품 결과와 연결하세요. 그렇지 않으면 최적화가 기준점을 잃습니다.

### 비용 귀속 추적 형태

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

모든 호출 시 내보내세요. 데이터 레이크에 저장하세요. 차원별로 집계하세요. 17단계 · 13관측성 스택이 이 부분이 위치합니다.

### 복합 절감 스택

스택: 캐시 + 배치 + 라우팅 + 게이트웨이. 네 가지를 모두 적용하면:
- L2 캐시 (17단계 · 14): 입력 비용이 약 10배 저렴합니다.
- 배치 (17단계 · 15): 50% 절감.
- 저비용 모델로 라우팅 (17단계 · 16): 비용 60% 감소.
- 게이트웨이 효율성 (17단계 · 19): 중복 제거 + 재시도.

최적의 스택 구성: 단순한 기준선의 약 5-10%. 대부분의 팀은 2-3가지 레버를 활용하며, 네 가지를 모두 스택하는 팀은 드뭅니다.

### 기억해야 할 수치

- 귀속 차원: 사용자별, 작업별, 테넌트별.
- 네 가지 토큰 레이어: 프롬프트, 도구, 메모리, 응답.
- 킬 스위치: 지출 z-점수 > 4.
- 단위 지표: 해결된 쿼리당 비용, $/M 토큰이 아닙니다.
- 스택 최적화: 기준선의 약 5-10%까지 절감 가능합니다.

## 사용하기

`code/main.py`는 3단계 강제 실행 사다리(ladder)를 가진 다중 테넌트 LLM 서비스를 시뮬레이션합니다. 악성 테넌트를 주입하고 킬 스위치가 작동하는 것을 보여줍니다.

## 출시하기

이 강의는 `outputs/skill-finops-plan.md`를 생성합니다. 제품과 규모를 고려하여 귀속 스키마와 강제 실행 사다리를 설계합니다.

## 연습 문제

1. `code/main.py`를 실행하세요. 킬 스위치는 어떤 z-점수에서 작동합니까? 임계값은 어떻게 선택하나요?
2. 테넌트별, 작업별 비용 대시보드를 설계하세요. 가장 먼저 구축해야 할 5가지 뷰는 무엇인가요?
3. 가장 큰 테넌트가 단위 경제적으로 마이너스입니다. 고객 영향 순으로 세 가지 개입 방안을 제안해 보세요.
4. 지원 제품의 해결된 티켓당 비용을 계산해 보세요: 티켓당 3M 토큰, 하루 약 800 티켓, GPT-5 캐시된 요금.
5. 소급 태깅이 성공할 수 있는지 논증해 보세요. 언제 허용되는가요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| 사용자별 귀속 | "사용자 수준 비용" | 모든 호출에 `user_id`이 스탬프됨 |
