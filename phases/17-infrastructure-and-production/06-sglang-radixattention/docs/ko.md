# 접두어 캐시 서빙 — RadixAttention과 KV 재사용

> KV 캐시를 라디시 트리에 저장된 일급(first-class) 재사용 가능한 리소스로 취급하고, 이를 기반으로 스케줄링을 변경합니다. vLLM이 FCFS(선입선출) 방식으로 스케줄링하는 것과 달리, 캐시 인식(caches-aware) 스케줄러는 더 긴 공유 접두어를 가진 요청을 우선 처리합니다. 이는 사실상 깊이 우선(depth-first) 라디시 순회로, 핫(hot) 브랜치가 HBM에 상주하도록 유지합니다. SGLang는 이 아이디어를 중심으로 서빙을 구축한 엔진입니다. Llama 3.1 8B 모델에서 ShareGPT 유사 1K 프롬프트를 사용할 때, SGLang는 vLLM의 약 12,500 tok/s 대비 약 16,200 tok/s를 달성하며 약 29%의 우위를 보입니다. 접두어가 많은 RAG 워크로드에서는 이 이점이 6.4배까지 확대됩니다. 음성 클로닝 형태의 워크로드에서는 캐시 적중률이 86%를 넘었습니다. 2026년 xAI, LinkedIn, Cursor, Oracle, GCP, Azure, AWS 등 400,000개 이상의 GPU에 배포되었습니다. 주의할 점은 접두어 순서가 일관되지 않으면 6.4배라는 수치가 사라진다는 것입니다. 순서 조절은 엔지니어가 활용할 수 있는 레버입니다.

**유형:** Learn
**언어:** Python (표준 라이브러리, 장난감 라디시 트리 캐시 + 캐시 인식 스케줄러)
**선수 요건:** 17단계 · 04강 (서빙 엔진 내부 구조), 14단계 (에이전트형 RAG)
**시간:** 약 75분

## 학습 목표

- RadixAttention 다이어그램: 접두어가 라디시 트리에 저장되는 방식과, 같은 브랜치에 뿌리를 둔 시퀀스 간에 KV 블록이 공유되는 방식을 설명합니다.
- 캐시 인식(caches-aware) 스케줄링을 설명하고, 접두어가 많은 트래픽에 FCFS가 부적합한 이유를 설명합니다.
- 접두어 캐시 적중률과 프롬프트 길이 분포를 고려하여 워크로드의 예상 속도 향상(speedup)을 계산합니다.
- 6.4배라는 수치를 실제로 만들거나 잠재적 이득을 잃게 만드는 프롬프트 순서 규율을 명시합니다.

## 문제점

전통적인 서빙은 각 요청의 프롬프트를 불투명한(opaque) 것으로 취급합니다. 5,000개의 RAG 요청이 모두 동일한 2,000토큰 시스템 프롬프트와 동일한 검색(retrieval) 전처리 문구로 시작하더라도, vLLM은 그 2,000토큰 접두어를 5,000번 프리필(prefill)합니다. GPU는 동일한 작업을 반복 수행합니다.

관찰: 에이전트형 및 RAG 워크로드의 프롬프트는 거의 항상 긴 접두어를 공유합니다. 시스템 프롬프트, 도구 스키마, 소수 예시(few-shot examples), 검색 헤더, 대화 기록 — 이 모든 요소는 요청 간에 반복됩니다. 해당 접두어의 KV 캐시를 한 번만 저장하고 재사용한다면, 다시 프리필할 필요가 없습니다.

RadixAttention은 정확히 이 방식을 따릅니다. 토큰은 라디크스 트리(radix tree)에 인덱싱되며, 각 노드는 루트에서 해당 노드까지의 경로에 있는 토큰 시퀀스에 대한 KV 블록을 소유합니다. 새로운 요청이 트리를 순회할 때, 토큰이 일치하는 노드가 있으면 해당 노드의 KV 블록을 재사용합니다. 프리필(prefill) 비용은 전체 프롬프트가 아닌 '새로운' 접미사에 비례하게 됩니다.

과제는 스케줄링입니다. 두 요청이 2,000토큰 접두어를 공유하고 세 번째 요청이 같은 접두어의 200토큰만 공유한다면, 긴 접두어가 HBM에 유지되도록 두 개의 긴 공유 요청을 함께 처리하는 것이 좋습니다. FCFS는 그 반대입니다. FCFS는 먼저 도착한 요청을 처리하므로, 다음 긴 접두어 요청이 들어오기 전에 핫(hot) 브랜치를 제거(evict)할 수 있습니다.

## 개념

### KV 인덱스로서의 라디크스 트리

라디크스 트리(compact trie)는 토큰 시퀀스를 저장합니다. 각 노드는 토큰 범위와 해당 범위에 대해 계산된 KV 블록을 소유합니다. 자식 노드는 시퀀스를 하나 이상의 토큰만큼 확장합니다.

```
root
 |- "You are a helpful assistant..."  (2,000 tokens, 124 KV blocks)
      |- "Context: <doc A>..."        (500 tokens, 31 blocks)
           |- "Question: Alice..."    (80 tokens, 5 blocks)
           |- "Question: Bob..."      (95 tokens, 6 blocks)
      |- "Context: <doc B>..."        (520 tokens, 33 blocks)
```

새로운 요청이 `system prompt + "Context: <doc A>" + "Question: Carol"` 형태로 들어옵니다. 스케줄러는 다음과 같이 순회합니다: 시스템 접두어가 일치하면 (124개 블록 재사용), doc-A 브랜치가 일치하면 (31개 블록 재사용), 그 후 `Question: Carol`에 대해서만 새로운 블록을 할당합니다 (4개 블록). 프리필 비용: 새로운 토큰에 대한 4개 블록. 트리가 없다면: 160개 블록. 프리필 시 약 40배의 절감 효과가 있습니다.

### 캐시 인식 스케줄링

캐시가 계속 변한다면 라디크스 트리 기반 재사용은 무의미합니다. 두 가지 핵심 정책이 있습니다:

1. **깊이 우선(depth-first) 디스패치**. 큐에서 다음 요청을 선택할 때, 현재 실행 중인 세트와 같은 브랜치에 뿌리를 둔 요청을 우선시합니다. 이렇게 하면 핫 브랜치가 고정(pinned)됩니다.
2. **블록 수준이 아닌 브랜치 수준의 LRU**. 캐시 형태가 라디크스 트리의 형태와 일치하도록, 개별 블록이 아닌 전체 브랜치(가장 짧게 사용된 리프부터 시작)를 제거(evict)합니다.

FCFS는 이 두 정책을 모두 위반합니다. 2,000토큰을 공유하는 요청이 50토큰을 공유하는 요청 뒤에 놓이면, 50토큰 요청을 수용하기 위해 2,000토큰 브랜치가 제거(evict)됩니다.

### 암기해야 할 벤치마크 수치

- Llama 3.1 8B, H100, ShareGPT 1K 프롬프트: SGLang 약 16,200 tok/s vs vLLM 약 12,500 (약 29% 우위).
- 접두어 중심 RAG (동일한 시스템 + 동일한 문서, 질문만 변경): SGLang에서 최대 6.4배 향상.
- 음성 클로닝 작업 부하: 접두어 캐시 적중률 86.4%.
- SGLang 고객의 프로덕션 히트율은 프롬프트 규율에 따라 50-99%입니다.
- 2026년에 400,000개 이상의 GPU에 배포되었습니다.

### 순서 관련 함정

6.4배 수치는 일관된 프롬프트 템플릿 순서에 의존합니다. 클라이언트가 일부 요청에서는 `[system, tools, context, history, question]`로, 다른 요청에서는 `[system, context, tools, history, question]`로 프롬프트를 구성한다면, 트리는 공유 접두어를 찾을 수 없습니다. 사람이 보기에는 공유 접두어처럼 보이지만, 라디크스 트리(radix tree)에는 두 개의 서로 다른 시퀀스로 인식됩니다.

엔지니어의 레버: 프롬프트 템플릿은 캐시 키입니다. 순서를 고정하세요. 변경 불가능한 요소(시스템, 도구, 스키마)를 먼저 배치하세요. 검색 컨텍스트를 그 다음에 배치하세요. 사용자 질문을 마지막에 배치하세요. 동적 콘텐츠를 접두어에 섞지 마세요.

연구 사례: 캐시 가능한 접두어에서 동적 콘텐츠를 제거하는 한 가지 변경만으로 한 배포의 캐시 히트율이 7%에서 74%로 상승했습니다.

### RadixAttention이 이기는 곳과 지는 곳

이기는 경우:
- RAG (동일한 검색 접두어, 다양한 질문).
- 에이전트 (동일한 도구 스키마, 다양한 쿼리).
- 긴 시스템 프롬프트가 있는 채팅.
- 반복되는 접두어가 있는 음성 / 비전 워크로드.

지는 경우 (vLLM 수준의 처리량으로 돌아감):
- 고유한 프롬프트를 사용하는 단일 샷 생성 (코드 완성, 시스템 프롬프트가 없는 개방형 채팅).
- 모든 요청이 고유한 콘텐츠를 접두어에 섞어 넣는 동적 프롬프트.

### 왜 이것이 커널 문제가 아니라 스케줄러 문제인가

KV 재사용은 커널 트릭으로 구현할 수 있습니다. SGLang의 통찰은, 재사용이 효과를 거두려면 스케줄러가 핫 브랜치(hot branch)를 상주 상태로 유지해야 한다는 것입니다. 단순한 "사용 가능하면 재사용" 정책은 혼합 부하에서 캐시를 소진(churn)시킵니다. 라디크스 트리 인덱스 기반 스케줄러가 커널 트릭을 29%의 프로덕션 우위로 전환합니다.

### vLLM과의 상호작용

두 시스템은 엄격한 경쟁 관계가 아닙니다. 2026년 vLLM은 접두어 캐싱(`--enable-prefix-caching`)과 캐시 인식 라우터(Rust 기반 vLLM Router)를 추가했습니다. 격차는 좁혀졌지만 완전히 사라지지 않았습니다. SGLang의 전체 스택은 라디크스 우선(radix-first) 설계인 반면, vLLM은 이를 접목(grafted)했습니다. 접두어 재사용이 지배적인 워크로드에서는 SGLang이 여전히 기본 선택입니다. 강한 접두어 패턴이 없는 범용 서빙에서는 vLLM이 동등하거나 더 좋습니다.

## 사용하기

`code/main.py`은 장난감 radix-tree KV 캐시와 FCFS 및 캐시 인식(cache-aware) 두 가지 정책을 가진 스케줄러를 구현합니다. 동일한 워크로드를 두 정책 모두로 실행하고, 접두어 캐시 적중률과 처리량 차이를 보고합니다. 이후 "순서 뒤섞기(scrambled ordering)" 워크로드를 실행하여 6.4배의 성능 붕괴를 보여줍니다.

## 연습 문제

1. `code/main.py`을 실행하세요. 동일한 워크로드에서 FCFS와 캐시 인식 정책을 비교하세요. 차이는 어디에서 발생합니까? 프리필 절감, 디코딩 절감, 아니면 큐 지연입니까?
2. 프롬프트가 `[system, tools, context]`을 무작위로 순열하도록 워크로드를 수정하세요. 다시 실행하세요. 적중률에는 어떤 변화가 생깁니까? 왜 그런가요?
3. Llama 3.1 8B에서 2,000개 토큰의 시스템 프롬프트를 하나의 radix branch로 상주(resident)시키는 HBM 비용을 계산하세요. 접두어 재사용이 없는 16개 시퀀스 배치의 비용과 비교하세요.
4. SGLang RadixAttention 논문을 읽어보세요. 접두어 중심(prefix-heavy) 부하에서 트리 형태의 LRU 퇴거(eviction)가 블록 형태의 LRU 퇴거보다 더 나은 이유를 세 문장으로 설명하세요.
5. 고객이 캐시 적중률이 8%에 불과하다고 보고합니다. 세 가지 가능한 원인을 나열하고, 각각에 대해 실행할 진단을 제시하세요.

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|----------------|------------------------|
| RadixAttention | "the SGLang thing" | KV 캐시를 radix tree로 인덱싱하여 공유 접두어가 블록을 재사용하도록 함 |
| Radix tree | "compact trie" | 각 노드가 토큰 범위와 해당 KV 블록을 소유하는 트리 |
| 캐시 인식 스케줄러 | "hot-branch-first" | 상주하는 branch를 공유하는 요청을 선호하는 스케줄러 |
| 접두어 캐시 적중률 | "how much of your prompt was free" | 재사용된 KV 블록에서 제공된 프롬프트 토큰의 비율 |
| FCFS | "first-come first-served" | 접두어 지역성(locality)을 깨뜨리는 기본 스케줄링 |
| Branch-level LRU | "evict the leaf" | radix 형태에 맞춘 퇴거(eviction) 정책 |
| 프롬프트 템플릿 순서 | "the cache key" | 프롬프트의 구성 요소 순서가 트리가 공유할 수 있는 대상을 결정함 |
| 시스템 프롬프트 고정 | "상주 접두어" | 변경 불가능한 시스템 부분을 고정하여 퇴거 스래시를 방지 |
