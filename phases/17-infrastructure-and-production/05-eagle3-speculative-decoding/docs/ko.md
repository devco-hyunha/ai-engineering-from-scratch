# 프로덕션 환경에서의 EAGLE-3 추론적 디코딩(Speculative Decoding)

> 추론적 디코딩(Speculative Decoding)은 빠른 초안 모델과 대상 모델을 짝을 이룹니다. 초안 모델이 K개의 토큰을 제안하면, 대상 모델이 단일 순전파로 이를 검증하며, 승인된 토큰은 사실상 무료입니다. 2026년 현재, EAGLE-3는 프로덕션급 변형입니다. 이는 원시 토큰이 아닌 대상 모델의 은닉 상태(hidden states)에 초안 헤드를 학습시켜, 일반 채팅 트래픽에서 승인율 alpha를 0.6~0.8 범위로 끌어올립니다. 올바른 질문은 "초안 모델이 얼마나 빠른가"가 아니라 "내 트래픽에서의 alpha는 얼마인가"입니다. alpha가 약 0.55 미만으로 떨어지면, 높은 동시성 환경에서는 모든 거부된 초안이 대상 모델의 두 번째 순전파를 유발하므로 추론적 디코딩은 순적으로 부정적인 효과가 됩니다. 이 강의에서는 먼저 alpha를 측정하고, 그 다음에 플래그를 켜는 방법을 가르쳐 드립니다.

**유형:** Learn
**언어:** Python (표준 라이브러리, toy acceptance-rate simulator)
**선수 요건:** 17단계 · 04강 (서빙 엔진 내부 구조), 10단계 · 18강 (다중 토큰 예측)

## 학습 목표

- 추론적 디코딩(Speculative Decoding)의 세 가지 세대를 나열하고, EAGLE-3가 EAGLE-2 및 전통적인 초안 모델과 비교하여 무엇을 변경하는지 설명해 보세요.
- 승인율 alpha를 정의하고, alpha와 K (초안 길이)로부터 예상 속도 향상을 계산하며, 대상 동시성에 대한 손익분기 alpha를 식별해 보세요.
- vLLM 2026에서 추론적 디코딩(Speculative Decoding)이 왜 opt-in (기본값이 아님)인지, 그리고 alpha를 측정하지 않고 이를 켜는 것이 왜 프로덕션 안티 패턴인지 설명해 보세요.
- 측정 계획을 작성해 보세요: 어떤 벤치마크, 어떤 프롬프트 분포, 어떤 동시성 지점, 어떤 지표로 게이트를 설정할지 결정합니다.

## 문제점

디코딩은 메모리 바운드(memory-bound)입니다. H100에서 Llama 3.3 70B FP8을 실행할 때, 디코딩된 각 토큰은 약 140 GB/s의 가중치를 읽고 토큰 하나를 방출합니다. 디코딩 중에는 GPU 연산이 거의 유휴 상태이며, 병목은 HBM 대역폭이지 matmul 처리량이 아닙니다.

추론적 디코딩(Speculative Decoding)은 이 간극을 활용합니다. 값싼 초안 모델로 K개의 후보 토큰을 생성한 후, 대상 모델이 단일 순전파로 K개 전체를 검증하도록 요청합니다. 검증된 각 토큰은 사실상 무료입니다 (대상 모델이 어차피 수행해야 했던 K개 배치 순전파에 상각(amortized)됩니다).

클래식 드래프트 모델 방식은 동일한 계열의 더 작은 모델을 사용합니다 (Llama 3.3 70B에 대해 Llama 3.2 1B가 드래프트를 수행). 이 방식은 작동하지만 수용률(acceptance rate)이 중간 수준입니다. 작은 모델의 분포가 타깃 모델의 분포와 갈라지기 때문입니다. EAGLE, 이후 EAGLE-2, 그리고 EAGLE-3는 타깃 모델의 내부 상태에 직접 가벼운 드래프트 헤드를 학습하므로, 드래프트의 분포가 타깃을 훨씬 더 밀접하게 추적합니다. 그래서 alpha가 드래프트 모델 방식에서는 0.4인 반면, EAGLE-3에서는 0.6~0.8로 상승하는 것입니다.

주의할 점: vLLM 2026에서 EAGLE-3는 opt-in 방식입니다. `speculative_config`를 명시적으로 설정해야 합니다. 플래그가 없으면 가속이 없습니다. 실제 트래픽에서 alpha를 측정하지 않고 이 기능을 켜는 팀은 꼬리 지연(tail latency)이 개선되지 않고 오히려 악화되는 것을 자주 경험합니다.

## 개념

### 추론적 디코딩(Speculative Decoding)이 실제로 얻는 이점

추론적 디코딩이 없으면 토큰당 비용은 타깃 모델의 한 번의 순전파(forward)입니다. 드래프트 길이 K와 수용률 alpha로 추론적 디코딩을 적용하면, 타깃 순전파당 예상 토큰 수는 `1 + K * alpha`입니다. 가속 비율은 `(1 + K * alpha) / (1 + epsilon)`이며, 여기서 epsilon은 드래프트 및 검증 오버헤드입니다. K=5, alpha=0.7인 경우: `(1 + 5*0.7) / (1 + 0.1) = 4.5 / 1.1 = 4.1x`. 실제 트래픽에서는 alpha가 그 정도로 높지 않고, 높은 배치 크기에서 epsilon이 증가하기 때문에 실제 수치들은 2~3배 주변에 집중됩니다.

### alpha가 유일한 중요 지표인 이유

거절된 토큰은 사라지지 않습니다. 거절된 첫 번째 토큰에 대해 두 번째 타깃 순전파를 강제합니다. alpha가 0.4로 떨어지는 워크로드에서는 드래프트 오버헤드, 검증, 그리고 재롤(re-roll) 비용을 지불해야 합니다. 높은 동시성(예: 256 동시 요청)에서는 디코딩 배치가 이미 충분히 크기 때문에, '타깃 단독'과 '타깃 + 검증' 사이의 메모리 대역폭 격차가 줄어듭니다. 대부분의 2026년 하드웨어에서 alpha가 0.55 미만이면 추론적 디코딩은 순적으로 부정적입니다.

alpha는 워크로드에 따라 달라집니다. ShareGPT 스타일의 일반 채팅에서는 ShareGPT로 학습된 EAGLE-3가 0.6~0.8을 달성합니다. 도메인 특화 트래픽(코드, 의료, 법률)에서는 일반 데이터로 학습된 드래프트 헤드가 0.4~0.6으로 떨어집니다. 도메인 특화 드래프트 헤드를 학습하면 alpha를 회복할 수 있습니다. 이는 타깃 미세 조정(fine-tuning)에 비해 가볍고 빠른 학습 작업입니다.

### EAGLE 세대를 한눈에 보기

- **클래식 드래프트 모델**: 동일한 계열의 작은 모델. Alpha는 0.3~0.5. 인프라가 단순합니다. 두 모델을 로드하며, 드래프트는 타깃 순전파마다 K번의 순전파를 수행합니다.
- **EAGLE-1 (2024)**: 타겟 은닉 상태(마지막 레이어)에 대해 학습된 단일 드래프트 헤드. Alpha ~0.5-0.6. 타겟 위에 작은 파라미터 오버헤드.
- **EAGLE-2 (2025)**: 적응형 드래프트 길이 및 트리 기반 드래프트(타겟 패스 한 번으로 여러 브랜치 검증). Alpha ~0.6-0.7. 더 복잡한 드래프트 스케줄러.
- **EAGLE-3 (2025-2026)**: 여러 타겟 레이어(마지막 레이어뿐만 아니라)에 대해 학습된 드래프트 헤드, 더 나은 정렬. 일반 채팅에서 Alpha ~0.6-0.8.

### 2026년 프로덕션 레시피

1. 타겟 모델을 그대로 출시하세요. 타겟 동시성에서 기준 TTFT, ITL, 처리량을 측정하세요.
2. vLLM `speculative_config`을 통해 EAGLE-3 드래프트를 활성화하세요. 벤치마크를 다시 실행하세요.
3. 수락률 alpha를 기록하세요. vLLM V1은 이를 `spec_decode_metrics.accepted_tokens_per_request`로 보고합니다. 요청된 드래프트 길이로 나누어 alpha를 구하세요.
4. 프로덕션 트래픽 분포에서 alpha가 0.55 미만이면, 스펙 디코딩을 비활성화하거나 도메인 특화 EAGLE-3 드래프트를 학습하세요.
5. 프로덕션 동시성에서 다시 실행하세요. P99 ITL이 악화되지 않았는지 확인하세요.

### 프로덕션 함정: P99 꼬리

스펙 디코딩으로 평균 ITL은 감소합니다. 튜닝하지 않으면 P99가 악화될 수 있습니다. 거부된 드래프트는 2패스 시퀀스(드래프트 + 검증 실패 + 재롤)를 유발합니다. 전체 배치에서는 이 두 패스가 직렬화됩니다. P50이 아닌 P99 ITL을 모니터링하세요.

### EAGLE-3가 이미 배포된 곳

Google은 2025년 AI Overviews에 스펙ulative 디코딩을 배포했습니다(동일한 품질, 더 빠른 응답). vLLM V1은 `speculative_config`를 문서화된 인터페이스로 제공하며, 기능 매트릭스는 스펙ulative 디코딩이 청크 프리필과 호환됨을 표시합니다. SGLang는 접두어 중심 워크로드에 권장되는 드래프트 경로로 EAGLE-3를 지원합니다.

### 한 줄로 보는 손익분기점 계산

예상 속도 향상: `S(alpha, K) = (1 + K*alpha) / (1 + verify_overhead)`. `S = 1`을 설정하면 alpha를 구할 수 있습니다: `alpha_breakeven = verify_overhead / K`. 일반적인 verify_overhead ~0.15 및 K=5의 경우: `alpha_breakeven = 0.03`. 하지만 이는 순수 디코딩 계산입니다. 높은 동시성에서는 검증 오버헤드가 증가하고 디코딩 배치가 이미 시퀀스 간 메모리 읽기를 상각하므로, 실제 유효 alpha_breakeven은 ~0.45-0.55로 상승합니다.

### 스펙ulative 디코딩을 사용하지 말아야 할 때

- 레이턴시가 중요하지 않은 배치-1 오프라인 생성. 타겟을 그대로 사용하세요.
- 매우 짧은 출력(50 토큰 미만). 드래프트 오버헤드 및 검증 비용이 지배적입니다.
- 도메인 전용 학습된 초안 헤드가 없는 전문화된 도메인. 알파가 너무 낮습니다.
- 모든 기능 쌍이 조합된다고 가정하지 마세요. 사용 중인 버전의 vLLM 호환성 매트릭스를 확인해 보세요: v0.18.0은 추론적 디코딩(Speculative Decoding)이 청크 프리필(Chunked Prefill)과 호환됨을 표시합니다.

|------|----------------|------------------------|
| 추론적 디코딩(Speculative Decoding) | "초안 및 검증" | 저렴한 모델로 K개의 토큰을 제안하고, 하나의 타겟 순전파(forward)에서 모든 K를 검증 |

| 검증 오버헤드 epsilon | "추론 오버헤드" | 검증 및 재롤링이 단순 타겟 순전파(forward)보다 추가적으로 발생하는 비용; 배치가 커짐에 따라 증가 |
| EAGLE-3 | "최신 EAGLE" | 2025-2026 변형; 여러 타겟 레이어에서 초안 헤드(draft head)를 학습; 일반 채팅에서 알파(alpha) 0.6-0.8 |
| `speculative_config` | "vLLM spec config" | vLLM V1에서의 명시적 옵트인(opt-in); 기본값이 없으므로 가속이 없음 |
| N-gram spec decode | "N-gram draft" | 프롬프트에서 N-gram 조회를 사용하는 GPU 측 초안; 청크 프리필(chunked-prefill) 호환 |
| Break-even alpha | "no-op alpha" | 스펙 디코딩(spec decode)이 속도 향상을 제공하지 않는 알파(alpha); 프로덕션 동시성에서 이 값을 주의 깊게 살펴보세요 |
| Rejected-draft two-pass | "reroll cost" | 초안이 거부될 경우 두 번의 타겟 forward; P99 꼬리 지연(tail latency)을 유발 |
