팀 규모, 인시던트 볼륨, 관측 가능성 성숙도, 위험 허용도를 고려하여 AI SRE 계획을 작성해 보세요.

다음 내용을 작성합니다:

1. 아키텍처. 다중 에이전트: 감독자 + 로그 에이전트 + 메트릭 에이전트 + 런북 에이전트 + 인간 게이트. 전문화된 에이전트를 기존 데이터 소스(Datadog, Grafana, Loki, Confluence)에 매칭합니다.
2. 런북 변환. 비구조화된 Confluence에서 증상 / 가설 / 검증 / 조치 섹션이 포함된 구조화된 마크다운으로 이동합니다. git에서 버전을 관리합니다.
3. 제품 선택. Datadog Bits AI, Azure SRE Agent, NeuBird Hawkeye, Incident.io Autopilot, 또는 DIY.
4. 자동 복구 범위. 좁은 안전 세트(팟 재시작, 배포 롤백, 범위 내 스케일링). 명시적 거부 목록(토폴로지, 코드, IAM, 데이터베이스). 정책을 코드로 정의합니다.
5. 적대적 평가. 자동 복구를 위한 두 모델의 합의 게이트를 지정합니다. 불일치 시 에스컬레이션합니다.
6. 예측 감지 태세. 고려 중인 경우(MIT 89% 결과), 실행 정책 — 페이지, 사전 드레인, 자동 스케일링 — 을 명시합니다. 그렇지 않으면 단순 대시보드일 뿐입니다.

거부 항목:
- 광범위한 변경에 대해 인간 게이트 없이 자동 복구하는 경우. 거부합니다 — 안전 세트를 명시적으로 지정합니다.
- 비구조화된 런북을 지식 베이스로 사용하는 경우. 거부합니다 — 구조화되고 버전 관리되는 마크다운을 요구합니다.
- "설정하고 잊어버리는" 프레임. 거부합니다 — 자율적인 것과 자율적이지 않은 것을 명시적으로 범위를 지정합니다.

거부 규칙:
- 인시던트 볼륨이 월 10건 미만인 경우, 전체 AI SRE 롤아웃을 거부합니다 — 비용이 이익을 초과합니다. 구조화된 런북만 권장합니다.
- 팀의 관측 가능성이 미성숙한 경우(로그 검색 불가, 메트릭 희소), 거부합니다 — AI SRE는 나쁜 데이터를 증폭시킵니다.
- 팀이 "예측 감지 → 자동 복구"를 첫 번째 기능으로 제안하는 경우, 거부합니다 — 먼저 실행 정책 질문에 대해 검토합니다.

출력: 아키텍처, 런북 계획, 제품 선택, 자동 복구 범위, 적대적 게이트, 예측적 태세를 포함한 한 페이지 계획입니다. 12주 롤아웃 일정으로 마무리하세요: 1-4주는 구조화된 런북, 5-8주는 트리아지 에이전트, 9-12주는 좁은 범위의 자동 복구입니다.
