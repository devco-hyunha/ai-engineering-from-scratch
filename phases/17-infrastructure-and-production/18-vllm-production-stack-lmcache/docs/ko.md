# 프로덕션 서빙 스택 — KV 오프로딩 및 캐시 인식 라우팅

> 프로덕션 서빙 스택은 라우터, 엔진, 관측 가능성을 하나의 Kubernetes 배포로 연결하며, KV 캐시를 GPU 밖으로 이동할 수 있는 자원으로서 취급합니다. KV 오프로딩은 KV 캐시를 GPU 메모리에서 추출하여 쿼리 및 엔진 간에 재사용합니다(CPU DRAM, 그 다음 디스크/Ceph). vLLM의 production-stack은 참조 배포이며, LMCache는 오프로딩 계층입니다. vLLM 0.11.0의 KV 오프로딩 커넥터(2026년 1월)는 Connector API(v0.9.0+)를 통해 이를 비동기적이고 플러그인 방식으로 만듭니다. 오프로드 경로는 일반적으로 요청 경로에서 숨겨지지만, 캐시 미스 및 승격은 엔드투엔드 지연을 추가할 수 있습니다. LMCache는 공유 접두어가 없어도 유용합니다 — GPU가 KV 슬롯을 소진하면, 선점된 요청은 프리필을 재계산하는 대신 CPU에서 복원할 수 있습니다. 4개의 a3-highgpu-4g에 걸친 16x H100 (80GB HBM)에 대한 공개 벤치마크: KV 캐시가 HBM을 초과하면, 네이티브 CPU 오프로딩과 LMCache 모두 처리량을 크게 개선합니다; 낮은 KV 풋프린트에서는 모든 구성이 작은 오버헤드와 함께 기준선과 일치합니다.

**유형:** Learn
**언어:** Python (stdlib, 장난감 KV-스필 시뮬레이터)
**선수 요건:** 17단계 · 04강 (서빙 엔진 내부 구조), 17단계 · 06강 (SGLang/RadixAttention)
**시간:** 약 60분

## 학습 목표

- vLLM 프로덕션 스택 계층(라우터, 엔진, KV 오프로드, 관측 가능성)을 다이어그램으로 표현해 보세요.
- KV 오프로딩 커넥터 API(v0.9.0+)와 0.11.0 비동기 경로가 오프로드 지연을 숨기는 방식을 설명해 보세요.
- LMCache CPU-DRAM이 도움이 되는 경우(KV > HBM)와 오버헤드를 추가하는 경우(KV가 HBM에 충분히 작게 fits)를 정량화해 보세요.
- 배포 제약 조건을 고려하여 네이티브 vLLM CPU 오프로딩과 LMCache 커넥터 중 하나를 선택해 보세요.

## 문제점

vLLM 서빙은 동시성이 상승할 때마다 GPU가 HBM의 100%를 사용하며 선점 이벤트를 보여줍니다. 요청이 퇴거되고, 재큐잉되며, 같은 2K 토큰 프롬프트를 1분 안에 네 번 다시 프리필합니다. GPU 연산은 중복 프리필에 사용되며; 순수 처리량(Goodput)은 원시 처리량보다 훨씬 낮습니다.

GPU를 추가하는 비용은 선형적으로 증가합니다. HBM을 추가하는 것은 불가능합니다. 하지만 CPU DRAM은 저렴합니다 — 하나의 소켓은 HBM보다 지연이 몇 자릿수 더 나쁘지만 "임시적으로 따뜻한" KV 캐시에는 충분한 512 GB+를 제공합니다.

LMCache는 KV 캐시를 CPU DRAM으로 추출하여 선점된 요청이 빠르게 복구되도록 하고, 여러 엔진 간에 반복되는 접두어가 캐시를 공유하여 각 엔진이 프리필을 다시 수행하지 않도록 합니다.

## 개념

### vLLM 프로덕션 스택

`github.com/vllm-project/production-stack`는 참조 Kubernetes 배포입니다:

- **라우터** — 캐시 인식 (17단계 · 11강). KV 이벤트를 소비합니다.
- **엔진** — vLLM 워커. GPU당 하나 또는 TP/PP 그룹당 하나입니다.
- **KV 캐시 오프로드** — LMCache 배포 또는 네이티브 커넥터.
- **관측 가능성** — Prometheus 스크레이프, Grafana 대시보드, OTel 추적.
- **제어 평면** — 서비스 검색, 구성, 롤링 업데이트.

Helm 차트 + 오퍼레이터로 출시됩니다.

### KV 오프로딩 커넥터 API (v0.9.0+)

vLLM 0.9.0은 플러그형 KV 캐시 백엔드를 위한 커넥터 API를 도입했습니다. 엔진은 블록을 커넥터로 오프로드하며, 커넥터는 이를 저장합니다(RAM, 디스크, 객체 저장소, LMCache). 요청이 블록을 필요로 하면 커넥터가 이를 다시 로드합니다.

vLLM 0.11.0 (2026년 1월)은 비동기 오프로드 경로를 추가했습니다. 오프로드가 백그라운드에서 수행되어 일반적인 경우 엔진이 이를 차단하지 않습니다. 엔드투엔드 지연 시간과 처리량은 워크로드 형태, KV 캐시 적중률, 시스템 압력에 따라 달라지며, vLLM 자체 노트는 낮은 적중률에서 커스텀 커널 오프로드가 처리량을 저하시킬 수 있고, 비동기 스케줄링이 추론적 디코딩(Speculative Decoding)과 알려진 상호작용 문제가 있음을 명시합니다.

### 네이티브 CPU 오프로드 vs LMCache

**네이티브 vLLM CPU 오프로드**: 엔진 로컬. KV 블록을 호스트 RAM에 저장합니다. 구현이 빠르고 네트워크 홉이 없습니다. 엔진 간에 공유되지 않습니다.

**LMCache 커넥터**: 클러스터 규모. 블록을 공유 LMCache 서버(CPU DRAM + Ceph/S3 티어)에 저장합니다. 블록은 모든 엔진이 접근할 수 있습니다. 16x H100 벤치마크가 공개되었습니다.

단일 엔진이 HBM 압력을 받을 때는 네이티브를 선택하세요. 여러 엔진이 접두어를 공유할 때(공통 시스템 프롬프트가 있는 RAG, 공유 템플릿을 사용하는 멀티 테넌트)는 LMCache를 선택하세요.

### 벤치마크 동작

4개의 a3-highgpu-4g에 분산된 16x H100 (80 GB HBM) 테스트:

- 낮은 KV 풋프린트(짧은 프롬프트, 낮은 동시성): 모든 구성이 기준선과 일치하며, LMCache는 약 3-5%의 오버헤드를 추가합니다.
- 중간 규모 사용량: LMCache가 엔진 간 접두어 재사용을 지원하기 시작합니다.
- KV가 HBM을 초과하는 경우: 네이티브 CPU 오프로드와 LMCache 모두 처리량을 크게 개선합니다. LMCache는 엔진 간 공유가 가능하므로 더 큰 이점을 제공합니다.

### LMCache가 결정적인 경우

- 시스템 프롬프트가 테넌트 간에 공유되는 멀티 테넌트 서빙.
- 문서 청크가 쿼리 간에 반복되는 RAG.
- 동일한 기본 모델의 미세 조정 변형(LoRA)에서 기본 모델 KV 재사용이 중복 작업을 줄이는 경우.
- 선점(preemption)이 많은 워크로드: CPU에서 복원하는 것이 재프리필보다 저렴합니다.

### 활성화하지 말아야 하는 경우

- HBM 압력이 작은 경우 — 이점 없이 오버헤드만 발생합니다.
- 짧은 컨텍스트(<1K 토큰) — 전송 시간이 재프리필보다 오래 걸립니다.
- 단일 테넌트 단일 프롬프트 워크로드 — 재사용할 것이 없습니다.

### 분산 서빙과의 통합

17단계 · 17분산 서빙 + LMCache 결합: 프리필 풀에서 디코딩 풀로 전송된 KV가 사용되지 않으면 LMCache에 저장됩니다. 이후 쿼리는 LMCache에서 가져옵니다. 17단계 · 11캐시 인식 라우터는 로컬 캐시 또는 LMCache 공유 캐시가 일치하는 엔진으로 라우팅할 수 있습니다.

### 기억해야 할 수치

- vLLM 0.9.0: Connector API가 출시되었습니다.
- vLLM 0.11.0 (2026년 1월): 비동기 오프로드 경로가 추가되었습니다. 엔드투엔드 지연 영향은 워크로드, KV 적중률 및 시스템 압력에 따라 달라지며, 절대적인 보장은 아닙니다.
- 16x H100 벤치마크: KV 사용량이 HBM을 초과할 때 LMCache가 도움이 됩니다.
- HBM 압력이 작은 경우: 이점 없이 3-5% 오버헤드가 발생합니다.

## 연습 문제

1. `code/main.py`를 실행해 보세요. LMCache가 이점을 내기 시작하는 HBM 사용률은 몇 %인가요?
2. 한 테넌트가 시간당 200개 쿼리에 걸쳐 6K 토큰 시스템 프롬프트를 공유합니다. 테넌트당 예상 LMCache 절감량을 계산해 보세요.
3. LMCache 서버는 단일 장애점입니다. HA 전략(복제본, 네이티브 폴백)을 설계해 보세요.
4. LMCache는 회전 디스크의 Ceph에 저장합니다. 70B FP8의 4K 토큰 KV(500 MB)의 경우, 읽기 시간과 재프리필 시간을 비교해 보세요.
5. vLLM 0.11.0의 비동기 경로가 "무료"인지 논증해 보세요. 오버헤드는 어디에 숨겨져 있나요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| Production-stack | "참조 배포" | vLLM의 Kubernetes Helm 차트 + 오퍼레이터 |
| Connector API | "KV 백엔드 인터페이스" | vLLM 0.9.0+의 플러그인형 KV 저장소 인터페이스 |
| Native CPU offload | "엔진 로컬 스플" | 동일한 엔진의 호스트 RAM에 KV를 저장 |
| LMCache | "클러스터 KV 캐시" | CPU DRAM + 디스크 기반의 엔진 간 KV 캐시 서버 |
| 0.11.0 async | "비차단 오프로드" | 엔진 스트림 뒤에 숨겨진 오프로드 |
| Preemption | "공간 확보를 위한 퇴거" | HBM이 가득 찼을 때 KV 캐시를 재배치 |
| Prefix reuse | "동일한 시스템 프롬프트" | 여러 쿼리가 시작 부분을 공유하며 캐시 적중 |
| Ceph tier | "디스크 티어" | 캐시 계층 구조에서 DRAM 아래에 있는 내구성 있는 저장소 |
