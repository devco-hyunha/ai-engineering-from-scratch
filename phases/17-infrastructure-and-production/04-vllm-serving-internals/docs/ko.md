# 서빙 엔진 내부 구조 — PagedAttention, 연속 배치, 청크 프리필

> 현대 서빙 엔진의 처리량은 단일 트릭이 아닌 세 가지 기본 설정의 복합에 의존합니다. PagedAttention은 항상 켜져 있습니다. 연속 배치는 디코딩 반복 사이에 활성 배치에 새 요청을 주입합니다. 청크 프리필은 긴 프롬프트를 잘게 쪼개 디코딩 토큰이 고갈되지 않도록 합니다. 이 세 가지를 모두 켜면 단일 H100 SXM5에서 Llama 3.3 70B FP8는 128개 동시 요청에서 2,200-2,400 tok/s를 달성합니다. 이는 vLLM 자체 기본값보다 약 25% 높고, 단순한 PyTorch 루프의 3-4배입니다. 이 강의는 세 기법의 참조 엔진인 vLLM의 스케줄러와 어텐션 커널을 다이어그램으로 표현할 수 있는 수준에서 다루며, vLLM처럼 프리필과 디코딩을 스케줄링하는 `code/main.py`의 토이 연속 배처로 마무리됩니다.

## 학습 목표

- PagedAttention을 KV 캐시 할당자로 설명하세요: 블록, 블록 테이블, 그리고 프로덕션 부하에서 단편화가 4% 미만으로 유지되는 이유를 포함합니다.
- 반복 단위에서 연속 배치를 다이어그램으로 표현하세요: 완료된 시퀀스가 배치를 떠나고 새 시퀀스가 배치를 비우지 않고 합류하는 방식을 포함합니다.
- 청크 프리필을 한 문장으로 설명하고, 이 기법이 보호하는 지연 지표의 이름을 지정하세요 (힌트: 평균 처리량이 아닌 TTFT 꼬리 지연입니다).
- 모든 최적화를 한 번에 활성화하기 전에, 사용 중인 버전의 호환성 매트릭스와 비교하여 vLLM 기능 조합을 확인하세요.

## 문제점

단순한 PyTorch 서빙 루프는 한 번에 하나의 요청만 처리합니다: 토큰화, 프리필, EOS까지 디코딩, 반환. 사용자가 한 명일 때는 잘 작동합니다. 사용자가 백 명일 때는 인내심 있는 사람들의 대기열이 됩니다. 명백한 해결책인 정적 배치는 윈도우 내 모든 요청을 가장 긴 프롬프트에 맞춰 패딩하고, 모든 디코딩을 가장 긴 예상 출력에 맞춰 패딩하며, 가장 느린 시퀀스에 전체 배치를 멈추게 합니다. 사용하지 않는 패딩에 비용을 지불하고, 빠른 요청이 느린 요청을 기다려야 합니다.

vLLM은 세 가지 문제를 동시에 해결합니다. PagedAttention은 고전적인 연속 할당 방식이 GPU 메모리의 60-80%를 소모하는 KV 캐시 파편화를 방지합니다. 연속 배치(Continuous Batching)는 각 디코딩 반복 사이에 요청이 배치에 합류하거나 이탈할 수 있게 하여, 배치가 항상 실제 작업으로 가득 차도록 합니다. 청킹 프리필(Chunked Prefill)은 32k 토큰 프롬프트를 약 512 토큰 조각으로 나누어 디코딩과 인터리빙(interleave)하므로, 긴 프롬프트가 GPU의 모든 디코딩 토큰을 동결하지 않습니다.

2026년 프로덕션 기본 설정은 세 가지 모두 활성화된 상태입니다. 실패 모드(scheduler)는 모델이 아니라 스케줄러에 있으므로, 각각이 무엇을 하는지 이해해야 합니다.

## 개념

### 가상 메모리 시스템으로서의 PagedAttention

KV 캐시는 `num_layers × 2 × num_heads × head_dim × seq_len × bytes_per_element` 시퀀스당입니다. Llama 3.3 70B에서 8192 토큰의 경우, BF16에서 시퀀스당 약 1.25 GB입니다. 모든 요청에 대해 8192 슬롯을 사전 예약하지만 평균 요청이 1500 토큰만 사용한다면, 예약한 HBM의 약 82%를 낭비하게 됩니다. 고전적인 배치는 이 낭비를 감당합니다.

PagedAttention은 OS 가상 메모리의 아이디어를 차용합니다. KV 캐시는 시퀀스별로 연속적이지 않습니다. 고정 크기 블록(기본값 16 토큰)으로 할당됩니다. 각 시퀀스는 논리적 토큰 위치를 물리적 블록 ID에 매핑하는 블록 테이블을 가집니다. 시퀀스가 할당된 블록을 초과하여 성장하면 추가 블록이 하나 더 할당됩니다. 시퀀스가 완료되면 그 블록들은 풀(pool)로 반환됩니다.

파편화는 60-80%(고전적 방식)에서 PagedAttention을 통해 4% 미만으로 감소합니다. PagedAttention은 플래그로 활성화하지 않습니다. 이는 vLLM이 제공하는 유일한 할당자입니다. 조절 변수는 `--gpu-memory-utilization` (기본값 0.9)이며, 가중치와 활성화를 로드한 후 KV 블록을 위해 HBM의 얼마나 많은 부분을 예약할지 vLLM에 지시합니다.

### 반복(iteration) 수준의 연속 배치

이전의 "동적 배치"는 배치를 채우기 위해 창(window, 예: 10 ms)을 기다린 후, 모든 시퀀스가 완료될 때까지 프리필 + 디코딩 + 디코딩 + 디코딩을 실행했습니다. 빠른 시퀀스는 일찍 종료되어 GPU가 느린 시퀀스를 처리하는 동안 유휴 상태로 대기했습니다.

연속 배치는 각 디코딩 단계 사이에서 작동합니다. 실행 중인 시퀀스 집합을 `RUNNING` 목록이라고 부릅니다. 각 반복(iteration)에서:

1. `RUNNING`에서 EOS 또는 max_tokens에 도달한 시퀀스는 제거됩니다.
2. 스케줄러는 대기 큐를 확인합니다. 자유 KV 블록이 있다면, 새로운 시퀀스(프리필 또는 재개)를 수용(admit)합니다.
3. 순방향 전파는 `RUNNING`에 현재 있는 내용을 기반으로 실행되며, 각 시퀀스에 대해 하나의 새 토큰을 생성합니다.

배치 크기는 고정된 숫자로 패딩되지 않습니다. 출력 위치가 서로 다른 시퀀스들은 하나의 융합된 순방향 전파를 공유합니다. 2026년 vLLM에서는 이를 `V1 scheduler`이라고 부릅니다. 핵심 불변 조건: 스케줄러는 요청당 한 번이 아니라 디코딩 반복(iteration)당 한 번 실행됩니다.

### 청킹 프리필은 TTFT 꼬리 지연을 보호합니다

프리필은 연산 집약적입니다. Llama 3.3 70B에서 32k 토큰 프롬프트는 H100 하나에서 순수 프리필에 약 800ms가 소요됩니다. 프리필이 실행되는 동안, 배치 내의 다른 모든 시퀀스에 대한 디코딩 토큰은 대기합니다. 서빙 루프에서 긴 프롬프트의 첫 토큰 지연(TTFT)은 수십 명의 다른 사용자에게 토큰 간 지연(ITL)의 급격한 상승(blip)으로 이어집니다.

청킹 프리필은 프리필을 고정 크기 청크(기본값 512 토큰)로 분할하고 각 청크를 단위로서 스케줄링합니다. 청크 사이에서 스케줄러는 디코딩 시퀀스를 한 토큰만큼 진행할 수 있습니다. 작은 절대 프리필 지연 증가(청크당 몇 ms)를 감수하는 대신 디코딩 시간의 지터(jitter)를 크게 낮출 수 있습니다. 공개된 벤치마크에 따르면 혼합 부하에서의 P99 ITL은 약 50ms에서 약 15ms로 감소합니다.

### 세 가지 기본 설정이 상호작용합니다

세 가지 기능 모두 서로를 전제합니다. PagedAttention은 스케줄러가 교환할 수 있는 세밀한 KV 자원을 제공합니다. 연속 배치는 새로운 시퀀스를 수용할 때 전역 재배치가 발생하지 않도록 하기 위해 이 세밀한 자원을 필요로 합니다. 청킹 프리필은 동일한 `RUNNING` 목록에서 스케줄러가 내리는 결정입니다. 이는 별도의 시스템이 아니라 스케줄러의 또 다른 정책입니다.

모든 플래그를 알 필요는 없습니다. 스케줄러가 최적화하는 것을 알아야 합니다: 청킹 프리필 슬라이싱의 제약 하에 KV 블록 예산 내에서 순수 처리량(goodput)을 최적화하는 것입니다.

### 호환성 매트릭스를 확인하세요

모든 기능을 한 번에 활성화하기 전에, 릴리스 간에 조합이 변경될 수 있으므로 정확한 vLLM 버전에 대한 호환성 매트릭스를 모든 기능 조합에 대해 확인하세요. v0.18.0에서는 기능 매트릭스가 추론적 디코딩(Speculative Decoding)을 청킹 프리필 및 접두어 캐싱과 호환되는 것으로 표시하며, 추론적 디코딩 페이지는 두 가지 알려진 비호환성을 나열합니다: v0.15.0까지의 파이프라인 병렬화, 그리고 v0.10.0까지의 드래프트 모델 추론. 드래프트 방법 자체의 경우, 2026년 기본값은 종종 EAGLE-3 (`"method": "eagle3"`)이며, 이는 17단계 · 05강에서 다루어집니다.

### 기억해야 할 수치

- Llama 3.3 70B FP8, H100 SXM5, 동시 요청 128개, 세 가지 기능 모두 활성화: 2,200-2,400 tok/s.
- 동일 모델, 기본 vLLM (청킹 프리필 없음): ~1,800 tok/s.
- 동일 모델, 단순한 PyTorch 순방향 루프: ~600 tok/s.
- 프로덕션 부하에서 PagedAttention 하의 KV 조각화 낭비: <4%.
- 혼합 부하에서의 P99 ITL: 청킹 프리필 사용 시 ~15 ms, 미사용 시 ~50 ms.

### 스케줄러의 모습

```
while True:
    finished = [s for s in RUNNING if s.is_done()]
    for s in finished: release_blocks(s); RUNNING.remove(s)

    while WAITING and have_free_blocks_for(WAITING[0]):
        s = WAITING.pop(0)
        allocate_initial_blocks(s)
        RUNNING.append(s)

    # 프리필 청크와 디코딩을 하나의 배치로 스케줄링
    batch = []
    for s in RUNNING:
        if s.in_prefill:
            batch.append(next_prefill_chunk(s))   # 예: 512 토큰
        else:
            batch.append(decode_one_token(s))     # 1 토큰

    run_forward(batch)                            # 하나의 융합된 GPU 호출
```

`code/main.py`는 가짜 토큰 수와 가짜 순방향 지연 시간을 사용하여 stdlib Python으로 작성된 이 루프를 정확히 구현한 것입니다. 이를 실행하면 긴 프리필 동안 청킹 프리필이 디코딩 시퀀스를 어떻게 유지하는지 확인할 수 있습니다.

## 사용하기

`code/main.py`는 토글 가능한 기능을 갖춘 vLLM 스타일 스케줄러를 시뮬레이션합니다. 실행하여 다음을 확인해 보세요:

- `NAIVE` 모드: 한 번에 하나의 요청만 처리, 배치 없음.
- `STATIC` 모드: 패딩하고 대기, 전통적인 배치 처리.
- `CONTINUOUS` 모드: 반복 단위 수용 및 해제.
- `CONTINUOUS + CHUNKED` 모드: 프리필 슬라이스를 디코딩과 교대로 처리.

출력은 총 처리량 (가상 초당 토큰 수), TTFT 평균 및 P99 ITL을 보여줍니다. `CONTINUOUS + CHUNKED` 행은 혼합 트래픽에서 가장 높은 성능을 보여야 합니다.

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|----------------|------------------------|
| PagedAttention | "the KV trick" | KV 캐시를 위한 고정 크기 블록 할당자; 파편화 <4% |
| 블록 테이블 | "the page table" | 논리적 토큰 위치에서 물리적 KV 블록으로의 시퀀스별 맵 |
| 연속 배치 | "dynamic batching, but right" | 매 디코딩 반복마다 수용/해제 결정이 이루어짐 |
| 청킹 프리필 | "prefill splitting" | 긴 프리필을 디코딩과 교대로 수행되는 512토큰 슬라이스로 분할 |
| TTFT | "first token time" | 프리필 + 큐 + 네트워크; 긴 프롬프트에서는 프리필이 지배적 |
| ITL | "inter-token latency" | 연속적인 디코딩 토큰 사이의 시간; 배치 크기가 지배적 |
| 순수 처리량 | "throughput that meets SLO" | 모든 요청이 TTFT 및 ITL 목표를 충족하는 토큰/초 |
| V1 스케줄러 | "the new scheduler" | vLLM의 2026년 스케줄러; 청킹 프리필과 함께 연속 배치를 실행 |
| `--gpu-memory-utilization` | "the memory knob" | 가중치와 활성화 이후 KV 블록을 위해 예약된 HBM의 비율 |
