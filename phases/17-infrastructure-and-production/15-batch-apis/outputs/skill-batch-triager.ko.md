워크로드(이름, 사용자의 지연 시간 기대치, 트래픽 볼륨, 공유 프롬프트 구조)가 주어지면 분류(triage) + 비용 계획을 산출합니다.

산출물:

1. 레인. 인터랙티브(TTFT 제한, 동기), 준인터랙티브(분 단위 허용, 비동기 큐), 또는 배치(아침까지 허용, 배치 API). 사용자의 구체적인 기대치를 근거로 정당화합니다.
2. 현재 비용. 현재 구성(동기, 캐시 없음 등)에서의 월간 비용을 계산합니다.
3. 목표 비용. 권장 구성(배치 + 캐시 또는 동기 + 캐시) 이후의 비용을 계산합니다. 현재 비용의 %로 표현합니다.
4. 이전 계획. 제공자별 단계(워크로드의 모델과 일치하는 하나만 선택합니다. 둘 다 선택하지 마세요):
   - OpenAI: `/v1/batches`로 이전합니다. 자격을 갖춘 프롬프트(≥1024 토큰)에 대해 프롬프트 캐싱이 자동으로 활성화됩니다 — `cache_control`를 설정할 필요가 없습니다. 선택적으로 `prompt_cache_key`를 전달하여 더 엄격한 귀속을 수행할 수 있습니다.
   - Anthropic: Message Batches로 이전합니다. 캐시 재사용을 위해 캐시 가능한 프롬프트 범위에 명시적인 `cache_control` 블록(예: `{"type": "ephemeral"}`)이 필요합니다. 배치 할인은 캐시 읽기 가격과 스택됩니다.
   - 둘 다: 성공/실패 웹훅과 배치의 처리 시간 창(turnaround window)을 초과하는 경우 동기 레인으로 스플로버(spillover)하는 레인을 계측(instrument)합니다.
5. 리스크. P99에서 배치 처리 시간(turnaround)이 20시간이라면 어떻게 될까요? 다운스트림 시스템의 동작(이메일 전달, 동기 레인으로의 큐 스플로버)을 명시합니다.
6. 관측 가능성. 오분류(triage)를 포착하는 지표: 배치 작업 완료 지연 P95; 12시간 초과 시 알람을 발생시킵니다.

하드 리젝트(Hard rejects):
- 사용자가 '아침까지'의 지연 시간만 필요로 하는데, 배치 없이 동기 모드로 야간 파이프라인을 실행하는 경우. 거절하세요 — 약 90%의 낭비된 지출을 지적합니다.
- 15분 미만의 사용자 기대치가 있는 모든 것에 배치를 약속하는 경우. 거절하세요 — 배치 SLA는 24시간입니다.
- 공유 시스템 프롬프트가 있는 배치 워크로드에서 프롬프트 캐싱을 무시하는 경우. 거절하세요 — 스택 할인이 핵심입니다.

거절 규칙:
- 작업 부하가 "실시간"으로 마케팅되지만, 실제 사용자 기대가 몇 분 단위라면, 배치 처리를 권장하기 전에 명시적인 확인을 요구해야 합니다.
- 작업 부하가 배치에서 프롬프트 캐싱을 제공하지 않는 공급자(예: KV 접두어 재사용이 없는 모든 커스텀 또는 자체 호스팅 스택)를 대상으로 하는 경우, 배치 할인만 적용됨을 명시하고 누적된 절감 효과를 제외하고 재계산해야 합니다. OpenAI 배치 캐싱은 자동이며, Anthropic 배치 캐싱은 명시적인 `cache_control` 블록이 필요합니다.
- 작업 부하가 엄격한 지연 SLA(예: P99 < 60초)를 가진 경우, 배치 처리를 즉시 거부해야 합니다. 이는 다른 레인에 속합니다.

출력: 레인, 현재 비용, 목표 비용, 마이그레이션 단계, 위험, 관측 가능성을 포함한 한 페이지 분량의 트리아지 문서입니다. 제품 표면이 변경됨에 따라 모든 작업 부하를 분기별로 재트리아지하는 주기(cadence)로 마무리하세요.
