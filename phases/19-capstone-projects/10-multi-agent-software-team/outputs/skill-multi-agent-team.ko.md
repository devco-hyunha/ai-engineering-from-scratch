GitHub 이슈 URL과 병렬화 수준을 입력으로 받아, 병합 준비가 완료된 PR을 생성하는 다중 에이전트 소프트웨어 팀을 배포합니다. 50개의 SWE-bench Pro 이슈로 평가하고, 핸드오프 실패 히스토그램을 게시합니다.

구축 계획:

1. 작업 보드: 파일 기반(또는 Redis) JSONL 저장소에 타입이 지정된 메시지를 저장합니다. 메시지 종류: plan_request, subtask, diff_ready, review_needed, review_feedback, approved, test_needed, test_passed, test_failed, replan_needed.
2. 아키텍트(Opus 4.7): 이슈를 읽고 계획을 작성하며, 명시적 인터페이스(접촉 파일, 공개 함수, 테스트 영향)를 가진 하위 작업의 DAG를 생성합니다.
3. N명의 코더(Sonnet 4.7): 각 코더는 하위 작업을 담당하고, 새로운 `git worktree add` + Daytona 샌드박스를 생성하여 독립적으로 구현합니다.
4. 병합 조정자: 3-way 병합을 수행하며, 파일 수준 겹침이 있는 경우에만 LLM을 통해 충돌을 해결합니다.
5. 리뷰어(GPT-5.4): 병합된 diff를 읽습니다. 본인이 작성한 diff는 승인할 수 없으며, 승인(approved) 또는 리뷰 피드백(review_feedback)을 관련 코더에게 라우팅합니다.
6. 테스터(Gemini 2.5 Pro): 깨끗한 샌드박스에서 테스트 스위트를 실행하며, 아티팩트와 함께 test_passed 또는 test_failed를 생성합니다.
7. 핸드오프 회계: 모든 역할 간 메시지는 페이로드 크기와 모델을 포함하는 Langfuse span이 됩니다. 토큰 증폭 = total_tokens / single_agent_baseline_tokens를 계산합니다.
8. 명백한 버그 프로브(실행의 10%)를 주입하여 리뷰어의 오탐 승인(false-approve)률을 측정합니다.
9. 50개의 SWE-bench Pro 이슈에서 실행합니다. pass@1, 단일 에이전트 기준 대비 실제 시간(wall-clock), 역할별 토큰 분해, 핸드오프 실패 히스토그램을 게시합니다.

평가 기준표:

| 가중치 | 기준 | 측정 |
|:-:|---|---|
| 25 | SWE-bench Pro pass@1 | 50개 이슈 하위 집합의 pass@1 |
| 20 | 병렬 속도 향상 | 단일 에이전트 기준 대비 실제 시간(wall-clock) |
| 20 | 리뷰 품질 | 주입된 버그 프로브에 대한 오탐 승인(false-approval)률 |
| 20 | 토큰 효율성 | 해결된 이슈당 총 토큰 수 vs 단일 에이전트 |
| 15 | 조정 엔지니어링 | 병합 충돌 해결, 핸드오프 실패 히스토그램 |

하드 리젝트:

- 자신이 작성하거나 제안한 diff를 승인할 수 있는 리뷰어. 하드 제약 조건입니다.
- 매칭된 단일 에이전트 기준선 실행이 없는 보고서. 멀티 에이전트는 *달러당* 승리를 해야 하며, 단순히 pass@1을 통과하는 것만으로는 부족합니다.
- 메시지가 자유 형식 문자열이 아닌 타입 지정된 A2A 메시지인 작업 보드.
- 충돌하는 diff를 재계획을 위해 라우팅하지 않고 조용히 버리는 병합 조정자.

거부 규칙:

- 역할별 예산 상한(토큰 + 달러) 없이 실행하는 것을 거부합니다.
- 테스터가 깨끗한 샌드박스에서 검증하지 않은 PR을 여는 것을 거부합니다.
- 단일 실행에서 코더를 8명 이상으로 확장하는 것을 거부합니다. 그 이상에서는 조정 오버헤드가 지배적입니다.

출력: 작업 보드 + 역할별 워커, 50개 이슈 SWE-bench Pro 실행 로그, 매칭된 단일 에이전트 기준선 실행, 역할 태그가 지정된 스팬 및 역할별 토큰 분해가 포함된 Langfuse 대시보드, 주입된 버그 탐지 보고서, 가장 자주 깨진 세 개의 핸드오프와 각각을 줄인 메시지 스키마 또는 프롬프트 변경을 명시한 사후 분석이 포함된 저장소입니다.
