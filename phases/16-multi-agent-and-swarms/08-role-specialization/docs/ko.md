# 역할 전문화 — 플래너, 비평가, 실행자, 검증자

> 2026년 가장 일반적인 다중 에이전트 분해 방식: 한 에이전트가 계획하고, 한 에이전트가 실행하며, 한 에이전트가 비평하거나 검증합니다. MetaGPT (arXiv:2308.00352)는 이 방식을 `Code = SOP(Team)`을 따르는 역할 프롬프트에 인코딩된 SOP로 공식화합니다 — 제품 관리자, 아키텍트, 프로젝트 관리자, 엔지니어, QA 엔지니어. ChatDev (arXiv:2307.07924)는 디자이너, 프로그래머, 리뷰어, 테스터를 "채팅 체인"으로 연결하며 "의사소통 기반 환각 제거" (에이전트가 누락된 세부 정보를 명시적으로 요청)를 사용합니다. 검증자는 핵심적인 역할을 수행합니다: Cemri et al. (MAST, arXiv:2503.13657)은 모든 다중 에이전트 실패가 누락되거나 손상된 검증으로 추적될 수 있음을 보여줍니다. PwC는 CrewAI의 구조화된 검증 루프를 통해 7배의 정확도 향상 (10% → 70%)을 보고했습니다.

**유형:** Learn + Build
**언어:** Python (stdlib)
**선수 요건:** 16단계 · 04강 (원시 모델), 16단계 · 05강 (슈퍼바이저)
**시간:** 약 60분

## 문제점

범용 다중 에이전트 시스템은 범용적인 출력만 생성합니다. 그룹 채팅에 있는 세 명의 코더는 동일한 수준의 mediocre 코드를 세 가지 변형으로 작성합니다. 에이전트를 더 추가하고 라운드를 더 늘려도 품질 임계값을 넘지 못합니다.

해결책은 더 많은 에이전트가 아니라 *다른* 에이전트입니다. 서로 다른 역할을 할당하세요. 플래너가 갖지 못한 도구를 비평가에게 제공하세요. 검증자에게 객관적인 테스트 스위트를 제공하세요. 이제 시스템은 단순한 병렬 추측이 아니라, 근거 있는 수정을 포함하는 내부적 불일치를 갖게 됩니다.

## 개념

### 네 가지 표준 역할

**플래너.** 목표를 읽고 단계 목록이나 사양을 생성합니다. 도구: 지식 검색, 문서. 출력: 구조화된 계획.

**실행자.** 한 번에 하나의 계획 단계를 읽고 산출물을 생성합니다. 도구: 실제 작업 도구 (코드 컴파일러, 셸, API 클라이언트). 출력: 산출물.

**비평가.** 플래너의 의도와 비교하여 실행자의 출력을 읽습니다. 도구: 산출물에 대한 읽기 전용 접근, 정적 분석. 출력: 이유와 함께 승인/거절.

**검증자.** 산출물을 읽고 결정론적 검사를 실행합니다. 도구: 테스트 러너, 타입 체커, 스키마 검증기. 출력: 증거와 함께 통과/실패.

비평가는 주관적이고 의견이 강하며, LLM에 기반하는 경우가 많습니다. 검증자는 객관적이고 결정론적이며, 코드에 기반하는 경우가 많습니다. 두 역할은 동일하지 않습니다.

### MetaGPT의 SOP 패턴

MetaGPT (arXiv:2308.00352)는 소프트웨어 엔지니어링 SOP를 역할 프롬프트로 인코딩합니다:

- **제품 관리자**는 PRD를 작성합니다.
- **아키텍트**는 시스템 설계를 산출합니다.
- **프로젝트 관리자**는 작업을 분할합니다.
- **엔지니어**는 구현합니다.
- **QA 엔지니어**는 테스트를 실행합니다.

각 역할은 엄격한 입력/출력 스키마를 가집니다. 역할 프롬프트는 역할이 *무엇*인지와 *무엇을 산출해야 하는지*를 명시합니다. `Code = SOP(Team)` 공식화 — 결정론적 SOP는 LLM 팀을 예측 가능한 파이프라인으로 전환합니다.

### ChatDev의 의사소통 기반 환각 제거

ChatDev는 핵심적인 조치를 추가합니다: 실행자가 계획에 없던 특정 세부 정보가 필요할 경우, 계속 진행하기 전에 설계자에게 명시적으로 요청합니다. 이는 LLM이 세부 정보를 그럴듯하게 만들어내는 고전적인 실패를 방지합니다.

구현: 역할 프롬프트에 "주어진 정보 중 특정 정보가 필요할 경우, 출력 생성 전에 관련 역할을 이름으로 지정하여 요청하세요"가 포함됩니다.

### 검증자가 가장 중요한 이유

Cemri 등(MAST)은 1642건의 다중 에이전트 실행 실패를 추적했습니다. 21.3%는 검증 공백이 원인이며, 시스템은 아무도 확인하지 않은 답변을 출시했습니다. 나머지 79%는 "실패한 검사가 조용히 진행되었거나, 아예 실행되지 않았다"로 거슬러 올라가는 경우가 많습니다. 검증은 핵심적인 역할을 담당합니다.

PwC는 (CrewAI 배포, 2025) 구조화된 검증 루프를 추가하면 정확도가 10%에서 70%로 향상된다고 보고했습니다. 하나의 역할로 7배의 향상입니다.

### 비평가 vs 검증자

- 비평가는 산출물의 품질을 검토하는 LLM입니다. 주관적입니다. 그럴듯한 문장에 속을 수 있습니다.
- 검증자는 산출물에서 실행되는 결정론적 프로그램입니다. 객관적입니다. 증거와 함께 통과/실패를 제공합니다.

두 가지를 모두 사용하세요. 비평가는 검증자가 표현할 수 없는 취향 관련 문제를 포착합니다. 검증자는 비평가가 볼 수 없는 버그를 포착합니다. 왜냐하면 버그는 런타임에만 나타나기 때문입니다.

### 안티 패턴

시스템의 모든 역할이 LLM이고, 모든 역할의 출력이 "나쁘지 않네요"인 경우입니다. 전형적인 MAST 실패 모드입니다. 통과/실패가 LLM이 아닌 코드로 결정되는 검증자를 최소한 하나 추가해 보세요.

### 프레임워크 매핑

- **CrewAI** — `Agent(role, goal, backstory)`는 교과서적인 전문화 표면입니다.
- **LangGraph** — 노드에는 전문화된 프롬프트를 사용할 수 있으며, 엣지는 파이프라인을 강제합니다.
- **AutoGen** — GroupChat에서 한 단어 이름의 역할별 ConversableAgent를 사용합니다.
- **OpenAI Agents SDK** — 역할이 전문화된 Agent들 간의 핸드오프 도구를 사용합니다.

## 구현하기

`code/main.py`는 간단한 Python 함수를 구축하는 4역할 파이프라인을 구현합니다:

- **Planner**는 사양을 생성합니다.
- **Executor**는 코드 문자열을 생성합니다.
- **Critic** (LLM 시뮬레이션)은 명백한 문제를 표시합니다.
- **Verifier**는 생성된 코드를 샌드박스 (`exec`)에서 테스트 케이스에 대해 실행합니다.

데모는 두 번 실행됩니다: 한 번은 Executor가 올바른 코드를 생성하는 경우 (Critic과 Verifier 모두 통과), 한 번은 Executor가 사양에서 벗어난 코드를 생성하는 경우 (Critic은 그럴듯해 보이기 때문에 버그를 놓치지만, Verifier는 테스트가 실패하기 때문에 이를 잡아냅니다).

실행:

```
python3 code/main.py
```

## 사용하기

`outputs/skill-role-designer.md`는 작업을 받아 역할 목록 (3-5개 역할), 역할별 입력/출력 스키마 및 검증자 체크를 생성합니다. 에이전트를 프레임워크에 연결하기 전에 이 도구를 사용해 보세요.

## 출시하기

체크리스트:

- **최소 한 개의 결정론적 검증자.** 모든 역할이 LLM인 상태는 피해야 합니다.
- **역할별 명시적 I/O 스키마.** Planner는 산문이 아닌 사양을 반환해야 하며, Executor는 그 스키마를 읽어야 합니다.
- **소통 기반 환각 제거.** Executor는 정보가 부족할 때 Planner에게 요청해야 하며, 절대 자체적으로 만들어내지 않아야 합니다.
- **Critic/Verifier 순서.** Critic을 먼저 실행하세요 (저렴하며 설계 문제를 잡아냄), 그 다음 Verifier를 실행하세요 (느리지만 버그를 잡아냄).
- **루프 예산.** 인간에게 에스컬레이션하기 전까지 Critic-Executor 수정 라운드는 최대 2회로 제한하세요.

## 연습 문제

1. `code/main.py`를 실행하고 Verifier가 Critic이 놓친 버그를 잡아내는 방식을 관찰해 보세요. 추가 검증자로서 정적 분석 체크 (`return`의 발생 횟수 세기)를 추가해 보세요. 런타임 테스트가 놓치는 것을 이 체크가 잡아내는 것은 무엇인가요?
2. 5번째 역할인 '요구사항 분석가'를 추가하여 사용자의 희망을 플래너가 준비할 수 있는 사양으로 번역하세요. 어떤 의사소통적 환각 제거 요청이 이 역할로 전달되어야 합니까?
3. MetaGPT 섹션 3("Agents")을 읽고 MetaGPT의 5가지 역할 각각의 입력/출력 스키마를 나열하세요.
4. ChatDev의 채팅 체인 다이어그램(arXiv:2307.07924 그림 3)을 읽고, 의사소통적 환각 제거가 본래 무한 루프가 될 것을 끊는 지점을 식별하세요.
5. PwC의 7배 정확도 향상은 검증 루프에서 나왔습니다. 검증기를 추가해도 도움이 되지 않는 세 가지 작업을 가설로 세우세요. 즉, 정확성에 대한 결정론적 검사가 불가능하거나 비용이 prohibitive(엄청나게 비싼)한 경우입니다.

| 역할 전문화 | "다른 에이전트, 다른 작업" | 플래너/실행자/비평가/검증자 역할에 맞춰 조정된 별도의 시스템 프롬프트. |
| SOP 패턴 | "인코딩된 표준 운영 절차" | MetaGPT의 프레임: 역할별 엄격한 I/O 스키마가 팀을 파이프라인으로 만듭니다. |
| 의사소통적 환각 제거 | "발명하기 전에 물어보기" | ChatDev 패턴: 실행자가 세부 정보가 누락되면 임의로 만들어내지 않고 플래너에게 묻습니다. |
| 비평가 | "LLM 리뷰어" | 주관적이고 의견이 강한 리뷰어. 취향(taste) 문제를 잡습니다. 그럴듯한 문장에 속을 수 있습니다. |

| 수정 루프 | "비평가가 되돌려 보냄" | 비평가의 거절이 피드백과 함께 실행자 재실행을 트리거합니다. 예산이 필요합니다. |
| 모든 LLM 안티 패턴 | "나에게 좋아 보임" | 모든 역할이 LLM이며 결정론적 검사가 없습니다. 전형적인 MAST 실패입니다. |
