# 감독자 / 오케스트레이터-워커 패턴

> 리드 에이전트(Agent)가 계획을 수립하고 위임(Delegation)하며, 전문화된 워커가 병렬 컨텍스트에서 실행한 후 보고합니다. 이는 Anthropic의 Research 시스템(Claude Opus 4가 리드, Sonnet 4가 서브 에이전트)의 패턴으로, 내부 연구 평가에서 단일 에이전트 Opus 4 대비 +90.2%의 성능 향상으로 측정되었습니다. Anthropic의 엔지니어링 블로그는 BrowseComp의 분산(variance) 중 80%가 토큰 사용량만으로 설명된다고 보고합니다. 멀티 에이전트(Multi-Agent)가 승리하는 주된 이유는 각 서브 에이전트(Subagent)가 새로운 컨텍스트 윈도우(Context Window)를 얻기 때문입니다. 이 강의는 기본 요소(Primitive)로부터 감독자 패턴을 구축하며, 프로덕션 배포에서 나온 2026년 엔지니어링 교훈을 다룹니다.

**유형:** Learn + Build
**언어:** Python (stdlib, `threading`)
**선수 요건:** 16단계 · 04강 (기본 모델)
**시간:** 약 75분

## 문제점

연구는 단일 에이전트 시스템이 실패하는 전형적인 작업입니다. "2023년과 2026년 사이에 멀티 에이전트 시스템에서 무엇이 변했나요?"라고 질문하면, 단일 에이전트는 다섯 개의 논문을 순차적으로 읽고, 컨텍스트의 절반을 그 텍스트로 채운 뒤, 모든 논문을 함께 추론해야 합니다. 다섯 번째 논문에 도달할 때쯤 첫 번째 논문은 잊어버립니다. 병렬화할 수도 없습니다.

감독자 패턴은 이를 해결합니다. 리드 에이전트가 검색을 계획하고, 각 하위 질문을 워커에게 위임하며, 종합합니다. 각 워커는 좁은 질문을 위해 자체 200k 토큰 윈도우를 받습니다. 리드는 원본 논문을 보지 않으며, 워커의 요약만 봅니다.

Anthropic의 프로덕션 Research 시스템은 단일 Opus 4 대비 내부 연구 평가에서 +90.2%를 보고합니다. 같은 블로그는 BrowseComp의 분산(variance) 중 80%가 *토큰 사용량만으로* 설명된다고 지적합니다. 서브 에이전트(Subagent)당 새로운 컨텍스트가 주요 메커니즘입니다.

## 개념

### 패턴

```
                 ┌──────────────┐
                 │   Lead       │  plans, decomposes,
                 │  (Opus 4)    │  synthesizes
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ Worker1 │  │ Worker2 │  │ Worker3 │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
         fresh       fresh        fresh
         context     context      context
```

리드는 원본 자료를 읽지 않습니다. 워커는 리드가 종합하기 전까지 서로의 작업을 보지 않습니다. 각 화살표는 좁은 산출물(Artifact)을 가진 핸드오프(Handoff)입니다.

### 승리하는 이유

세 가지 메커니즘:

1. **서브 에이전트(Subagent)당 새로운 컨텍스트.** "FIPA-ACL 유산"을 탐색하는 워커는 리드가 계획하는 데 사용된 40k 토큰을 운반하지 않습니다. 하나의 질문을 위해 200k 윈도우를 받습니다.
2. **프롬프트를 통한 전문화.** 리드의 프롬프트는 "분해 및 합성"이지, "연구"가 아닙니다. 각 워커의 프롬프트는 좁게 설정되어 있습니다: "X에서 변경된 내용을 찾기." 집중된 프롬프트는 집중된 출력을 생성합니다.
3. **병렬 처리.** 워커는 동시에 실행됩니다. 벽 시계 시간은 `max(worker_times) + plan + synthesis`에 가깝고, `sum(worker_times)`이 아닙니다.

### 엔지니어링 교훈 (Anthropic 2025)

Anthropic의 게시물은 2026년에도 여전히 유효한 몇 가지 프로덕션 교훈을 나열합니다:

- **노력을 쿼리 복잡도에 맞춰 조정하세요.** 단순한 쿼리: 에이전트 1개, 도구 호출 3-10회. 복잡한 쿼리: 에이전트 10개 이상. 리드가 이를 추정해야 하며, 호출자가 아닙니다.
- **먼저 넓게, 그 다음 좁게.** 먼저 넓은 하위 질문으로 분해한 후, 답변이 깊이를 요구한다면 하위 질문당 더 많은 워커를 생성하세요.
- **레인보우 배포.** 에이전트는 장시간 실행되며 상태가 있습니다. 전통적인 블루-그린 방식은 작동하지 않습니다. Anthropic은 레인보우 방식을 사용합니다: 구버전이 소진되는 동안 새 버전을 점진적으로 롤아웃하는 방식입니다.
- **토큰 사용량이 지배적입니다.** 멀티 에이전트는 단일 에이전트의 약 15배 토큰을 사용합니다. 작업 가치가 비용을 정당화할 때만 실행하세요.

### 그래프 네이티브 전환

LangGraph는 원래 고수준 `create_supervisor` 헬퍼가 포함된 `langgraph-supervisor` 라이브러리를 출시했습니다. 2025년 LangChain은 도구 호출을 통해 직접 슈퍼바이저 패턴을 구현하는 것을 권장하도록 변경했습니다. 도구 호출이 *슈퍼바이저가 보는 내용*에 대한 더 많은 제어(컨텍스트 엔지니어링)를 제공하기 때문입니다. 라이브러리는 여전히 작동합니다. 문서에서는 이제 도구 호출 형식을 권장합니다.

### 실패 모드

- **리드가 계획을 환각합니다.** 리드가 실제 질문을 분해하지 않는 하위 질문을 생성하면, 워커는 잘못된 대상에 대해 정밀한 연구를 수행합니다.
- **워커가 과도하게 탐색합니다.** 명시적인 범위 경계가 없으면, 워커는 할당된 하위 질문을 벗어나 합성 단계를 오염시킵니다.
- **합성 충돌.** 두 워커가 모순되는 사실을 반환합니다. 리드는 재질문(라운드 추가)을 하거나 불일치를 명시적으로 기록해야 합니다. 한쪽을 조용히 선택하는 것은 최악의 실패입니다: 사용자는 불일치가 발생했다는 것을 알지 못합니다.

### 슈퍼바이저가 잘못된 경우

- **순차적 작업.** 단계 2가 문자 그대로 단계 1의 출력을 필요로 한다면, 병렬 처리는 아무것도 얻지 못합니다. 파이프라인(CrewAI Sequential, LangGraph 선형 그래프)을 사용하세요.
- **단순 쿼리.** 단일 에이전트(Agent)가 더 빠르고 저렴하게 처리합니다. 워커를 생성하기 전에 리드의 '노력 규모' 체크를 사용하세요.
- **엄격한 결정론.** 감독자(Supervisor)는 LLM이 선택한 위임(Delegation)을 사용합니다. 적응성보다 감사/재생이 더 중요할 때는 정적 그래프가 더 좋습니다.

## 구현하기

`code/main.py`는 `threading`를 사용하여 세 개의 병렬 워커를 감독하는 감독자(Supervisor)를 구현합니다. 리드는 쿼리를 하위 질문으로 분해하고, 워커는 각 하위 질문에서 동시에 실행되며, 리드는 이를 종합합니다. 실제 LLM은 없습니다. 워커는 가져오기 및 요약(fetch-and-summarize)을 시뮬레이션하도록 스크립트되어 있습니다.

주요 구조:

- `Lead.plan(query)`는 쿼리를 3개의 하위 질문으로 분할합니다.
- `Worker.run(sub_q)`는 가짜 요약을 반환합니다(프로덕션에서는 도구 사용 에이전트(Agent)가 될 수 있습니다).
- `Lead.run(query)`는 스레드에서 워커를 시작하고, 합류(join)하며, 종합합니다.

실행:

```
python3 code/main.py
```

출력은 계획, 시작/종료 타임스탬프가 포함된 병렬 워커 추적(Trace), 그리고 최종 종합을 보여줍니다. 벽시계(wall-clock) 시간 절감을 확인할 수 있습니다. 세 개의 0.3초 워커가 0.9초가 아닌 약 0.35초에 실행됩니다.

## 사용하기

`outputs/skill-supervisor-designer.md`는 사용자 쿼리를 받아 감독자 패턴 설계를 생성합니다. 리드 시스템 프롬프트(System Prompt), 워커 역할, 하위 질문 분해 규칙, 종합 템플릿을 포함합니다. 새로운 연구 스타일 에이전트(Agent) 시스템을 구축하기 전에 이 도구를 사용하세요.

## 출시하기

감독자 패턴을 배포하기 전의 체크리스트:

- **모델 페어링.** 리드는 추론 등급 모델(Opus 클래스, `o3` 클래스)을 사용합니다. 워커는 더 빠르고 저렴한 모델(Sonnet, `o4-mini`)을 사용합니다.
- **워커 타임아웃.** 중앙값 실행 시간의 2배를 초과하는 워커는 종료됩니다. 리드는 범위를 좁혀 다시 생성하거나 해당 워커 없이 진행합니다.
- **워커별 토큰 예산(Token Budget).** 하드 리밋(예: 예상 종합 입력의 10배)은 폭주하는 워커가 예산을 초과하는 것을 방지합니다.
- **관측 가능성(Observability).** 리드의 계획, 각 워커의 도구 호출, 종합을 추적(Trace)하세요. 이는 사후 디버깅의 기초가 됩니다.
- **무지개 릴리스(Rainbow rollout).** 상태가 있는 장기 실행 에이전트(Agent)는 핫 스왑이 아닌 점진적인 버전 전환이 필요합니다.

## 연습 문제

1. `code/main.py`을 실행한 후, 리드(lead)가 3명이 아닌 5명의 워커를 생성하도록 수정해 보세요. 벽 시계(wall-clock) 효과를 관찰하세요. 이 데모에서 워커 생성 오버헤드가 병렬 처리의 절감 효과를 초과하는 워커 수는 몇 개일까요?
2. 워커 시간 제한(time-out)을 구현하세요: 0.5초 이상 실행되는 워커는 종료하고, 리드가 남은 결과를 종합하도록 하세요. 워커가 중단되었음을 알기 위해 어떤 관측 가능성(Observability)이 필요할까요?
3. 리드의 종합(synthesis) 단계에 충돌 감지 단계를 추가하세요: 두 워커가 모순되는 답변을 반환하면, 리드는 하나를 선택하지 않고 불일치를 기록합니다. LLM을 호출하지 않고 모순을 감지하려면 어떻게 해야 할까요?
4. Anthropic의 연구 시스템 엔지니어링 관련 게시물을 읽어 보세요. 이 장난감 데모가 프로덕션 환경에서 실행하기 위해 채택해야 할 세 가지 실천 사항을 나열하세요.
5. LangGraph의 `create_supervisor` (레거시)과 새로운 도구 호출(tool-calling) 권장 사항을 비교하세요. 감독자(supervisor)가 무엇을 보는지 더 잘 통제할 수 있는 것은 무엇인가요? Anthropic이 종합 단계에 워커의 원시 컨텍스트가 아닌 하위 답변(sub-answers)만 명시적으로 전달하는 이유는 무엇인가요?

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|------|----------------|------------------------|
| Supervisor | "리드 에이전트" | 계획을 수립하고, 위임하며, 종합하는 오케스트레이터 에이전트입니다. 스스로 작업을 수행하지 않습니다. |
| Worker | "서브 에이전트" | 감독자(supervisor)가 좁은 범위와 자체 컨텍스트 윈도우를 가지고 호출하는 집중된 에이전트입니다. |
| Orchestrator-worker | "감독자 패턴" | 같은 것을 다른 이름으로 부르는 것입니다. 2026년 문헌에서는 두 용어를 모두 사용합니다. |
| Fresh context | "클린 윈도우" | 워커의 컨텍스트는 시스템 프롬프트와 할당된 질문에서 시작하며, 리드의 히스토리를 포함하지 않습니다. |
| Rainbow deployment | "점진적 롤아웃" | 장시간 실행되는 상태 유지(stateful) 에이전트는 블루-그린(blue-green) 방식이 아닌, 버전화된 드레인 및 교체(drain-and-replace)가 필요합니다. |
| Token dominance | "컨텍스트가 변수다" | Anthropic에 따르면, 연구 평가의 변동성(variance) 중 80%는 모델 선택이 아닌 사용된 총 토큰 수에서 기인합니다. |
| Scale effort | "에이전트 수를 복잡도에 맞추기" | 리드가 쿼리의 난이도를 추정하고, 이에 따라 1명 대 10명 이상의 워커를 생성합니다. |
| Synthesis conflict | "워커 간 불일치" | 두 워커가 모순되는 사실을 반환하면, 리드는 조용히 하나를 선택하지 않고 불일치를 드러내야 합니다. |
