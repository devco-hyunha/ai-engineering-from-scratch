# 멀티 에이전트 프리미티브 모델

> 네 가지 프리미티브, 그 이상은 없습니다 — 에이전트, 핸드오프, 공유 상태, 오케스트레이터 — 이 네 가지가 4차원 설계 공간을 구성하며, 2026년 출시 예정인 주요 멀티 에이전트 프레임워크(AutoGen, LangGraph, CrewAI, OpenAI Agents SDK, Microsoft Agent Framework)는 이 공간 내의 점들입니다. 이 강의에서는 이 프리미티브를 처음부터 구축하고, 네 가지 프리미티브를 모두 사용하는 토이 시스템을 실행한 후, 모든 주요 프레임워크를 동일한 축 위에 매핑하여 새로운 릴리스를 한 단락으로 읽을 수 있도록 합니다.

**유형:** Learn
**언어:** Python (stdlib)
**선수 요건:** 14단계 (에이전트 엔지니어링), 16단계 · 01강 (왜 멀티 에이전트인가)
**시간:** 약 60분

## 문제점

6개월마다 새로운 멀티 에이전트 프레임워크가 출시됩니다. 2023년에는 AutoGen, 2024년에는 CrewAI, LangGraph 및 OpenAI Swarm, 2025년 4월에는 Google ADK, 2026년 2월에는 Microsoft Agent Framework RC가 나왔습니다. 각 보도자료는 "올바른 추상화"라고 주장합니다.

이들을 하나씩 학습하면 번아웃될 것입니다. API가 서로 다르고, 문서들은 "에이전트"의 정의에 대해 의견이 갈립니다. 한 프레임워크는 공유 메모리를 "블랙보드"라고 부르고, 다른 프레임워크는 "메시지 풀"이라고 부르며, 세 번째는 "StateGraph"라고 부릅니다. 이 분야가 단순히 유행만 반복하고 있다는 의심이 생깁니다.

그렇지 않습니다. 마케팅 이면에는 네 가지 프리미티브가 안정적으로 존재합니다. 이들을 한 번만 학습하면 모든 새로운 프레임워크를 한 단락으로 읽을 수 있습니다.

## 개념

### 네 가지 프리미티브

1. **에이전트** — 시스템 프롬프트(System Prompt)와 도구 목록의 조합. 상태 비저장(Stateless)이며, 모든 실행은 시스템 프롬프트와 현재 메시지 히스토리에서 시작합니다.
2. **핸드오프(Handoff)** — 한 에이전트에서 다른 에이전트로 제어권을 구조적으로 전달하는 것. 기계적으로는 새로운 에이전트를 반환하는 도구 호출이나 조건을 따르는 그래프 엣지입니다.
3. **공유 상태** — 두 개 이상의 에이전트가 읽을 수 있는(때로는 쓸 수 있는) 모든 데이터 구조. 메시지 풀, 블랙보드, 키-값 저장소, 벡터 메모리 등.
4. **오케스트레이터(Orchestrator)** — 누가 다음에 말할지 결정하는 주체. 옵션: 명시적 그래프(결정론적), LLM 화자 선택기(소프트), 마지막 화자의 핸드오프 호출(OpenAI Swarm), 큐에 대한 스케줄러(스웜 아키텍처).

이것이 전체 설계 공간입니다. 모든 프레임워크는 각 축에 대해 기본값을 선택하며, 나머지는 표면 구문(surface syntax)입니다.

### 2026년 모든 프레임워크가 이 설계 공간에 매핑되는 방식

| 프레임워크 | 에이전트 | 핸드오프 | 공유 상태 | 오케스트레이터 |
|-----------|-------|---------|--------------|--------------|
| OpenAI Swarm / Agents SDK | `Agent(instructions, tools)` | 도구가 Agent 반환 | 호출자의 문제 | LLM의 다음 핸드오프 호출 |
| AutoGen v0.4 / AG2 | `ConversableAgent` | GroupChat의 화자 선택기 | 메시지 풀 | 선택 함수 (LLM 또는 라운드 로빈) |
| CrewAI | `Agent(role, goal, backstory)` | `Process.Sequential / Hierarchical` | Task 출력 체이닝 | 관리자 LLM 또는 정적 순서 |
| LangGraph | 노드 함수 | 그래프 엣지 + 조건 | `StateGraph` 리듀서 | 그래프, 결정론적 |
| Microsoft Agent Framework | 에이전트 + 오케스트레이션 패턴 | 패턴별 | 스레드 / 컨텍스트 | 패턴별 |
| Google ADK | 에이전트 + A2A 카드 | A2A 작업 | A2A 아티팩트 | 호스트가 결정 |

표면적인 차이는 커 보이지만, 그 밑에는 동일한 네 가지 조절 변수(knobs)가 있습니다.

### 이것이 중요한 이유

기본 구성 요소(primitives)를 이해하면, 프레임워크 비교는 짧은 체크리스트가 됩니다:

- 오케스트레이터가 라우팅을 LLM에 맡기는가(Swarm) 아니면 코드에 라우팅을 고정하는가(LangGraph)?
- 공유 상태가 전체 히스토리(GroupChat)인가 아니면 투영된 상태(StateGraph 리듀서)인가?
- 에이전트가 서로의 프롬프트를 수정할 수 있는가(CrewAI 관리자) 아니면 단지 핸드오프만 수행하는가(Swarm)?

이 세 가지 질문이 주어진 문제에 어떤 프레임워크가 적합한지 80%를 결정합니다. "최고의 멀티 에이전트 프레임워크"를 쇼핑하는 것을 멈추고, 실제로 중요하게 생각하는 축에 대해 설계하기 시작합니다.

### 상태 비저장(Stateless) 통찰

공유 상태를 제외한 모든 기본 구성 요소는 상태 비저장입니다. 에이전트는 (프롬프트, 도구)의 함수입니다. 핸드오프는 함수 호출입니다. 오케스트레이터는 스케줄러입니다. **시스템에서 유일한 상태ful한 요소는 공유 상태입니다.** 모든 흥미로운 버그는 여기에 있습니다: 메모리 오염(15강), 메시지 순서, 버전 관리, 쓰기 경쟁(write contention).

공유 상태를 숨기는 프레임워크(Swarm)는 문제를 호출자에게 넘깁니다. 공유 상태를 중앙화하는 프레임워크(LangGraph 체크포인트, AutoGen 풀)는 이를 검사 가능하게 만들지만, 조정 비용을 공유 상태 구현으로 전가합니다.

### 단일 프리미티브의 구조

#### 에이전트(Agent)

```
Agent = (system_prompt, tools, model, optional_name)
```

메모리 없음. 상태 없음. 동일한 시스템 프롬프트와 도구를 가진 두 에이전트는 서로 교체 가능합니다. 에이전트별 상태로 보이는 모든 것은 실제로 공유 상태나 핸드오프 프로토콜에 있습니다.

#### 핸드오프(Handoff)

```
Handoff = (from_agent, to_agent, reason, payload)
```

세 가지 구현 방식이 지배적입니다:

- **함수 반환** — 도구가 다음 에이전트를 반환합니다. 이는 OpenAI Swarm 패턴입니다. 에이전트는 도구 스키마에 라우팅 정보를 포함합니다.
- **그래프 엣지** — LangGraph. 엣지는 선언적입니다. LLM이 값을 생성하면 조건이 다음 노드를 선택합니다.
- **화자 선택** — AutoGen GroupChat. 선택자 함수(때로는 LLM 호출 자체)가 풀을 읽고 다음에 말할 주체를 선택합니다.

#### 공유 상태

```
SharedState = { messages: [], artifacts: {}, context: {} }
```

최소한 메시지 목록이 필요합니다. 더 많은 것이 포함되는 경우가 많습니다: 구조화된 산출물(CrewAI Task 출력), 타입이 지정된 컨텍스트(LangGraph 리듀서), 외부 메모리(MCP, 벡터 DB).

두 가지 토폴로지: **풀(pool) 전체** (모든 에이전트가 모든 메시지를 봄)과 **투영(projected)** (에이전트가 역할 범위 내의 뷰를 봄). 풀 전체는 단순하지만 확장성이 떨어집니다. 투영된 풀은 확장되지만 사전에 스키마 설계가 필요합니다.

#### 오케스트레이터(Orchestrator)

```
Orchestrator = ({state, last_speaker}) -> next_agent
```

네 가지 유형이 있습니다:

- **정적(Static)** — 그래프가 빌드 타임에 고정됩니다(LangGraph 결정적, CrewAI Sequential).
- **LLM 선택** — LLM이 풀을 읽고 다음 화자를 선택합니다(AutoGen, CrewAI Hierarchical).
- **핸드오프 주도** — 현재 에이전트가 핸드오프 도구를 호출하여 결정합니다(Swarm).
- **큐 주도** — 워커가 공유 큐에서 가져오며, 명시적인 다음 화자가 없습니다(swarm 아키텍처, Matrix).

### 프레임워크 간에 달라지는 것

프리미티브가 고정되면, 남은 설계 결정은 다음과 같습니다:

- **메모리 전략** — 일시적 대 내구성 있는 체크포인팅(LangGraph checkpointer).
- **안전 경계** — 누가 핸드오프를 승인할 수 있는가(인간 개입 루프).
- **비용 회계** — 에이전트별 토큰 예산.
- **관측 가능성** — 핸드오프 추적, 재생을 위한 상태 저장.

모두 프리미티브 위에 구현 가능합니다. 그중 어느 것도 새로운 프리미티브가 아닙니다.

## 구현하기

`code/main.py`는 표준 라이브러리 Python으로 약 150줄에 네 가지 기본 요소를 구현합니다. 실제 LLM은 없으며, 각 에이전트(Agent)는 스크립트된 정책이므로 초점은 조정 구조에 맞춰집니다.

파일에서 내보내는 항목은 다음과 같습니다:

- `Agent` — 이름, 시스템 프롬프트(System Prompt), 도구, 정책 함수를 포함하는 데이터 클래스입니다.
- `Handoff` — 새 에이전트(Agent)를 반환하는 함수입니다.
- `SharedState` — 스레드 안전 메시지 풀입니다.
- `Orchestrator` — 세 가지 변형: `StaticOrchestrator`, `HandoffOrchestrator`, `LLMSelectorOrchestrator` (시뮬레이션됨).

데모는 동일한 3-에이전트 파이프라인(연구 → 작성 → 검토)을 세 가지 오케스트레이터(Orchestration) 유형 모두를 통해 실행하며, 마지막에 메시지 풀을 출력합니다. 출력은 *누가 다음을 선택하는가*에서만 차이가 나며, 에이전트(Agent)와 공유 상태는 모든 실행에서 동일하다는 것을 확인할 수 있습니다.

실행해 보세요:

```
python3 code/main.py
```

예상 출력: 패턴별로 하나씩 세 가지 오케스트레이터(Orchestration) 실행이 나옵니다. 각각 최종 메시지 풀을 출력합니다. 핸드오프(Handoff) 기반 실행은 연구자가 조기 완료로 판단할 경우 더 적은 수의 에이전트(Agent)에 도달합니다. 이는 LLM 라우팅의 트레이드오프를 축소한 것입니다.

## 사용하기

`outputs/skill-primitive-mapper.md`는 다중 에이전트 코드베이스나 프레임워크 문서를 읽고 네 가지 기본 요소 매핑을 반환하는 스킬입니다. 문서를 깊이 읽기 전에 한 단락의 이해를 얻기 위해 새로운 프레임워크 릴리스에 실행해 보세요.

## 연습 문제

1. `code/main.py`를 서로 다른 에이전트 정책으로 세 번 실행하세요. 오케스트레이터(Orchestration) 선택이 어떤 에이전트(Agent)가 실행되는지 어떻게 변화시키는지 관찰하세요.
2. 네 번째 오케스트레이터(Orchestration) 유형을 구현하세요: 에이전트(Agent)가 작업을 위해 공유 상태를 폴링하는 큐 기반 오케스트레이터입니다. 어떤 데드락이 발생할 수 있으며, 이를 어떻게 감지하나요?
3. LangGraph 퀵스타트(https://docs.langchain.com/oss/python/langgraph/workflows-agents)를 가져와 네 가지 기본 요소로 다시 작성하세요. LangGraph의 추상화 중 어떤 것이 1:1로 매핑되고, 어떤 것이 편의 래퍼인가요?
4. OpenAI Swarm cookbook (https://developers.openai.com/cookbook/examples/orchestrating_agents)을 읽어 보세요. Swarm이 네 가지 프리미티브 중 어느 것을 가장 인체공학적으로 만드는지, 그리고 어느 것을 호출자에게 넘기는지 식별해 보세요.
5. 이 표에서 공유 상태를 완전히 숨기는 프레임워크를 하나 찾아 보세요. 에이전트가 히스토리를 다시 읽지 않고 핸드오프(handoff)를 통해 조정해야 할 때 무엇이 깨지는지 설명해 보세요.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| 에이전트(Agent) | "도구를 가진 LLM" | `(system_prompt, tools, model)` 삼중 구조입니다. 상태 비저장입니다. |
| 핸드오프(Handoff) | "제어 전달" | 다음 에이전트와 선택적 페이로드를 지정하는 구조화된 호출입니다. 세 가지 구현 방식: 함수 반환, 그래프 엣지, 화자 선택. |
| 공유 상태 | "메모리" / "컨텍스트" | 멀티 에이전트 시스템의 유일한 상태 유지 부분입니다. 메시지 풀(pool) 또는 블랙보드. |
| 오케스트레이터(Orchestrator) | "조정자" | 누가 다음에 실행되는지 결정하는 주체입니다. 정적 그래프, LLM 선택기, 핸드오프 주도형, 또는 큐 주도형. |
| 프리미티브(Primitive) | "추상화" | 모든 프레임워크가 매개변수화하는 네 가지 축 중 하나입니다. 프레임워크 기능이 아닙니다. |
| 메시지 풀(pool) | "공유 채팅 히스토리" | 전체 히스토리 공유 상태. 추론하기 쉽지만 확장성이 좋지 않습니다. |
| 투사된 상태 | "스코프된 뷰" | 공유 상태에 대한 역할별 뷰입니다. 확장성이 좋으며 스키마 설계가 필요합니다. |
| 화자 선택 | "누가 다음에 말하는가" | 함수(종종 LLM)가 그룹에서 다음 에이전트를 선택하는 오케스트레이터 패턴입니다. |
