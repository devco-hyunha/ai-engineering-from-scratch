# 프로덕션 확장 — 큐, 체크포인트, 내구성

> 멀티 에이전트 시스템을 수천 개의 동시 실행으로 확장하려면 **내구성 있는 실행(Durable Execution)**이 필요합니다. 작업 큐와 체크포인트를 활용하면, 리스 처리, 멱등성 있는 사이드 이펙트, 결정적 재생이 갖춰진 상태에서 크래시가 발생하더라도 모든 워커가 모든 실행을 재개할 수 있습니다. LangGraph 런타임은 이를 잘 보여주는 참고 사례입니다. 각 슈퍼 스텝 후 `thread_id`을 키로 사용하여 체크포인트를 기록합니다(기본값은 Postgres). 워커가 크래시하면 리스가 해제되고 다른 워커가 실행을 재개합니다. 에이전트는 인간 입력을 기다리며 무한히 대기할 수 있습니다. **MegaAgent**(arXiv:2408.09955)는 에이전트별 생산자-소비자 큐를 Idle / Processing / Response의 세 가지 상태와 두 계층의 조정(그룹 내 채팅 + 그룹 간 관리자 채팅)으로 구현했습니다. LLM 스트리밍에서는 **Fiber/async**가 스레드별 작업 처리보다 우수합니다. 스레드는 토큰을 기다리는 동안 99%의 시간을 유휴 상태로 보내는 반면, Fiber는 I/O에서 협력적으로 양보(yield)합니다. 반론으로, Ashpreet Bedi의 "Scaling Agentic Software"는 부하가 이를 증명하기 전까지 **FastAPI + Postgres + 그 외 아무것도 없는** 단순한 아키텍처가 예상보다 더 멀리 간다고 주장합니다. 이 강의에서는 내구성 있는 체크포인트 로그, 상태 전이를 포함한 에이전트별 작업 큐, async 대 스레드 데모를 구축하고, 실용적인 "단순하게 시작하라"는 규칙을 마무리합니다.

**유형:** Learn + Build
**언어:** Python (stdlib, `asyncio`, `sqlite3`)
**선수 요건:** 16단계 · 09강 (병렬 스웜 네트워크), 16단계 · 13강 (공유 메모리)
**시간:** 약 75분

## 문제점

프로토타입 멀티 에이전트 시스템은 한 노트북에서 세 개의 에이전트를 메모리 내 이벤트 루프에서 실행합니다. 프로덕션으로 전환하면:

- 에이전트가 몇 시간 동안 실행되는 경우가 있습니다(긴 연구, 인간 개입 루프(HITL) 대기).
- 워커 프로세스가 크래시합니다. 재시작하면 상태가 손실됩니다.
- 피크 부하가 평균의 10배이며, 수평 확장이 필요합니다.
- 사용자가 에이전트 실행 단위로 과금하므로, 과금을 위해 정확히 한 번(exactly-once)의 시맨틱이 필요합니다.

메모리 내 이벤트 루프는 이 중 어느 것도 처리하지 못합니다. 그 아래에 내구성 있는 실행 레이어가 필요합니다. 2026년 표준적인 선택지는 다음과 같습니다:

1. 체크포인트가 있는 워크플로우 엔진(Temporal, LangGraph 런타임).
2. 상태 저장소가 있는 메시지 큐(Postgres + SQS/RabbitMQ).
3. 액터 모델 프레임워크 (MegaAgent의 에이전트별 생산자-소비자 패턴).
4. 직접 만든 FastAPI + Postgres (Bedi의 주장).

이 강의에서는 각각의 미니멀한 구현을 만들어 보세요.

## 개념

### 내구성 있는 실행(Durable Execution), 패턴

내구성 있는 실행(Durable Execution) 엔진은 각 "단계" (LangGraph의 용어로 super-step) 후에 전체 프로그램 상태를 저장합니다. 충돌 시:

```
worker crashes mid-step
  -> lease timeout
  -> another worker picks up the thread_id
  -> resumes from last checkpoint
  -> no duplicate side effects
```

이것이 작동하기 위한 요구 사항:

- **직렬화 가능한 상태.** 모든 에이전트 상태는 저장 가능해야 합니다. 라이브 데이터베이스 연결을 가진 함수 클로저는 살아남지 못합니다.
- **결정적 재개.** 동일한 상태와 동일한 입력이 주어지면, 에이전트는 동일한 액션을 생성합니다 (또는 LLM 호출에 대해 외부 결정적 오라클에 의존합니다).
- **멱등성 있는 사이드 이펙트.** 외부 호출 (도구 호출, 결제)은 멱등성(Idempotency)을 가져야 하거나 중복 제거 키를 사용해야 합니다.

LangGraph는 각 super-step 후 체크포인트(Checkpoint)를 기록합니다; Temporal은 각 activity 후 기록합니다; Restate는 이벤트 소스 저널을 사용합니다. 세 가지 모두 동일한 패턴을 구현합니다.

### 단계별 체크포인트(Checkpoint) 런타임

LangGraph의 런타임이 실전 예제입니다: 각 에이전트는 `thread_id`를 가지며; 상태는 타입이 지정된 dict입니다; 각 super-step은 checkpoints 테이블에 행을 기록합니다. 재개 시, 런타임은 처음부터가 아니라 마지막 체크포인트(Checkpoint)부터 재생합니다. 에이전트는 `interrupt()` 인간 입력을 기다릴 수 있습니다; 런타임은 이를 저장하고 워커를 해제합니다. 입력이 도착하면, 어떤 워커든 재개할 수 있습니다.

이것은 2026년 4월의 참고 생산 디자인입니다.

### MegaAgent의 에이전트별 큐

arXiv:2408.09955는 규모 실험을 설명합니다: 하나의 클러스터에서 수천 개의 동시 에이전트. 아키텍처:

```
agent i:
  state ∈ {Idle, Processing, Response}
  in_queue   <- messages addressed to agent i
  out_queue  -> replies + side effects

coordinators:
  intra-group chat  (agents in the same group)
  inter-group admin chat  (high-level routing)
```

2층 조정은 그룹 내 대화가 밀집하게 일어나도록 하면서 그룹 간은 희소하게 유지합니다 — 수천 개의 에이전트에서 비용을 선형으로 유지하기 위해 사용되는 패턴입니다.

### 비동기 vs 작업별 스레드

LLM 호출은 I/O 바운드입니다. 다음 토큰을 기다리는 스레드는 99%의 시간 동안 유휴 상태입니다. 스레드는 각각 약 1MB RAM을 소모합니다; 10,000개의 동시 호출에서는 스택만으로도 10GB가 됩니다.

파이버(Python `asyncio`, Go 고루틴, Rust `tokio`)는 I/O에서 협력적으로 양보합니다. 10,000번의 호출이 프로세스 내에서 여유롭게 처리됩니다. LLM 에이전트 규모에서는 비동기 처리는 최적화가 아니라 아키텍처입니다.

예외: CPU 바운드 후처리(임베딩, 토크나이저 트릭)는 여전히 스레드나 프로세스를 필요로 합니다. I/O 계층과 CPU 계층을 분리하세요.

### Bedi의 반론

"Scaling Agentic Software" (Ashpreet Bedi, 2026)는 대부분의 팀이 부하를 측정하기 전에 과잉 설계한다고 주장합니다. 실용적인 기본값은 다음과 같습니다:

- FastAPI + Postgres.
- 각 에이전트 실행은 한 행이며, 낙관적 동시성을 통해 상태가 제자리에서 업데이트됩니다.
- `pg_notify` 또는 간단한 Celery 워커를 통해 백그라운드 작업을 처리합니다.
- 재시도 정책은 애플리케이션 코드에 구현합니다.

관리 가능한 작업에서 약 100개의 동시 에이전트 실행 이하의 부하라면, 이것이 대개 필요한 전부입니다. 실패가 측정될 때 업그레이드하세요.

규칙: 단순한 아키텍처가 해결할 수 없는 구체적인 문제에 직면했을 때 내구성 있는 실행(Durable Execution) 프레임워크를 채택하세요. premature adoption은 효과가 없는 의식(ceremonies)에 시간을 낭비합니다.

### 정확히 한 번(exactly-once) 시맨틱

유료 에이전트 실행의 경우, "정확히 한 번 효과(exactly-once effective)"(최소 한 번 전달(at-least-once delivery) + 멱등성 있는 소비자)가 필요합니다. 엔지니어링 조치들은 다음과 같습니다:

- **실행별 중복 제거 키(Dedup key).** 모든 사이드 이펙트 호출에 포함하세요.
- **아웃박스 패턴(Outbox pattern).** 사이드 이펙트는 먼저 테이블에 기록한 후, 별도의 프로세스가 이를 실행합니다. 두 단계 모두 멱등적이어야 합니다.
- **보상 트랜잭션(Compensating transactions).** 사이드 이펙트가 성공했지만 추적 기록이 실패한 경우, 보상 조치를 예약하세요.

이것들은 LLM 특유의 패턴이 아니라 데이터베이스 엔지니어링 패턴입니다. LLM의 부담은 LLM 호출이 느리다는 점뿐이며, 나머지는 표준 분산 시스템입니다.

### 레인보우 배포(Rainbow deployment)

Anthropic의 멀티 에이전트 연구 시스템은 "레인보우 배포"를 사용합니다. 에이전트 런타임의 여러 버전이 동시에 실행되어, 코드 배포 시마다 장시간 실행되는 에이전트를 종료하지 않아도 됩니다. 트래픽의 일부에 새 버전을 카나리 릴리스(Canary Release)로 배포하고, 에이전트가 완료되면 구버전을 종료합니다.

이것은 장시간 실행되는 상태 유지 시스템에 대한 표준입니다. 2026년 적응은 에이전트가 수 시간 동안 살아남을 수 있으므로, 배포 주기가 이를 수용해야 한다는 것입니다.

### 표준 프로덕션 체크리스트

- 내구성 있는 상태 (체크포인트, 스냅샷, 또는 아웃박스 + 재생 가능한 로그).
- 멱등성 있는 사이드 이펙트.
- LLM 호출을 위한 비동기 I/O 레이어.
- 중복 제거를 통한 최소 한 번(at-least-once) 전달.
- 상태 유지 워크로드를 위한 무지개/카나리 배포.
- 관측 가능성: 에이전트별 추적, 슈퍼 스텝 감사, 재시도 카운터.

## 구현하기

`code/main.py`는 다음을 구현합니다:

- `CheckpointStore` — 스레드 ID 키를 사용하는 SQLite 기반 체크포인트 로그. 각 슈퍼 스텝이 행을 추가합니다.
- `run_with_checkpoint(agent, thread_id)` — 실행 중 크래시를 시뮬레이션합니다. 두 번째 워커가 마지막 체크포인트에서 재개합니다.
- `AgentQueue` — 작은 작업 큐를 가진 에이전트별 Idle / Processing / Response 상태 머신.
- `demo_async_vs_threads()` — asyncio와 스레드를 통해 500개의 동시 "LLM 호출"을 시뮬레이션하며, 벽시계 시간과 피크 메모리(근사치)를 보고합니다.

실행:

```
python3 code/main.py
```

예상 출력: 시뮬레이션된 크래시 후 체크포인트 재개가 성공합니다. 비동기 버전은 1초 미만으로 500개의 동시 호출을 처리합니다. 스레드 버전은 몇 초가 걸리며, 동시 단위당 메모리 사용량이 몇 배 더 높습니다.

## 출시하기

표준 프로덕션 강화:

- **단순하게 시작하세요 (Bedi의 규칙).** 실패를 측정할 때까지 FastAPI + Postgres를 사용하세요.
- **최적화하기 전에 모든 것을 계측하세요.** 실행별 지연 히스토그램, 스텝별 시간, 재시도 횟수, 실패 분류.
- **사이드 이펙트를 위한 아웃박스 패턴.** 특히 결제 및 외부 API 호출.
- **무지개 배포.** 배포 중에 진행 중인 에이전트 실행을 절대 종료하지 마세요.
- **특정 문제에 직면했을 때 내구성 있는 실행 엔진(Temporal / LangGraph / Restate)을 채택하세요:** 수 시간 동안의 인간 개입 루프(HITL) 대기, 지역 간 조정, 복잡한 재시도/보상 정책.
- **I/O 계층에는 비동기 처리를 사용하세요.** CPU 바운드 후처리에는 스레드만 사용하세요.

## 연습 문제

1. `code/main.py`을 실행하세요. 체크포인트 재개가 작동하는지 확인하고, 비동기와 스레드 동시성 차이를 측정해 보세요.
2. **아웃박스(outbox)** 테이블을 구현하세요. 모든 도구 호출은 먼저 아웃박스에 기록한 후, 별도의 고루틴/태스크가 실행하도록 하세요. 도구 호출을 두 번 실행하여 멱등성(Idempotency)을 검증해 보세요.
3. **레인보우 배포(rainbow deploy)**를 시뮬레이션하세요. 두 개의 동시 실행 버전이 존재하며, 새로운 thread_id의 절반을 각각으로 라우팅합니다. 오래된 버전에서 진행 중인 스레드가 중단되지 않는지 확인하세요.
4. LangGraph의 런타임 문서(아래 링크 참조)를 읽어보세요. 런타임의 어떤 기능들이 수제 FastAPI + Postgres 버전에서 복제하는 데 가장 오래 걸리는지 식별하세요. 이것이 채택해야 하는 이유인가요, 아니면 미룰 수 있나요?
5. MegaAgent (arXiv:2408.09955)의 3장을 읽어보세요. 두 계층의 조정(그룹 내 + 그룹 간 관리자 채팅)이 명시되어 있습니다. 이를 두 개의 큐 계열을 가진 메시지 큐로 매핑하는 방법을 스케치해 보세요.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| 내구성 있는 실행(Durable Execution) | "프로그램 상태를 영속화" | 엔진이 각 슈퍼 스텝(super-step) 후 상태를 기록합니다. 크래시 복구는 결정적입니다. |
| 슈퍼 스텝(Super-step) | "트랜잭션 경계" | 체크포인트 사이의 작업 단위입니다. LangGraph 용어입니다. |
| thread_id | "에이전트 실행 식별자" | 체크포인트와 재개 로직을 바인딩하는 키입니다. |
| 멱등성(Idempotency) | "재시도해도 안전" | 사이드 이펙트를 반복해도 한 번 시도한 것과 동일한 결과가 나옵니다. |
| 아웃박스 패턴(Outbox pattern) | "사이드 이펙트 분리" | 의도를 테이블에 기록합니다. 별도의 실행기가 수행하고 완료 표시를 합니다. |
| 최소 한 번 전달(At-least-once delivery) | "중복 가능성" | 메시지 큐의 의미론입니다. 중복 제거 키가 소비자를 한 번만 효과적으로 처리하게 만듭니다. |
| 레인보우 배포(Rainbow deploy) | "버전 겹침" | 장기 실행 워크로드 동안 여러 런타임 버전이 동시에 존재합니다. |
| 비동기 파이버(Async fiber) | "협조적 양보" | 사용자 모드 동시성입니다. I/O 바운드 부하에서는 스레드보다 저렴합니다. |
| 체크포인트(Checkpoint) | "상태 스냅샷" | 슈퍼 스텝 경계에서의 직렬화된 상태입니다. 재개의 키입니다. |
