다중 에이전트 프로덕션 배포 계획을 고려하여, 내구성 있는 실행(Durable Execution) 기반 구조를 추천합니다.

다음 내용을 생성합니다:

1. **부하 프로필.** 동시 에이전트 실행 수 (p50, p99). 실행당 지속 시간 (초 단위에서 시간 단위). 인간 개입 루프(Human-in-the-Loop (HITL)) 대기 시간이 필요한 실행의 비율. 배포 빈도.
2. **상태 프로필.** 실행당 상태 크기 (KB 단위에서 MB 단위). 유지 요구 사항 (체크포인트 이력 초 단위, 또는 전체 감사 로그). 결정성: 실행을 체크포인트에서 결정적으로 재생할 수 있는지, 아니면 로그에서만 재생할 수 있는지 여부.
3. **사이드 이펙트 프로필.** 정확히 한 번(exactly-once) 실행이 필요한 사이드 이펙트 (결제, 외부 API, 이메일)는 무엇입니까? 최소 한 번(at-least-once) 실행을 허용할 수 있는 사이드 이펙트 (순수한 도구 읽기)는 무엇입니까? 정확히 한 번(exactly-once) 실행을 위해 아웃박스 패턴이 필요합니까?
4. **추천 등급.**
   - 1등급 (Bedi의 규칙): FastAPI + Postgres. 동시 실행이 약 100개 미만이고, 지속 시간이 1시간 미만이며, 단순한 재시도인 경우.
   - 2등급: LangGraph 런타임 또는 Temporal. 1시간 단위 실행, 인터럽트/재개, 구조화된 재시도인 경우.
   - 3등급: 아웃박스 + 이벤트 소싱을 포함한 커스텀. 특수한 요구 사항, 높은 처리량, 엄격한 감사인 경우.
5. **배포 모델.** 단일 버전입니까, 아니면 무지개(canary) 배포입니까? 장시간 지속되는 상태 유지 작업 부하에는 무지개(canary) 배포가 필요합니다.
6. **비동기 / 스레드 경계.** 어떤 부분이 비동기 (LLM 호출, 도구 I/O)이고, 어떤 부분이 스레드/프로세스 (CPU 바운드 후처리, 임베딩)입니까?
7. **관측 가능성(Observability).** 실행별 추적, 슈퍼 스텝 감사, 재시도 카운터. 추적 저장소 (체크포인트 저장소와 분리됨).

거부 조건:

- 10개 동시 실행 프로토타입에 Temporal을 추천하는 것. 의식 비용이 가치보다 큽니다.
- 작업당 스레드(thread-per-job) LLM 호출 아키텍처. I/O 바운드 + 스레드당 1MB는 확장되지 않습니다.
- 유료 사이드 이펙트에 대해 아웃박스 패턴이 없는 설계. 중복 청구는 비용이 많이 듭니다.
- 다중 시간 단위 에이전트 실행에 대한 단일 버전 배포. 코드 푸시마다 사용자가 상태를 잃습니다.

거절 규칙:

- 로드가 알려지지 않고 테스트되지 않은 경우, Tier 1을 권장하고 부하 테스트를 수행하세요. premature optimization은 시간을 낭비합니다.
- 사용자가 토큰화 / 블록체인 지속성 시스템을 원하는 경우, durable-execution 엔진은 일반적으로 이를 해결하지 못한다고 설명하세요 (자체 이벤트 소싱을 작성해야 함); 토큰화된 흐름에 대해 법적 검토를 권장하세요.
- 팀에 on-call 엔지니어가 없는 경우, Temporal / LangGraph 런타임 유지보수가 과소 공급된 상태입니다; on-call 인력이 충원될 때까지 Tier 1을 권장하세요.

출력: 두 페이지 분량의 브리프. 한 문장의 권장 사항으로 시작하세요 ("현재 로드에는 Tier 1 (FastAPI + Postgres + outbox)을 권장하며, p99 실행 시간이 10분을 초과하거나 동시 실행이 200을 초과하면 LangGraph 런타임으로 에스컬레이션하세요."), 그 다음 위에 언급된 7개 섹션을 포함하세요. 90일 업그레이드 경로로 마무리하세요: 모니터링할 지표, 에스컬레이션 임계값, runbook 개요.
