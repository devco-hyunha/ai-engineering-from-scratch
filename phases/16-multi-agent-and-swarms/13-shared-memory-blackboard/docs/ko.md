# 공유 메모리와 블랙보드 패턴

> 2026년 다중 에이전트 시스템에는 두 가지 접근 방식이 공존합니다: **메시지 풀** (AutoGen GroupChat나 MetaGPT처럼 모든 에이전트가 서로의 메시지를 보는 방식)과 **구독이 있는 블랙보드** (Context-Aware MCP나 Matrix 프레임워크처럼 에이전트가 관련 이벤트에 구독하는 방식)입니다. 둘 다 다중 에이전트 시스템의 유일한 상태 유지 부분이며, 이는 흥미로운 버그가 발생하는 지점임을 의미합니다. 참고할 만한 실패 모드인 **메모리 오염**은 한 에이전트가 "사실"을 환각(Hallucination)으로 생성하고, 다른 에이전트들이 이를 검증된 것으로 취급하며, 즉각적인 충돌보다 디버깅이 훨씬 어려운 방식으로 점진적으로 정확도가 저하되는 현상입니다. 이 강의에서는 stdlib로 두 구조를 구축하고, 오염 공격을 주입하며, 실제 프로덕션 환경에서 효과가 있는 세 가지 완화 전략을 보여줍니다.

**유형:** Learn + Build
**언어:** Python (stdlib, `threading`)
**선수 요건:** 16단계 · 04강 (원시 모델), 16단계 · 09강 (병렬 스웜 네트워크)
**시간:** 약 75분

## 문제점

다중 에이전트 시스템은 에이전트들이 사실을 공유할 장소를 필요로 합니다. 문자 그대로의 선택지는 "모든 것을 메시지로 전달하는 것"이지만, 이는 추가적인 복사로 공유 상태를 재발명하는 셈입니다. 다른 선택지는 "모두에게 전역 로그를 제공하는 것"이지만, 전역 로그는 무한히 증가하고 쉽게 오염됩니다. 세 번째 선택지는 "에이전트별로 뷰를 투사하는 것"인데, 확장성은 좋지만 스키마가 복잡합니다.

에이전트 중 하나가 환각(Hallucination)을 일으켜 이를 공유 상태에 기록하면, 그 상태를 읽는 모든 후속 에이전트가 환각을 사실로 채택합니다. 사람이 알아차릴 때쯤이면 추론 체인은 5단계 깊이이고, 근본 원인은 세 번째로 기록된 메시지입니다. 다중 에이전트 시스템의 정확도 저하를 디버깅하는 것은 충돌을 디버깅하는 것보다 어렵습니다.

이것이 메모리 오염입니다. MAST 분류 체계(Cemri et al., arXiv:2503.13657)에서 두 번째로 많이 문서화된 실패 계열이며, 구조적인 문제입니다: 출처 추적(provenance)과 기록 불가능한 검증자(unwritable verifier)가 없는 모든 공유 메모리 설계는 결국 이 문제를 드러내게 됩니다.

## 개념

### 두 가지 주요 토폴로지

**전체 메시지 풀.** 모든 에이전트가 모든 메시지를 읽습니다. AutoGen GroupChat과 MetaGPT가 이 방식을 사용합니다. 단순하고 투명하며 검사하기 쉽지만, 각 에이전트의 컨텍스트가 다른 에이전트의 작업으로 채워지기 때문에 약 10개 이상의 에이전트로 확장되지 않습니다.

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

**구독 기능이 있는 블랙보드.** 에이전트(Agent)는 관심 있는 주제를 선언하며, 하위 구조는 관련 있는 메시지만 라우팅합니다. CA-MCP (arXiv:2601.11595)와 Matrix 분산 프레임워크 (arXiv:2511.21686)는 이 방식을 사용합니다. 확장성은 더 좋지만, 구독이 의미 있도록 사전에 스키마를 설계해야 합니다.

```
                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘
```

### 각 방식이 이기는 경우

- **풀(pool) 전체 공유**는 에이전트 수가 적을 때 (< 10), 이질적이며, 대화가 짧은 기간에 끝날 때 이깁니다. 모든 사람이 모든 것을 보므로 누가 무엇을 말했는지 추론하는 것은 사소한 일입니다.
- **블랙보드**는 에이전트 수가 많을 때, 역할은 동일하지만 인스턴스 수가 많은 경우 (스웜(Swarm)), 대화가 장기간 지속될 때 이깁니다. 라우팅은 토큰 비용과 컨텍스트 오염을 줄여줍니다.

프로덕션 시스템은 보통 혼합합니다: 상단에는 작은 풀 전체 공유 (계획 계층), 하단에는 블랙보드 (워커 계층)를 사용합니다.

### 메모리 오염, 한 시나리오

세 에이전트가 연구 작업을 수행합니다. 에이전트 A는 검색 에이전트입니다. 에이전트 B는 요약기입니다. 에이전트 C는 분석가입니다.

1. A는 페이지를 가져와 공유 상태에 메시지를 작성합니다: "연구는 42%의 정확도 개선을 보고했습니다."
2. 가져온 페이지는 실제로 "4.2% 개선"이라고 말했습니다. A는 소수점을 환각(Hallucination)했습니다.
3. B는 공유 상태를 읽고 작성합니다: "큰 42%의 정확도 개선이 보고되었습니다 (출처: A)."
4. C는 공유 상태를 읽고 작성합니다: "채택을 권장합니다 — 42% 상승은 혁신적입니다."
5. 최종 보고서는 존재하지 않았던 42%라는 숫자를 인용합니다.

어떤 에이전트도 충돌하지 않았습니다. 어떤 테스트도 실패하지 않았습니다. 시스템은 "작동"했습니다. 환각은 공유 상태를 통해 한 에이전트의 컨텍스트에서 모든 하류(downstream) 에이전트의 추론으로 전달되었습니다.

### 이것이 구조적인 이유

공유 상태가 없으면, 에이전트 A의 환각은 A의 컨텍스트에 남습니다. 하류 에이전트들은 다시 가져오거나 재유도하여 오류를 잡을 수 있습니다. 단순한 공유 상태를 사용하면, A의 컨텍스트는 모든 사람의 컨텍스트가 되며, 환각은 사실로 세탁됩니다.

문제는 공유 상태 자체는 아닙니다 — **출처(provenance)와 독립적인 검증자(verifier)가 없는 공유 상태**가 문제입니다. 세 가지 완화 조치가 이를 해결합니다:

1. **모든 쓰기 작업에 출처 속성을 부여합니다.** 공유 상태의 모든 항목은 누가, 언제, 어떤 프롬프트로, 그리고 (해당하는 경우) 에이전트가 인용한 출처가 무엇인지를 기록합니다. 하류 에이전트는 출처에 기반한 회의적인 태도로 항목을 읽습니다.
2. **쓰기 작업은 버전화하며, 추가 전용으로 취급합니다.** 수정은 기존 항목을 제자리에서 업데이트하는 것이 아니라, 이를 대체하는 새 항목입니다. 감사 추적은 보존됩니다.
3. **공유 상태에 쓸 수 없는 에이전트를 최소한 하나 유지합니다.** 읽기 전용 검증 에이전트는 항목을 샘플링하고, 출처를 다시 가져오며, 불일치를 플래그합니다. 이 에이전트는 풀에 쓸 수 없으므로, 풀에 의해 오염될 수 없습니다.

### 블랙보드 선례 (Hayes-Roth, 1985)

블랙보드 패턴은 LLM 에이전트보다 40년 앞서 존재했습니다. Hayes-Roth (1985, "A Blackboard Architecture for Control")는 전역 블랙보드를 관찰하고, 부분적인 솔루션을 기여하며, 다른 소스를 트리거하는 전문가 지식 소스(Knowledge Sources)를 설명했습니다. 2026년 블랙보드(CA-MCP, Matrix)는 지식 소스로 LLM 에이전트를, 부분 솔루션으로 JSON 블롭을 사용하는 동일한 패턴입니다. 이전 문헌은 쓰기 경쟁, 기회주의적 제어, 일관성에 대한 솔루션을 문서화했으며, 현대 시스템은 이를 재발견하고 있습니다.

### 투영 vs 전체 보기

순수 블랙보드는 모든 구독자에게 동일한 투영(주제 범위)을 제공합니다. 더 공격적인 설계는 **에이전트별 투영**입니다. 각 에이전트는 역할에 맞춘 맞춤형 뷰를 받습니다. LangGraph의 상태 리듀서는 2026년 표준 구현입니다. 리듀서 함수는 전역 상태를 역할별 슬라이스로 접습니다.

에이전트별 투영은 더 확장되지만 스키마가 필요합니다. 스키마가 없으면 모든 에이전트의 프롬프트에서 임시 투영을 다시 구축해야 합니다.

### 쓰기 경쟁 패턴

여러 에이전트가 동시에 쓰는 것은 LLM 문제가 아니라 동시성 문제입니다. 세 가지 패턴이 작동합니다:

- **순차적 작성자(단일 생산자).** 모든 쓰기 작업은 직렬화하는 하나의 조정 에이전트를 거칩니다. 단순하지만 병목 현상이 됩니다.
- **버전화를 통한 낙관적 동시성.** 각 항목은 버전을 가지며, 작성자는 버전 불일치 시 실패하고 재시도합니다. 전형적인 데이터베이스 기법입니다.
- **주제 분할.** 서로 다른 에이전트가 서로 다른 주제를 소유합니다. 주제 간 경쟁이 없습니다. 설계된 분할 경계가 필요합니다.

대부분의 2026년 프레임워크는 순차적 작성자(sequential writer)를 기본값으로 설정합니다. LLM 호출이 충분히 느려서 경쟁(contention)이 드물고, 병목 현상이 해를 끼치지 않기 때문입니다.

### 쓰기 불가능한 검증자

가장 중요한 완화 조치는 읽기 전용 검증자입니다. 구현 규칙은 다음과 같습니다:

- 검증자는 팀과 상태를 공유합니다(블랙보드 또는 풀을 읽음).
- 검증자는 공유 상태에 대한 쓰기 핸들(handle)이 없으며, 오직 별도의 검증 채널에만 접근할 수 있습니다.
- 검증자는 쓰기 작업에 인용된 출처를 독립적으로 가져옵니다. 불일치를 플래그(flag)합니다.
- 검증자의 자체 출력은 인간이나 별도의 결정 에이전트(agent)로 라우팅되며, 절대 풀(pool)로 되돌려 보내지지 않습니다.

이러한 분리가 없으면 검증자의 출력은 풀의 새로운 항목이 되며, 이는 오염된 풀이 검증자를 오염시키고, 그 오염이 검증 자체를 오염시킨다는 것을 의미합니다.

```figure
swarm-blackboard
```

## 구현하기

`code/main.py`은 스테일파이썬(stdlib Python)로 두 가지 토폴로지(topology)를 구현하며, 장난감(toy) 오염 공격과 세 가지 완화 조치를 포함합니다.

- `MessagePool` — 전체 읽기(read-out)가 가능한 스레드 안전(thread-safe) append-only 로그.
- `Blackboard` — 에이전트별 구독(subscription)을 지원하는 주제(topic) 키 기반 pub/sub.
- `ProvenanceEntry` — 모든 쓰기는 (작성자, 타임스탬프, prompt_hash, source_uri)를 기록합니다.
- `PoisoningScenario` — 에이전트 A가 소수점 값을 환각(hallucinate)하는 3 에이전트 연구 작업을 실행합니다. 최종 보고서를 출력합니다.
- `Verifier` — 출처를 다시 가져오고 불일치를 플래그하는 읽기 전용 에이전트입니다. 검증자가 존재하는 동일한 시나리오를 실행합니다.

실행:

```
python3 code/main.py
```

예상 출력:
- 실행 1 (검증자 없음): 환각된 42%가 최종 보고서로 전파됩니다.
- 실행 2 (검증자 있음): 검증자가 불일치를 플래그하며, 풀은 "flagged"로 라벨링되고, 최종 보고서에는 철회(retraction)가 포함됩니다.

| 메시지 풀 | "공유 채팅 기록" | 모든 에이전트가 읽는 추가 전용 로그. 완전한 투명성을 제공하지만 확장성이 낮습니다. |
| 블랙보드 | "공유 작업 공간" | 토픽 키 기반의 발행/구독(pub/sub) 시스템. 에이전트가 관련 토픽을 구독합니다. 더 높은 확장성을 제공합니다. |
| 출처(Provenance) | "누가 무엇을 작성했는가" | 각 쓰기 작업에 대한 메타데이터: 작성자, 타임스탬프, 프롬프트, 소스. |
| 메모리 오염 | "환각의 확산" | 한 에이전트의 오류가 공유 상태에 유입되면, 하류(downstream) 에이전트가 이를 사실로 채택합니다. |
| 추가 전용 | "제자리 업데이트 없음" | 수정은 기존 항목을 대체하는 새 항목으로 기록됩니다. 감사 추적(audit trail)을 보존합니다. |
| 쓰기 불가 검증 에이전트 | "독립적인 감사자" | 소스를 다시 가져와 불일치를 식별하는 읽기 전용 에이전트. |
| 투영(Projection) | "범위가 지정된 뷰" | 전역 상태에서 계산된 에이전트별 뷰. LangGraph 리듀서가 대표적인 사례입니다. |
| 지식 소스 | "전문가 에이전트" | Hayes-Roth의 1985년 논문에서 블랙보드 참여자를 지칭하는 용어. |
