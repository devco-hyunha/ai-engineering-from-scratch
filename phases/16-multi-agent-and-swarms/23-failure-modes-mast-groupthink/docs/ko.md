# 실패 모드 — MAST, 집단 사고, 단일 문화, 연쇄 오류

> 2026년 기준 참조 분류 체계는 **MAST**입니다 (Cemri et al., NeurIPS 2025, arXiv:2503.13657). 이는 7개의 최신 오픈소스 다중 에이전트 시스템(MAS)의 1642개 실행 추적에서 파생되었으며, **41–86.7%의 실패율**을 보여줍니다. 세 가지 근본 범주는 다음과 같습니다: **명세 문제** (41.77%) — 역할 모호성, 불명확한 작업 정의; **조율 실패** (36.94%) — 통신 붕괴, 상태 비동기화; **검증 공백** (21.30%) — 누락된 검증, 부재한 품질 검사. **집단 사고**(Groupthink) 계열 (arXiv:2508.05687)은 다음을 추가합니다: 단일 문화 붕괴 (동일한 기본 모델 → 상관된 실패), 순응 편향 (에이전트들이 서로의 오류를 강화함), 결함 있는 마음 이론, 혼합 동기 역학, 연쇄적 신뢰성 실패. 연쇄 예시: 재시도 폭풍(retry storms)은 결제 실패가 주문 재시도를 유발하고, 이것이 재고 재시도를 유발하며, 재고 서비스를 압도합니다 (수 초 만에 10배 부하 — 서킷 브레이커가 필요함). 메모리 오염: 한 에이전트의 환각이 공유 메모리에 유입되면, 하류 에이전트들이 이를 사실로 취급합니다; 정확도가 점진적으로 감소하여 근본 원인 진단이 고통스럽습니다. **STRATUS** (NeurIPS 2025)는 전문화된 감지 / 진단 / 검증 에이전트를 통해 완화 성공률을 1.5배 개선한다고 보고합니다. 이 강의는 실패 모드를 일급 엔지니어링 목표로 취급합니다.

**유형:** Learn
**언어:** Python (stdlib)
**선수 요건:** 16단계 · 13강 (공유 메모리), 16단계 · 14강 (합의와 BFT), 16단계 · 15강 (투표 및 토론 토폴로지)
**시간:** 약 75분

## 문제점

다중 에이전트 시스템은 실제 작업에서 41-86.7%의 확률로 실패합니다 (Cemri et al. 2025가 7개의 오픈소스 MAS를 통해 측정함). 이는 "에이전트를 더 추가하기만 하면" 디버깅할 수 있는 것이 아닙니다. 실패에는 구조적 원인이 있습니다. MAST 분류 체계가 범주를 제공합니다. 이 강의는 각 범주를 구체적인 감지, 진단, 및 완화 패턴에 매핑하여 숫자들이 임의로 보이지 않도록 합니다.

2026년 생산 실무는 실패 모드를 설계 입력으로 취급하는 것입니다. 각 MAST 범주를 가리키고 배치한 완화책을 이름으로 지칭할 수 있을 때까지는 아키텍처가 "충분히 좋다고" 할 수 없습니다.

## 개념

### MAST 범주

**명세 문제 (실패의 41.77%).** 에이전트(Agent)의 작업이 충분히 엄밀하게 정의되지 않았습니다. 예시:

- 역할 모호성: 두 에이전트(Agent)가 모두 자신을 리뷰어(Reviewer)라고 생각합니다.
- 작업 불명세: 사용자가 특정 관점을 원했는데 "이것을 요약해"라고 요청했습니다.
- 성공 기준이 암묵적임: 에이전트(Agent)가 성공했는지 판단할 수 없습니다.

완화책:
- 명시적인 역할 계약을 작성하세요. 각 에이전트(Agent)의 프롬프트(Prompt)는 수행하는 작업 *그리고 수행하지 않는 작업*을 명시합니다.
- 작업별 수용 테스트를 설정하세요. 에이전트(Agent)가 시작하기 전에 "완료된 상태는 X처럼 보인다"를 정의합니다.
- 사전 명세 점검: 별도의 에이전트(Agent)가 작업 정의가 파견(dispatch)되기 전에 검토합니다.

**조율 실패 (36.94%).** 통신 또는 상태 붕괴입니다.

예시:
- 두 에이전트(Agent)가 동기화 없이 공유 상태를 업데이트합니다.
- 에이전트(Agent) 간 메시지 유실 (큐(Queue) 실패, 시간 초과).
- 상태 드리프트: 에이전트(Agent) A는 작업이 완료되었다고 생각하지만, 에이전트(Agent) B는 아직 실행 중입니다.

완화책:
- 낙관적 동시성을 적용한 버전 관리된 공유 상태를 사용하세요.
- 중요한 메시지에 대해 명시적인 확인 응답을 요구하세요 (확인될 때까지 재시도).
- 주기적인 상태 동기화 체크포인트(Checkpoint)를 설정하여 드리프트를 조기에 감지하세요.

**검증 공백 (21.30%).** 출력에 대한 독립적인 검사가 없습니다.

예시:
- 한 에이전트(Agent)가 성공을 주장하지만, 아무도 검증하지 않습니다.
- 에이전트(Agent) 체인에서 각 에이전트(Agent)가 이전 에이전트(Agent)의 출력을 신뢰합니다.
- 합성된 동작에 대한 테스트 커버리지(Coverage)가 누락되었습니다.

완화책:
- 독립적인 검증 에이전트(Agent)를 사용하세요 (13강). 읽기 전용이며 독립적인 소스 접근을 허용합니다.
- 명시적인 핸드오프(Handoff) 계약을 설정하세요: "A의 출력은 B가 시작하기 전에 검사기 C를 통과해야 합니다."
- 사후 분석을 위해 결과 로깅(Logging)을 수행하세요.

### 집단 사고 계열 (arXiv:2508.05687)

에이전트(Agent)가 서로를 모방하거나 균일화될 때 발생하는 다섯 가지 관련 실패:

**단일 문화 붕괴.** 동일한 기반 모델이나 학습 데이터 → 상관된 오류. 세 에이전트(Agent)가 LLM (대규모 언어 모델)(LLM (Large Language Model))을 공유하면, 그 환각(Hallucination)도 공유합니다.

**순응 편향.** 에이전트(Agent)는 가장 큰 소리를 내거나 가장 확신하는 동료 에이전트에게 맞춰 조정하며, 심지어 그 동료 에이전트가 틀린 경우에도 그렇게 합니다.

**결함 있는 ToM.** 에이전트(Agent)가 서로의 신념을 모델링하지 못해 조율이 무너집니다 (18강).

**혼합 동기 역학.** 부분적으로 정렬된 인센티브를 가진 에이전트(Agent)는 타협 중간점으로 이동하며, 이는 누구도 만족시키지 못합니다.

**연쇄적 신뢰성 실패.** 한 구성 요소의 오류 패턴이 의존하는 구성 요소의 오류 패턴을 유발합니다.

### 연쇄적 예시 — 재시도 폭풍

2026년 전형적인 인시던트 패턴입니다:

```
payment service fails 10% of requests
   ↓
order agent retries payment (exponential backoff but naive)
   ↓
each retry is a new order-inventory check
   ↓
inventory service sees 2x normal load
   ↓
inventory service starts timing out
   ↓
every order retries inventory check
   ↓
inventory service sees 10x normal load
   ↓
cluster goes down
```

해결책은 고전적입니다: **서킷 브레이커(Circuit Breakers)**. 다운스트림 오류율이 임계값을 초과하면 캐시된 결과나 기본 결과로 단락 처리합니다. 또한 요청별 재시도 예산(Retry Budget)을 상한으로 제한합니다.

서킷 브레이커(Circuit Breaker)는 분산 시스템에서 수정 없이 직접 차용할 수 있는 몇 안 되는 다중 에이전트 실패 완화 수단 중 하나입니다.

### 메모리 오염 (재고)

13강에서: 한 에이전트(Agent)의 환각(Hallucination)이 공유 메모리 사실이 되며, 다운스트림 에이전트(Agent)가 오염된 사실에 기반해 추론합니다. MAST 용어로는, 이는 공유 메모리 계층에서의 검증 게이트(Verification Gate) 공백입니다.

점진적 정확도 감소가 증상입니다. 크래시가 발생하지는 않지만, 근본 원인을 파악하기 어려운 느린 드리프트가 발생합니다.

완화책: 추기 전용 로그, 출처 증명(Provenance Attestation), 쓰기 불가능한 검증기. 13강에서 이미 다루었습니다.

### STRATUS — 실패 감지를 위한 전문화된 에이전트(Agent)

STRATUS (NeurIPS 2025)는 다음을 배포할 때 완화 성공률이 1.5배 개선된다고 보고합니다:

- **감지 에이전트(Detection Agent).** 증상 패턴 (높은 불일치, 재시도 급증, 정확도 드리프트)을 감시합니다.
- **진단 에이전트(Diagnosis Agent).** 증상을 받아 MAST 분류 체계에서 가능한 근본 원인을 추론합니다.
- **검증 에이전트(Validation Agent).** 완화책이 적용된 후 증상이 해소되는지 확인합니다.

이는 에이전트 시스템에 적용된 SRE 스타일의 인시던트 대응(Incident Response)입니다. 세 가지 역할 모두 전문화된 프롬프트를 가진 LLM 에이전트(LLM Agent)가 될 수 있습니다.

### 실패 모드 감사

2026년 모범 사례는 연례 (또는 주요 릴리스별) 실패 모드 감사입니다:

1. **추적 샘플(Trace Sample).** 약 1000개의 실제 실행 추적(Trace)을 수집합니다.
2. **분류.** 각 추적의 실패를 MAST + Groupthink 범주에 매핑합니다.
3. **범주별 실패율 계산.** 어떤 범주가 시스템에서 지배적인가요?
4. **완화책 순위 매기기.** 어떤 수정이 가장 많은 실패를 제거할 수 있나요?
5. **2-3개 완화책 선택.** 구현하고 다음 분기에 재감사합니다.

특정 선택보다 규율이 더 중요합니다. 감사 없이는 실패가 잡음에 섞여 체계적으로 해결되지 않습니다.

### 시스템이 조용히 실패할 때

가장 위험한 실패 범주는 조용한 정확성 실패입니다. 큰 소리로 실패하는 시스템(크래시, 예외, 알림)은 모니터링할 수 있습니다. 그럴듯하지만 잘못된 출력을 생성하는 시스템은 예외 로그로 감지할 수 없습니다. 그래서 검증 공백이 개수로는 21.30%에 불과하지만, 실패당 가장 비싼 범주입니다.

다음에 투자하세요:
- 샘플 기반 인간 검토.
- 골든 데이터셋 회귀 테스트.
- 중요한 출력에 대한 에이전트 간 교차 검증.

### 실패 vs 느린 실패

일부 실패는 즉각적이고, 일부는 느립니다. 즉각적인 실패(타임아웃, 스키마 불일치, 인증 오류)는 감지가 저렴합니다. 느린 실패(메모리 오염, 단일 문화 드리프트, 역할 모호성)는 감지와 예방이 비쌉니다.

2026년 엔지니어링 전략: 느린 실패의 대리 지표(proxies)를 계측하여 가시적인 오류가 되기 전에 드리프트를 포착하세요. 일치율, 재시도율, 출력 길이 분포, 연속 에이전트 버전 간 편집 거리는 모두 유용한 대리 지표입니다.

## 구현하기

- `FailureTaxonomy` — 시뮬레이션된 인시던트를 MAST + Groupthink 범주로 분류합니다.

- `RetryStormSimulator` — 연쇄적 실패를 보여줍니다; 서킷 브레이커를 켜고 끄는 토글입니다.

```
python3 code/main.py
```

- 서킷 브레이커 사용: 임계값에서 상한을 설정; 저하 모드 응답이 제공됩니다.
- 감지 에이전트가 패턴을 식별하고 MAST 범주를 지정합니다.

## 출시하기

프로덕션에서의 실패 모드 규율:

- **분기별 MAST 감사.** 연도가 아닌 분기별. 시스템이 성장함에 따라 범주가 변합니다.
- **전역 서킷 브레이커.** 모든 의존 서비스에 대한 모든 아웃바운드 호출. 기본 열림 임계값은 5-10% 오류율입니다.
- **골든 데이터셋.** 작고 고품질이며 수동으로 감사된 데이터셋. 매주 이를 대상으로 회귀 테스트를 수행합니다.
- **STRATUS 트리오.** 프로덕션을 모니터링하는 감지 + 진단 + 검증 에이전트. 감지 에이전트만 먼저 시작하고, 증상이 노이즈가 많을 때 진단을 추가합니다.
- **실패 예산.** 범주별 오류율에 대한 명시적인 SLO. 예산을 초과하면 출시 중단 논의가 촉발됩니다.

## 연습 문제

1. `code/main.py`를 실행하세요. 서킷 브레이커가 재시도 폭풍을 제한하는지 확인하세요. 실패 임계값을 변경하고 트레이드오프를 관찰하세요.
2. **느린 실패 프록시**를 구현하세요: 3개의 병렬 에이전트 간 일치율. 일치율이 급격히 떨어지면 경보를 트리거합니다. 에이전트 출력의 상관성을 점진적으로 높여 단일 문화(monoculture) 드리프트를 시뮬레이션하세요.
3. Cemri et al. (arXiv:2503.13657)을 읽어보세요. 그들의 7개 MAS 시스템 중 하나를 선택하여 상위 3개 실패 범주를 매핑하세요. MAST가 예측하는 것과 비교했을 때 어떻게 다른가요?
4. Groupthink 논문 (arXiv:2508.05687)을 읽어보세요. 프로덕션에서 감지하기 가장 어려운 5가지 패턴 중 하나를 식별하세요. 프록시 메트릭을 제안하세요.
5. 알고 있는 특정 다중 에이전트 시스템에 대해 STRATUS 스타일의 감지-진단-검증 트리오는 설계하세요. 감지는 어떤 증상을 주시하나요? 진단은 어떤 완화 조치를 권장하나요? 검증은 어떻게 효과가 있음을 확인하나요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| MAST | "2026년 분류 체계" | Cemri 2025; 3개 루트 범주 + 14개 하위 유형 실패. |
| 사양 문제 | "역할 모호성" | 작업이나 역할이 불명확하게 정의됨; 에이전트가 무엇을 해야 할지 모름. |
| 조정 실패 | "상태 드리프트" | 에이전트 간 통신 또는 동기화 장애. |
| 검증 격차 | "아무도 확인하지 않음" | 독립적인 검증 없이 출력물이 승인됨. |
| 집단 사고 계열 | "동질성 실패" | 단일 문화, 순응, 결함 있는 ToM, 혼합 동기, 연쇄. |
| 단일 문화 붕괴 | "동일 모델, 동일 환각" | 공유된 기본 모델이나 학습 데이터에서 발생한 상관된 오류. |
| 재시도 폭풍 | "연쇄적 오류 증폭" | 하나의 실패가 재시도를 유발하여 하류 부하를 증폭시킴. |
| 서킷 브레이커 | "오류율에 대해 빠르게 실패" | 오류율이 임계값을 초과하면 열림; 기본값으로 단락. |
| STRATUS | "인시던트 대응 삼중주" | 감지 + 진단 + 검증 에이전트. 1.5배 완화 성공률. |
| 메모리 오염 | "환각이 전파됨" | 공유 메모리의 사실이 오염됨; 하류 에이전트가 오염된 정보로 추론. |
