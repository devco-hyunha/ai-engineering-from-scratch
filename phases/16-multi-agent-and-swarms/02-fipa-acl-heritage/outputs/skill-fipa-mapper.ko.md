새로운 에이전트 프로토콜 사양이 주어지면, FIPA-ACL 매핑을 생성하여 독자가 어떤 부분이 재발명이고 어떤 부분이 진정한 신규 구조인지 파악할 수 있도록 합니다.

다음 내용을 생성합니다:

1. **엔벨로프 매핑.** 사양이 정의하는 각 메시지 유형에 대해 가장 가까운 FIPA 퍼포마티브(`inform`, `request`, `query-if`, `query-ref`, `propose`, `accept-proposal`, `reject-proposal`, `cfp`, `subscribe`, `cancel`, `failure`, `not-understood` 또는 기타 약 20개 중 하나)를 지정합니다. 적합한 퍼포마티브가 없다면, 그 공백을 정확히 설명합니다.
2. **상관 모델.** 사양은 요청을 응답에, 취소를 원 요청에, 스트리밍된 이벤트를 구독에 어떻게 상관(correlate)합니까? FIPA의 `:conversation-id` 및 `:reply-with` 필드와 비교합니다.
3. **콘텐츠 언어 입장.** 사양은 콘텐츠 스키마(타입 지정된 아티팩트, JSON-Schema)를 의무화합니까, 자연어를 허용합니까, 아니면 열려 있게 합니까? FIPA의 SL0/SL1 및 온톨로지 필드와 비교합니다.
4. **상호작용 프로토콜 라이브러리.** 사양 위에 구현 가능한 FIPA 상호작용 프로토콜은 무엇입니까: contract-net, subscribe-notify, request-when, propose-accept? 각 프로토콜을 구현하는 메시지를 지정합니다.
5. **발견 모델.** 에이전트는 상대방과 기능을 어떻게 찾습니까(MCP `listTools`, A2A Agent Card, ANP DID + 메타 프로토콜)? FIPA의 디렉토리 퍼실리테이터 및 옐로 페이지 서비스와 비교합니다.
6. **재발명 vs 신규성.** 세 개의 열을 가진 짧은 표를 생성합니다: [FIPA 개념, 현대 사양의 등가물, 변경된 점]. 각 행을 [reinvention] 또는 [novel-structure]로 표시합니다. 행이 "novel-structure"인 경우는 사양이 FIPA에 없던 프리미티브를 도입했을 때만 해당합니다 — 분산된 신원, 타입 지정된 멀티모달 아티팩트, LLM으로 해석 가능한 콘텐츠가 일반적인 후보입니다.

거부 조건:

- FIPA에 없던 프리미티브를 제시하지 않고 사양이 "혁명적"이라고 주장하는 모든 매핑은 거부됩니다. 실패 요인은 발화행위 이론 + 온톨로지 오버헤드였지, 프리미티브가 아니었습니다.
- 발견 계층을 무시하는 프레임워크 비교. 발견 계층이 없는 사양은 혁신적인 것이 아니라 불완전한 것입니다.
- "프로토콜 X가 FIPA를 대체한다"와 같은 진술은 두 에이전트가 콘텐츠 의미에 대해 의견이 불일치할 때 발생하는 상황(의미적 드리프트)을 다루지 않습니다.

거부 규칙:

- 사양이 표준화 이전 단계(초안 기간이 6개월 미만이며 공개 구현이 없는 경우)라면, 매핑이 잠정적임을 명시하고 가장 가능성이 높은 세 가지 변경 사항을 표시하세요.
- 사양이 비공개 소스이거나 기업 전용인 경우(일부 ACP 변형), 문서화된 부분을 매핑하고 공백을 명시하세요.
- 사용자가 블로그 게시물만 제공한 경우(사양 문서 없음), 매핑하기 전에 사양을 요청하세요.

출력: 한 페이지 분량의 브리프. 한 문장 요약("프로토콜 X는 JSON 구문과 DID 기반 발견 계층을 갖춘 FIPA `request`/`subscribe`입니다.")으로 시작한 후, 위의 6개 섹션을 나열하고, 마지막 단락으로 "이 사양이 어떤 오래된 FIPA 실패 모드를 재발견할 것인가?"에 답하세요.
