# 병렬 / 스웜 / 네트워크 아키텍처

> 슈퍼바이저와 대조: 중앙 결정자가 없습니다. 에이전트(Agent)는 공유 이벤트 버스를 읽고, 비동기적으로 작업을 가져와 결과를 다시 씁니다. LangGraph는 분산되고 동적인 환경을 위해 "Swarm Architecture"를 명시적으로 지원합니다. Matrix (arXiv:2511.21686)는 오케스트레이터(Orchestrator) 병목을 없애기 위해 제어 흐름과 데이터 흐름 모두를 분산 큐를 통해 전달되는 직렬화된 메시지로 표현합니다. 트레이드오프는 명확합니다: 확장성을 위해 결정성과 추적성을 희생합니다. 스웜(Swarm)은 많은 독립적인 하위 문제를 가진 작업에 적합하며, 단일한 일관된 계획이 필요한 작업에는 적합하지 않습니다.

**유형:** Learn + Build
**언어:** Python (stdlib, `threading`, `queue`)
**선수 요건:** 16단계 · 05강 (슈퍼바이저 패턴), 16단계 · 04강 (원시 모델)
**시간:** 약 75분

## 문제점

슈퍼바이저는 소수의 워커까지 확장됩니다. 수백 개는 어떨까요? 슈퍼바이저 자체가 병목이 됩니다: 누가 무엇을 하는지에 대한 모든 결정이 하나의 에이전트(Agent)를 통해 집중됩니다. 느린 계획 단계 하나가 전체 시스템을 멈추게 합니다.

스웜(Swarm) 아키텍처는 설계를 뒤집습니다. 중앙 계획자가 작업을 분배하는 대신, 워커가 공유 큐에서 작업을 가져갑니다. "조율"은 이벤트 버스 의미론에 내장되어 있습니다. 오케스트레이터(Orchestrator)가 없으므로, 시스템은 큐가 감당할 수 있는 한까지 확장됩니다.

## 개념

### 형태

```
                ┌──── shared queue ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     Worker  Worker  Worker   Worker
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            results pool
```

오케스트레이터(Orchestrator)가 없습니다. 각 워커는 다음을 반복합니다: 작업 가져오기, 처리, 결과 쓰기 (그리고 선택적으로 후속 작업 큐잉).

### 스웜(Swarm)이 적합한 경우

- **많은 독립적인 작업.** 스크래핑, 변환, 분류. 작업들이 서로 의존하지 않습니다.
- **변동하는 작업 시간.** 어떤 작업은 100ms, 다른 작업은 10s가 걸린다면, 스웜(Swarm)은 자동으로 부하를 균형 잡습니다 — 빠른 워커가 다음 작업을 가져갑니다. 슈퍼바이저는 작업 시간을 예측해야 합니다.
- **결정성보다 처리량.** 총 완료 시간에 신경 쓰며, 엄격한 순서에는 신경 쓰지 않습니다.

### 스웜(Swarm)이 실패하는 경우

- **순서가 있는 워크플로우.** 3단계가 2단계의 출력에 의존한다면, 스웜(Swarm)은 2단계가 끝나기 전에 3단계가 실행될 위험이 있습니다.
- **전역 계획 작업.** 복잡한 연구 질문은 계획자의 도움을 받습니다. 스웜(Swarm) 연구자들은 독립적인 사실을 산출할 뿐, 일관된 보고서를 만들지 못합니다.
- **디버깅.** 중앙 로그가 없고 비동기 작업이 이루어지면 버그를 재현하는 비용이 많이 듭니다.

### Matrix (arXiv:2511.21686)

Matrix는 스웜을 자연스러운 결론으로 가져가는 2025년 논문입니다. 제어 흐름과 데이터 흐름 모두 분산 큐의 직렬화된 메시지입니다. 중앙 조정자는 없습니다. 내결함성은 메시지의 내구성에서 나옵니다. 확장성은 시스템의 문제가 아니라 메시지 브로커의 문제입니다.

기여: 다중 에이전트 조정이 "이 에이전트가 어떤 메시지 주제에 구독하는가?"가 아니라 "감독자가 다음에 어떤 에이전트를 선택하는가?"인 프로그래밍 모델입니다. 이는 시스템을 pub/sub 이벤트 메시처럼 보이게 만듭니다.

### 그래프 프레임워크에서의 스웜

LangGraph 2025 문서에서는 "스웜 아키텍처"를 다중 에이전트 패턴 중 하나로 명시적으로 설명합니다. 에이전트는 노드이며, 엣지는 사이클을 포함하는 방향성 그래프를 형성하고, 풀(pool)의 모든 노드가 활성화될 수 있습니다. 워커는 감독자의 할당이 아니라 조건에 따라 가용한 작업 중 하나를 선택합니다.

### 실패 모드: 기아(starvation) 및 핫스팟(hot-spotting)

모든 워커가 가장 빨리 처리 가능한 작업을 가져간다면, 장시간 실행되는 작업은 마지막 하나만 남을 때까지 선택되지 않습니다. 전형적인 큐 기아 현상입니다.

완화 조치:
- 대기 시간에 따라 우선순위를 높이는 명시적 에이징(aging)을 사용하는 우선순위 큐.
- 워커 전문화: 일부 워커는 "긴" 작업만 처리합니다.
- 백프레셔: 빠른 작업이 큐에 들어가는 수를 제한합니다.

### 콘텐츠 기반 라우팅 링크

스웜은 콘텐츠 기반 라우팅(22강)과 자연스럽게 짝을 이룹니다. 범용 큐 대신 메시지 유형별로 큐를 하나씩 둡니다. 전문가 워커는 자신의 유형에만 구독합니다. 이는 수천 개의 에이전트로 확장되는 메시지 버스 아키텍처의 기초입니다.


## 구현하기

`code/main.py`는 공유 `queue.Queue`에서 작업을 가져오는 4개의 워커 스레드로 구성된 스웜을 구현합니다. 작업은 지속 시간이 다양합니다(빠른 작업과 느린 작업이 있음). 데모는 다음을 비교합니다:

- **순차적 기준선:** 하나의 워커가 모든 작업을 순차적으로 처리합니다.
- **고정 할당:** 각 작업이 특정 워커에 사전 할당됩니다(감독자 스타일).
- **스웜:** 워커가 공유 큐에서 작업을 가져옵니다.

스웜(Swarm)은 부하를 자동으로 균형화합니다. 고정 할당은 할당된 작업이 느릴 때 빠른 워커를 유휴 상태로 만듭니다.

실행:

```
python3 code/main.py
```

출력은 워커별 작업 수(스웜은 불균등하지만 최적적으로 분배)와 실제 소요 시간을 보여줍니다.

## 사용하기

`outputs/skill-swarm-fit.md`는 작업이 스웜(Swarm) 대 감독자(Supervisor) 중 어느 것을 사용해야 하는지 평가합니다. 입력: 작업 독립성, 지속 시간 변동, 순서 요구 사항, 디버깅 필요성.

## 출시하기

체크리스트:

- **노화(Aging)가 포함된 우선순위 큐.** 긴 작업의 기아(starvation)를 방지합니다.
- **워커 멱등성(Idempotency).** 워커가 실행 중 충돌하면 작업이 두 번 이상 가져올 수 있습니다. 워커는 멱등적이어야 합니다.
- **내구성 있는 큐(Durable Queue).** 프로덕션에서는 Kafka, Redis Streams 또는 데이터베이스 기반 큐를 사용하세요. `queue.Queue`는 메모리 전용입니다.
- **작업별 관측 가능성(Observability).** 모든 작업에는 추적 ID가 있으며, 모든 워커는 이를 포함하여 시작/종료를 기록합니다.
- **백프레셔(Back-pressure).** 큐가 워커가 처리하는 속도보다 빠르게 증가하면 생산자(Producer)의 속도를 늦추세요.

## 연습 문제

1. `code/main.py`를 실행하세요. 지속 시간이 변하는 작업 부하에서 스웜(Swarm)이 순차 실행보다 얼마나 빠른가요? 고정 할당보다 얼마나 빠른가요?
2. 우선순위 큐 변형을 추가하세요(`queue.PriorityQueue` 사용). 작업의 "importance" 필드로 우선순위를 할당하세요. 연속적인 부하에서 낮은 우선순위 작업이 기아(starvation) 상태에 빠지는지 관찰하세요.
3. 핫스팟(Hot-spot) 감지기를 구현하세요: 가장 느린 워커가 처리한 작업 수의 3배 이상을 처리하는 워커가 있을 때 기록하세요. 이것이 작업 지속 시간 분포에 대해 무엇을 나타내나요?
4. Matrix 논문(arXiv:2511.21686)의 초록과 섹션 3을 읽으세요. Matrix가 수용하는 특정 트레이드오프(확장성 향상)와 포기하는 것(추적 가능성, 결정성)을 각각 하나씩 식별하세요.
5. 스웜(Swarm) 데모를 (task_type, payload) 튜플의 `queue.Queue`를 사용하도록 변환하세요. 워커는 특정 유형만 구독합니다. 작업이 이질적일 때 어떤 라우팅 규칙이 합리적인가요?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|------|----------------|------------------------|
| 스웜(Swarm) 아키텍처 | "분산 에이전트" | 워커가 공유 큐에서 가져오며, 중앙 오케스트레이터가 없습니다. |
| 이벤트 버스(Event Bus) | "에이전트가 주제에 구독" | 유형이나 콘텐츠에 따라 워커로 작업을 라우팅하는 메시지 브로커. |
| 기아 상태 | "작업이 실행되지 않음" | 높은 우선순위의 작업이 지속적으로 도착하여 낮은 우선순위 작업이 선택되지 않는 상태. |
| 핫스팟 | "한 워커가 과부하됨" | 한 워커가 대부분의 작업을 받는 부하 불균형. |
| 백프레셔 | "생산자 속도 조절" | 큐가 가득 찼을 때 상류에 생산 중단을 알리는 메커니즘. |
| 멱등성 워커 | "재실행이 안전함" | 작업을 두 번 처리해도 같은 결과가 나옴. 워커가 실행 중 충돌할 수 있으므로 필수. |
| 내구성 있는 큐 | "충돌에도 생존" | 디스크나 복제된 저장소에 백업된 큐; 워커가 충돌해도 작업이 손실되지 않음. |
| 매트릭스 프레임워크 | "전체 메시지 전달 스웜" | 데이터와 제어 흐름 모두 분산 큐에서 직렬화된 메시지로 처리됨. |
