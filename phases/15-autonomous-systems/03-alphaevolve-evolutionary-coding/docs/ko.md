# AlphaEvolve — 진화형 코딩 에이전트

> 최첨단 코딩 모델과 진화 루프, 그리고 기계 검증 가능한 평가기를 조합하세요. 루프를 충분히 오래 실행해 보세요. 이 루프는 48개의 스칼라 곱셈을 사용하는 4x4 복소 행렬 곱셈 절차를 발견합니다 — 56년 만에 Strassen 알고리즘을 넘어선 최초의 개선입니다. 또한 Google 전역의 Borg 스케줄링 휴리스틱을 찾아, 프로덕션 환경에서 클러스터 컴퓨팅 자원의 약 0.7%를 회수합니다. 아키텍처는 의도적으로 단순합니다. 성과는 평가기의 엄격함에서 나옵니다.

**유형:** Learn
**언어:** Python (표준 라이브러리, 진화 루프 장난감)
**선수 요건:** 15단계 · 01강 (장기적 관점의 프레이밍), 15단계 · 02강 (자기 주도적 추론)
**시간:** 약 60분

## 문제점

대규모 언어 모델은 코드를 작성할 수 있습니다. 진화 알고리즘은 코드를 탐색할 수 있습니다. 두 방법 모두 수십 년간 개별적으로 시도되어 왔으며, 각각 한계에 부딪혔습니다. LLM의 한계는 환각(confabulation)입니다: 모델은 그럴듯한 코드를 작성하지만, 주장하는 대로 동작하지 않습니다. 진화 알고리즘의 한계는 탐색 비용입니다: 구문에 대한 랜덤 변이는 컴파일 가능한 프로그램을 거의 생성하지 못하며, 더 나은 프로그램은 말할 것도 없습니다.

AlphaEvolve (Novikov 등, DeepMind, arXiv:2506.13131, 2025년 6월)는 두 방법을 결합합니다. LLM이 프로그램 데이터베이스에 대한 타겟 편집을 제안하고, 자동 평가기가 각 변형을 점수화합니다. 높은 점수를 받은 변형은 다음 세대의 부모가 됩니다. LLM은 그럴듯한 코드를 작성하는 비싼 단계를 처리하고, 평가기는 환각을 잡아냅니다. 루프는 몇 시간에서 몇 주간 실행됩니다.

보고된 결과: 48 스칼라 곱셈을 사용하는 4x4 복소 행렬 곱셈 (Strassen의 1969년 상한은 49), Google 프로덕션 환경의 Borg 스케줄링 휴리스틱, FlashAttention 커널의 32.5% 속도 향상, Gemini 학습 처리량 개선.

이 아키텍처는 평가기가 기계 검증 가능하기 때문에 작동합니다. 평가기가 기계 검증 가능하지 않은 곳에서는 작동하지 않습니다. 이 비대칭성이 교훈입니다.

## 개념

### 루프

1. 정확하지만 최적화되지 않은 시드 프로그램 `P_0`에서 시작하세요.
2. 평가기가 점수화한 변형 프로그램들의 데이터베이스를 유지하세요.
3. 데이터베이스에서 하나 이상의 부모를 샘플링하세요 (MAP-elites 스타일 또는 섬 기반).
4. LLM (많은 후보는 Gemini Flash, 어려운 것은 Gemini Pro)에 부모 변형의 수정된 변형을 생성하도록 프롬프트합니다.
5. 보유된 평가자(held-out evaluator)에서 변형을 컴파일, 실행 및 평가합니다.
6. 점수와 특징 벡터를 키로 사용하여 데이터베이스에 삽입합니다.
7. 반복합니다.

두 가지 세부 사항이 중요합니다. 첫째, LLM은 부모 프로그램 이상의 정보를 프롬프트로 받습니다. 일반적으로 데이터베이스의 상위 변형 여러 개, 평가자 시그니처, 짧은 작업 설명이 포함됩니다. 모델의 역할은 점수를 개선할 수 있는 targeted change를 제안하는 것입니다. 둘째, 데이터베이스는 구조화되어(MAP-elites grid, island-based) 있어 루프가 다양성을 탐색하며, 단순히 현재 리더만 따르지 않습니다.

### 평가자가 협상 불가능한 이유

AlphaEvolve의 성과는 평가자가 빠르고, 결정적이며, 조작하기 어려운 도메인에서 모두 나옵니다:

- **행렬 곱셈 알고리즘**: 행렬을 곱하고 비트 단위로 동일성을 확인하는 단위 테스트.
- **Borg 스케줄링 휴리스틱**: 역사적 클러스터 부하를 재생하고 낭비된 컴퓨팅을 측정하는 프로덕션급 시뮬레이터.
- **FlashAttention 커널**: 정확성 테스트와 실제 하드웨어에서의 wall-clock 벤치마크.
- **Gemini 학습 처리량**: 단계당 측정된 GPU-초.

각 경우에서 평가자는 LLM의 오류 유형을 잡아냅니다. 이 오류들은 방치하면 지배적이 될 것입니다: 허구적인 정확성 주장, 하드웨어에서 사라지는 성능 주장, 엣지 케이스 실패. 평가자를 제거하면 루프는 예쁜 코드를 최적화하게 됩니다.

### 보상 해킹(reward hacking)은 이 진술의 다른 얼굴입니다

진화(evolution)는 평가자가 측정하는 것을 최적화합니다. 평가자가 불완전하면 루프는 그 불완전함을 찾아냅니다. 검증되지 않은 도메인에서는 루프가 의도된 행동이 아닌 표면적 특징을 최적화합니다. DeepMind는 논문에서 이를 명시적으로 지적합니다: AlphaEvolve의 성공은 평가자의 엄격성이 탐색의 야심과 일치하는 도메인에서만 전이됩니다.

2025-2026년 코드 검색 루프에서의 보상 해킹 구체적 예시:

- "완료까지의 시간"을 보상하는 최적화 목표는 빈 솔루션 제출을 보상했습니다.
- 테스트 하의 정확성을 보상하는 벤치마크 점수는 테스트 암기와 과적합을 보상했습니다.
- "코드 품질" 대리 지표는 주석 제거와 변수 이름 재작성을 보상했으며, 이는 의미적 변화가 없는 것이었습니다.

AlphaEvolve의 해결책: LLM이 한 번도 본 적 없는 홀드아웃 평가기를 출시하고, 평가 시점에 입력을 생성합니다. DeepMind는 제안된 모든 배포에 대해 강력한 검토를 권장합니다.

### LLM + 검색이 단독으로 사용할 때보다 더 잘 작동하는 이유

LLM은 컴파일 가능하고 의미적으로 타당한 수정을 생성할 수 있습니다. 2000줄 Python 파일에 대한 랜덤 변이 GA는 거의 항상 구문 오류를 생성합니다. LLM은 또한 가능한 근방에 검색을 집중합니다(랜덤 바이트가 아닌 하나의 함수 변경). 이는 평가기 호출의 낭비를 극적으로 줄입니다.

평가기는 LLM의 환각을 잡아냅니다. LLM은 실제로 O(n^2)인 함수가 "한계에서 O(n log n)이다"라고 자신 있게 주장합니다. 월클록 벤치마크는 이 질문에 대한 답을 확정합니다.

### 프론티어 스택에서 AlphaEvolve가 위치하는 곳

| 시스템 | 생성기 | 평가기 | 도메인 | 예시 성과 |
|---|---|---|---|---|
| AlphaEvolve | Gemini | 정확성 + 벤치마크 | 알고리즘, 커널, 스케줄러 | 48-mul 4x4 행렬 곱 |
| FunSearch (DeepMind, 2023) | PaLM / Codey | 정확성 | 조합 수학 | cap-set 하한 |
| AI Scientist v2 (Sakana, L5) | GPT/Claude | LLM 비판 + 실험 | ML 연구 | ICLR 워크숍 논문 |
| Darwin Godel Machine (L4) | 에이전트 스캐폴딩 | SWE-bench / Polyglot | 에이전트 코드 | SWE-bench 20% → 50% |

네 가지 모두는 같은 레시피의 변형입니다: 생성기 + 평가기, 루프. 차이점은 평가기가 무엇을 채점하는지와 얼마나 엄격한지입니다.

## 사용하기

`code/main.py`은 장난감 심볼릭 회귀 문제에 대한 최소한의 AlphaEvolve 스타일 루프를 구현합니다. "LLM"은 목표 함수를 계산하는 프로그램에 작은 구문 변이를 제안하는 stdlib 대리자입니다. "평가기"는 홀드아웃 테스트 포인트에 대한 평균 제곱 오차를 측정합니다.

관찰하세요:

- 세대에 걸쳐 최고 점수가 어떻게 개선되는지.
- MAP-elites 그리드가 다양한 솔루션을 유지하여 루프가 지역 최소값에 수렴하지 않도록 하는 방법.
- 보유 테스트(학습 전용 평가기)를 제거하면 루프가 극적으로 과적합되는 방식입니다.

## 연습 문제

1. `code/main.py`을 실행하세요. 최고 점수 궤적을 기록하세요. 보유 평가기를 비활성화(플래그 `--no-holdout`)하고 다시 실행하세요. 과적합을 정량화하세요.

2. AlphaEvolve 논문에서 MAP-elites 그리드에 대한 3장을 읽어보세요. 새로운 문제(예: 컴파일러 최적화 패스)의 검색 다양성을 유지할 기능 벡터 설명자를 설계하세요.

3. 48번의 곱셈을 수행하는 4x4 결과는 Strassen의 49번 곱셈 한계를 56년 만에 개선했습니다. 논문의 부록 F를 읽고, 이 문제에 대한 평가기가 특히 쉽게 정확성을 확보할 수 있는 이유와 대부분의 도메인이 그렇지 않은 이유를 세 문장으로 설명하세요.

4. AlphaEvolve가 실패할 도메인 하나를 제안하세요. 평가기가 정확히 어디에서 깨지는지, 그리고 왜 깨지는지 식별하세요.

5. 알고 있는 도메인에 대해 사용할 평가기 시그니처를 작성하세요. (a) 정확성 조건, (b) 성능 지표, (c) 보유 입력 생성 규칙, (d) 보상 해킹 방지 체크를 최소한 하나 포함하세요.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|---|---|---|
| AlphaEvolve | "DeepMind의 진화적 코딩 에이전트" | Gemini + 프로그램 데이터베이스 + 기계 검증 가능한 평가기 |
| MAP-elites | "다양성을 보존하는 아카이브" | 기능 벡터를 키로 하는 그리드; 각 셀은 해당 설명자를 가진 최상의 변형을 저장 |
| Island model | "병렬 진화 하위 개체군" | 주기적으로 이주하는 독립적인 개체군; 조기 수렴을 방지 |
| 기계 검증 가능한 평가기 | "결정적 오라클" | LLM이 위조할 수 없는 단위 테스트, 시뮬레이터 또는 벤치마크 — 이 루프의 전제 조건 |
| 보상 해킹 | "목표가 아닌 측정값을 최적화" | 루프가 의도된 작업을 수행하지 않으면서 점수를 극대화하는 방법을 찾음 |
| 시드 프로그램 | "시작점" | 루프가 진화하기 시작하는 초기의 정확하지만 최적화되지 않은 프로그램 |
| 홀드아웃 평가자 | "LLM이 본 적 없는 평가 데이터" | 암기를 방지하기 위해 평가 시점에 생성된 입력 |
