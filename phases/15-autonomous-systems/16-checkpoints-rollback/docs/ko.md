# 체크포인트와 롤백

> 모든 그래프 상태 전환은 영속화됩니다. 워커가 충돌하면 리스가 만료되고, 다른 워커가 최신 체크포인트에서 작업을 이어받습니다. Cloudflare Durable Objects는 몇 시간 또는 몇 주간 상태를 유지합니다. 제안 후 커밋(15강)은 각 작업에 대한 롤백 계획을 정의합니다. 작업 후 검증이 루프를 닫습니다. EU AI Act 제14조는 고위험 시스템에 대해 효과적인 인간 감독을 의무화합니다. 이는 실제로 체크포인트가 조회 가능해야 하고, 롤백이 사전에 연습되어야 하며, 감사 추적이 배포 후에도 살아남아야 함을 의미합니다. 날카로운 실패 모드: 멱등성 키와 전제 조건 검사가 없으면, 일시적 실패 후 재시도가 이미 승인된 작업을 이중 실행할 수 있습니다. 작업 후 검증이 이를 잡아냅니다.

**유형:** Learn
**언어:** Python (stdlib, 체크포인트 및 롤백 상태 머신)
**선수 요건:** 15단계 · 12강 (내구성 있는 실행), 15단계 · 15강 (제안 후 커밋)
**시간:** 약 60분

## 문제점

내구성 있는 실행(12강)은 충돌한 에이전트를 재개 가능하게 만듭니다. 제안 후 커밋(15강)은 승인된 작업을 감사 가능하게 만듭니다. 이 강의는 이 둘을 결합합니다: 승인된 작업이 부분적으로 실행되고, 충돌하고, 재개될 때 무슨 일이 일어나는가? 롤백은 언제 실행되며, 어떤 상태를 기준으로 하는가?

실제 시스템은 이를 서로 다른 방식으로 연결합니다:

- **LangGraph**는 모든 그래프 상태 전환을 PostgreSQL에 체크포인트로 저장합니다. 워커 충돌 시 리스가 해제되고, 다른 워커가 최신 체크포인트에서 재개합니다. 워크플로우는 `interrupt()`에서 일시 중지되며, 이 상태 자체가 영속화됩니다.
- **Cloudflare Durable Objects**는 키별 상태를 몇 시간 또는 몇 주간 유지합니다. 승인된 작업의 연산을 스토리지와 함께 위치(co-locate)시킵니다.
- **Microsoft Agent Framework**는 워크플로우 API에서 `Checkpoint` 프리미티브를 노출합니다; 재생(replay)과 멱등성이 재시도를 커버합니다.

모든 경우에서 실제로 작동하는 조합은 다음과 같습니다: 멱등성 키(이중 실행 방지) + 전제 조건 검사(상태가 우리가 승인한 기준과 여전히 일치하는지) + 작업 후 검증(사이드 이펙트가 실제로 발생했는지) + 검증 실패 시 롤백.

## 개념

### 모든 전환이 영속화됨

그래프 상태 전이는 워크플로우를 하나의 명명된 상태에서 다른 상태로 이동하는 모든 단계입니다. 단순한 구현은 특정 커밋 시점에서만 상태를 저장하지만, 프로덕션 구현은 모든 전이를 저장합니다. 비용(몇 번의 추가 쓰기)은 신뢰성 향상(재실행이 어디에서나 가능하고, 리스 복구가 정확함)에 비해 작습니다.

### 리스 복구

워커가 충돌하면 워크플로우는 사라지지 않습니다. 리스(이 워커가 이 실행을 수행하고 있음을 나타내는 짧은 수명의 클레임)는 단순히 만료될 뿐입니다. 다른 워커가 최신 체크포인트를 가져와 재개합니다. 리스 메커니즘은 프로덕션 시스템이 진행 중인 작업을 잃지 않고 롤링 배포를 생존할 수 있게 해줍니다.

### 멱등성 및 전제 조건

멱등성만으로는 충분하지 않습니다. 고려해 보세요: 워크플로우가 "$100 from A to B when balance > $1000 이전"을 승인받았습니다. 워크플로우가 커밋되고, 실행 중 충돌하여 재개됩니다. 멱등성 키만 확인되고 실행이 재개되면, 이전은 한 번 실행됩니다(정확함). 하지만 충돌과 재개 사이에 다른 워크플로우를 통해 A의 잔액이 $500으로 떨어졌다고 가정해 보세요. 멱등성 체크는 여전히 통과하지만, 전제 조건은 통과하지 못합니다. 전제 조건 체크가 없으면, 우리는 초과 인출을 발생시킵니다.

모든 중요한 행동에는 다음 두 가지가 필요합니다:

- **멱등성 키**: 이중 실행을 방지합니다.
- **전제 조건 체크**: 승인된 내용과 상태가 여전히 일치하는지 확인합니다.

### 행동 후 검증

"도구가 200을 반환했다"는 검증이 아닙니다. 진정한 검증은 대상 상태를 다시 읽고, 사이드 이펙트가 실제로 발생했는지 확인합니다. 패턴:

- 데이터베이스 업데이트: `UPDATE ... RETURNING *` 후, 반환된 행이 의도된 상태와 일치하는지 어서트합니다.
- 이메일 전송: 제출 후 메시지 ID를 보낸 폴더에서 확인합니다.
- 파일 쓰기: 파일을 다시 읽고 해시를 계산합니다.
- API 호출: 대상 리소스에 대한 후속 `GET`를 수행합니다.

검증이 실패하면, 워크플로우는 알려진 불량 상태에 있습니다. 롤백이 발동됩니다.

### 롤백 계획

제안 후 커밋(15강)의 모든 중요한 행동은 롤백 계획을 포함합니다. 유형:

- **인밴드 롤백**: 사이드 이펙트를 직접 역전합니다(`INSERT` 후 `DELETE`, 전송 후 `Send-correction-email`).
- **보상 트랜잭션**: 원본을 중화하는 새로운 조치 (표준 SAGA 패턴).
- **아웃오브밴드 롤백**: 인간에게 알림을 보내고, 워크플로우를 일시 중지하며, 조사하기 위해 잘못된 상태를 유지합니다.

롤백이 없는 작업("이것을 되돌릴 수 없음")은 제안서에 명시해야 합니다. 롤백이 없는 작업은 커밋 시 더 강력한 인간 개입 루프 (HITL)(Human-in-the-Loop (HITL))가 필요합니다 (15강의 도전-응답 과제).

### EU AI Act 제14조 운영적 해석

제14조는 고위험 시스템에 대해 "효과적인 인간 감독"을 요구합니다. 운영 측면에서 구현자들은 이를 다음과 같이 해석합니다:

- 체크포인트는 감사자가 조회할 수 있습니다.
- 롤백은 리허설됩니다 (최소 한 번 엔드투엔드로 테스트됨).
- 감사 추적은 배포 후에도 유지됩니다 (체크포인트 백엔드는 비영구적이지 않습니다).
- 실패한 검증은 조용히 기록되지 않고 알림이 발생합니다.

커밋 중 크래시가 발생하고, 재개되며, 검증 + 롤백 경로 없이 사이드 이펙트를 완료하는 워크플로우는 제14조 테스트를 통과하지 못합니다.

### 날카로운 실패 모드: 이중 실행

이 영역에서 가장 흔한 프로덕션 인시던트입니다:

1. 조치가 승인되고, 멱등성 키 k가 부여됩니다.
2. 커밋이 시작되어 실행되고, 200을 반환합니다.
3. 워크플로우가 "커밋됨" 상태를 영속화하기 전에 크래시합니다.
4. 워크플로우가 재개되어 "승인되었지만 커밋되지 않음"을 보고, 재실행합니다.
5. 사이드 이펙트가 두 번 발생합니다.

완화책: 실행 전에 "in-flight" 의도를 영속화하고, 멱등성 키로 실행한 후, 사후 검증이 성공한 경우에만 "커밋됨"으로 표시합니다. 조치가 실행되고 상태 쓰기가 실패하면, 검증하고 (필요하다면) 재발화해야 함을 알 수 있습니다. 상태 쓰기가 성공하고 조치가 실패하면, 복구 경로를 통해 정확히 한 번 검증하고 발화합니다.

```figure
checkpoint-replay
```

## 사용하기

`code/main.py`는 멱등성, 전제 조건, 검증 및 롤백을 갖춘 체크포인트 워크플로우를 구현합니다. 드라이버는 네 가지 시나리오를 시뮬레이션합니다: 클린 실행, 크래시 후 재시도 (멱등성이 잡아냄), 전제 조건 실패 (워크플로우가 발화하지 않고 중단됨), 검증 실패 (롤백이 발화됨).

## 출시하기

`outputs/skill-rollback-rehearsal.md`는 제안된 워크플로우에 대한 롤백 리허설 테스트를 설계하고 감사 추적 지속성을 위해 체크포인트 백엔드를 감사합니다.

## 연습 문제

1. `code/main.py`를 실행하세요. 네 가지 시나리오를 검증하세요. 커밋 중 크래시 발생 시나리오의 경우, 재시도 전반에 걸쳐 액션이 정확히 한 번만 실행되는지 확인하세요.

2. "먼저 완료로 표시한 후 실행" 패턴을 수정하여 액션이 실행된 후 상태 쓰기가 발생하도록 하세요. 크래시 시나리오를 다시 실행하세요. 중복 액션이 몇 번 실행되는지 측정하세요.

3. 특정 프로덕션 액션(예: "Slack 채널에 게시")에 대한 롤백 계획을 설계하세요. 인밴드(in-band), 보상(compensating), 아웃오브밴드(out-of-band) 중 하나로 분류하세요. 선택의 근거를 설명하세요.

4. 알고 있는 워크플로우 하나를 가져오세요. 모든 상태 전환을 식별하세요. 각각에 지속성 요구 사항(지속 / 지속하지 않음)을 표시하세요. 현재 지속하지 않는 항목의 수를 세어 보세요.

5. 리허설된 롤백 테스트: 실제 워크플로우를 실행하고 크래시를 발생시키며 롤백 경로가 실행되는지 확인하는 엔드투엔드 테스트를 설계하세요. 이 테스트는 무엇을 어서트(assert)하나요?

## 핵심 용어

| 용어 | 사람들이 말하는 표현 | 실제 의미 |
|---|---|---|
| 체크포인트(Checkpoint) | "저장 지점" | 모든 그래프 상태 전환이 내구성 있는 저장소에 지속됨 |
| 리스(Lease) | "워커 클레임" | 워커가 실행을 수행 중임을 나타내는 짧은 수명의 클레임; 크래시 시 만료됨 |
| 전제 조건(Precondition) | "상태 게이트" | 상태가 승인된 액션과 여전히 일관됨을 주장하는 어서션 |
| 액션 후 검증(Post-action verify) | "재읽기 체크" | 대상 시스템에서 사이드 이펙트가 실제로 발생했는지 확인 |
| 인밴드 롤백(In-band rollback) | "직접 되돌리기" | 사이드 이펙트를 역연산으로 되돌림 |
| 보상 트랜잭션(Compensating transaction) | "SAGA undo" | 원본을 중화하는 새로운 액션 |
| 먼저 완료로 표시(Mark-as-done-first) | "상태 쓰기 순서" | 커밋에서 반환하기 전에 커밋된 상태를 지속함 |
| 제14조(Article 14) | "EU AI Act 인간 감독" | 운영적: 조회 가능한 체크포인트, 리허설된 롤백, 감사 가능한 추적 |
