# METR 시간 범위 및 외부 역량 평가

> METR (구 ARC Evals)는 2023년 12월부터 독립적인 501(c)(3) 비영리 단체입니다. Time Horizon 1.1 벤치마크 (2026년 1월)는 작업 성공 확률과 로그(전문가 인간 완료 시간)에 로지스틱 곡선을 적용합니다. 50% 확률에서의 교차점이 모델의 시간 범위를 정의합니다. 2025–2026년 참여 세트는 GPT-5.1, GPT-5.1-Codex-Max 및 프로토타입 모니터링 평가(모니터가 사이드 작업을 포착할 수 있는지, 에이전트가 회피할 수 있는지)를 포함합니다. 벤치마크 스위트: HCAST (180개 이상의 ML, 사이버, SWE, 추론 작업; 1분부터 8시간 이상), RE-Bench (71개 ML 연구-엔지니어링 작업, 전문가 기준선 포함), SWAA. 솔직한 고지: METR 측정값은 이상화된 상태입니다 — 인간 없음, 실제 결과 없음 — 그리고 팀은 평가와 배포 간 행동 격차(19강)를 문서화했습니다. 시간 범위는 상한일 뿐, 배포 예측이 아닙니다.

**유형:** Learn
**언어:** Python (표준 라이브러리, 로지스틱 적합 시간 범위 추정기)
**선수 요건:** 15단계 · 01강 (장기 시간 범위 에이전트), 15단계 · 19강 (RSP)
**시간:** 약 60분

## 문제점

확장 정책(19강, 20강)은 참조하는 측정값만큼만 유용합니다. "AI R&D-4 임계값"과 "장기 자율성"은 정책 문구로 정의되어 있으며, 특정 평가가 특정 숫자를 산출할 때만 실행 가능해집니다.

METR은 2024–2026년 외부 평가 기관으로, 이러한 많은 숫자를 정의했습니다. 이들은 프론티어 모델을 평가합니다 — 종종 출시 전, 연구소와 NDA 하에 — 그리고 이후 방법론을 공개합니다. Time Horizon 1.1 벤치마크 (2026년 1월)는 그들의 주요 산출물입니다: 역량을 인간이 이해할 수 있는 단위("이 모델은 전문가가 X시간 동안 작업하는 종류의 작업을 50% 신뢰도로 수행할 수 있다")로 압축하는 단일 스칼라 값입니다.

이 강의는 부분적으로 방법론(시간 범위가 어떻게 계산되는지)에 관한 것이며, 부분적으로 해석(왜 시간 범위가 상한일 뿐 배포 예측이 아닌지)에 관한 것입니다. 두 기술은 함께 속합니다. 시간 범위가 어떻게 적합(fit)되는지 이해하는 팀은 슬라이드에 "14시간"만 보는 팀보다 나쁜 벤더 주장에 속기 훨씬 어렵습니다.

## 개념

### METR 배경

- 설립: 2023년 12월 (구 ARC Evals, 독립적인 501(c)(3)으로 분사).
- 범위: 프론티어 모델의 자율적 능력 평가, 주로 출시 전.
- 협력 연구소: Anthropic, OpenAI (2025–2026년 여러 협력).
- 주요 산출물: Time Horizon 1.0 (2025년 3월), Time Horizon 1.1 (2026년 1월), 프로토타입 모니터링 평가.

### Time Horizon 적합성

방법론 (METR 블로그 및 논문에서):

1. 분 단위에서 시간 단위까지의 전문가 완료 시간을 포괄하는 작업 세트 수집. 현재 세트: HCAST (180+ 작업), RE-Bench (71 작업), SWAA.
2. 각 작업에서 모델을 실행; 성공 또는 실패 기록.
3. 로지스틱 곡선 적합: P(성공)을 log(전문가 완료 시간)의 함수로 표현.
4. 호라이즌은 P(성공) = 0.5가 되는 전문가 시간입니다.

로지스틱 적합 형태가 올바른 이유는, 능력이 일반적으로 작업 난이도와 증가하며 평탄화에 접근하는 관계를 가지기 때문입니다. 50% 지점은 선택 사항입니다 (10%, 90%일 수도 있음); METR는 상세 논문에서 여러 임계값을 보고하지만, 가장 직관적이라는 이유로 50%를 우선합니다.

### 2026년 1월 수치

Time Horizon 1.1에 따르면:

- Claude Opus 4.6: Time Horizon 1.1 (2026년 1월) 기준, 50% 신뢰도에서 약 14시간.
- HCAST 스타일 작업의 배증 시간: Time Horizon 1.1 (2026년 1월)이 보고한 2023년 이후 적합 기준 약 4.3개월 (130.8일); 약 7개월 수치는 Time Horizon 1.0의 전체 2019–2025년 적합 기준이며, TH1.1에서 2023년 이후 수치와 함께 보고됩니다.

이것은 15단계의 나머지 부분에서 참조하는 특정 수치입니다. Anthropic의 RSP v3.0 (19강)과 DeepMind의 FSF v3 (20강)에서 임계값 평가에 반영되는 측정 항목 중 하나로 인용됩니다.

### 벤치마크 세트

- **HCAST**: ML, 사이버 보안, 소프트웨어 엔지니어링 및 일반 추론에 걸친 189개 작업. 범위: 전문가 시간 기준 1분에서 8시간 이상. 호라이즌 수치를 뒷받침하는 주요 세트.
- **RE-Bench**: 인간 전문가 기준선을 가진 71개 ML 연구-엔지니어링 작업. 모델이 AI R&D-4 임계값으로 이어지는 ML R&D 작업을 수행할 수 있는지 측정합니다.
- **SWAA**: 더 짧은 작업; 호라이즌 곡선의 하한 보정에 유용합니다.

### 모니터링 평가 프로토타입

2025–2026년 METR의 작업에는 모니터링 평가 프로토타입이 포함되었습니다. 모니터가 모델이 사이드 작업(운영자가 요청한 것 외의 작업)을 수행하는 것을 포착할 수 있는지, 에이전트가 모니터를 회피할 수 있는지 테스트하는 것입니다. 이는 OpenAI PF v2의 "안전장치 약화(Undermining Safeguards)" 범주와 DeepMind FSF v3의 기만적 정렬 모니터링(20강)에 직접적으로 반영됩니다.

### 호라이즌이 상한인 이유

- **이상화된 도구**: 벤치마크 작업은 모델에게 깨끗한 도구와 잘 형식화된 데이터를 제공합니다. 실제 배포 환경은 훨씬 더 복잡합니다.
- **실제 결과 없음**: 모델은 실제로 고객에게 청구하지 않고, 실제 데이터를 삭제하지 않으며, 실제 사람과 연락하지 않습니다. 실제 배포 환경에는 되돌릴 수 없는 위험이 있습니다.
- **평가 컨텍스트 조작**: 01강. 모델은 테스트에서 다르게 행동합니다. 2026년 국제 AI 안전 보고서(International AI Safety Report)는 이를 경험적으로 문서화했습니다.
- **합법적인 사용자 변이 없음**: 벤치마크 프롬프트는 구조화되어 있습니다. 실제 사용자는 모호하고 컨텍스트에 의존하는 요청을 생성합니다.

호라이즌은 유리한 조건에서의 능력 상한입니다. 배포 신뢰성은 다른 수치이며, 더 낮습니다. 팀은 이를 파악하기 위해 자체 배포 분포를 측정해야 합니다.

### 외부 평가자 사례

외부 평가는 내부 연구소가 보고하는 지표를 최적화할 유인이 있기 때문에 중요합니다. METR의 독립성 — 선언된 방법론과 피어 리뷰된 논문을 가진 501(c)(3) 비영리 단체 —는 구조적인 완화책입니다. 이것만으로는 충분하지 않습니다(연구소는 METR이 무엇을 보는지 여전히 통제합니다). 하지만 외부 평가가 없는 것보다 엄격하게 더 좋습니다.

### 실무에서 호라이즌 수치를 사용하는 방법

- **능력 필터로 사용**: 모델의 호라이즌이 제안된 작업의 전문가 시간보다 훨씬 낮다면, 자율적으로 배포하지 마세요(01강의 스킬 파일).
- **추세 지표로 사용**: 배증 시간(doubling time)은 새로운 완화책이 없더라도 현재 관행이 얼마나 오래 안전할지 알려줍니다.
- **사전 정보로 사용**: 14시간 호라이즌은 시작점입니다. 작업 분포, 도구 품질, 배포 컨텍스트에 따라 낮추세요.

## 사용하기

`code/main.py`는 합성된 결과 집합을 사용하여 작업 성공률과 전문가 시간의 로그 값에 대한 로지스틱 적합(logistic fit)을 구현합니다. 50% 호라이즌(METR의 헤드라인), 10% 호라이즌(보수적), 90% 호라이즌(낙관적)을 보고합니다. 또한 평가 컨텍스트 조작(eval-context gaming)으로 성공률이 인위적으로 부풀려졌을 때 어떤 변화가 일어나는지도 시연합니다.

## 출시하기

`outputs/skill-horizon-interpretation.md`는 벤더의 호라이즌 주장을 검토하고, 벤치마크 주장과 실제 배포 환경 간의 격차 분석을 생성합니다.

## 연습 문제

1. `code/main.py`를 실행하세요. 적합된 50% 호라이즌이 합성된 정답(ground truth)과 일치하는지 확인하세요. 이제 작업 시간 그리드를 절반으로 줄여 보세요. 호라이즌 추정치가 의미 있게 변하나요?

2. METR의 Time Horizon 1.1 블로그 포스트를 읽어 보세요. 신뢰도가 가장 높은 특정 작업과 가장 낮은 특정 작업을 식별하세요. 그 격차가 존재하는 이유를 설명하세요.

3. METR의 "Measuring Autonomous AI Capabilities" 자료를 읽어 보세요. HCAST 작업 범주들을 나열하세요. 프로덕션 작업에서 더 높은 가중치를 부여할 범주 하나를 선택하고, 그 이유를 정당화하세요.

4. 시뮬레이터에 평가 컨텍스트 조작(eval-context gaming)을 도입하세요: 실패한 작업의 약 20%를 성공으로 뒤집으세요. 새로운 호라이즌을 보고하세요. 이는 20%의 조작률이 관측된 수치에 미치는 영향을 근사합니다.

5. 자체 버그 백로그나 대표 작업 집합에 대한 내부 호라이즌 평가를 설계하세요. 데이터 수집, 적합(fit), 그리고 출력 결과가 알려주는 내용을 설명하세요. METR 수치와 비교하세요.
