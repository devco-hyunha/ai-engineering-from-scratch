# 장기 실행 백그라운드 에이전트: 내구성 있는 실행(Durable Execution)

> 프로덕션 장기 에이전트는 `while True`에서 실행되지 않습니다. 모든 LLM 호출은 체크포인트, 재시도, 재생을 포함하는 활동(activity)이 됩니다. Temporal의 OpenAI Agents SDK 통합은 2026년 3월 GA가 되었습니다. Claude Code Routines (Anthropic)는 지속되는 로컬 프로세스 없이 예약된 Claude Code 호출을 실행합니다. 세션은 인간 입력 시 일시 중지되고, 배포를 생존하며, `thread_id`을 키로 하는 최신 체크포인트에서 재개됩니다. 새로운 인체공학 뒤에 오래된 패턴인 워크플로 오케스트레이션이 있으며, 새로운 입력은 하나입니다: LLM 호출은 복구 시 결정적으로 재생되어야 하는 비결정적 활동입니다.

**유형:** Learn
**언어:** Python (stdlib, 최소한의 내구성 있는 실행 상태 머신)
**선수 요건:** 15단계 · 10강 (권한 모드), 15단계 · 01강 (장기 에이전트)
**시간:** 약 60분

## 문제점

4시간 동안 실행되는 에이전트를 고려해 보세요. 이 에이전트는 세 개의 도구를 호출하고, 사용자에게 두 번 프롬프트를 요청하며, 40번의 LLM 호출을 수행합니다. 실행 중반에 호스트가 재부팅됩니다. 어떻게 될까요?

- 소박한 `while True` 루프에서는 모든 것이 손실됩니다. 실행은 처음부터 다시 시작됩니다. 세 개의 도구 호출(실제 사이드 효과가 있음)이 다시 실행됩니다. 사용자가 이미 승인한 사항에 대해 다시 프롬프트를 요청받습니다. 40번의 LLM 호출이 다시 청구됩니다.
- 내구성 있는 실행(Durable Execution)을 사용하면 실행은 최신 체크포인트에서 재개됩니다. 이미 완료된 활동은 다시 실행되지 않으며, 그 결과는 내구성 있는 로그에서 재생됩니다. 사용자는 이미 승인한 사항을 다시 승인하지 않습니다. 이미 수행된 LLM 호출은 다시 청구되지 않습니다.

이 패턴은 워크플로 엔진이 10년 동안 제공해 온 것과 동일합니다 (Temporal, Cadence, Uber의 Cherami). 새로운 점은 LLM 호출이 이제 활동의 일종이 되었다는 것입니다. 비결정적이고, 비용이 높으며, 사이드 효과가 있으며, 이 패턴에 깔끔하게 맞습니다.

이 강의의 반복되는 주제: 장기 신뢰성이 감소합니다 (METR은 "35분 감소"를 관찰합니다. 성공률이 기간에 따라 대략적으로 2차 함수적으로 감소합니다). 내구성 있는 실행은 신뢰성 프로파일이 지원하는 것보다 긴 실행을 가능하게 합니다. 설계가 올바르면 안전하게 실패하는 새로운 방법이며, 설계가 잘못되면 위험하게 실패합니다.

## 개념

### 활동, 워크플로, 재생

- **워크플로**: 결정적인 오케스트레이션 코드입니다. 활동의 순서, 분기, 대기 시간을 정의합니다. 이벤트 로그에서 재생할 때 예상치 못한 분기(divergence)가 발생하지 않도록 결정적이어야 합니다.
- **활동**: 비결정적이며 실패할 수 있는 작업 단위입니다. LLM 호출, 도구 호출, 파일 쓰기, HTTP 요청 등이 이에 해당합니다. 각 활동은 입력과 (완료되면) 출력이 기록됩니다.
- **이벤트 로그**: 내구성 있는 백업 저장소입니다. 모든 활동의 시작, 완료, 실패, 재시도 및 모든 워크플로 결정이 기록됩니다.
- **재생**: 복구 시 워크플로 코드가 처음부터 다시 실행됩니다. 이미 완료된 모든 활동은 재실행되지 않고 기록된 결과를 반환합니다. 완료되지 않은 활동만 실제로 실행됩니다.

이는 React가 가상 DOM에 대해 다시 렌더링하거나, Git이 커밋에서 작업 트리를 재구성하는 것과 동일한 형태입니다. 오케스트레이터의 결정성이 내구성 있는 시스템을 저렴하게 만드는 핵심입니다.

### LLM 호출이 이 패턴에 적합한 이유

LLM 호출은 다음과 같습니다:
- 비결정적입니다 (온도(Temperature) > 0; 온도 0에서도 모델 버전에 따라 결과가 달라질 수 있습니다).
- 비용이 많이 듭니다 (비용 및 지연 시간).
- 실패할 가능성이 있습니다 (속도 제한, 시간 초과).
- 측면 효과가 있습니다 (도구를 호출하는 경우).

이것은 정확히 활동의 프로필입니다. 모든 LLM 호출을 활동으로 래핑하면 백오프 재시도(Retry with Backoff), 재시작 간 체크포인팅, 디버깅을 위한 재생 가능한 추적을 얻을 수 있습니다.

### `thread_id`을 키로 하는 체크포인트

LangGraph, Microsoft Agent Framework, Cloudflare Durable Objects, Claude Code Routines는 모두 동일한 API 형태에 수렴했습니다. `thread_id` (또는 동등한 것)이 세션을 식별하며, 각 상태 전환은 백엔드(PostgreSQL 기본, 개발용 SQLite, 캐시용 Redis)에 지속됩니다. 재개(resume)는 최신 체크포인트를 읽습니다.

백엔드 선택이 중요합니다:

- **PostgreSQL**: 내구성 있고, 쿼리 가능하며, 배포를 통해 데이터가 유지됩니다. LangGraph의 기본값입니다.
- **SQLite**: 로컬 개발 전용; 호스트 간에 데이터가 손실됩니다.
- **Redis**: 빠르지만 AOF/스냅샷이 설정되지 않으면 휘발성입니다.
- **Cloudflare Durable Objects**: 투명하게 분산됨; 고유 키로 범위 지정; 몇 시간에서 몇 주까지 지속됨.

### 1급 상태로서의 인간 입력

제안 후 커밋(15강)은 "인간 대기 중"이라는 내구성 있는 상태가 필요합니다. 워크플로우가 일시 중지되고, 외부 큐가 대기 중인 요청을 유지하며, 승인이 이루어지면 정확히 그 지점에서 재개됩니다. 내구성 없이는 최선 노력(best-effort)에 불과하지만, 내구성이 있으면 밤사이 승인이 도착하고 아침에 워크플로우가 이어집니다.

### 35분 이후의 성능 저하

METR는 측정된 모든 에이전트 유형이 약 35분 이상의 연속 운영 후 신뢰성 감쇠를 보인다고 관찰했습니다. 작업 시간을 두 배로 늘리면 실패율이 약 네 배로 증가합니다. 내구성 있는 실행은 이를 해결하지 못합니다; 신뢰성 프로파일이 허용하는 것보다 더 오래 실행할 수 있게 할 뿐입니다. 안전한 패턴은 내구성 있는 실행과 재진입 시 새로운 HITL을 요구하는 체크포인트, 그리고 벽시계 시간과 무관하게 총 컴퓨팅을 제한하는 예산 킬 스위치(13강)를 결합하는 것입니다.

### 내구성 있는 실행이 잘못된 답인 경우

- 몇 분 미만으로 실행되며 인간 입력이 없는 경우. 오버헤드가 이점보다 큽니다.
- 엄격하게 읽기 전용인 정보 검색.
- 정확성이 하나의 컨텍스트 윈도우 내에서 엔드투엔드로 완료되어야 하는 작업 (일부 추론 작업; 일부 원샷 생성).

## 사용하기

`code/main.py`는 스탄다드 라이브러리 Python으로 최소한의 내구성 있는 실행 엔진을 구현합니다. 이는 다음을 지원합니다:

- 입력과 출력을 JSON 이벤트 로그에 기록하는 `@activity` 데코레이터.
- 액티비티를 순서대로 연결하는 워크플로우 함수.
- 완료된 액티비티를 재실행하지 않고 재생(replay)하는 `run_or_replay(workflow, event_log)` 함수.

드라이버는 세 개의 액티비티로 구성된 워크플로우를 시뮬레이션하고, 중간에 크래시를 일으키며, (a) 모든 것을 재실행하는 단순 재시도와 (b) 누락된 액티비티만 실행하는 재생을 보여줍니다.

## 출시하기

`outputs/skill-durable-execution-review.md`는 제안된 장기 실행 에이전트 배포가 올바른 내구성 있는 실행 형태를 갖는지 검토합니다: 액티비티, 결정성, 체크포인트 백엔드, 인간 입력 상태, 그리고 재개 시 HITL 정책.

## 연습 문제

1. `code/main.py`을 실행하세요. 단순 재시도와 리플레이 간 활동 실행 횟수의 차이를 관찰하세요. 크래시 지점을 변경하고 리플레이 횟수가 이에 따라 어떻게 변하는지 확인하세요.

2. 토이 엔진이 `thread_id`을 명시적으로 사용하도록 변환하세요. 엔진을 공유하는 두 개의 동시 세션을 시뮬레이션하고, 이벤트 로그가 충돌하지 않음을 확인하세요.

3. 토이 엔진에서 하나의 활동을 선택하세요. 비결정성(워크플로 결정 내부의 벽시계 타임스탬프)을 도입하세요. 리플레이 시 발산(divergence)을 시연하세요. 실제 엔진이 이를 어떻게 처리하는지(사이드 이펙트 등록, `Workflow.now()` API) 설명하세요.

4. LangChain의 "프로덕션 딥 에이전트 뒤의 런타임(Runtime behind production deep agents)" 게시물을 읽으세요. 런타임이 지속(persist)하는 모든 상태를 나열하고, 각 상태가 어떤 장애 모드(failure mode)를 다루는지 명시하세요.

5. 6시간 자율 코딩 작업에 대한 체크포인트 정책을 설계하세요. 어디에서 체크포인트를 찍나요? 크래시 후 재개(resume-on-crash)는 어떤 모습인가요? 무엇이 새로운 HITL(인간 개입 루프)을 필요로 하나요?
