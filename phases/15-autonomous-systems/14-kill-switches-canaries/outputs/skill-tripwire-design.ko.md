에이전트 배포를 위해 제안된 감지 스택을 3종 감지 참조(킬 스위치, 서킷 브레이커, 카나리)에 대해 감사하고, 누락된 항목, 잘못 조정된 항목, 에이전트에 노출된 항목을 식별해 보세요.

다음 내용을 생성합니다:

1. **킬 스위치 감사.** 스위치가 어디에 위치하는지 확인하세요(기능 플래그, Redis, 서명된 설정). 에이전트의 자격 증명이 스위치를 트리거할 수 없음을 확인하세요. 모든 중요한 작업이 시작 시점뿐만 아니라 매번 스위치를 확인함을 확인하세요. 재활성화가 명시적인 인간 작업임을 확인하세요.
2. **서킷 브레이커 인벤토리.** 브레이커가 감시하는 모든 패턴을 나열하세요(반복, 연속 실패, 속도, 신뢰 밖 읽기 이후 특정 도구). 각 패턴에 대해 임계값과 쿨다운을 명시하세요. 임계값이 10 이상인 경우 보통 너무 느슨합니다.
3. **카나리 설계.** 환경 내 모든 카나리 토큰을 나열하세요. 각 토큰에 대해: 종류(가짜 자격 증명, 가짜 DB 레코드, 가짜 파일, 가짜 메모리 항목), 위치, 알람을 트리거하는 접근, 호출 대상 페이지를 확인하세요. 카나리가 합법적으로 건드려야 할 이유가 없음을 확인하세요.
4. **통계적 + 하드 레이어링.** 스택이 통계적 감지(EWMA, z-점수) 외에도 적어도 하나의 하드 한도(17강의 헌법적 스타일)를 사용함을 확인하세요. 통계적 감지 만으로는 느린 드리프트를 허용합니다.
5. **격리 경로.** 감지기가 발동되면 어떻게 되는지 확인하세요. 전체 에이전트 중지, 경로별 일시 정지, 트래픽 리디렉션(eBPF / Cilium 허니팟), 알람 전용. 경로가 적어도 한 번 엔드투엔드로 테스트되었음을 확인하세요.

하드 거부 조건:
- 외부 킬 스위치가 없는 모든 배포.
- 에이전트가 쓰기 권한을 가진 시스템에 저장된 카나리 토큰.
- 하드 한도 없이 통계적 감지 만을 사용하는 경우.
- 인간 검토 없이 자동으로 재활성화되는 쿨다운을 가진 서킷 브레이커.
- 킬 스위치가 시작 시점에만 확인되고 작업 단위로는 확인되지 않는 무인 실행.

거부 규칙:
- 사용자가 에이전트의 자격 증명을 제외한, 킬 스위치를 호스팅하는 특정 시스템을 지정할 수 없다면 거절하세요. "에이전트가 읽는 구성 파일을 사용합니다"는 에이전트가 구성 파일을 쓸 수 있다면 킬 스위치가 아닙니다.
- 사용자가 자동 모드 분류기(10강)를 트립와이어의 대체 수단으로 취급한다면 거절하세요. 분류기는 탐지 및 대응과 직교하는 관계입니다.
- 제안된 카나리가 에이전트가 합법적으로 읽을 수 있는 시스템에 위치한다면 거절하고 재설계를 요구하세요.

출력 형식:

다음 내용을 포함한 트립와이어 감사 결과를 반환하세요:
- **킬 스위치 라인** (위치, 점검 주기, 재활성화 절차)
- **서킷 브레이커 표** (패턴, 임계값, 쿨다운)
- **카나리 표** (토큰, 위치, 알람, 소유자)
- **계층화 노트** (통계적 한계 + 하드 한계 존재 여부)
- **격리 흐름** (무엇이 트리거되는지, 어떤 일이 일어나는지, 테스트 여부)
- **준비 상태** (프로덕션 / 스테이징 / 연구 전용)
