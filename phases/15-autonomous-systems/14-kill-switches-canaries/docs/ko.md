# 킬 스위치, 서킷 브레이커, 카나리 토큰

> 킬 스위치는 에이전트의 편집 영역 외부에 있는 부울 값입니다. Redis 키, 기능 플래그, 서명된 설정 등이 있으며, 에이전트를 완전히 비활성화합니다. 서킷 브레이커는 더 세분화되어 있습니다. 특정 패턴(예: 연속된 5번의 동일한 도구 호출)에서 작동하며, 문제 있는 경로를 일시 중지하고 인간에게 에스컬레이션합니다. 카나리 토큰은 고전적인 기만 전략에서 유래했습니다. 에이전트가 합법적인 이유로 건드릴 수 없는 가짜 자격 증명이나 허니팟 레코드를 의미하며, 접근 시 경보가 발생합니다. eBPF 기반 데이터 경로(예: Cilium)는 격리된 포드의 아웃고 traffic를 커널 레벨에서 포렌식 허니팟으로 재작성할 수 있습니다. 공개된 Cilium 벤치마크는 부하 상태에서 P99 데이터 경로 지연이 밀리초 미만이라고 보고합니다. 전파 예산은 정책 업데이트가 노드에 도달하는 방식에 따라 달라지며, 데이터 경로 자체에는 의존하지 않습니다. 이동하는 기준선에 적응하는 통계적 탐지자(EWMA, CUSUM)는 드리프트를 조용히 수용합니다. 굽혀지지 않는 하드한 헌법적 한계와 함께 계층화해 보세요.

**유형:** Learn
**언어:** Python (stdlib, 세 탐지자 시뮬레이터: 킬 스위치, 서킷 브레이커, 카나리)
**선수 요건:** 15단계 · 13강 (비용 거버너), 15단계 · 10강 (권한 모드)
**시간:** 약 60분

## 문제점

비용 거버너(13강)는 에이전트가 지출할 수 있는 금액을 제한합니다. 예산 내에서 에이전트가 할 수 있는 행동은 제한하지 않습니다. $50 속도 제한이 있는 에이전트도 비밀을 유출하거나, 잘못된 게시물을 발행하거나, 리소스를 삭제할 수 있습니다. 비싼 행동은 토큰 측면에서는 종종 저렴한 행동입니다.

이 강의는 비용 계층 옆에 있는 세 탐지자를 다룹니다:

1. **킬 스위치**: 에이전트의 접근 범위 외부에 있는 부울 오프 버튼.
2. **서킷 브레이커**: 특정 경로를 일시 중지하는 행동 패턴 탐지자.
3. **카나리 토큰**: 합법적인 이유로 건드릴 수 없는 에이전트가 건드림으로써 스스로를 드러내는 미끼.

이 세 가지는 모두 LLM 이전의 엔지니어링입니다. 고전적인 기만 전략, 속도 제한 서킷 브레이커, 기능 플래그 킬은 자율 에이전트보다 먼저 존재했습니다. 새로운 것은 공격 표면입니다. 에이전트는 신뢰할 수 없는 콘텐츠를 읽고(11강), 자신의 메모리를 편집하며, 많은 안전해 보이는 행동을 하나의 위험한 행동으로 구성할 수 있습니다. 여기서 언급된 탐지자는 에이전트의 자기 보고를 신뢰하지 않기 때문에 작동합니다.

## 개념

### 킬 스위치

킬 스위치는 에이전트가 읽을 수 있지만 쓸 수 없는 부울 값입니다. 구현 선택지:

- **관리형 서비스의 기능 플래그.** LaunchDarkly, Statsig, Unleash. 업데이트가 몇 초 내에 전파됩니다.
- **에이전트가 폴링하는 Redis 키.** 단순합니다; 에이전트 프로세스가 매 턴마다 확인해야 합니다.
- **객체 저장소의 서명된 설정.** 에이전트는 부팅 시 서명을 검증하며, 서명되지 않은 상태를 거부합니다.
- **OS 수준 신호 또는 컨테이너 생명주기 킬.** Docker `kill`, Kubernetes `kubectl delete pod`, systemd stop.

올바른 킬 스위치가 가져야 할 속성:

- 에이전트가 이를 `off`로 설정할 수 없습니다. (에이전트의 자격 증명이 쓰기 권한을 갖지 않는 시스템에 존재합니다.)
- 부팅 시뿐만 아니라 모든 중요한 작업에서 확인됩니다.
- 오프 상태일 때, 에이전트는 외부적으로 관찰 가능한 모든 동작(에이전트가 접근할 수 있는 시스템에 대한 로깅 포함)을 수행하지 않습니다.
- 재활성화는 자동 타임아웃이 아닌 명시적인 인간 작업입니다.

### 서킷 브레이커

서킷 브레이커는 전체 에이전트가 아닌 특정 패턴을 일시 중지합니다. 고전적인 형태 (2007년 Nygard의 책에서 유래, 현재까지 유효):

- **Closed**: 작업이 허용됩니다.
- **Open**: 작업이 차단됩니다.
- **Half-open**: 쿨다운 후, 1~3번의 프로브 시도가 허용됩니다 (기본값 1); 성공하면 브레이커가 닫히고, 남은 실패가 있으면 다시 열립니다.

에이전트 관련 트리거:

- 연속 5번의 동일한 도구 호출 (반복 루프).
- 서로 다른 입력으로 같은 도구에서 연속 5번의 실패 (시스템적 실패).
- 임계값을 초과하는 도구 호출 속도 (13강 속도).
- 신뢰 경계 밖의 콘텐츠를 읽은 후 특정 도구 호출 (예: `file.delete`) (11강).

### 카나리 토큰

카나리 토큰 (허니토큰이라고도 함)은 에이전트가 절대 건드려서는 안 되는 입력입니다. 접근은 알람입니다.

에이전트용 예시:

- 실제 권한이 없는 환경에 가짜 `AWS_SECRET_ACCESS_KEY`를 배치합니다. 유출 시도는 즉시 귀속 가능합니다.
- 알려진 센티널 값으로 플래그가 지정된 가짜 데이터베이스 레코드입니다. 이 레코드를 읽거나 업데이트하면 알림이 발생합니다.
- 작업 공간에 있는 가짜 파일입니다. 이 파일을 읽거나 편집하는 것은 의심스러운 활동입니다.
- 세션 시작 시 주입된 가짜 메모리 항목입니다. 이 항목이 이후 출력에 나타나면 메모리가 유출된 것입니다.

카나리 설계는 워크플로우에 특화되어 있습니다. 에이전트가 합법적인 이유로 건드릴 수 있는 카나리는 잡음입니다.

### 통계적 한계와 하드 한계를 계층화하는 이유

통계적 탐지 도구(EWMA, CUSUM, 도구 호출률에 대한 z-점수)는 이동하는 기준선에 적응합니다. 이는 합법적인 드리프트에는 기능이지만, 적대적 드리프트에는 버그입니다. 끈기 있는 공격자는 기준선을 천천히 변화시켜 알람이 울리지 않게 할 수 있습니다.

하드 헌법적 한계(17강)는 굽지 않습니다. "`secrets@`에 이메일을 보내지 마라"와 같은 헌법적 규칙은 더 단순하고, 감사 가능하며, 느린 드리프트로 조작할 수 없습니다. 계층화 패턴: 통계적 탐지 도구는 대부분의 잡음을 잡으며, 하드 한계는 탐지기를 지나온 공격을 잡습니다.

### eBPF 데이터 경로 리디렉션을 통한 격리

Cilium의 eBPF 기반 네트워크 정책은 격리된 pod의 egress를 커널 레이어에서 포렌식 허니팟으로 재작성할 수 있습니다. Cilium의 공개 벤치마크는 TCP_RR에서 P99 데이터 경로 지연이 밀리초 미만이라고 보고합니다; 클러스터에서 격리를 *트리거*하는 데 걸리는 월클록 예산은 정책 업데이트가 제어 평면에서 노드로 전파되는 방식에 의해 지배됩니다(연산자가 사전 로드된 Kubernetes에서는 몇 백 밀리초가 현실적입니다; 꼬리 지연은 클러스터 크기와 조정 주기(reconcile cadence)에 따라 달라집니다). 이는 두 가지를 제공합니다: 에이전트가 실제 데이터를 유출하지 않으며, 허니팟 내부의 에이전트 행동이 완전히 관찰됩니다. 카나리 토큰과 같은 패턴, 다른 레이어입니다: 에이전트는 격리 상태에서 시도하는 것을 통해 의도를 드러냅니다.

### 어떤 탐지기도 잡지 못하는 것

- **허용된 프리미티브로 구성되는 시맨틱 공격.** 개별적인 모든 행동은 모든 탐지기를 통과합니다; 구성이 문제입니다. 이는 10강의 Auto Mode 복합 실패입니다.
- **탐지기를 페이로드의 일부로 포함하는 공격.** 에이전트가 "행동하기 전에 카나리를 비활성화하라"라고 적힌 페이지를 읽고 에이전트가 그 기능을 가지고 있다면, 탐지기가 손상됩니다. 카나리 토큰은 에이전트가 수정할 수 없는 시스템에 있어야 합니다.

## 사용하기

`code/main.py`는 세 가지 감지기를 통해 짧은 에이전트(Agent) 궤적을 시뮬레이션합니다. 외부 dict에 보관된 kill switch, 동일한 도구 호출이 5번 반복될 때 작동하는 서킷 브레이커(Circuit Breaker), 읽기 시 경보를 발생시키는 canary 파일이 있습니다. 합성 궤적(legitimate actions, repetitive loop, canary probe, kill-switch-triggered scenario)을 입력하여 에이전트의 작업이 중단되는 상황을 시뮬레이션합니다.

## 연습 문제

1. `code/main.py`를 실행하세요. 서킷 브레이커(Circuit Breaker)가 5번째 턴(5번째 동일한 호출)에서 작동하고, canary가 9번째 턴(fake-key read)에서 작동하는지 확인하세요.

2. 통계적 감지기를 추가하세요: 도구 호출 속도에 대한 EWMA z-score를 적용합니다. 천천히 드리프트하는 궤적을 입력하여 감지기가 작동하지 않는 것을 확인하세요. 이제 하드 리밋(10분 내 도구 호출 50회 제한)을 추가하여 동일한 궤적에서 하드 리밋이 작동하는 것을 확인하세요.

3. 브라우저 에이전트(Agent)를 위한 canary 토큰 세트(11강)를 설계하세요. 최소 세 개의 canary를 나열하고 각각이 무엇을 감지하는지 설명하세요.

4. Cilium 네트워크 정책 문서를 읽어보세요. egress-redirect 격리 흐름을 구체적으로 설명하세요: 어떤 정책 selector, 어떤 pod, 어떤 egress rewrite, 어떤 alert가 사용되는지 설명하세요. "격리 결정"부터 "첫 번째 redirect된 packet"까지의 wall-clock latency는 무엇이 결정합니까?

5. kill-switch된 에이전트(Agent)의 재활성화 절차를 정의하세요. 누가 재활성화할 수 있습니까? 무엇이 문서화되어야 합니까? 재활성화 전에 에이전트(Agent)에 무엇이 변경되어야 합니까?

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|---|---|---|
| Kill switch | "Off button" | 에이전트(Agent)의 편집 영역 외부에 있는 Boolean; 모든 중요한 작업마다 체크됨 |
| 서킷 브레이커(Circuit Breaker) | "Pattern pause" | 반복, 실패율, 속도 제한(rate-limit)에 대한 작업별 작동 |
| Canary 토큰(Token) | "Honeytoken" | 에이전트(Agent)가 합법적인 이유로 건드릴 수 없는 미끼; 접근 시 경보가 발생 |
| Honeypot | "Forensic sandbox" | 격리된 에이전트(Agent)가 관찰되는 redirect된 트래픽 / 작업 공간 |
| EWMA | "Moving average" | 지수 가중치; 드리프트(feature + bug)에 적응 |
| CUSUM | "누적 합" | 기준선에서의 지속적 변화를 감지합니다 |
| Hard limit | "헌법적 규칙" | 적응하지 않으며, 이력과 무관하게 일정합니다 |
| Constitutional limit | "항상 참인 규칙" | 17강의 헌법과 연결되어 있으며, 에이전트가 편집할 수 없습니다 |
