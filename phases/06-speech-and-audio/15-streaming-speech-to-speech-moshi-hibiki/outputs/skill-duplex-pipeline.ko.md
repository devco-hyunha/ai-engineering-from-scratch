워크로드(레이턴시 목표, 도구 호출 필요성, 언어 커버리지, 하드웨어 예산, 클라우드 vs 엣지)를 고려하여 다음을 출력합니다:

1. 아키텍처. 전체 이중 통신(Moshi / GPT-4o Realtime / Gemini Live) vs 파이프라인(LiveKit + STT + LLM + TTS, 12강). 한 문장 이유.
2. 모델. Moshi · Hibiki · Hibiki-Zero · Sesame CSM · GPT-4o Realtime · Gemini 2.5 Live · 전통적 파이프라인. 이유.
3. 확장성. 세션당 GPU 비용(Moshi는 슬롯을 점유함), 최대 동시 세션 수, 콜드 스타트 영향.
4. 도구 호출 경로. 필요 시 — 하이브리드 파이프라인(이중 통신 + 도구 호출용 외부 LLM) 또는 순수 파이프라인. 트레이드오프를 설명합니다.
5. 언어 커버리지. 전체 이중 통신 모델은 언어 지원 범위가 좁습니다. 파이프라인은 LLM의 다국어 기능을 상속받습니다.

도구 호출 / 검색이 필요한 엔터프라이즈 에이전트에 전체 이중 통신 전용 아키텍처를 거부합니다. Moshi는 대화 모델이며 에이전트 프레임워크가 아닙니다. 250 ms 미만 레이턴시의 대화형 에이전트에 파이프라인 전용 아키텍처를 거부합니다. 단계가 누적됩니다. 한 GPU에서 4개 이상의 동시 세션에 Moshi를 거부합니다. 경쟁(contention)이 발생합니다.

예시 입력: "언어 학습용 음성 동반자 — 대화형 유창성 연습. 영어 + 프랑스어. &lt; 250 ms 응답성. 일일 활성 사용자 10k."

예시 출력:
- 아키텍처: 전체 이중 통신(Moshi). 250 ms 미만 레이턴시 요구사항 + 대화형 유창성은 Moshi의 강점에 부합합니다.
- 모델: Moshi. EN + FR 모두 잘 지원됩니다. CC-BY 4.0 라이선스.
- 확장성: 동시 세션 4-6개당 L4 GPU 1개 → 동시성 10%인 10k DAU의 피크 시 약 1500 GPU. 조용한 경로에는 Kyutai Pocket TTS + 로컬 Whisper를 사용하는 온디바이스 라이트 모드를 계획합니다.
- 도구 호출: 최소화 — "문법 힌트 표시" 및 "이 구문 번역"은 작은 LLM 사이카를 통해 라우팅할 수 있습니다. 대부분의 상호작용은 Moshi가 빛나는 오픈 엔드 대화입니다.
- 언어 커버리지: EN + FR (네이티브); ES / DE / JP는 Hibiki-Zero 적응을 통해 지원(새 언어당 1000시간의 오디오 필요).
