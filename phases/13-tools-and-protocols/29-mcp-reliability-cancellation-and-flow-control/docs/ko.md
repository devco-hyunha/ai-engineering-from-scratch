# MCP 신뢰성, 취소 및 흐름 제어

> 요청 ID는 메시지를 상관관계 짓습니다. 이는 사이드 이펙트를 안전하게 만들지 않으며, 워커를 중지하지도, 느린 소비자로 인한 스트림을 보호하지도 않습니다.

**유형:** Build
**언어:** Python
**선수 요건:** 13단계, 09강 및 13강
**시간:** 약 120분

## 학습 목표

- stdio 및 Streamable HTTP에 대한 올바른 취소 신호를 구현해 보세요.
- 취소 후 메시지를 보내지 않으면서 완료 및 취소 경쟁을 해결해 보세요.
- 요청 취소를 내구성 있는 `tasks/cancel` 의미론과 분리해 보세요.
- 사이드 이펙트와 명시적인 멱등성 키를 기반으로 재시도 결정을 구축해 보세요.
- 최종 응답을 보존하면서 진행 상황 큐를 제한해 보세요.
- 재연결, 재검색 및 지터가 포함된 백오프를 통해 스트림을 복구해 보세요.

## 문제점

정상적인 경로(happy path)는 가장 비용이 많이 드는 분산 시스템 버그를 숨깁니다.

클라이언트가 도구를 호출합니다. 서버가 작업을 시작합니다. 진행 상황이 도착합니다. 프록시가 스트림을 버퍼링합니다. 클라이언트가 타임아웃에 도달하고 연결을 끊습니다. 서버는 1밀리초 후에 완료합니다. 클라이언트는 새로운 JSON-RPC id로 재시도합니다. 변경(mutation)이 두 번 실행됩니다.

모든 구성 요소는 로컬적으로 정상적으로 동작했습니다. 시스템은 전역적으로 실패했습니다.

MCP는 메시지와 전송 동작을 정의하지만, 애플리케이션은 여전히 다음을 소유합니다:

- 시간 예산;
- 비즈니스 멱등성;
- 제한된 큐;
- 재시도 분류;
- 내구성 있는 작업 상태;
- 재연결 및 재검색 정책.

이 강의는 이러한 결정을 결정론적인 시뮬레이터에 구축합니다. 슬립(sleep), 소켓, 랜덤 실패는 없습니다. 취소 이벤트 순서를 직접 제어합니다. 하나의 동기화된 스레드 테스트가 두 개의 원장(ledger) 클라이언트가 동일한 멱등성 키를 놓고 경쟁하도록 강제합니다.

## 요청 취소는 전송 방식에 특화되어 있습니다

모든 전송 방식에서 의도는 동일합니다: 클라이언트가 진행 중인 결과(in-flight result)를 더 이상 필요로 하지 않습니다. 전송 신호(wire signal)는 다릅니다.

### stdio

stdio는 하나의 공유 양방향 채널을 사용합니다. 클라이언트는 알림(notification)을 보냅니다:

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 41,
    "reason": "User closed the operation"
  }
}
```

알림은 fire-and-forget입니다. 서버는 이에 대한 JSON-RPC 응답을 보내지 않습니다.

서버는 작업을 중단하고, 자원을 해제하며, 취소된 요청에 대한 응답을 보내지 않아야 합니다. 요청이 알려지지 않았거나, 이미 완료되었거나, 안전하게 중단할 수 없는 경우 취소를 무시할 수 있습니다.

형식이 잘못된 알림, 알려지지 않은 알림, 이미 완료된 취소 알림은 무시됩니다. 이러한 경쟁 조건을 새로운 오류로 바꾸면 더 많은 경쟁 조건이 발생합니다.

### 스트리밍 HTTP

최신 스트리밍 HTTP는 각 요청에 자체 HTTP 응답 또는 SSE 응답 스트림을 제공합니다. 클라이언트는 해당 요청의 응답 스트림을 닫음으로써 취소를 수행합니다.

일반적인 HTTP 요청에 대해 `notifications/cancelled`을 POST하지 마세요. 스트림 닫기가 취소 신호입니다.

서버가 연결 끊김을 감지하면, 작업을 중단하고 해당 요청에 대해 더 이상 메시지를 보내지 않아야 합니다.

### 서버가 보내는 취소는 범위가 좁습니다

서버는 `notifications/cancelled`을 사용하여 임의의 클라이언트 호출을 취소하지 않습니다. stdio에서는 서버가 보내는 취소가 `subscriptions/listen` 요청을 종료하는 용도로만 예약됩니다. 이 경로를 일반적인 클라이언트 요청 취소와 분리하여 유지하세요.

## 취소는 경쟁 조건입니다

두 가지 이벤트 순서 모두 유효합니다.

### 취소가 우선합니다

```text
request starts
client sends cancellation signal
server marks request cancelled
worker reaches completion
server suppresses the response
```

### 완료 우선합니다

```text
request starts
worker commits the result
server sends the response
cancellation arrives late
server ignores the late notification
```

클라이언트는 이미 포기한 요청에 대한 늦은 응답도 무시해야 합니다. 네트워크 지연 때문에 어느 쪽이 먼저 이벤트를 관찰했는지 증명할 수 없습니다.

```figure
mcp-reliability-race
```

이 강의의 `RequestCoordinator`은 하나의 최종 상태를 저장합니다. `complete()`은 취소 후 응답을 반환하지 않습니다. 늦은 취소는 완료된 레코드를 변경할 수 없습니다.

## 타임아웃은 두 개의 시계가 필요합니다

단일 비활성 타이머만으로는 충분하지 않습니다.

두 가지 제한을 사용하세요:

1. **유휴 타임아웃.** 요청이 유용한 활동을 생성하지 않을 수 있는 기간.
2. **최대 타임아웃.** 요청 시작부터의 절대적인 벽시계 예산.

진행 상황은 유휴 시계를 리셋할 수 있습니다. 최대 마감 시간을 제거해서는 안 됩니다.

```text
start: 0 ms
progress: 400 ms
progress: 800 ms
progress: 1200 ms
idle timeout: 500 ms
maximum timeout: 2000 ms
```

1500ms 시점에서는 최신 진행 상황이 300ms 전이므로 요청은 여전히 활성 상태입니다. 2000ms 시점에서는 1999ms에 또 다른 진행 이벤트가 도착했더라도 최대 마감 시간이 요청을 취소합니다.

진행 상황은 선택 사항입니다. 서버는 진행 토큰을 수락하고 업데이트를 전혀 내보내지 않을 수 있습니다. 토큰의 존재를 무한한 시간 초과로 전환하지 마세요.

MCP 진행 값은 반드시 증가해야 합니다. 완료 또는 취소 후 알림이 중단됩니다. 빠른 작업자가 전송을 압도하지 않도록 진행 상황을 속도 제한하세요.

## 요청 취소는 `tasks/cancel`가 아닙니다

이러한 메커니즘은 서로 다른 수명 주기를 해결합니다.

| 메커니즘 | 대상 | 신호 | 성공의 의미 |
|-----------|--------|--------|--------------------|
| stdio에서의 요청 취소 | 하나의 진행 중인 RPC | `notifications/cancelled` | 클라이언트가 요청을 포기했습니다. 서버는 가능한 경우 중단해야 합니다 |
| HTTP에서의 요청 취소 | 하나의 진행 중인 응답 스트림 | 스트림을 닫습니다 | 클라이언트가 요청을 포기했습니다. 서버는 가능한 경우 중단해야 합니다 |
| `tasks/cancel` | 하나의 지속성 있는 Task | 일반적인 MCP 요청 | 서버가 취소 의도를 확인했습니다 |

성공적인 `tasks/cancel` 결과는 작업자가 중단되었음을 증명하지 않습니다. 작업자가 체크포인트에서 플래그를 관찰할 때까지 Task가 `working` 상태로 남아 있을 수 있습니다. 그 체크포인트 이전에 작업이 완료될 수 있습니다.

HTTP 연결이 닫힐 때 지속성 있는 Task 상태를 지우지 마세요. Task를 생성하는 이유는 그 수명 주기가 하나의 요청과 하나의 연결을 초월하기 때문입니다.

## 새로운 JSON-RPC ID는 멱등성이 아닙니다

JSON-RPC ID는 요청과 응답을 상관시킵니다. 비즈니스 작업을 식별하지는 않습니다.

클라이언트가 id `41`로 결제를 제출하고 응답을 잃어버린 후 id `42`로 재시도한다고 가정해 보세요. 서버는 두 개의 서로 다른 메시지를 봅니다. 애플리케이션 키가 없으면, 서버는 이 두 메시지가 하나의 체크아웃을 나타낸다는 것을 알 수 없습니다.

멱등성 키는 비즈니스 의도를 식별합니다:

```json
{
  "name": "charge_account",
  "arguments": {
    "account": "acct-7",
    "cents": 1200,
    "idempotencyKey": "checkout-7"
  }
}
```

서버는 다음을 저장합니다:

- 키;
- 작업 인자의 지문;
- 커밋된 결과.

동일한 키와 동일한 인자는 저장된 결과를 반환합니다. 동일한 키에 다른 인자를 사용하는 것은 거부됩니다. 이는 실수로 키를 재사용하여 다른 비즈니스 작업을 변경하는 것을 방지합니다.

### 원장 경계는 원자적이고 지속성 있어야 합니다

이 순서는 안전하지 않습니다:

```text
check key
run mutation
store result
```

두 워커가 모두 누락된 키를 관찰하고 변형을 실행할 수 있습니다. 효과 발생 후 저장 전에 충돌이 발생하면 재시도 시 동일한 모호성이 생깁니다.

이 강의는 파일 기반 SQLite 원장을 사용합니다. `BEGIN IMMEDIATE`는 키 확인, 시뮬레이션된 비즈니스 효과, 실행 카운터, 저장된 결과를 하나의 트랜잭션으로 직렬화합니다. 동일한 키로 경쟁하는 두 개의 독립적인 원장 연결은 하나의 커밋된 결과와 하나의 실행을 관찰합니다. 원장을 닫고 다시 열어도 해당 기록은 유지됩니다.

모든 반환 값은 저장된 JSON에서 재구성됩니다. 호출자는 원장이 보유한 변경 가능한 객체를 받지 않으므로, 반환된 사전(dictionary)을 변경해도 이후 재생(replay) 결과가 손상되지 않습니다.

시뮬레이터의 비즈니스 효과는 동일한 SQLite 트랜잭션 내의 영수증 및 실행 카운터입니다. 실제 결제, 배포, 외부 API 호출은 로컬 테이블에 쓰기만 한다고 해서 원자적(atomic)이 되지 않습니다. 프로덕션 환경에서는 내구성 있는 공유 데이터베이스 트랜잭션, 트랜잭션 아웃박스(outbox), 또는 동일한 멱등성 키를 강제하는 상류(upstream) 공급자가 필요합니다. 프로세스 잠금(lock)만으로는 여러 복제본(replica)을 보호하지 못하며 재시작 후에도 유지되지 않습니다.

### 재시도 매트릭스

구현하기 전에 재시도를 분류해 보세요.

| 분류 | 예시 | 재시도 규칙 |
|------|---------|------------|
| 안전 | 사이드 효과가 없는 결정적 읽기 | 실패 경계를 파악한 후 새로운 JSON-RPC id로 재시도 |
| 조건부 | 내구성 있는 멱등성 키가 있는 변형 | 동일한 키와 동일한 인자로 재시도 |
| 위험 | 비즈니스 중복 제거가 없는 변형 | 자동으로 재시도하지 마세요. 먼저 정합성을 맞춰 보세요. |

`readOnlyHint` 및 `idempotentHint`와 같은 도구 주석은 신뢰할 수 없는 힌트로 남습니다. 애플리케이션 계약과 서버 구현이 재시도 안전성을 결정합니다.

## 백프레셔는 정확성의 일부입니다

SSE 생산자는 클라이언트, 프록시, 네트워크가 소비하는 속도보다 빠르게 진행 상황을 생성할 수 있습니다. 무제한 큐는 지연을 메모리 고갈로 변환합니다.

유한한(bounded) 큐를 사용하고 무엇을 잃을 수 있는지 정의해 보세요.

진행 상황은 대체 가능합니다. 동일한 토큰에 대해 이후의 진행 상황 값이 이전 값을 대체합니다. 최종 JSON-RPC 응답은 대체 불가능합니다.

이 강의의 버퍼는 이 정책을 적용합니다:

1. 동일한 토큰에 대한 인접한 진행 상황을 병합합니다.
2. 용량 한도에 도달하면 가장 오래된 진행 상황을 삭제합니다.
3. 스트림을 권위 있는 재조회가 필요한 상태로 표시합니다.
4. 최종 응답을 보존합니다.
5. 최종 응답을 보존하려면 다른 최종 응답을 삭제해야 하는 상태를 거부합니다.

이것은 명시적인 복구를 동반한 제한된 손실입니다. 조용한 손실은 전략이 아닙니다.

### 프록시 버퍼링

서버는 정상적으로 스트리밍할 수 있지만, 리버스 프록시가 이벤트를 버퍼에 보관할 수 있습니다.

SSE 응답의 경우 다음을 전송합니다:

```http
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

2026 Streamable HTTP 사양은 `X-Accel-Buffering: no`를 권장하며, 이를 통해 호환되는 프록시가 이벤트를 즉시 전달합니다.

조용한 장수명 스트림의 경우, 주기적으로 SSE 주석을 방출합니다:

```text
:
```

클라이언트는 주석 라인을 무시합니다. 중간 매개체는 트래픽을 감지하며 유휴 연결을 닫을 가능성이 낮아집니다.

Keepalive는 진행 상황이 아닙니다. 전송 주석이 도착했다는 이유만으로 작업의 의미적 유휴 시간 제한을 리셋하지 마세요.

## 재연결은 재조회를 의미합니다

최신 Streamable HTTP는 `Last-Event-ID`를 통한 재개 가능한 SSE를 지원하지 않습니다.

`subscriptions/listen` 스트림이 끊어진 후:

1. 새로운 JSON-RPC id로 새로운 listen 요청을 엽니다.
2. 원하는 구독 필터를 복원합니다.
3. 권위 있는 메서드에서 영향을 받은 도구, 리소스, 프롬프트 또는 Tasks를 재조회합니다.
4. 안정적인 식별자로 애플리케이션 상태를 중복 제거합니다.
5. 응답이 손실되었다는 이유만으로 안전하지 않은 변경을 재생하지 마세요.

샘플 복구 계획은 `sendLastEventId`를 false로 명시적으로 설정하고 재조회할 리소스를 나열합니다.

### 재연결 무리를 방지합니다

10,000명의 클라이언트가 정확히 1초에 재연결하면 복구 중인 서버가 다시 실패합니다.

지터와 상한이 있는 지수 백오프를 사용하세요. 이 교재는 테스트가 재현 가능하도록 클라이언트 id와 시도 횟수로부터 결정론적 지터를 계산합니다:

```text
attempt 0: up to 250 ms
attempt 1: up to 500 ms
attempt 2: up to 1000 ms
...
cap: 8000 ms
```

프로덕션 환경에서는 암호학적으로 안전한 난수나 런타임 난수를 사용할 수 있습니다. 불변 조건은 특정 공식이 아니라 분포입니다.

## 구현하기

`code/main.py`는 5개의 작은 신뢰성 구성 요소를 구축합니다.

### `RequestCoordinator`

- 유휅 및 최대 마감 시간을 사용하여 진행 중인 요청을 시작합니다;
- 단조로운 진행 알림을 방출합니다;
- 올바른 stdio 또는 HTTP 취소 신호를 생성합니다;
- 유효하지 않은 취소 알림을 무시합니다;
- 취소 및 완료의 최종 경쟁을 명시적으로 만듭니다;
- stdio 구독에 서버가 전송하는 취소를 예약합니다.

### `MutationLedger`

- 비즈니스 키 없이 두 JSON-RPC id가 두 번 실행되는 것을 증명합니다;
- 파일 기반 SQLite 트랜잭션을 키 확인, 시뮬레이션된 효과,
실행 카운터 및 결과 커밋에 사용합니다;
- 독립적인 원장 연결 간에 하나의 멱등성 키 아래에서 일치하는 인수를 중복 제거합니다;
원장 연결;
- 다른 인수와 함께 재사용된 하나의 키를 거부합니다;
- 방어적 복사본을 반환하고 재열기 시 커밋된 레코드를 보존합니다.

### `DurableTaskService`

- 취소 요청을 승인합니다;
- 작업 `working`을 워커 체크포인트까지 유지합니다;
- 승인이 최종 상태가 아닌 이유를 시연합니다.

### `BoundedSseBuffer`

- 압력 하에서 진행을 병합하거나 드롭합니다;
- 권위 있는 재조회가 필요하다는 것을 기록합니다;
- 최종 응답을 절대 드롭하지 않습니다.

### 복구 헬퍼

- 프록시 안전한 SSE 헤더와 유지 유지 주석(comments)을 반환합니다;
- 재연결 및 재조회 계획을 생성합니다;
- 결정적인 지수 백오프와 지터를 사용하여 재시도를 분산합니다.

## 인터랙티브 랩

sleep을 추가하지 않고 네 가지 이벤트 순서를 실행해 보세요.

1. 요청 `A`을 시작하고, 이를 취소한 후 `complete()`을 호출해 보세요.
2. 요청 `B`을 시작하고, 이를 완료한 후 취소 신호를 전달해 보세요.
3. 요청 `C`을 시작하고, 모든 유휴 마감 시간 전에 진행 상황을 방출한 후 최대 마감 시간을 초과해 보세요.
4. Streamable HTTP를 통해 요청 `D`을 시작하고 응답 스트림을 닫아 보세요.

각 시나리오에 대해 다음을 기록해 보세요:

- 요청의 최종 상태;
- 최종 응답이 존재하는지 여부;
- 전송된 취소 신호;
- 클라이언트가 무시해야 할 이벤트.

그런 다음 `D`을 stdio로 변경해 보세요. 작업은 동일하지만, 취소 신호는 변경되어야 합니다.

## 실습 랩

`MutationLedger`에 `reserve_inventory` 변형을 추가해 보세요.

요구 사항:

1. 키는 SKU, 수량, 테넌트 및 작업 이름을 바인딩합니다.
2. 동일한 키와 동일한 인수를 사용한 재시도는 첫 번째 예약을 반환합니다.
3. 수량이 변경된 재시도는 추가 예약 없이 실패합니다.
4. 커밋되었지만 응답을 잃어버린 실행은 키를 통해 조정할 수 있습니다.
5. 결과에는 비밀 데이터나 결제 데이터가 기록되지 않습니다.
6. 클라이언트가 키를 제공하지 않은 경우 자동 재시도는 비활성화됩니다.
7. 시뮬레이션된 구독 드롭을 추가하고, 다음에 무엇을 할지 결정하기 전에 재고 레코드를 다시 가져오세요.
8. 배리어에서 두 개의 원장 연결을 시작하고 동일한 키를 동시에 제출하세요. 하나의 예약이 커밋되었는지 단언하세요.
첫 번째로 반환된 예약 객체를 변형하세요. 키를 재생하고 저장된 결과가 변경되지 않았음을 증명하세요.
9. 원장 파일을 닫고 다시 열은 후, 키를 통해 예약을 조정하세요.
랩을 정직하게 유지하세요: 재고가 다른 서비스에 있다면, 그 서비스가 동일한 멱등성 키를 허용하는지, 아니면 트랜잭션 아웃박스가 로컬 커밋을 원격 효과로 연결하는지 설명하세요.
10. 출시된 아티팩트

실험실의 정직성을 유지하세요: 재고(inventory)가 다른 서비스에 있다면, 그 서비스가 동일한 멱등성 키를 허용하는지, 아니면 트랜잭션 아웃박이 로컬 커밋을 원격 효과로 연결하는지 설명해 보세요.

## 검증하기

다음 문장들이 참이면 강의를 완료한 것입니다:

- stdio 취소는 `notifications/cancelled`를 전송하고 응답을 받지 못합니다.
- Streamable HTTP 취소는 요청 스트림을 닫고 취소 POST를 전송하지 않습니다.
- 완료 전 취소는 최종 응답을 억제합니다.
- 취소 전 완성은 응답을 보존하고 늦은 취소를 무시합니다.
- 진행 상황은 유휴 시간 초과를 리셋할 수 있지만, 최대 시간 초과는 리셋할 수 없습니다.
- 새로운 JSON-RPC id만으로는 변경 작업을 다시 실행합니다.
- 동일한 인자와 하나의 멱등성 키는 동시
두 연결 경합 하에서 한 번만 실행됩니다.
- 커밋된 레코드는 재열기 후에도 생존하며, 재생 시 방어적 복사본을 반환합니다.
- 반환된 결과를 변경해도 저장된 결과를 변경할 수 없습니다.
- 유한 버퍼는 용량 내에 유지되며 최종 응답을 보존합니다.
- 재연결은 새 요청을 사용하며, `Last-Event-ID`를 전송하지 않고 영향을 받은 상태를 다시 가져옵니다.
- `tasks/cancel` 확인은 워커가 이를 관찰할 때까지 작업을 비종료 상태로 유지합니다.

| 서버가 승인된 취소 후 응답함 | 클라이언트가 사용 불가능한 늦은 결과를 받음 | 취소가 이겼을 때 작업을 중단하고 추가 메시지를 억제하세요 |
| 진행 상황이 모든 마감 시간을 리셋함 | 멈춘 작업이 영원히 생존함 | 별도의 절대 최대 시간 초과를 유지하세요 |
| 새로운 RPC id가 중복 제거로 취급됨 | 청구, 배포 또는 삭제가 두 번 실행됨 | 내구성 있는 애플리케이션 멱등성 키를 추가하세요 |
| 키 확인과 효과가 분리됨 | 동시 워커가 둘 다 누락된 키를 관측함 | 키 주장, 효과 레코드 및 결과를 원자적으로 커밋하세요 |
| 복제본 간에 사용되는 메모리 내 원장 | 재시작하거나 다른 워커가 이전 커밋을 잊음 | 공유 내구성 스토리지 또는 상류 멱등성 사용 |
| 저장된 변경 가능한 결과를 직접 반환 | 호출자의 변경이 이후 재실행을 손상시킴 | 커밋된 결과를 직렬화하고 방어적 복사본 반환 |
| 변경된 인수로 키 재사용 | 하나의 키가 두 개의 비즈니스 의도를 별칭으로 사용 | 인수 지문을 저장하고 비교 |
| 무제한 진행 상황 큐 | 느린 소비자로 인해 메모리 증가 | 제한 내에서 대체 가능한 진행 상황을 병합하고 드롭 |
| 압력 하에서 최종 응답 드롭 | 클라이언트가 요청 결과를 알 수 없음 | 용량을 예약하거나 진행 상황을 제거하되, 최종 응답은 절대 제거하지 않음 |
| 프록시가 SSE를 버퍼링 | 진행 상황이 버스트로 도착하거나 타임아웃 후 도착 | 버퍼링을 비활성화하고 호환되는 프록시 타임아웃을 구성 |
| `Last-Event-ID` 가정 | 클라이언트가 서버가 지원하지 않는 상태에서 재개 | 새 요청으로 재연결하고 재조회 |
| 모든 클라이언트가 즉시 재연결 | 복구가 또 다른 장애를 발생시킴 | 지터가 포함된 상한 지수 백오프 사용 |
| Task ack를 최종 취소로 취급 | UI가 중지라고 표시한 후에도 워커가 계속 실행 | 종료 상태가 될 때까지 Task를 폴링 |

## 캡스톤 연결

도구 생태계 캡스톤은 신뢰성을 아키텍처 다이어그램의 단락이 아닌 실행 가능한 증거로 취급해야 합니다.

다음 산출물을 요구합니다:

- 각 전송에 대한 취소 경쟁 트랜스크립트 하나;
- 모든 노출된 변경에 대한 재시도 표;
- 멱등성 키 기록 및 불일치 픽스처;
- 동시 동일 키 트랜스크립트, 재오픈 검사 및 변경 별칭 검사;
- 유한 버퍼 과부하 결과;
- 역방향 프록시 SSE 헤더 및 유휴 정책;
- 권위 있는 재조회 방법을 명시하는 재연결 계획;
- 캡스톤이 Tasks를 사용할 때 내구성 있는 Task 취소 추적.

로컬 프로세스에서의 녹색 요청은 해피 패스만 증명합니다. 손실된 응답, 늦은 취소, 느린 소비자 및 재연결 무리가 결정적인 결과를 가질 때 캡스톤은 프로덕션 준비가 완료됩니다.
