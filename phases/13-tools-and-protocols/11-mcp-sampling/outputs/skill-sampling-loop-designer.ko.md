프로토콜 개정 `2026-07-28`을 목표로 하는 MCP 서버의 모델 지원 동작을 설계해 보세요.

하나의 결정부터 시작하세요: 서버가 모델 제공자와 직접 통합할 수 있습니까? 샘플링(Sampling)은 새로운 설계에서 폐기되었습니다. 클라이언트의 모델과 자격 증명을 사용하는 것이 명시적인 제품 요구 사항이 아닌 한, 직접 통합을 우선시하세요.

다음 내용을 생성하세요:

1. 아키텍처 결정. 직접 추론 또는 호환성 샘플링(Sampling)을 선택하고 그 이유를 설명하세요.
2. 발견 계약. `server/discover`을 표시하고 정확한 `supportedVersions`, 광고된 기능, `ttlMs`, `cacheScope`을 포함하세요. 도구가 광고되는 경우, 유효한 객체 `inputSchema`, `resultType: "complete"`, 서버 식별자 메타데이터, 캐시 힌트를 포함하는 필수적인 결정론적 `tools/list` 설명자를 포함하세요.
3. 요청 봉투. 모든 요청의 `_meta`에 프로토콜 버전과 클라이언트 기능을 포함하세요. 버전이 없거나 문자열이 아닌 경우 `-32602`을 사용하세요. 지원되지 않는 버전의 경우 정확한 `supported`과 `requested` 데이터를 사용하여 `-32022`을 사용하세요. 샘플링(Sampling)이 없는 경우 `requiredCapabilities` 객체를 사용하여 `-32021`을 사용하세요. 클라이언트 식별자 메타데이터는 정보 전용으로 취급하세요. id가 없는 알림에 대해 JSON-RPC 응답을 절대 생성하지 마세요. 승인된 HTTP 알림은 본문 없이 `202`을 받습니다.
4. 라운드 테이블. 각 MRTR 라운드에 대해 `inputRequests` 키, 내장된 요청 메서드, 예상 응답 스키마, 검증, 예산을 지정하세요.
5. 재시도 계약. 원본 메서드와 인자, 새로운 JSON-RPC id, 현재 라운드 `inputResponses`, 바이트 단위 정확 일치 `requestState`을 요구하세요.
6. 상태 보호. 인증된 주체, 메서드, 인자 요약, 단계, 짧은 만료 기간에 HMAC 또는 인증된 암호화를 바인딩하세요.
7. 안전 정책. 승인, 최대 라운드 수, 토큰 및 바이트 제한, 응답 검증, 로깅, 거부 동작을 정의하세요.
8. 제거 계획. 샘플링(Sampling)이 남아 있다면, 직접 통합으로 대체하는 조건과 날짜를 지정하세요.

하드 거부:

- 문서화된 요구 사항 없이 폐기된 샘플링(Sampling)을 채택하는 새로운 설계.
- `sampling/createMessage`을 라이브 서버-클라이언트 요청으로 전송하는 2026-07-28 서버입니다.
- `initialize`, `notifications/initialized`, `Mcp-Session-Id` 또는 숨겨진 프로토콜 세션 상태의 모든 사용입니다.
- 권한 부여, 리소스 접근, 비즈니스 로직에 영향을 미치는 서명되지 않은 `requestState`입니다.
- 원래 JSON-RPC id를 재사용하거나 원래 인수를 변경하는 재시도입니다.
- 기능 체크, 승인 정책, 검증 및 하드 라운드 제한이 없는 클라이언트 모델 루프입니다.
- `includeContext: "allServers"` 또는 암시적 서버 간 컨텍스트입니다.

거부 규칙:

- 비밀스러운 모델 호출이나 서버의 의도를 사용자에게 숨기는 모든 설계를 거부합니다.
- 모델 출력을 신원, 권한 부여, 사용자 동의의 증거로 사용하는 것을 거부합니다.
- 하나의 결정론적 도구 호출로 충분할 때 다중 라운드 설계를 거부합니다.
- 클라이언트 및 서버 메타데이터를 인증된 신원으로 호출하는 것을 거부합니다.

결정, 와이어 흐름, 라운드 테이블, 서명된 상태 내용, 안전 예산, 실패 사례, 마이그레이션 계획을 포함한 한 페이지 아키텍처를 출력합니다. `direct inference`, `temporary MRTR compatibility`, `no model required` 중 하나의 판정으로 마무리합니다.
