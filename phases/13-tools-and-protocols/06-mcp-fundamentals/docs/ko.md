# MCP 기초: 상태 비저장 요청과 JSON-RPC

> 현대 MCP에는 핸드셰이크도 프로토콜 세션도 없습니다. 각 요청은 그 자체로 이해, 인증, 라우팅, 재시도가 가능하도록 충분한 메타데이터를 담아야 합니다.

**유형:** Learn
**언어:** Python
**선수 요건:** 13단계, 01-05강
**시간:** 약 55분

## 학습 목표

- MCP의 서버 프리미티브와 클라이언트 측 기능을 구분해 보세요.
- MCP `2026-07-28`에 대한 유효한 JSON-RPC 2.0 요청 및 응답을 만들어 보세요.
- 모든 요청에 프로토콜 버전, 클라이언트 기능, 클라이언트 식별자를 포함해 보세요.
- `server/discover`을 사용하고, `UnsupportedProtocolVersionError`을 핸드셰이크 없이 처리해 보세요.
- 검증부터 완전한 결과까지 하나의 독립적인 요청을 추적해 보세요.

## 문제점

MCP 서버는 같은 프로세스나 HTTP 워커에서 서로 다른 기능을 가진 두 클라이언트로부터 연속된 요청을 받을 수 있습니다. 서버가 이전 요청이 선언한 내용을 기억한다면, 잘못된 권한을 적용하거나 잘못된 형식의 응답을 반환할 수 있습니다.

MCP `2026-07-28`은 이러한 모호성을 제거합니다. 프로토콜의 핵심은 상태 비저장(Stateless)입니다. 서버는 연결 이력이 아닌, 현재 요청만으로 현재 요청을 처리하는 방법을 결정해야 합니다.

이는 사고방식을 바꿉니다. 이전 순서는 연결, 핸드셰이크, 연산 순서였습니다. 현대의 순서는 더 단순합니다:

1. 클라이언트가 자기 서술(self-describing) 요청을 보냅니다.
2. 서버가 해당 요청의 버전과 기능을 검증합니다.
3. 서버가 메서드를 처리합니다.
4. 서버가 타입이 지정된 결과나 JSON-RPC 오류를 반환합니다.

다음 요청은 처음부터 같은 과정을 반복합니다.

## 개념

### 서버 프리미티브

MCP 서버는 세 가지 주요 프리미티브를 노출합니다:

1. **도구(Tools)**는 모델이 제어하는 액션으로, `tools/list`로 발견하고 `tools/call`로 호출합니다.
2. **리소스(Resources)**는 URI로 주소가 지정된 데이터로, `resources/list`로 발견하고 `resources/read`로 가져옵니다.
3. **프롬프트(Prompts)**는 재사용 가능한 템플릿이며, `prompts/list`로 발견하고 `prompts/get`로 렌더링합니다.

루트(Roots), 샘플링(Sampling), 로깅(Logging)은 호환성을 위해 `2026-07-28` 스키마에 남아 있지만, 더 이상 권장되지 않습니다. 새로운 구현에서는 루트(Roots)에 대해 명시적인 도구 또는 리소스 입력을, 샘플링(Sampling)에 대해 직접적인 모델 제공자 API를, 로깅(Logging)에 대해 stderr 또는 OpenTelemetry를 사용해야 합니다. elicitation은 Multi Round-Trip Requests를 통해 계속 사용할 수 있으며, 서버가 입력 요청을 반환하면 클라이언트가 원래 작업을 재시도합니다. 현대적인 서버는 독립적인 JSON-RPC 요청을 시작하지 않습니다.

### JSON-RPC 엔벨로프

MCP는 JSON-RPC 2.0을 사용합니다:

- 요청: `{jsonrpc, id, method, params}`
- 응답: `{jsonrpc, id, result}` 또는 `{jsonrpc, id, error}`
- 알림: `id`가 없는 `{jsonrpc, method, params}`

요청 `id`는 하나의 응답과 상관관계가 있습니다. 이는 프로토콜 세션을 생성하지 않습니다.

### 필수 요청 메타데이터

모든 현대적인 요청은 `params` 내부에 `_meta` 객체를 포함합니다:

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "course-client",
        "version": "1.0.0"
      }
    }
  }
}
```

프로토콜 버전과 클라이언트 기능은 필수입니다. 클라이언트 식별은 권장됩니다. 이는 자가 보고된 표시 및 디버깅 데이터이며, 보안 자격 증명이 아닙니다.

서버는 이전 요청, stdio 프로세스, HTTP 연결, 또는 전송 헤더만으로는 이러한 값들을 추론해서는 안 됩니다.

### 완전한 결과 및 서버 식별

모든 성공적인 현대적인 결과는 `resultType`를 포함합니다. 일반적인 최종 결과는 `"complete"`를 사용합니다. 서버는 결과 메타데이터에서 자신을 식별해야 합니다:

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "resultType": "complete",
    "tools": [],
    "ttlMs": 30000,
    "cacheScope": "public",
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "notes-server",
        "version": "1.0.0"
      }
    }
  }
}
```

`tools/list`, `resources/list`, `prompts/list`, `resources/templates/list`, `resources/read`, `server/discover`는 캐시 가능한 결과입니다. 이들은 `ttlMs`와 `cacheScope`를 포함합니다. 안전한 기본값은 `ttlMs: 0`와 `cacheScope: "private"`입니다. 목록 항목은 결정적인 순서를 가져야 하며, 이를 통해 동등한 응답이 안정적인 캐시 키와 안정적인 모델 컨텍스트를 생성하도록 해야 합니다.

### 핸드셰이크 없는 발견

모든 현대적인 서버는 `server/discover`를 구현해야 합니다. 클라이언트는 다른 메소드 호출 전에 이를 호출하여 다음을 가져올 수 있습니다:

- `supportedVersions`
- 서버 `capabilities`
- 선택적 사용 `instructions`
- 결과 `_meta`의 서버 식별
- 캐시 힌트

발견은 유용하지만 게이트는 아닙니다. 클라이언트는 `tools/list`을 먼저 보낼 수 있습니다. 그 요청이 이미 프로토콜 버전과 기능을 담고 있기 때문입니다.

요청된 버전이 지원되지 않으면 서버는 JSON-RPC 코드 `-32022`을 다음 내용과 함께 반환합니다:

```json
{
  "requested": "2027-01-01",
  "supported": ["2026-07-28"]
}
```

클라이언트는 상호 지원되는 최신 버전을 선택하고 새로운 JSON-RPC 요청 id로 재시도합니다.

### 단일 요청 생명주기

최신 요청을 이 순서로 추적하세요:

1. JSON-RPC 엔벨로프를 하나 파싱합니다.
2. `jsonrpc`이 `"2.0"`인지, `id`이 존재하는지, `method`이 문자열인지, `params`가 객체인지 확인합니다.
3. `params._meta`에 버전 문자열과 기능 객체를 요구합니다. 형식이 잘못되거나 메타데이터가 누락되면 `-32602`입니다.
4. HTTP 경계에서 버전, 메서드 및 적용 가능한 이름 헤더를 본문과 비교합니다. 두 버전 값 중 하나가 지원되지 않는 경우에도 불일치는 `-32020`입니다.
5. 일치가 확인된 후, 일치하지만 지원되지 않는 버전은 `-32022`으로 거부합니다.
6. 필수 기능을 확인한 후 `method`으로 라우팅하고 메서드별 인수를 검증합니다.
7. 구체적인 작업의 핸들러가 실행되기 전에 인증 및 권한 부여를 수행합니다.
8. 서버 식별 정보를 포함한 완전한 결과를 반환합니다.
9. 요청 범위 프로토콜 메타데이터를 잊습니다.

이 순서는 두 구성 요소가 서로 다른 호출을 해석하는 것을 방지합니다. 게이트웨이는 원점이 `params.name: notes.delete`을 실행하는 동안 `Mcp-Name: notes.read`을 권한 부여해서는 안 됩니다. 또한 형식이 잘못된 입력, 헤더 혼란, 버전 협상, 기능 실패, 권한 부여 및 핸들러 실패를 각각Distinct한 증거로 유지합니다.

stdin을 닫거나 HTTP 응답이 끝나면 전송 활동이 종료됩니다. 이는 프로토콜 세션을 종료하지 않습니다. 최신 MCP에는 프로토콜 세션이 없기 때문입니다.

### 명시적 레거시 호환성

`2025-11-25`까지의 버전은 `initialize`, `notifications/initialized`, 연결 범위 기능 및 이전 Streamable HTTP에서는 선택적 프로토콜 세션을 사용합니다. 그 동작은 이중 시대(dual-era) 클라이언트가 오래된 서버와 통신할 때 여전히 관련이 있습니다.

시대별 구분은 유지해야 합니다. 현대적 요청은 요청별 필수 메타데이터로 식별됩니다. 레거시 연결은 문서화된 폴백 경로로만 선택됩니다. `2026-07-28` 서버의 기본값으로 `initialize`을 보내지 마세요.

“상태 비저장(Stateless)”은 시대별로 의미가 다릅니다. `2026-07-28`에서는 프로토콜 불변 조건입니다. 모든 일반 요청은 독립적으로 해석 가능해야 하며, MCP 세션은 존재하지 않습니다. `2025-11-25`까지의 버전에서는 초기화와 협상된 기능이 연결에 속하므로, 호환성 어댑터는 그 레거시 연결 상태를 유지할 수 있습니다. 이중 시대 구현은 하나의 허용적인 상태 머신이 아닙니다. 이는 명확한 선택 결정이 두 파서 중 어느 것도 실행되기 전에 이루어지는, 격리된 레거시 어댑터 옆의 상태 비저장 현대 코어입니다.

두 의미 모두 내구성 있는 애플리케이션 상태를 금지하지는 않습니다. 워크플로, 작업, 초안은 공유 저장소의 불투명 핸들 뒤에 존재할 수 있습니다. 클라이언트는 그 핸들을 일반 입력으로 보내며, 모든 복제본은 그 사용에 대해 인증 및 권한 부여를 수행합니다. 프로토콜 컨텍스트는 제거된 세션의 대체물로서 그 저장소에 유입되어서는 안 됩니다.

```figure
mcp-tool-call
```

## 사용하기

`code/main.py`은 프레임워크 없이 현대 MCP 메시지를 빌드, 검증, 추적, 전송합니다. 실행하세요:

```bash
python3 code/main.py
python3 -m unittest discover code/tests -v
```

출력에서 세 가지 불변 조건을 확인하세요:

- 모든 요청은 `_meta` 필드를 반복합니다.
- 모든 성공적인 결과는 `resultType: "complete"`이며 서버 식별자를 포함합니다.
- 목록 결과는 결정적으로 정렬되어 있으며 명시적인 캐시 힌트를 포함합니다.

## 연습 문제

1. 한 요청의 프로토콜 버전을 `2027-01-01`으로 변경하세요. 에러 코드가 `-32022`이며 데이터가 지원되는 버전을 광고하는지 확인하세요.
2. 두 번째 요청에서 `io.modelcontextprotocol/clientCapabilities`을 제거하세요. 서버가 첫 번째 요청의 기능을 재사용하지 않는지 확인하세요.
3. 메모리 내 도구 레지스트리를 역순으로 정렬하세요. `tools/list`이 여전히 동일한 결정적 순서를 반환하는지 확인하세요.
4. `cacheScope`을 `public`에서 `private`로 변경하세요. 각 경우에서 응답을 재사용할 수 있는 인증 컨텍스트가 무엇인지 설명하세요.
5. 선택적 `clientInfo` 생략 테스트를 추가하세요. 클라이언트 식별은 권장 사항이며 필수 사항이 아니므로 요청은 유효해야 합니다.

| 용어 | 의미 |
