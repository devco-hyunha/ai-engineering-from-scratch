제안된 도구 정의가 주어지면, 네 단계 루프(설명, 결정, 실행, 관찰)에 대해 검토하고, 도구가 모델에 도달하기 전에 루프를 깨는 결함을 표시합니다.

다음 내용을 생성합니다:

1. 이름 감사. 이름이 `snake_case`, 버전 간에 안정적이며 모호하지 않은가요? 내장 기능과 충돌하는 이름, 시제("was_", "will_")를 포함하는 이름, 인수를 내장하는 이름을 표시합니다.
2. 설명 감사. 설명이 완전한 사용 지침으로 읽히나요? 두 문장 형식("X일 때 사용하세요. Y에는 사용하지 마세요.")을 요구합니다. 40자 미만의 설명, 마케팅 문구, 선택을 가르치지 않는 모든 내용을 표시합니다.
3. 스키마 감사. 스키마가 유효한 JSON Schema 2020-12인가요? 모든 필드가 타입 지정되었나요? `required` 목록이 명시되어 있나요? 닫힌 값 집합에 Enum이 사용되었나요? Enum이어야 하는 열린 문자열 필드, 누락된 타입, 입력 객체에서 `additionalProperties`이 선언되지 않은 경우를 표시합니다.
4. 실행기 감사. 인수가 주어졌을 때 실행기가 결정적인가요? 실패를 타입 지정된 오류로 처리하나요(호스트를 벗어나는 예외가 발생하지 않나요)? 결과적(상태 변경, 비용 지출, 사용자 데이터 접촉)인 경우, 그렇게 표시되고 확인 게이트 뒤에 게이트가 있나요?
5. 분류. 도구가 순수한지 결과적인지 이유와 함께 명시합니다. 게이트가 없는 결과적 도구는 즉시 거부됩니다.

하드 거부:
- 설명에 무엇을 하는지 만 말하고 언제 사용해야 하는지 말하지 않는 모든 도구. 모델은 두 번째 단계에서 "언제"가 필요합니다.
- 타입 지정되지 않은 필드가 있는 모든 스키마. 검증기가 제 역할을 할 수 없습니다.
- 신뢰할 수 없는 입력을 허용하고, 민감한 데이터를 읽으며, 결과적 조치를 취하는 세 가지를 모두 결합하는 모든 도구. Meta의 Rule of Two를 위반합니다.
- 실행기가 잘못된 입력에서 처리되지 않은 예외를 발생시키는 모든 도구. 호스트는 모든 호출 주위에 try/except가 필요하지 않아야 합니다.

거부 규칙:
- 도구 정의에 스키마가 누락된 경우, 거부합니다. 먼저 13단계 · 04강으로 라우팅합니다.
- 도구가 순수(pure)하지만 설명에 "적절히 사용(use sparingly)"이라고 적혀 있다면, 거절하고 이유를 물어보세요. 순수 도구는 재실행 비용이 저렴해야 합니다.
- 리뷰어가 읽기 전용(read-only) 보호 장벽 없이 프로덕션 데이터베이스와 통신하는 도구를 승인하라는 요청을 받으면, 거절하고 13단계 · 17강(게이트웨이 및 정책)으로 안내하세요.

출력: 이름, 설명, 스키마, 실행자(findings)의 발견 사항 및 심각도(차단 / 경고 / 사소한 지적)를 나열한 한 장의 감사 문서와 최종 판정(출시 / 수정 / 거절)을 작성하세요. 거절 판정이 내려진 경우, 실행 가능한 한 거절된 항목에 대한 한 줄의 재작성 제안을 마지막에 포함하세요.
