# 스킬 발견 및 점진적 공개

> 스킬은 본문이 로드되기 전에 유용해집니다. 스킬의 이름과 설명은 카탈로그에 자리를 차지하며, 더 깊은 파일들은 작업이 그 파일들에 도달했을 때에만 컨텍스트를 차지합니다.

**유형:** Build
**언어:** Python (stdlib)
**선수 요건:** 13단계 · 22강 (에이전트 스킬: 이식 가능한 계약 및 런타임 경계)
**시간:** 약 105분

## 학습 목표

- 범위, 검증, 충돌 정책, 카탈로그 게시를 분리하는 파일시스템 발견 파이프라인을 구축하세요.
- 카탈로그 메타데이터, 활성 지침, 작업별 리소스라는 세 가지 공개 수준을 설명하세요.
- 에이전트가 전체 패키지를 로드하지 않고도 필요한 세부 사항에 직접 접근할 수 있도록 참조를 설계하세요.
- 카탈로그 공간을 활성 스킬 컨텍스트와 독립적으로 예산을 배정하세요.
- 스킬이 자체 리소스를 읽을 때 경로 순회 및 심링크 탈출을 거부하세요.

## 문제점

에이전트에 200개의 스킬이 설치되어 있습니다. 세션 시작 시 모든 `SKILL.md`, 참조 파일, 스크립트, 템플릿을 로드하면 현재 작업이 관련 없는 절차에 묻혀버릴 것입니다. 아무것도 로드하지 않으면 사용자가 정확한 파일시스템 경로를 기억해야 합니다.

일반적인 절충안은 카탈로그입니다. 자격을 갖춘 각 스킬에 대해 모델에게 간결한 식별자 및 라우팅 설명을 보여주고, 선택된 후에만 전체 본문을 로드합니다. 이는 두 가지 새로운 엔지니어링 문제를 만듭니다.

첫째, 발견은 단순한 재귀적 파일 검색이 아닙니다. 스킬은 프로젝트, 사용자, 관리자, 플러그인, 내장 범위 등 다양한 범위에 존재할 수 있습니다. 두 패키지가 이름을 공유할 수 있습니다. 심링크가 신뢰된 루트 밖을 가리킬 수 있습니다. 형식이 잘못된 패키지는 카탈로그 공간을 소비하거나 호출이 불가능해질 수 있습니다.

둘째, 점진적 공개가 점진적 혼란으로 변질될 수 있습니다. `SKILL.md`가 "관련 가이드를 읽으세요"라고 말하고 패키지에 열두 개의 가이드가 있다면, 모델은 추측해야 합니다. 모든 가이드가 세 개의 추가 파일을 가리킨다면, 로딩은 무한한 그래프 탐색이 됩니다.

좋은 런타임은 발견을 결정적으로 만들고 공개를 의도적으로 만듭니다.

## 개념

### 발견은 컴파일러 파이프라인입니다

파일시스템을 소스 입력으로 취급하세요. 원시 경로를 모델에 직접 게시하지 마세요.

```figure
skill-discovery-pipeline
```

각 단계는 구조화된 데이터와 구조화된 실패를 생성해야 합니다. 발견 로그는 다음 질문에 답해야 합니다:

- 어떤 루트를 검색했나요?
- 어떤 후보가 발견되었나요?
- 어떤 후보가 거부되었으며, 그 이유는 무엇인가요?
- 충돌 시 어떤 패키지가 승리했나요?
- 예산 때문에 어떤 카탈로그 항목이 단축되거나 생략되었나요?

그 증거가 없으면, "모델이 내 스킬을 사용하지 않았다"는 진단이 거의 불가능합니다.

### 범위는 런타임 정책입니다

이식 가능한 사양은 스킬 패키지를 정의하며, 하나의 보편적인 설치 경로나 우선순위 순서를 정의하지 않습니다. 호스트가 검색 위치를 결정합니다.

범용 런타임은 다음 범위를 사용할 수 있습니다:

| 범위 | 예시 루트 | 의도된 소유권 |
|---|---|---|
| 워크스페이스 | `<repo>/.agents/skills/` | 프로젝트 유지 관리자 |
| 사용자 | `<user-data>/skills/` | 단일 개발자 |
| 관리자 | `<system>/skills/` | 머신 또는 조직 정책 |
| 플러그인 | 서명된 플러그인 번들 | 플러그인 게시자 및 설치자 |
| 내장 | 런타임 패키지 | 런타임 공급업체 |

2026년 8월 기준, Codex는 `$CWD/.agents/skills`부터 저장소 루트까지의 상위 디렉터리를 통해 프로젝트 발견을 문서화하며, 사용자, 관리자 및 내장 위치도 포함합니다. 심링크된 스킬 디렉터리를 지원합니다. 중복된 이름은 병합되지 않고 둘 다 나타날 수 있습니다. 이는 Codex의 동작이며 `SKILL.md`의 요구 사항이 아닙니다. 어댑터를 작성할 때 현재 [Codex skill documentation](https://learn.chatgpt.com/docs/build-skills)을 확인하세요.

디렉터리 이름에서 우선순위를 발명하지 마세요. 정책으로 선언하고 테스트하세요. 이 강의 실습은 각 `Scope`에 명시적인 정수 순위를 사용하므로 동일한 후보 집합이 항상 동일한 방식으로 해결됩니다.

### 충돌은 `name` 이상의 식별자가 필요합니다

`release-readiness`이라는 이름의 두 패키지는 합법적일 수 있습니다. 하나는 워크스페이스 덮어쓰기이고 다른 하나는 사용자 기본값일 수 있습니다. 따라서 카탈로그 항목은 적어도 다음을 포함해야 합니다:

```json
{
  "name": "release-readiness",
  "description": "Inspect a release candidate for this repository.",
  "scope": "workspace",
  "source": "/repo/.agents/skills/release-readiness",
  "selected": true
}
```

일반적인 충돌 정책은 다음과 같습니다:

| 정책 | 이점 | 위험 |
|---|---|---|
| 모든 후보 유지 | 숨겨진 것이 없음 | 모델이 모호한 이름을 보게 됨 |
| 가장 높은 우선순위의 범위가 승리 | 단순 호출 | 로컬 패키지가 신뢰할 수 있는 패키지를 가릴 수 있음 |
| 중복 거부 | 조용한 가림(shadowing) 없음 | 합법적인 오버라이드가 작동하지 않게 됨 |
| 출처로 이름 한정 | 명시적 식별 | 사용자-facing 이름이 길어짐 |

호스트에 하나의 정책을 선택하세요. 모델 카탈로그에 없는 경우에도 거부되거나 가려진 후보를 진단 정보에 보존하세요.

### 세 가지 공개 수준

Agent Skills 사양은 단계적 로딩을 설명합니다. 핵심은 각 수준이 서로 다른 목적을 가진다는 점입니다.

```figure
skill-disclosure-levels
```

#### 수준 1: 카탈로그 메타데이터

모델은 이 스킬을 이웃 스킬과 구분할 충분한 정보가 필요합니다. 사양은 카탈로그 항목당 약 100 토큰을 추정하지만, 실제 직렬화와 토큰화는 호스트의 몫입니다.

유용한 설명은 두 절로 구성됩니다:

```yaml
description: Validate a release candidate and produce a readiness report. Use when the user asks whether a version, tag, or package is ready to publish.
```

첫 번째 절은 능력을 명시합니다. 두 번째 절은 트리거 경계를 명시합니다. 25강에서는 긍정적 프롬프트와 아슬아슬한(near-miss) 프롬프트로 이 경계를 평가합니다.

#### 수준 2: 활성 지침

활성화 후, 본문은 지도이자 절차로 기능해야 합니다. 사양은 `SKILL.md`을 500 줄 미만으로 유지할 것을 권장합니다. 이는 설계 신호이며, 채워야 할 목표가 아닙니다.

본문에는 다음이 포함되어야 합니다:

- 작업 경계;
- 기본 워크플로;
- 분기 조건;
- 더 깊은 파일에 대한 직접 참조;
- 도구 및 스크립트 계약;
- 실패 및 중단 동작;
- 예상 출력 및 그 검증.

입력 파일을 짧게 만들기 위해 중앙 워크플로를 참조로 이동하지 마세요. 활성화는 모델이 올바르게 시작할 충분한 컨텍스트를 제공해야 합니다.

#### 수준 3: 지원 리소스

참조는 산문이나 데이터를 제공합니다. 스크립트는 결정론적 연산을 제공합니다. 자산은 지침으로 취급되지 않으며, 산출물로 복사, 채우기, 변환됩니다.

| 디렉터리 | 모델이 읽나요? | 모델이 실행하나요? | 일반적인 내용 |
|---|:---:|:---:|---|
| `references/` | 필요할 때 예 | 아니오 | 스키마, 정책, 도메인 가이드 |
| `scripts/` | 검사 가능 | 허용된 도구를 통해 | 검증기, 변환기, 수집기 |
| `assets/` | 유용한 경우에만 | 아니오 | 템플릿, 픽스처, 이미지, 시작 파일 |

이 이름들은 관례일 뿐이며, 마법 같은 기능이 아닙니다. 호스트는 여전히 파일 접근 및 실행 도구가 필요합니다.

### 브랜치별 참조가 주제 덤프보다 우선합니다

엔트리 파일을 결정 맵(decision map)으로 작성하세요:

```markdown
## Choose the path

- For a Python package, read `references/python-release.md`.
- For a container image, read `references/container-release.md`.
- For a documentation-only release, read `references/docs-release.md`.
- If the release combines artifact types, read only the guides for those artifacts.
```

이렇게 하면 모든 참조에 관찰 가능한 로드 조건이 부여됩니다. "`references/`를 더 읽어보세요"는 그렇지 않습니다.

참조 그래프를 얕게 유지하세요. 공식 가이드는 `SKILL.md`에서 직접 링크를 연결하고 깊은 체인을 피할 것을 권장합니다. 한 홉(hop)은 도달 가능성을 테스트 가능하게 만들며, 필요한 제약 조건이 컨텍스트에 포함되지 않을 가능성을 줄입니다.

```figure
skill-reference-map
```

### 카탈로그 예산과 활성 컨텍스트는 서로 다른 예산입니다

`c_i`을 스킬 `i`의 직렬화된 카탈로그 비용, `B_c`를 카탈로그 예산, `b_j`를 활성 본문 비용, `r_k`를 실제로 로드된 리소스라고 해 보세요.

```text
catalog_cost = sum(c_i for every published skill)
active_cost = sum(b_j for every activated skill) + sum(r_k for every disclosed resource)
```

한 예산을 줄인다고 해서 다른 예산이 자동으로 줄지 않습니다. 짧은 설명은 카탈로그 공간을 절약할 수 있지만, 활성화된 900줄 본문은 여전히 작업을 압도할 수 있습니다. 본문을 참조로 분리하는 것은 런타임과 지침이 실제로 관련 없는 브랜치를 로드하지 않을 때만 활성 비용을 줄일 수 있습니다.

Codex는 현재 컨텍스트 윈도우 크기가 알려진 경우, 초기 스킬 목록을 컨텍스트 윈도우의 2퍼센트로 예산 설정합니다. 8,000자 값은 해당 크기를 알 수 없을 때만 적용되는 폴백(fallback)이며, 2퍼센트 규칙과 결합된 두 번째 상한이 아닙니다. 카탈로그가 적용된 예산을 초과하면 설명이 단축되거나 생략될 수 있습니다. 이 수치들은 현재 Codex 정책으로 간주하며, Agent Skills 표준의 속성으로 간주하지 마세요.

### 리소스 경로는 신뢰 경계(Trust Boundary)입니다

스킬은 패키지 내부의 파일만 읽어야 합니다. 문자열 접두사 검사만으로는 충분하지 않습니다:

```text
references/../../../../.ssh/config
references/external-link -> /private/company-secrets
```

파일시스템의 의미론(semantics)으로 패키지 루트와 후보를 해석(resolve)하고, 절대 경로 입력을 거부하며, 해석된 후보가 해석된 루트 아래에 남아 있는지 확인하세요. 발견(discovery) 전에 심링크(symlink) 허용 여부를 결정하세요. 허용하는 경우, 해석된 대상을 매번 확인하세요.

```figure
skill-resource-containment
```

경로 포함은 콘텐츠 신뢰를 확립하지 않습니다. 유효한 패키지 내 참조가 악성 지침을 포함할 수 있습니다. 26강이 해당 위협을 다룹니다.

### 로딩은 관측 가능해야 합니다

비밀을 기록하지 않고 공개 이벤트를 기록하세요:

```json
{
  "event": "skill.resource.loaded",
  "skill": "release-readiness",
  "resource": "references/python-release.md",
  "reason": "candidate contains pyproject.toml",
  "bytes": 2840
}
```

이유는 컨텍스트 선택을 검토 가능한 증거로 만듭니다. 또한 에이전트가 "만약을 위해" 모든 파일을 로드하게 만드는 지침을 식별하는 데 도움이 됩니다.

## 구현하기

`code/main.py`는 결정적인 발견 및 공개 엔진을 구축합니다.

발견 표면은 다음을 포함합니다:

- 소스 및 우선순위 메타데이터용 `Scope`;
- 검증되지 않은 파일시스템 후보용 `SkillCandidate`;
- 즉시 스킬 디렉터리를 열거하기 위한 `discover_scope(scope)`;
- 선언된 정책 하나를 적용하기 위한 `resolve_collisions(candidates, precedence)`;
- 경계가 있는 메타데이터를 게시하기 위한 `CatalogEntry` 및 `build_catalog(...)`;
- 직렬화된 항목을 설명하기 위한 `CatalogBudget`이며, 문자가 범용 토큰인 척하지 않습니다.

공개 표면은 다음을 포함합니다:

- 레벨 2 활성화를 위한 `load_skill_body(entry, ...)`;
- 경로 포함을 위한 `validate_reference(skill_dir, reference)`;
- 경계가 있는 레벨 3 읽기를 위한 `load_reference(...)`.

실험을 실행하세요:

```bash
cd "$(git rev-parse --show-toplevel)"
cd phases/13-tools-and-protocols/24-skill-discovery-and-progressive-disclosure
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

이 블록은 로컬 클론이 필요하며, 해당 클론 내의 모든
작업 디렉터리에서 저장소 루트를 해결합니다.

데모는 임시 프로젝트 및 사용자 범위를 생성하고, 충돌을 삽입하며, 의도적으로 작은 예산으로 카탈로그를 구축하고, 하나의 스킬을 활성화하며, 유효한 참조 읽기와 경로 탈출(traversal escape)을 모두 시도합니다. 영구 파일은 설치되지 않습니다.

### 발견이 얕은 이유

`discover_scope`는 `SKILL.md`에 대해 즉시 하위 디렉터리를 확인합니다. 모든 중첩된 `SKILL.md`를 별도의 패키지로 재귀적으로 처리하지 않습니다. 이는 패키지 경계를 보존하고, 설치된 스킬 내부의 예제나 픽스처를 실수로 게시하는 것을 방지합니다.

### 실험이 임의의 YAML을 파싱하지 않는 이유

이 실험실은 카탈로그에 필요한 스칼라 frontmatter를 지원합니다. 프로덕션 런타임은 명시적 스키마, 크기 제한, 사용자 정의 객체 생성이 비활성화된 안전한 YAML 파서를 사용해야 합니다. "Stdlib 전용"은 교육적 제약일 뿐, 조용히 부분적인 YAML 방언을 발명할 권한이 아닙니다.

## 사용하기

이 체크리스트를 모든 발견(discovery) 어댑터에 적용해 보세요:

1. 구성된 모든 루트와 그곳에 쓸 수 있는 주체를 나열하세요.
2. 심링크된 패키지가 허용되는지 명시하세요.
3. 패키지 이름, 디렉터리 이름, 필수 메타데이터, 항목 본문 크기를 검증하세요.
4. 내부 식별자에서 출처와 범위를 보존하세요.
5. 중복 이름 동작을 선언하고 테스트하세요.
6. 모델로 전송되는 직렬화된 카탈로그의 정확한 크기를 측정하세요.
7. 본문이나 리소스가 로드된 이유를 기록하세요.
8. 리소스 읽기를 해석된 패키지 루트 내부로 제한하세요.
9. 참조된 파일이 누락되면 명확하게 실패하세요.
10. 설치나 정책이 변경되면 카탈로그를 재구축하세요.

## 출시하기

이 강의는 `skill-catalog-builder` 번들을 생성합니다. 명시적으로 순서가 지정된 루트를 스캔하고, 심링크된 항목 파일 및 이름-디렉터리 불일치를 거부하며, 교차 범위 충돌을 해석하고, 동일한 우선순위의 중복을 거부하며, 선택된 메타데이터를 선언된 항목, 설명, 직렬화 문자 예산에 맞춥니다.

JSON 보고서에는 선택된 항목, 가려진 후보, 생략된 항목, 검증 오류, 우선순위, 예산 사용량이 포함됩니다. 본문 및 참조 로드는 별도의 런타임 작업이므로, 카탈로그 빌더는 스크립트를 실행하거나 전체 패키지를 컨텍스트에 수용하지 않습니다.

## 연습 문제

1. 플러그인 범위를 추가하고 사용자 및 내장 우선순위 사이에 배치하세요. 충돌 결과를 테스트로 증명하세요.
2. 충돌 정책을 최고 우선순위에서 자격이 있는 이름으로 변경하세요. 카탈로그에 두 항목 모두를 보존하세요.
3. `load_reference`에 바이트 크기 제한을 추가하세요. 제한에 정확히 있는 파일과 그보다 1바이트 큰 파일을 테스트하세요.
4. 거의 동일한 두 설명을 만드세요. 트리거 경계가 겹치지 않도록 다시 작성하세요.
5. 모든 참조 및 스크립트의 해시를 포함하는 매니페스트를 추가하세요. 리소스를 로드하기 전에 수정된 리소스를 감지하세요.
6. 데모가 Level 1, Level 2, Level 3의 바이트 수를 각각 보고하도록 계측하세요.

## 핵심 용어

| 용어 | 사람들이 말하는 것 | 실제 의미 |
|---|---|---|
| 스킬 발견(Skill Discovery) | "모든 SKILL.md를 찾기" | 설정된 범위를 검색하고, 패키지를 검증하며, 출처를 첨부하고, 정책을 적용하는 것 |
| 스킬 카탈로그(Skill Catalog) | "설치된 스킬의 목록" | 자격 있는 패키지에 대한 모델이 볼 수 있는 간결한 라우팅 메타데이터 |
| 충돌 정책(Collision Policy) | "중복 중 무엇이 이기는가" | 서로 다른 출처에서 온 같은 이름 후보에 대한 선언된 규칙 |
| 점진적 공개(Progressive Disclosure) | "게 lazy 로딩" | 카탈로그에서 본문, 그리고 브랜치별 리소스로 단계적으로 컨텍스트를 수용하는 것 |
| 참조 그래프(Reference Graph) | "스킬이 연결한 파일들" | 도달 가능한 리소스 구조와 그 로드 조건 |
| 경로 포함(Path Containment) | "폴더 안에 머무르기" | 해석된 리소스 대상이 해석된 패키지 루트 내부에 남아 있는지 검증하는 것 |
