주어진 도메인에 대해 현대적인 MCP 서버 계획을 작성합니다. 애플리케이션 상태를 명시적으로 유지하고, 프로토콜 동작은 상태 비저장(Stateless)으로 유지해 보세요.

다음 내용을 생성합니다:

1. 프리imitive 분할. 원자적 도구, URI로 주소가 지정된 리소스, 유용한 프롬프트를 정의합니다. 도메인에 정당한 사용 사례가 없는 프리미티브는 생략합니다.
2. 발견 결과. `supportedVersions`, 서버 기능, 선택적 지침, `resultType: "complete"`, 캐시 힌트, 서버 식별자를 결과 `_meta`에 제공합니다.
3. 요청 검증기. 모든 `params._meta`에서 프로토콜 버전과 클라이언트 기능을 요구합니다. 존재하는 경우 권장되는 클라이언트 식별자를 검증합니다. 불일치 시 `-32022`를 요청된 버전과 지원되는 버전과 함께 반환합니다.
4. 결과 래퍼. 모든 성공에 `resultType: "complete"`과 서버 식별자를 추가합니다. 발견, 목록, 템플릿, 리소스 읽기에 `ttlMs`과 `cacheScope`를 추가합니다.
5. 순서 정책. 모든 목록 응답에 대해 안정적인 정렬 키를 정의합니다.
6. 상태 정책. 내구성 있는 상태는 데이터베이스에 저장하거나, 일반적인 도구 인자로서 명시적이고 불투명한 핸들을 반환합니다. 프로토콜 세션에 상태를 숨기지 마세요.
7. 호환성 경계. 레거시 지원이 필요한 경우 `2025-11-25` initialize 어댑터를 격리합니다. 레거시 트래픽에만 선택하고 두 시대를 독립적으로 테스트합니다.

하드 거부:

- 첫 번째 유효한 메서드가 `initialize`이어야 하는 현대 서버.
- 이전 요청에서 기능, 식별자, 버전을 재사용하는 것.
- 현대 HTTP 트래픽에 `Mcp-Session-Id`를 반환하는 것.
- 캐시 힌트 없이 목록 또는 리소스 읽기 결과를 반환하는 것.
- 주석(annotations)을 권한 제어 수단으로 취급하는 것.
- 서버에서 독립적인 JSON-RPC 요청을 보내는 것.

거부 규칙:

- 요청된 리소스가 권한 없이 비밀을 노출할 경우, 중단하고 접근 정책을 요구합니다.
- 도메인에 읽기 전용 데이터가 없는 경우, 리소스를 발명하지 말고 생략합니다.
- 재사용 가능한 템플릿이 없는 도메인에서는 채우기용 프롬프트를 포함하지 말고, 프롬프트 자체를 생략하세요.

한 페이지 분량의 아키텍처, 방법 표, 검증 의사코드, 결과 예시, 결정적 순서 규칙, 그리고 최소 6개의 적합성 테스트를 출력하세요. 애플리케이션 상태와 프로토콜 상태의 경계로 마무리하세요.
