# MCP 레지스트리 공급망: 수용, 드리프트, 롤백

> 레지스트리 항목은 게시자가 선언한 내용을 알려줍니다. 프로덕션 수용은 무엇을 가져왔는지, 무엇을 관찰했는지, 무엇을 승인했는지, 그리고 안전하게 복원할 수 있는 것이 무엇인지 증명합니다.

**유형:** Build
**언어:** Python
**선수 요건:** 13단계 · 17강 (게이트웨이 및 레지스트리), 13단계 · 18강 (프로덕션 인증)
**시간:** 약 90분

## 학습 목표

- 레지스트리 게시, 패키지 출처, 런타임 발견, 로컬 승인을 분리해 보세요.
- MCP 서버 네임스페이스를 자체 레코드 내부의 이름을 신뢰하지 않고 검증해 보세요.
- 불변의 게시물, 실행 소스, 출처, 라이브 디스크립터 증거를 고정해 보세요.
- 수용 후 레지스트리 상태 변경 및 런타임 드리프트를 감지해 보세요.
- 이력을 다시 쓰지 않고 이전에 수용된 버전으로 라우팅을 롤백해 보세요.
- 모든 결정을 설명하는 변조 방지 수용 대장을 유지해 보세요.

## 문제점

레지스트리에서 `com.example/inventory`을 찾습니다. 설명이 적절해 보입니다. 패키지가 존재합니다. 서버가 `server/discover`에 응답합니다.

이것은 하나의 사실이 아닙니다. 서로 다른 기관에서 온 사실들의 연쇄입니다:

1. 네임스페이스에 대해 인증된 게시자가 레코드를 제출했습니다.
2. 패키지 레지스트리가 특정 식별자와 다이제스트를 가진 아티팩트를 제공했습니다.
3. 실행 중인 엔드포인트가 프로토콜 버전, 기능, 도구 및 진단 서버 정보를 보고했습니다.
4. 조직이 이 정확한 조합이 허용된다고 결정했습니다.

이 사실들을 "레지스트리에 있으니 신뢰하라"로 축약하면 공급망 사각지대가 생깁니다. 유효한 게시물이 여전히 폐기될 수 있습니다. 다이제스트를 고정하지 않으면 패키지 태그가 예상치 못한 아티팩트를 가리킬 수 있습니다. 서버는 검토 후 파괴적인 도구를 추가할 수 있습니다. 롤백은 수용된 적 없는 버전을 조용히 선택할 수 있습니다.

해결책은 모든 경계에서 증거를 제공하는 수용 제어기입니다.

## 레지스트리는 인덱스일 뿐, 승인 시스템이 아닙니다

공식 MCP 레지스트리는 서버 메타데이터를 저장합니다. `server.json` 레코드는 서버 버전을 지정하고 하나 이상의 패키지 또는 원격 엔드포인트를 선언합니다. 게시 규칙은 네임스페이스 인증, 패키지 소유권 확인, 제한된 레지스트리 규칙, 그리고 좁게 정의된 게시자 메타데이터 위치를 추가합니다.

이러한 통제들은 게시 관련 질문에 답합니다. 생산 정책은 배포 관련 질문에 답해야 합니다:

| 경계 | 질문 | 증거 소유자 |
|---|---|---|
| 네임스페이스 | 게시자가 이 이름을 사용할 수 있었습니까? | 레지스트리 인증 및 검증된 네임스페이스 입력 |
| 레코드 | 게시자가 이 버전에 대해 무엇을 선언했습니까? | 불변 `server.json` 다이제스트 |
| 실행 소스 | 어떤 패키지 또는 원격 엔드포인트가 실행됩니까? | 선언된 소스 필드, 검증된 소유권 결과, 전송 및 신뢰된 다이제스트 |
| 런타임 | 엔드포인트는 현재 무엇을 노출합니까? | `server/discover` 및 도구 설명자 |
| 수용 | 정책이 이 정확한 세트의 사용을 승인했습니까? | 로컬 고정 및 원장 항목 |
| 운영 | 여전히 안전합니까, 그리고 무엇을 대체할 수 있습니까? | 드리프트 체크, 상태 동기화, 상태 확인 및 롤백 경로 |

레지스트리 스키마 버전과 MCP 프로토콜 버전은 독립적입니다. 레코드는 게시된 `2025-12-11` 서버 스키마를 사용할 수 있으며, 라이브 서버는 MCP `2026-07-28`을 지원할 수 있습니다. 서로를 유추하지 마세요.

```figure
mcp-registry-admission
```

## 하나의 수용 결정에 포함된 7가지 통제

### 1. 네임스페이스 검증

공식 레지스트리 이름은 인증된 네임스페이스를 사용합니다. 검증된 도메인은 역순 도메인 접두어에 매핑될 수 있습니다. 예를 들어, `example.com`의 제어는 `com.example/*`을 설정할 수 있습니다.

문자열 접두어 검사만으로는 허용하지 마세요:

```python
server_name.startswith("com.example")
```

이 방식은 `com.exampleevil/tool`도 허용합니다. `/`에서 이름을 분할하고, 비어 있지 않은 슬러그를 요구하며, 네임스페이스 세그먼트를 정확히 비교하세요. 더 중요한 것은, 인증 결과에서 검증된 네임스페이스를 수용 단계로 전달하는 것입니다. 신뢰할 수 없는 레코드에서 신뢰를 유추하지 마세요.

GitHub 기반 네임스페이스와 도메인 기반 네임스페이스는 서로 다른 인증 경로를 사용합니다. 두 경로 중 하나를 하나의 수용 입력으로 정규화하세요: 정확히 검증된 네임스페이스 문자열.

### 2. 출처 결합

패키지 레코드의 경우, 선언 내용과 가져온 아티팩트는 명시된 필드에서 조인되어야 합니다:

- 패키지 레지스트리 유형
- 패키지 식별자
- 패키지 버전
- 검증된 소유권 결과
- 다운로드된 아티팩트 다이제스트

선언된 패키지 전송 방식도 검증하세요. 원격 엔드포인트만 있는 레코드는 유효하며, 패키지가 없다는 이유로 거부되어서는 안 됩니다. 원격 소스의 경우, 선언된 URL과 전송 방식을 독립적으로 검증된 엔드포인트 소유권 및 신뢰된 연결 또는 배포 증거의 다이제스트와 조인하세요.

강의 코드는 두 가지 소스 유형을 모두 지원하며, 선택된 소스를 레지스트리 소스, 서버 이름, 레지스트리 버전, 레코드 다이제스트 및 증거 다이제스트와 함께 해싱합니다. 결과적인 출처(provenance) 다이제스트는 전체 증거 집합을 가리키는 간결한 포인터입니다. 증거를 보관하는 것의 대체물이 아닙니다.

검증하려는 아티팩트로부터만 제공된 다이제스트는 절대 수락하지 마세요. 신뢰된 가져오기 경계에서 계산하거나, 검증 결과를 확인하는 패키지 서비스로부터 수신하세요.

### 3. 버전뿐만 아니라 결정을 고정(Pin)하세요

레지스트리 버전은 고유한 게시 식별자입니다. 게시된 메타데이터는 변경할 수 없습니다. 변경된 레코드는 새로운 버전을 요구합니다. 시맨틱 버전 관리가 권장되지만, 레지스트리는 이를 요구하지 않으며 버전 범위를 수락하지 않습니다.

이는 `^1.4`이 수용 고정(admission pin)이 아님을 의미합니다. “latest”도 마찬가지입니다. 유용한 고정(pin)은 다음을 포함합니다:

```json
{
  "server": "com.example/inventory",
  "version": "1.0.0",
  "recordDigest": "...",
  "source": {"kind": "package", "registryType": "pypi"},
  "sourceDigest": "...",
  "toolsetDigest": "...",
  "provenanceDigest": "...",
  "registryStatus": "active"
}
```

여러 계층을 고정하면 어떤 경계가 변경되었는지 식별할 수 있습니다. 동일한 레지스트리 버전 하에서 레코드 다이제스트가 변경되면 레지스트리 무결성 실패입니다. 동일한 패키지 좌표나 원격 배포 하에서 소스 다이제스트가 변경되면 실행 소스 무결성 실패입니다. 도구 세트 다이제스트가 변경되면 런타임 드리프트입니다.

### 4. 라이브 드리프트 감지

수용(admission)은 실제로 트래픽을 받을 서버를 관찰해야 합니다. `server/discover`를 호출하고, 신뢰된 경로를 통해 노출된 도구 설명자를 나열하거나 획득하여 다음을 검증하세요:

- `2026-07-28`이 `supportedVersions`에 있음
- 로컬에서 요구되는 모든 기능이 존재함
- 모든 도구 설명자가 요구되는 식별자 및 스키마 표면을 가짐
- 정규화된 디스크립터 다이제스트가 이후 검사에서 승인된 핀과 일치합니다

선택적 `_meta["io.modelcontextprotocol/serverInfo"]` 값은 자체 보고된 표시, 로그 및 디버깅 컨텍스트입니다. 이를 진단 증거로 기록하되, 네임스페이스, 패키지 소유권, 엔드포인트 소유권, 승인 또는 기타 보안 결정을 확립하는 데 사용해서는 안 됩니다. `_meta` 외부의 직접 `serverInfo` 별칭은 계약 필드가 아니며, 진단 증거로 승격되어서는 안 됩니다.

순서에 의미가 없는 필드만 정규화하세요. 샘플은 해싱 전에 도구 목록을 안정된 이름으로 정렬하므로, 무해한 목록 순서 변경은 드리프트를 유발하지 않습니다. 디스크립터 필드를 폐기하지는 않습니다. 새로운 도구, 변경된 스키마, 변경된 설명 또는 새로운 주석은 핀을 변경합니다.

샘플은 잘못된 디스크립터와 모든 디스크립터 다이제스트 변경을 드리프트로 간주하며, 핀을 격리하고 활성 라우트를 제거하며 해당 버전을 롤백 대상으로 차단합니다. 설명이 모델의 도구 선택에 영향을 미치므로, 프로덕션 정책은 새로운 리뷰를 통해서만 편집 변경을 허용할 수 있습니다. "외관상" 메타데이터는 에이전트 동작을 변경할 수 있습니다.

### 5. 레지스트리 상태는 실시간 상태입니다

레지스트리 API는 각 서버 레코드 옆에 응답 수준의 `_meta` 객체를 첨부합니다. 레지스트리 관리 필드는 `_meta["io.modelcontextprotocol.registry/official"]` 아래에 있습니다. 응답 `_meta` 객체를 승인에 전달하고 `_meta["io.modelcontextprotocol.registry/official"].status`를 읽으세요. 직접 `_meta.status` 값은 공식적인 와이어 형식이 아닙니다. 응답 메타데이터를 간행물 레코드 자체의 `_meta`와 혼동하지 마세요. 상태는 다음과 같습니다:

- `active`: 기본값으로 반환되며 로컬 승인 대상이 됩니다
- `deprecated`: 경고와 함께 여전히 발견 가능하지만, 더 이상 안전한 자동 선택이 아닙니다
- `deleted`: 삭제된 뷰나 증분 뷰를 통해 역사적 기록이 남아 있는 동안 기본값으로 숨겨집니다

승인 후 동기화 상태입니다. 활성 버전이 폐기되거나 삭제되면 핀을 격리하고 새로운 작업을 라우팅하지 마세요. 증거는 유지하세요. 기본 목록에서 삭제된 것은 감사 추적 지우기의 권한이 아닙니다.

발행자가 제공한 사용자 정의 메타데이터는 간행물 레코드에서 `_meta.io.modelcontextprotocol.registry/publisher-provided` 아래에만 속합니다. 레지스트리 관리 응답 메타데이터는 분리되어 있습니다. 발행자가 자체 공식 상태를 설정하도록 허용하지 마세요.

### 6. 롤백은 라우트 복원입니다

불변 발행물은 롤백 중에 편집되지 않습니다. 롤백은 이전에 수용된 현재 자격 요건을 충족하는 핀을 선택하여 활성 라우트를 변경합니다.

안전한 대상은 다음을 충족해야 합니다:

1. 완료된 수용 기록이 있어야 합니다.
2. 정책에 따라 Registry 상태가 여전히 활성이어야 합니다.
3. 런타임 또는 보안 증거에 의해 격리되지 않아야 합니다.
4. 핀이 지정된 패키지와 라이브 디스크립터 집합으로 여전히 해석되어야 합니다.
5. 현재 건강 검사를 통과해야 합니다.

샘플은 첫 세 가지 조건에 집중합니다. 실제 리컨실리어(reconciler)는 활성화 전에 패키지를 다시 가져오고 라이브 엔드포인트를 다시 확인해야 합니다.

### 7. 수용 원장(ledger) 추가

수용 데이터베이스는 무엇이 활성인지 알려줍니다. 원장은 그 이유를 설명합니다.

각 샘플 항목에는 시퀀스, 시간, 이벤트, 서버, 버전, 결과, 이유, 증거, 이전 항목 해시 및 자체 해시가 포함됩니다. 이전 결과를 변경하면 해당 항목과 모든 후속 링크의 검증이 깨집니다.

이는 변조 증거(tamper-evident)가 있는 것이지, 마법처럼 변조 방지(tamper-proof)가 되는 것은 아닙니다. 서명된 릴리스 메타데이터나 쓰기 전용 저장소와 같은 별도의 신뢰 영역에 주기적인 원장 헤드를 앵커링하세요. 추가 권한을 제한하세요. 인증 토큰, 패키지 자격 증명, 도구 인자 및 비공개 엔드포인트 데이터를 증거에 포함하지 마세요.

## 구현하기

실행 가능한 컨트롤러는 `code/main.py`에 있습니다. Python 표준 라이브러리만 사용합니다.

유한한 시연으로 시작하세요:

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift
python3 code/main.py
```

시연은 다섯 가지 작업을 수행합니다:

1. 네임스페이스, 패키지 출처, 프로토콜, 기능 및 도구가 일치하는 `1.0.0`을 수용합니다.
2. `1.1.0`을 수용하고 활성 상태로 만듭니다.
3. 런타임에서 예상치 못한 삭제 도구를 관찰합니다.
4. `1.1.0`의 Registry 상태가 `deprecated`로 변경되는 것을 관찰합니다.
5. 여전히 수용된 `1.0.0` 핀으로 라우팅을 복원합니다.

예상 형태:

```json
{
  "admitted": [true, true],
  "driftAllowed": false,
  "rollbackAllowed": true,
  "activeVersion": "1.0.0",
  "ledgerValid": true
}
```

구현을 이 순서대로 읽어보세요:

1. `namespace_for_domain()`과 `namespace_matches()`은 정확한 명명 권한을 설정합니다.
2. `digest()`과 `normalized_tools()`은 결정론적 증거를 생성합니다.
3. `RegistryAdmissionController.admit()`은 발행물, 출처, 런타임 및 정책을 결합합니다.
4. `check_live()`은 새 관측값을 핀과 비교합니다.
5. `observe_registry_status()`은 레지스트리 상태가 변경된 버전을 격리합니다.
6. `rollback()`은 이전에 승인된 자격 있는 대상만 활성화합니다.
7. `AdmissionLedger.verify()`은 기록된 이력 변경을 감지합니다.

## 사용하기

발견과 라우팅 사이에 컨트롤러를 배치하세요:

```text
Registry sync -> artifact verifier -> live discovery -> admission controller -> route table
                                               |                 |
                                               v                 v
                                          evidence store    admission ledger
```

이 작업에는 각각 다른 신원을 사용하세요. 레지스트리 동기화 워커는 메타데이터 읽기 접근 권한이 필요합니다. 아티팩트 검증기는 패키지 가져오기 접근 권한이 필요합니다. 라우팅 조정기는 승인된 핀을 활성화할 권한이 필요합니다. 어느 것도 모든 자격 증명이 필요하지 않습니다.

롤아웃 상태를 명시적으로 만드세요. “승인됨”은 증거가 정책을 통과했음을 의미합니다. “활성”은 라우팅이 현재 이를 선택함을 의미합니다. “격리됨”은 새 작업을 받을 수 없음을 의미합니다. “대체됨”은 다른 승인된 버전이 활성 상태임을 의미합니다. 네 가지 의미를 하나의 부울 값에 인코딩하지 마세요.

`tools/list`에서 서버를 노출하기 전에 수용(admission)을 수행하세요. 그렇지 않으면 클라이언트가 게시와 정책 평가 사이의 공백 기간 동안 도구를 발견할 수 있습니다.

## 인터랙티브 랩

경계 실패를 하나씩 관찰하세요.

### 랩 A: 네임스페이스 충돌

코드 디렉토리에서 Python 셸을 여세요:

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift/code
python3 -q
```

그런 다음 실행하세요:

```python
from main import namespace_matches
namespace_matches("com.example/inventory", "com.example")
namespace_matches("com.exampleevil/inventory", "com.example")
```

첫 번째 결과는 `True`이고, 두 번째는 `False`입니다. 로컬에서 정확한 비교를 `startswith`로 대체하고 두 번째 이름이 경계를 넘나드는 이유를 관찰하세요. 계속 진행하기 전에 정확한 비교를 복원하세요.

### 랩 B: 디스크립터 드리프트

```python
from main import *
times = iter(f"2026-08-21T12:00:{n:02d}+00:00" for n in range(10))
c = RegistryAdmissionController(clock=lambda: next(times))
meta = {OFFICIAL_META_KEY: {"status": "active"}}
c.admit(sample_record("1.0.0"), meta, "com.example", evidence_for("1.0.0"), sample_live("1.0.0"))
c.check_live("com.example/inventory", "1.0.0", sample_live("1.0.0", True))
```

이유와 라우팅 상태를 검사하세요. 패키지와 레지스트리 레코드는 변경되지 않았습니다. 런타임 도구 표면은 변경되었으므로, 컨트롤러가 핀을 격리하고 비활성화했습니다. 공급망 통제는 설치 후에도 계속되어야 하는 이유입니다.

### 랩 C: 상태 및 롤백

`1.1.0`을 수용하고, 폐기 표시를 하고, 두 롤백 대상을 시도하세요:

```python
c.admit(sample_record("1.1.0"), meta, "com.example", evidence_for("1.1.0"), sample_live("1.1.0"))
c.observe_registry_status("com.example/inventory", "1.1.0", "deprecated")
c.rollback("com.example/inventory", "1.1.0", "unsafe retry")
c.rollback("com.example/inventory", "1.0.0", "restore known release")
c.ledger.verify()
```

격리된 대상은 거부됩니다. 이전 활성 핀은 승인됩니다. 원장(ledger)은 유효한 상태로 유지됩니다.

## 연습 랩

두 사람 승인 게이트를 포함하여 컨트롤러를 확장하세요.

요구 사항:

- 승인을 핀 내의 변경 가능한 이름이 아닌 서명된 증거 참조로 저장하세요.
- `destructiveHint: true`을 포함하는 도구 세트에 대해 두 개의 서로 다른 리뷰어 식별자를 요구합니다.
- 중복된 리뷰어 식별자를 거부합니다.
- 승인이 불완전한 경우 원본 수용 시도를 장부에 보존합니다.
- 0개, 1개, 중복, 그리고 두 개의 서로 다른 승인에 대한 테스트를 추가합니다.
- 서명, 자격 증명, 또는 전체 비공개 도구 인수를 기록하지 않습니다.

성공이란 두 식별자가 정확한 레코드, 패키지 및 도구 세트 다이제스트를 승인하기 전까지 파괴적 도구가 활성화될 수 없음을 의미합니다.

검증은 다음을 증명해야 합니다:

- 상태 변경이 활성 핀을 격리합니다
- 롤백이 격리되었거나 알 수 없는 버전을 선택할 수 없습니다
- 장부 변조가 감지됩니다

## 프로덕션 실패 모드

| 실패 | 발생 원인 | 필요한 대응 |
|---|---|---|
| 이름이 유효해 보이지만 네임스페이스가 인증되지 않았습니다 | 정책이 레코드 텍스트를 신뢰했습니다 | 신뢰할 수 있는 네임스페이스 검증자가 정확한 접두어를 제공할 때까지 거부합니다 |
| 동일한 패키지 좌표가 새로운 바이트를 반환합니다 | 변경 가능한 업스트림이나 손상된 배포입니다 | 활성화를 중지하고, 두 다이제스트를 보존하며, 가져오기 경계를 조사합니다 |
| “최신”이 검토 없이 변경됨 | 플로팅 선택이 고정(pinning)을 벗어남 | 승인된 정확한 버전과 다이제스트만 해석 |
| 승인 후 새로운 도구가 나타남 | 런타임 드리프트 또는 다른 배포 | 라우트를 격리하고 새로운 descriptor 관측을 캡처 |
| 폐기된 버전이 여전히 활성 상태 | 상태 동기화가 누락되거나 지연됨 | 활성화 전 및 정기적으로 상태를 조정 |
| 삭제된 레코드가 기본 동기화에서 사라짐 | 클라이언트가 활성 레코드만 요청함 | 증분 또는 삭제 인식 동기화를 사용하고 로컬 히스토리를 보존 |
| 롤백 대상이 승인된 적이 없음 | 라우트 제어와 승인 상태가 연결되지 않음 | 롤백을 거부하고 대상에 대해 새로운 승인 절차를 수행 |
| 공격자가 모든 항목을 재작성한 후에도 장부(Ledger)가 로컬에서 검증됨 | 해시 체인에 외부 앵커가 없음 | 서명된 장부 헤드를 별도의 신뢰 영역에 게시 |
| 증거에 베어러 토큰이나 도구 인수가 포함됨 | 로깅이 전체 요청을 복사함 | 수집 시점에 마스킹하고 최소한의 증거만 저장 |

## 운영 규칙

게시(Publication)는 “이 신원이 이 이름을 게시할 수 있는가?”에 답합니다. 승인(Admission)은 “이 정확한 아티팩트를 실행하고 이 정확한 동작을 노출할 것인가?”에 답합니다. 이 결정들을 분리하고, 모든 조인(join)을 고정(pinning)하며, 롤백이 기억이 아닌 증거를 선택하도록 하세요.
