# MCP 적합성 엔지니어링: 버전 관리, 증거, 운영

> 서버가 하나의 SDK를 통해 해피 패스(happy path)가 작동했다는 이유만으로 적합하다고 할 수는 없습니다. 적합성은 와이어(wire) 수준, 버전 경계, 중간 매개체, 롤백 과정에서 결정됩니다.

**유형:** Build
**언어:** Python
**선수 요건:** 13단계 · 09강 (전송), 13단계 · 17강 (게이트웨이), 13단계 · 30강 (레지스트리 수용)
**시간:** 약 100분

## 학습 목표

- 규범적인 MCP 규칙을 골든 및 네거티브 와이어 트랜스크립트로 변환해 보세요.
- 엄격한 `2026-07-28` 동작을 제한된 레거시 폴백(fallback)과 분리해 유지하세요.
- 추가적인 미지의 필드와 유효하지 않은 `resultType`을 구분해 보세요.
- 원시 JSON-RPC 증거를 SDK가 정규화한 뷰와 비교해 보세요.
- 실제 프록시 경계를 통해 헤더와 본문의 무결성을 증명해 보세요.
- 가려진 트랜스크립트, 상태, 롤백 증거를 통해 릴리스를 게이트하세요.

## 문제점

클라이언트가 SDK를 통해 `tools/list`을 호출하고 도구를 받습니다. 통합 테스트가 통과합니다.

이 결과로 중요한 질문들이 unanswered로 남습니다:

- 요청이 현대적인 요청별 프로토콜 메타데이터를 포함했습니까?
- `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`가 JSON-RPC 본문과 일치합니까?
- 응답이 와이어 상에 유효한 `resultType`을 포함했습니까, 아니면 SDK가 이를 합성했습니까?
- 클라이언트가 미래의 추가 필드를 보존합니까?
- 인식된 현대적인 오류가 실수로 레거시 핸드셰이크를 트리거합니까?
- 프록시가 원본 상태와 JSON-RPC 오류를 보존합니까?
- 알림 직렬화기가 금지된 응답을 방출합니까?
- 비밀을 저장하지 않고 릴리스가 승격되거나 롤백된 이유를 운영이 증명할 수 있습니까?

적합성은 관측 가능한 불변 조건(invariant)의 집합입니다. 프로덕션 트래픽이 이를 발견하기 전에 불변 조건을 포착하는 하네스를 구축하세요.

```figure
mcp-conformance-operations
```

## 버전 시대(Era)부터 시작하기

MCP `2026-07-28`는 요청별 자체 완결된 메타데이터를 사용합니다. 최신 요청은 `params._meta.io.modelcontextprotocol/protocolVersion`과 `params._meta.io.modelcontextprotocol/clientCapabilities`를 포함합니다. 정확한 네임스페이스 키가 중요하며, 단순한 `protocolVersion` 또는 `clientCapabilities` 별칭은 형식이 잘못된 것입니다. HTTP 경계에서 미러링된 라우팅 헤더가 존재하는 경우, 그 값은 JSON-RPC 본문과 일치해야 합니다. 최신 성공적인 결과는 `resultType`를 포함합니다.

`2025-11-25`까지의 버전은 초기화 시대를 사용합니다. `resultType`이 없는 레거시 결과는 클라이언트가 해당 초기 시대를 선택한 후에만 완료된 것으로 해석됩니다.

두 가지 형태를 동시에 허용하는 단일의 관대한 검증기를 만들지 마세요. 두 가지 분기를 사용하세요:

| 분기 | 진입 증거 | `resultType` 누락 | 초기화 |
|---|---|---|---|
| 최신 | 성공적인 `server/discover` 또는 인식된 최신 응답 | 유효하지 않음 | 기본 경로가 아님 |
| 레거시 | 설정된 허용 목록과 불확실한 최신 탐색 후 유효한 레거시 `initialize` 결과 | 완료된 것으로 해석 | 해당 시대에 필수 |

이러한 분리는 형식이 잘못된 최신 피어가 더 약한 검증으로 보상받는 것을 방지합니다.

### 엄격 모드

엄격 모드는 최신 동작에 대한 증거를 요구합니다. 성공적인 `server/discover`는 최신 분기를 증명합니다. 인식된 최신 JSON-RPC 오류도 이를 증명합니다. 요청을 수정하거나 중단하세요. 서버가 `-32020`, `-32021`, `-32022`를 반환했다고 해서 절대 다운그레이드하지 마세요.

### 폴백 모드

폴백 모드는 한 번의 제한된 최신 탐색을 수행합니다. 시간 초과, 빈 응답, 연결 종료, 인식되지 않는 응답은 불확실합니다. 이는 피어가 레거시임을 증명하지 못합니다. 호환성을 위해 명시적으로 설정되거나 허용 목록에 포함된 엔드포인트만 제한된 레거시 탐색을 받을 수 있으며, 클라이언트는 해당 탐색의 `initialize` 결과와 협상된 레거시 개정판을 검증한 후에만 레거시 분기를 선택합니다.

폴백은 "오류 발생 후 레거시를 시도하는 것"이 아닙니다. 인식된 최신 오류는 유용한 수정 정보를 포함합니다. 그 후 다운그레이드하면 헤더 불일치, 누락된 기능 선언, 지원되지 않는 버전을 숨길 수 있습니다.

이는 공격자, 장애, 필터링 프록시가 최신 응답을 드롭하여 다운그레이드를 강요하는 것을 방지합니다. 엔드포인트 정책, 불확실한 최신 관찰, 정확한 긍정적 레거시 증거, 선택된 시대를 함께 기록하세요.

모든 트랜스크립트 옆에 선택한 시대(era)를 기록하세요. 이 정보가 없으면 한 테스트 실행에서는 결손 필드가 허용되는 것처럼 보일 수 있지만, 다른 실행에서는 유효하지 않은 것으로 간주될 수 있습니다.

## 트랜스크립트 코퍼스(Corpus) 구축하기

트랜스크립트 픽스처(fixture)는 SDK 호출뿐만 아니라 경계를 통과한 내용을 기록합니다:

```json
{
  "name": "golden-modern-list",
  "era": "modern",
  "headers": {
    "MCP-Protocol-Version": "2026-07-28",
    "Mcp-Method": "tools/list"
  },
  "request": {
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/list",
    "params": {
      "_meta": {
        "io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {}
      }
    }
  },
  "responseStatus": 200,
  "responseBody": {
    "jsonrpc": "2.0",
    "id": 1,
    "result": {
      "resultType": "complete",
      "tools": []
    }
  }
}
```

두 가지 클래스의 픽스처를 유지하세요.

### 골든 트랜스크립트(Golden transcripts)

골든 트랜스크립트는 허용된 동작을 증명합니다:

- 메타데이터와 헤더가 일치하는 최신(discovery) 또는 메서드 요청
- 필수 필드가 포함된 완전한 결과
- 메서드가 추가 입력을 요청할 수 있는 경우의 `input_required` 결과
- 해당 기능이 광고(advertised)된 후에만 생성되는 확장(extension) 결과
- 선택한 레거시 시대에만 `resultType` 없이 생성되는 레거시 결과
- JSON-RPC 응답이 없는 알림(notification) 처리

골든 트랜스크립트는 정확해야 하며, 크기가 크지 않아야 합니다. 변동성이 있는 ID와 타임스탬프는 결정적으로(deterministic) 만들거나 비교 전에 정규화(normalize)하세요.

### 네거티브 트랜스크립트(Negative transcripts)

네거티브 트랜스크립트는 거부(refusal) 동작을 증명합니다:

- 헤더와 본문(body) 불일치
- 요청별 capabilities 누락
- 지원되지 않는 일치하는 프로토콜 버전
- 최신 `resultType` 누락
- 알 수 없거나 광고되지 않은 `resultType`
- `2.0`가 아닌 `jsonrpc` 응답, 또는 값이나 JSON 타입이 다른 ID
- `result`과 `error`를 모두 포함하거나 둘 다 포함하지 않는 응답
- 정수 `code`과 문자열 `message`가 없는 오류
- 잘못된 HTTP 상태로 매핑된 알려진 프로토콜 오류
- 알림(notification)에 대해 방출된 응답
- 형식이 잘못된 JSON-RPC 엔벨로프(envelope)
- 프록시(proxy)가 프로토콜 오류를 축소한 경우

각 네거티브 케이스에 대해 거부 경계(rejection boundary)와 안정적인 오류 코드를 단언(assert)하세요. "호출이 실패했다"는 너무 약한 표현입니다. 프록시가 생성한 500강 원점(origin)의 `-32020`는 모두 실패처럼 보일 수 있지만, 운영자에게 완전히 다른 이야기를 전달합니다.

헤더 불일치 픽스처는 서버의 실제 HTTP 400 JSON-RPC 응답을 포함해야 하며, 일치하는 요청 ID와 오류 코드 `-32020`를 포함해야 합니다. 로컬 검증기가 `HeaderMismatch`을 관찰할 때마다 이를 자동으로 강제하세요. 응답 검증은 선택적인 픽스처 플래그로 만들지 마세요. HTTP 500이고 본문이 없는 경우, 로컬 거부 코드가 정확했더라도 실패합니다. 자체 요청 검증기가 예외를 던진 후 멈추는 하네스는 서버의 와이어 동작이 아닌 자기 자신을 테스트한 것에 불과합니다.

공식 MCP 적합성 프로젝트는 외부 스위트 및 버전 관리된 참조로서 유용합니다. 로컬 트랜스크립트도 유지하세요. 로컬 트랜스크립트는 프록시, SDK, 인증, 확장 및 릴리스 경로를 포착하며, 이는 범용 스위트가 알 수 없는 부분입니다.

## 헤더 값은 RPC 본문과 일치해야 합니다

현대적인 Streamable HTTP에서는 중간 장치가 미러링된 헤더를 사용하여 라우팅하거나 정책을 강제할 수 있습니다. JSON-RPC 본문은 프로토콜의 진실된 출처(source of truth)로 남아 있습니다. 불일치는 하나의 값을 선택하라는 힌트가 아니라 무결성 실패입니다.

다음 순서로 검증하세요:

1. JSON-RPC 엔벨로프 및 메타데이터 유형을 파싱하고 검증하세요.
2. `MCP-Protocol-Version`와 `params._meta.io.modelcontextprotocol/protocolVersion`를 비교하세요.
3. `Mcp-Method`와 `method`를 비교하세요.
4. 메서드에 라우팅 이름이 있는 경우, `Mcp-Name`를 해당하는 본문 값과 비교하세요.
5. 일치가 확인된 후, 일치하는 버전 및 기능 세트가 지원되는지 결정하세요.

이 순서는 불일치 `-32020`과 지원되지 않는 버전 `-32022`을 구분합니다. 또한 게이트웨이가 헤더 이름을 승인하는 동안 원점이 다른 본문 이름을 실행하는 것을 방지합니다.

HTTP 필드 이름은 대소문자를 구분하지 않지만, 값은 대소문자를 구분합니다. 조회 전에 헤더 이름을 정규화하고 충돌하는 중복을 거부하세요. 안전하지 않은(non-ASCII) 값이나 앞뒤 공백이 있는 `Mcp-Name`의 경우, 본문과 비교하기 전에 정확한 `=?base64?{Base64EncodedValue}?=` UTF-8 센티넬을 디코딩하세요. 불완전한 센티넬, 유효하지 않은 Base64, 유효하지 않은 UTF-8, 또는 `-32020`를 포함하는 원시 unsafe 값은 거부하세요. 본문이 동일한 문자를 포함하더라도 원시 주변 공백은 유효하지 않습니다. 그 값은 전송 전에 센티넬 인코딩이 필요했기 때문입니다.

중개자는 요청이 MCP 서버에 도달하기 전에 잘못된 HTTP를 거부할 수 있으므로, 그 실패는 JSON-RPC가 없는 HTTP 오류일 수 있습니다. 거부가 중개자에서 발생했는지 원본(origin)에서 발생했는지 기록하세요. 원본 MCP 서버는 유효한 JSON-RPC 요청을 처리한 경우 프로토콜 오류 계약을 사용해야 합니다.

## 알 수 없는 필드는 알 수 없는 결과가 아닙니다

전방 호환성은 두 가지 다른 규칙을 요구합니다.

### 추가적인 알 수 없는 필드

결과 객체와 `_meta` 맵은 필드를 추가할 수 있습니다. 검증기는 필드가 예약된 계약을 위반하지 않는 한, 그 역할에 따라 추가된 필드를 보존하거나 무시해야 합니다. 샘플은 전체 원시(raw) 결과를 증거로 보존하며, 알려진 결과 옆에 `futureHint`을 허용합니다.

투명 프록시라면 알 수 없는 필드를 보존하는 것이 제거하는 것보다 일반적으로 더 안전합니다. 애플리케이션 클라이언트라면 이를 무시하는 것이 유효할 수 있습니다. 차등 테스트는 SDK가 이를 생략했음을 드러내야 하며, 이는 의도된 행동이어야 합니다.

### 알 수 없는 `resultType`

`resultType`는 판별자(discriminator)입니다. 핵심 현대적 결과는 `complete` 또는 `input_required`를 사용합니다. 확장 기능은 그 기능이 광고된 경우에만 다른 값을 추가할 수 있습니다. 예를 들어, Tasks 확장 기능은 협상된 기능 컨텍스트에서 `task`을 추가할 수 있습니다.

알 수 없거나 광고되지 않은 판별자는 안전하게 완전한 것으로 취급할 수 없습니다. 클라이언트는 폐기할 라이프사이클을 알지 못합니다. 이를 거부하세요.

따라서 동일한 원시 응답은 허용되는 알 수 없는 필드와 허용되지 않는 알 수 없는 결과 유형을 모두 포함할 수 있습니다. 두 경우 모두 테스트하세요.

디스크리미네이터는 첫 번째 레이어일 뿐입니다. 그 이후에 메소드별 페이로드를 검증해야 합니다. 완전한 `tools/list` 결과는 `tools` 배열이 필요하며, 이 배열의 설명자는 고유한 비어 있지 않은 이름, 유용한 설명, 객체 루트 `inputSchema` 값을 가져야 합니다. `task` 결과는 Tasks 기능(capability)을 가진 자격 있는 `tools/call`에 대해서만 유효하며, `taskId`, 알려진 상태, 생성 및 업데이트 타임스탬프, `ttlMs`, 그리고 유효한 선택적 폴링 간격이 필요합니다. 완전한 `completion/complete` 결과는 `completion` 객체가 필요하며, 이 객체는 100개 이하의 문자열 값, 반환된 값보다 작지 않은 선택적 비음 정수 `total`, 선택적 Boolean `hasMore`을 포함해야 합니다. 잘 표기된 `resultType`은 형식이 잘못된 페이로드를 규격에 맞게 만들 수 없습니다.

## 알림 불변 조건(Notification Invariant)

JSON-RPC 알림에는 `id`이 없습니다. 수신자는 JSON-RPC 성공 또는 오류 응답을 보내지 않아야 합니다.

수락된 HTTP 알림 형식의 경우, 하네스(harness)는 빈 본문을 가진 HTTP `202`을 기대합니다. MCP `2026-07-28`는 Streamable HTTP를 통한 핵심 클라이언트-서버 알림을 정의하지 않습니다. 샘플은 단방향 직렬화 불변 조건을 테스트하기 위해 네임스페이스화된 코스(course) 확장 알림만 사용합니다. 이를 새로운 핵심 메소드로 제시하지 마세요.

핸들러뿐만 아니라 직렬화기도 테스트하세요. 핸들러는 `None`을 반환할 수 있지만, 미들웨어가 이를 JSON 성공 객체로 감쌀 수 있습니다. 최종 아웃바운드(egress) 바이트를 캡처하세요.

## SDK 차이점(Differential) 추가하기

SDK는 종종 와이어(wire) 객체를 편리한 언어 타입으로 변환합니다. 이는 유용하지만, 정규화된(normalized) 객체는 수신된 내용을 증명할 수 없습니다.

모든 고위험(high-risk) 픽스처(fixture)에 대해 다음을 캡처하세요:

1. SDK 디코딩 전의 원시(raw) 상태 코드, 헤더, 응답 본문.
2. SDK가 정규화한 반환 값 또는 예외(exception).
3. 선택된 시대(era)에 대한 예상된 의미론적 투영(projection).
4. SDK에 의해 추출(lifted), 합성(synthesized), 제거(stripped)되거나 변경된 필드.

샘플은 `resultType`, `_meta`, `ttlMs`, `cacheScope`와 같은 알려진 와이어(bookkeeping) 필드의 SDK 전용 제거를 허용하며, 애플리케이션 페이로드를 비교합니다. `futureHint`가 사라진 것을 보고합니다. 이는 알려지지 않은 의미론적 필드가 사라졌기 때문입니다.

모든 차이가 SDK 버그라고 가정하지 마세요. 핵심은 변환을 가시화하는 것입니다. 추가 필드를 무시할 수 있는 애플리케이션 엔드포인트인지, 이를 보존해야 하는 투명한 중개자인지 결정하세요.

출시하는 모든 SDK와 버전에 대해 차분 분석을 실행하세요. 두 SDK가 동일한 트랜스크립트를 서로 다르게 정규화한다면, 릴리스 정책은 사후에 가장 편리한 출력을 선택하는 것이 아니라 어떤 동작이 허용되는지 명시해야 합니다.

## 프록시 증거 수집

대부분의 프로덕션 MCP 장애는 여러 프로세스에 걸쳐 발생합니다. 세 가지 관점을 기록하세요:

| 관점 | 최소 증거 |
|---|---|
| Ingress | 요청 헤더, JSON-RPC 본문, 콘텐츠 타입, 인증된 라우트, 수신 시간 |
| Origin | 전달된 헤더 및 본문 다이제스트, 원본 상태, 응답 헤더 및 본문 |
| Egress | 클라이언트가 볼 수 있는 상태, 헤더, 본문 및 전송 시간 |

샘플은 두 가지 일반적인 변환을 감지합니다:

- 원본 HTTP 400 또는 404 JSON-RPC 오류가 범용 프록시 500으로 변환됨
- Egress JSON-RPC 본문이 원본 본문과 다름

콘텐츠 타입, `Accept`, 압축, 요청 범위 SSE, 캐시 헤더 및 추적 상관관계에 대해 배포별 어서션을 추가하세요. 정책이 허용하는 경우 TLS 종단의 양쪽을 모두 캡처하세요. 경로를 증명하기 위해 자격 증명을 기록하지 마세요.

## 증거가 메모리를 떠나기 전에 마스킹

마스킹은 준거성 운영의 일부이며, 나중의 정리 작업이 아닙니다. 직렬화, 해싱, 로그, 테스트 아티팩트 또는 장애 업로드 전에 적용하세요.

샘플은 매칭 전에 키 이름을 케이스 폴딩하고 구분자를 제거한 후, `Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`, `accessToken`, `clientSecret`, `registrationAccessToken`, `token`, `password`, `secret` 및 `api_key`와 같은 키 아래 값을 재귀적으로 대체합니다. 정규화 및 거부 목록은 동일한 형식을 사용해야 하므로 camelCase, 하이픈, 언더스코어 및 점 변형이 서로의 정책을 우회할 수 없습니다. 프로덕션 수집기는 메서드별 인자 정책을 추가해야 합니다. `query`와 같이 무해한 키도 개인 정보나 규제 데이터를 포함할 수 있기 때문입니다.

편집된 증거 번들을 해시 처리합니다. 특정 조사가 필요할 때만 원본 캡처를 승인된 단기 시스템에 보관합니다. 다이제스트는 어떤 편집된 번들이 결정을 주도했는지 증명하며, 제거된 값을 드러내지 않습니다.

## 건강 상태 및 롤백을 게이트의 일부로 포함하기

프로토콜 준수는 릴리스에 필요하지만 충분하지는 않습니다. 준수된 후보는 여전히 시간 초과, 메모리 누수, 의존성 과부하가 발생할 수 있습니다.

롤아웃 전에 건강 상태 윈도우를 정의합니다:

- 최소 샘플 수
- 최대 오류율
- 최대 지연 백분위수
- 포화 또는 리소스 제한
- 관찰 기간
- 수용된 기준선과의 비교

롤아웃 전에 롤백 증거도 정의합니다:

- 정확한 이전 버전
- 수용 증거 다이제스트
- SHA-256 아티팩트 및 디스크립터 핀
- 현재 레지스트리 상태
- 현재 건강 상태 결과
- 라우트 복원 절차
- 신뢰할 수 있는 릴리스 컨트롤러 신원이 해당 필드들에 대해 수행한 증명(attestation)

후보가 실패한 후뿐만 아니라 승격 전에 롤백 대상이 검증되고 건강 상태여야 합니다. 사용 가능한 복구 경로가 없는 성공적인 릴리스는 프로덕션 준비가 완료되지 않은 것입니다.

후보가 실패하고 롤백 대상이 해당 증거를 결여한 경우, 추측하지 말고 트래픽을 유지합니다. "거기에 있던 것으로 롤백"은 운영적 통제 수단이 아닙니다.

준비 상태를 비어 있지 않은 버전, `healthy: "yes"`, 임의의 증거 문자열 같은 진위(truthiness) 체크로 환원하지 마세요. 샘플은 정확한 타입, 활성 상태, 세 개의 SHA-256 다이제스트, 신뢰할 수 있는 서명자, 그리고 전체 롤백 페이로드에 대한 유효한 HMAC-SHA-256 증명(attestation)을 요구합니다. 그 결정론적 데모 키는 비비밀 고정값(fixture)입니다. 프로덕션에서는 릴리스 경계에서 보호된 키, KMS 검증 결과, 또는 공개 키 증명 검증기를 주입하세요.

릴리스 게이트는 빈 트랜스크립트, SDK 차이점, 또는 프록시 증거도 거부합니다. 각 소스는 유효한 증거 다이제스트를 담아야 합니다. 녹색 건강 상태 윈도우는 관찰되지 않은 경계를 채울 수 없습니다.

## 구현하기

표준 라이브러리 하네스를 실행합니다:

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
```

이 데모는 유효한 완료 결과와 잘못된 완료 결과를 포함하여 정확히 15개의 골든 및 네거티브 트랜스크립트를 실행하며, 원시 결과와 SDK 뷰를 비교하고, 원본 오류를 축소한 프록시를 검사하고, 헬스를 평가하고, 롤백 증거를 인증하며, 해당 대상을 선택합니다.

예상 형태:

```json
{
  "transcriptsPassed": 15,
  "transcriptsTotal": 15,
  "sdkDroppedFields": ["futureHint"],
  "proxyIssues": [
    "proxy collapsed a protocol error into HTTP 500",
    "proxy changed the origin JSON-RPC body"
  ],
  "releaseAction": "rollback",
  "evidenceDigest": "..."
}
```

`code/main.py`를 이 순서대로 읽습니다:

1. `validate_request()`는 시대별 요청 및 헤더 규칙을 강제합니다.
2. `validate_result()`는 누락된 레거시 판별자, 유효한 현대 값, 확장 및 알 수 없는 값을 분리합니다.
3. `select_era()`는 엄격하고 제한된 폴백 정책을 구현합니다.
4. `run_transcript()`는 골든 및 네거티브 픽스처를 평가합니다.
5. `compare_sdk_view()`는 정규화 차이를 노출합니다.
6. `inspect_proxy()`는 ingress, origin 및 egress 증거를 비교합니다.
7. `redact()`는 증거 해싱 전에 명백한 비밀을 제거합니다.
8. `rollback_evidence_ready()`는 정확한 pin 필드와 신뢰할 수 있는 릴리스 증명을 검증합니다.
9. `ReleaseGate.evaluate()`는 비어 있지 않은 적합성, SDK, 프록시, 헬스 및 롤백 증거를 결합합니다.

## 사용하기

네 가지 지점에서 하네스를 실행합니다:

1. 프로세스 내 테스트 어댑터를 사용하여 모든 구현 변경 시.
2. 실제 전송을 통해 빌드된 클라이언트 및 서버 바이너리에 대해.
3. 스테이징 환경의 배포된 프록시 또는 게이트웨이를 통해.
4. 라이브 헬스 및 롤백 증거를 사용하여 카나리 롤아웃 중에.

레이어 전체에 걸쳐 동일한 안정적 케이스 이름을 유지합니다. `negative-header-body-mismatch`는 단위, 엔드 투 엔드, 프록시 및 카나리 보고서에서 동일한 불변성을 의미해야 합니다. 경계가 변경되었으므로 증거 다이제스트는 다를 수 있지만, 요구 사항은 달라져서는 안 됩니다.

픽스처 스키마는 버전 관리에 저장합니다. 편집된 실행 증거는 릴리스 시스템에 저장합니다. 단기 원시 캡처는 인시던트 접근 제어 하에서만 저장합니다.

## 인터랙티브 랩

### 랩 A: 시대 경계를 증명합니다

`code` 디렉토리에서 Python을 엽니다:

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations/code
python3 -q
```

실행합니다:

```python
from main import *
validate_result({"tools": []}, "legacy")
validate_result({"tools": []}, "modern")
```

레거시 호출은 `complete`를 추론합니다. 현대 호출은 `ProtocolViolation`를 발생시킵니다. 이제 폴백을 테스트합니다:

```python
select_era({"kind": "timeout"}, "fallback")
select_era(
    {"kind": "timeout"},
    "fallback",
    legacy_allowed=True,
    legacy_evidence={"kind": "initialize_success", "protocolVersion": LEGACY_VERSION},
)
select_era({"kind": "jsonrpc_error", "code": -32021}, "fallback")
```

첫 번째 타임아웃은 침묵이 레거시 증거가 아니므로 안전하게 실패합니다. 두 번째 호출은 구성이 허용하고 유효한 레거시 초기화 결과가 관찰되었기 때문에 레거시를 선택합니다. 인식된 기능 누락 오류는 현대적 브랜치를 증명합니다.

### 실험실 B: 추가 필드 대 판별자

```python
validate_result({"resultType": "complete", "tools": [], "futureHint": True}, "modern")
validate_result({"resultType": "future_mode", "tools": []}, "modern")
```

첫 번째 결과는 `futureHint`을 보존합니다. 두 번째는 라이프사이클 판별자가 알려지지 않았기 때문에 거부됩니다.

### 실험실 C: SDK 변환 검사

```python
compare_sdk_view(
    {"resultType": "complete", "tools": [], "futureHint": {"mode": "new"}},
    {"tools": []},
)
```

컴포넌트가 `futureHint`을 무시할 수 있는지, 아니면 반드시 전달해야 하는지 결정하세요. 그 선택을 릴리스 정책에 기록하세요. 차이를 조용히 지우지 마세요.

### 실험실 D: 프록시 복구

데모 교환을 수정하여 아웃바운드가 원본 상태와 본문을 보존하도록 하세요. `python3 main.py`을 다시 실행하세요. 프록시 문제가 사라져야 하지만, SDK 차이는 여전히 승격을 차단합니다. 그런 다음 SDK 뷰에 `futureHint`을 포함하고 모든 증거 소스가 통과할 때 `promote`로 동작이 변경되는지 관찰하세요.

## 연습 실험실

하네스에 요청 범위 SSE 트랜스크립트를 추가하세요.

요구사항:

- 응답 상태, 콘텐츠 유형, 순서화된 SSE 이벤트 및 스트림 종료를 캡처하세요.
- 각 JSON-RPC 이벤트가 유효한 시대별 결과 또는 오류를 가지고 있음을 증명하세요.
- 전달하기 전에 전체 스트림을 버퍼링하는 프록시에 대한 부정적인 케이스를 추가하세요.
- JSON-RPC id가 요청과 다른 SSE 이벤트에 대한 부정적인 케이스를 추가하세요.
- 증거를 작성하기 전에 이벤트 데이터를 편집하세요.
- 스트림 지속 시간, 첫 이벤트 지연 및 이벤트 수를 헬스 윈도우에 포함하세요.
- 스트림이 실패할 때 릴리스 게이트가 증거가 있는 롤백 대상만 선택하도록 하세요.

동일한 케이스가 직접 실행되고 프록시를 통해 실행되며, 동작을 변경한 정확한 경계를 식별하는 보고서가 생성되면 성공입니다.

## 검증하기

데모 및 결정적 테스트 스위트를 실행하세요:

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

검증은 다음을 증명해야 합니다:

- 포함된 모든 골든 및 네거티브 트랜스크립트가 예상된 결과에 도달합니다
- 모던 요청은 정확한 네임스페이스 메타데이터 키를 요구합니다
- HTTP 헤더 이름은 대소문자를 구분하지 않고 매칭되며, 인코딩된 `Mcp-Name` 값은 정확히 디코딩됩니다
- 헤더와 바디 불일치는 모던 불일치 코드를 반환합니다
- 응답 버전, ID, 결과 또는 오류 배타성, 오류 형식 및 HTTP 매핑이 검증됩니다
- 메소드별 도구 목록, 작업 및 완료 페이로드 요구 사항이 강제됩니다
- 관찰된 모든 `HeaderMismatch`는 실제 HTTP 400 JSON-RPC `-32020` 응답을 요구합니다
- 원시 `Mcp-Name` 공백은 거부되지만, 정확한 센티널 인코딩된 공백은 왕복 왕복됩니다
- 누락된 `resultType`는 선택된 레거시 시대에서만 유효합니다
- 추가 필드는 원시 검증을 통과하지만, 알 수 없는 결과 유형은 실패합니다
- 확장 결과 유형은 광고된 기능을 요구합니다
- 인식된 모던 오류는 레거시 폴백을 유발하지 않습니다
- 알림은 JSON-RPC 응답을 생성하지 않습니다
- SDK 장부 제거와 의미적 필드 손실이 구분됩니다
- 프록시 오류 붕괴가 감지되며, camelCase 및 구분자 변형에 걸쳐 자격 증명이 재귀적으로 마스킹됩니다
- 승격은 비어 있지 않은 트랜스크립트, SDK, 프록시 및 건강한 운영 증거를 요구합니다
- 승격 및 롤백 모두 인증된, 고정된, 활성, 건강한 롤백 대상을 요구합니다

## 프로덕션 실패 모드

| 실패 | 약한 테스트가 보고하는 내용 | 하네스가 증명해야 하는 내용 |
|---|---|---|
| SDK가 누락된 판별자를 합성함 | “tools/list 통과” | 원시 모던 결과가 `resultType`가 없으며 유효하지 않음 |
| `-32021` 이후 클라이언트가 다운그레이드함 | “레거시 재시도 성공” | 인식된 모던 오류는 폴백을 금지함 |
| 알 수 없는 결과 유형이 완료로 취급됨 | “응답 파싱됨” | 광고되지 않은 수명주기 판별자가 거부됨 |
| 프록시가 하나의 도구를 승인하고 오리진이 다른 도구를 실행함 | “요청이 서버에 도달함” | `Mcp-Name`는 모든 홉에서 바디 라우팅 이름과 일치합니다 |
| 하네스가 서버 응답을 읽기 전에 예외를 발생시킴 | “헤더 불일치 테스트 통과” | HTTP 400 및 JSON-RPC `-32020` 응답이 캡처되고 검증됩니다 |
| 프록시가 오리진의 400을 일반적인 500으로 변환함 | “업스트림 오류” | 오리진 및 이그레스 상태와 JSON-RPC 바디가 보존됩니다 |
| 알림 미들웨어가 `{result: null}`를 방출함 | “핸들러가 none을 반환함” | 최종 이그레스 바디가 비어 있고 JSON-RPC 응답이 존재하지 않습니다 |
| SDK가 추가 필드를 제거함 | “타입 지정된 객체가 일치함” | 원본 및 정규화된 뷰에서 정확히 제거된 필드가 표시됩니다 |
| 장애 아티팩트가 베어러 토큰을 유출함 | “디버그 번들 업로드됨” | 해싱, 로깅, 업로드 전에 가려짐 처리가 수행되었습니다 |
| 자격 증명 키 스타일이 가려짐 처리를 우회함 | “거부 목록에 api_key 포함” | CamelCase 및 구분자 변형이 하나의 표준화된 거부 목록 형식을 공유합니다 |
| 카나리에 샘플이 없지만 건강한 것으로 표시됨 | “오류 없음” | 최소 샘플 수 강제가 적용됩니다 |
| 롤백이 알 수 없는 빌드를 선택함 | “이전 배포가 복원됨” | 대상 버전, 수용 다이제스트, 고정(pins), 상태 및 건강 상태가 존재합니다 |

## 운영 규칙

보내는 바이트, 모든 중간자가 전달하는 바이트, 각 SDK가 노출하는 의미론, 그리고 압박 상황에서 운영이 사용할 증거를 테스트해 보세요. 호환성은 명시적인 분기입니다. 롤백은 증거에 기반한 릴리스 작업입니다. 둘 다 허용적인 파서로 인한 우연한 부작용이 되어서는 안 됩니다.
