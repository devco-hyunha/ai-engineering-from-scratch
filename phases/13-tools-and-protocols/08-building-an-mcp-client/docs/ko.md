# MCP 클라이언트 구축: 발견, 라우팅 및 이중 시대 폴백

> 현대적인 MCP 클라이언트는 모든 요청에서 계약(contract)을 반복합니다. 가장 어려운 호환성 결정은 오래된 서버가 실제로 오래된 것인지, 아니면 현대적인 서버가 수정 가능한 오류를 보고하는 것인지를 파악하는 것입니다.

**유형:** Build
**언어:** Python
**선수 요건:** 13단계, 07강
**시간:** 약 85분

## 학습 목표

- 모든 MCP `2026-07-28` 요청을 최신 메타데이터로 구축하세요.
- stdio 서버를 `server/discover`로 프로빙(probing)하고 상호 지원되는 버전을 선택하세요.
- 명시적으로 허용 목록(allowlist)에 포함된 피어(peer)에만 제한된 레거시 프로빙을 승인하세요.
- 지원되는 개정(revision)에 대한 긍정적인 `initialize` 결과를 검증한 후에만 레거시 시대를 허용하세요.
- 충돌을 조용히 덮어쓰지 않고 결정적인 도구 목록을 병합하세요.
- 프로토콜 세션을 발명하지 않고 각 도구를 소유한 피어로 호출을 라우팅하세요.

## 문제점

에이전트 호스트는 일반적으로 여러 MCP 서버와 통신합니다. 각 서버를 발견하고, 도구 카탈로그를 병합하며, 중복된 이름을 해결하고, 호출을 라우팅하고, 전송(transmission) 실패로부터 복구해야 합니다.

`2026-07-28` 개정(revision)은 모든 요청이 자기 완결적(self-contained)이므로 안정 상태(steady state)를 더 단순하게 만듭니다. 호환성은 시작(startup)을 더 미묘하게 만듭니다. 클라이언트는 다음을 만날 수 있습니다:

- 선호 버전을 지원하는 현대적인 서버;
- 인식된 버전 또는 헤더 오류를 반환하는 현대적인 서버;
- `server/discover`를 들어본 적이 없는 레거시 서버;
- `initialize`를 받을 때까지 침묵하는 레거시 서버.

모든 프로빙(probing) 오류를 레거시로 취급하는 것은 위험합니다. 잘못된 현대적인 요청, 과부하된 서버, 죽은 프로세스, 오래된 서버는 모두 동일한 시간 초과(timeout)나 연결 종료를 생성할 수 있습니다. 이러한 신호는 모호합니다. 클라이언트는 레거시 시대를 선택하기 전에 명시적인 운영자 의도와 긍정적인 프로토콜 증거를 결합해야 합니다.

## 개념

### 프로토콜 세션이 아닌 피어(peer)

각 서버 프로세스나 엔드포인트에 대해 하나의 전송 피어 레코드를 유지하세요:

- 전송 핸들(handle) 또는 전송(send) 함수;
- 선택된 프로토콜 시대 및 버전;
- 마지막으로 발견된 서버 기능;
- 마지막 결정적 도구 목록;
- 상관 관계를 위한 대기 중인 요청 ID;
- 전송 상태.

이것은 클라이언트 장부 기록입니다. 프로토콜 세션 상태가 아닙니다. 최신 MCP에서는 서버가 모든 요청에서 현재 버전과 기능을 계속 수신합니다.

### 모든 최신 요청을 처음부터 구축하기

```python
def modern_request(request_id, method, params, version, capabilities):
    return {
        "jsonrpc": "2.0",
        "id": request_id,
        "method": method,
        "params": {
            **params,
            "_meta": {
                "io.modelcontextprotocol/protocolVersion": version,
                "io.modelcontextprotocol/clientCapabilities": capabilities,
                "io.modelcontextprotocol/clientInfo": CLIENT_INFO,
            },
        },
    }
```

연결 객체에 메타데이터를 한 번만 첨부하고 전송된 것으로 가정하지 마세요. 최종 직렬화된 요청을 스탬프하고 검사해 보세요.

### 최신 발견

`server/discover`는 지원되는 버전, 서버 기능, 지침, 캐시 힌트 및 권장 서버 식별자를 반환합니다. 클라이언트는 상호 지원되는 최신 버전을 선택합니다.

최신 전용 클라이언트에게는 발견이 선택적이지만, stdio에서는 권장됩니다. 일부 레거시 서버는 초기화 전에 작업을 허용하므로, `tools/list`를 먼저 보내면 모호한 성공이 발생할 수 있습니다. `server/discover`는 명확한 시대 경계를 만듭니다.

### stdio 호환성 탐지

듀얼 시대 stdio 클라이언트는 다른 요청 전에 선호하는 최신 메타데이터와 함께 `server/discover`를 전송합니다. 세 가지 결과 클래스가 있습니다:

1. **DiscoverResult.** 서버가 최신입니다. 상호 지원되는 버전을 선택하고 요청별 메타데이터를 사용하여 계속 진행합니다.
2. **인식된 최신 오류.** 서버가 최신입니다. `-32022`의 경우 `data.supported`에서 선택하고 새 요청 ID로 재시도하세요. 헤더 또는 기능 오류의 경우 요청을 수정하세요. `initialize`를 전송하지 마세요.
3. **모호한 신호.** 인식되지 않는 JSON-RPC 오류, 시간 초과, 연결 종료 또는 빈 응답은 시대를 식별하지 못합니다. 해당 정확한 피어가 레거시 호환성을 위해 설정되지 않은 한, 안전하게 실패(fail closed)하세요.

인식된 최신 프로토콜 오류는 다음과 같습니다:

- `-32020` HeaderMismatch
- `-32021` MissingRequiredClientCapability
- `-32022` UnsupportedProtocolVersion

피어가 레거시 허용 목록에 있더라도 인식된 최신 오류는 최신 상태로 유지됩니다. 서버가 최신 오류 어휘를 이해한다는 것을 증명하면, `initialize`를 전송하는 것은 다운그레이드가 됩니다.

`-32601`를 긍정적인 레거시 증거로 취급하지 마세요. 이는 명시적으로 허용 목록에 포함된 피어가 단 한 번의 레거시 프로브를 수행할 자격을 갖게 할 뿐입니다. 이 규칙은 시간 초과, 연결 종료, 빈 응답에도 동일하게 적용됩니다.

### 허용 목록은 운영자의 의도이지 증거가 아닙니다

레거시 호환성은 고정된 피어 구성의 명시적인 속성이어야 합니다:

```python
client.add_server("archive", archive_transport, allow_legacy=True)
```

해당 선택을 설정된 명령이나 엔드포인트에 바인딩하세요. 임의의 서버가 더 약한 시맨틱을 스스로 선택할 수 있게 하는 와일드카드를 사용하지 마세요. `allow_legacy=True`가 없는 피어는 모호한 발견 결과 이후에 실패하며 `initialize`를 절대 받지 못합니다.

허용 목록은 프로브 권한을 부여합니다. 에라를 선택하지는 않습니다. 클라이언트는 전송 계층이 강제하는 마감 시간 하에 하나의 `initialize`를 전송한 후, 다음 모든 조건을 요구합니다:

- 요청 ID가 일치하는 JSON-RPC `2.0` 응답;
- 정확히 하나의 `result`가 있고 `error`가 없어야 함;
- 클라이언트의 설정된 레거시 리비전 집합에 `protocolVersion`가 포함되어야 함;
- 객체 값의 `capabilities` 필드;
- 비어 있지 않은 문자열 `name` 및 `version` 필드를 가진 `serverInfo` 객체.

시간 초과, 연결 종료, 오류 응답, 잘못된 결과, ID 불일치, 지원되지 않는 리비전은 fail-closed로 처리됩니다. 구조적으로 유효한 긍정적 결과만 레거시 에라를 선택합니다. 코드는 `legacy_probe_timeout_ms`를 전송 어댑터에 전달합니다; 실제 stdio 또는 HTTP 어댑터는 해당 마감 시간을 단순히 기록하는 것이 아니라 이를 강제해야 합니다.

선택된 에라를 전송 피어에 대해 캐시하세요. 모든 호출 전에 다시 프로브하지 마세요.

### 레거시는 호환성 분기입니다

유한한 프로브가 유효한 긍정적 레거시 증거를 반환하면, 클라이언트는 해당 리비전에서 정의된 대로 선택된 레거시 버전을 정확히 사용합니다:

1. 응답 엔벨로프와 상관 ID를 검증하세요.
2. 협상된 리비전이 설정된 레거시 집합에 있는지 검증하세요.
3. 검증된 기능과 서버 식별자를 기록하세요.
4. 모든 검사가 통과한 후에만 `notifications/initialized`를 전송하세요.
5. 해당 전송 수명 동안 레거시 요청 형식을 사용하세요.

이 분기는 알려진 피어와의 상호 운용성을 위해 존재합니다. 새로운 서버나 새로운 요청의 기본 설계가 아닙니다. 전송이 재시작되거나 엔드포인트가 변경되면, 피어 시대 캐시를 버리고 다시 협상하세요.

### 도구 발견 및 캐싱

각 활성 피어에 대해 `tools/list`를 호출하세요. 최신 결과는 `resultType`, `ttlMs`, `cacheScope`를 포함합니다. 올바른 인증 컨텍스트 내에서 신선도 힌트를 따르세요. 만료되거나 구독된 목록 변경 이벤트가 발생하면 다시 가져오세요.

클라이언트는 레거시 서버에서 `resultType`가 누락된 경우 `"complete"`로 처리해야 합니다. 이전 협상된 시대의 응답에 대해 최신 캐시 필드를 요구하지 마세요.

서버는 결정적인 순서를 반환해야 합니다. 클라이언트도 병합 전에 정렬하여, 로컬 레지스트리 순서가 프로세스 시작 시간에 의존하지 않도록 해야 합니다.

### 충돌 방지 네임스페이스 병합

두 서버가 모두 `search`를 노출할 수 있습니다. 선언된 정책을 선택하세요:

1. **충돌 시 접두사 사용.** 첫 번째 표준 이름을 유지하고, 이후 충돌은 `<server>/<tool>`로 노출하세요.
2. **충돌 시 거부.** 중복을 로드하지 말고, 명확한 구성 오류를 표시하세요.
3. **침묵 덮어쓰기.** 절대 사용하지 마세요. 모델이 선택한 작업이 어떤 서버로 전달되는지 숨겨집니다.

표준 이름과 로컬 이름을 모두 저장하세요. 모델은 표준 이름을 봅니다. 나가는 `tools/call`는 소유 서버가 선언한 로컬 이름을 사용합니다.

### 호출 라우팅

라우팅은 순수한 조회입니다:

```text
canonical tool name
  -> peer name + local tool name
  -> new JSON-RPC request id
  -> modern request metadata or explicit legacy shape
  -> matching response id
```

소유 전송이 사용 불가능할 때 호출을 보내지 마세요. 전송을 재연결하거나 재시작한 후, 발견 및 `tools/list`를 다시 실행하세요. 손상된 전송에서 손실된 최신 진행 중 요청은, 작업의 안전 정책이 허용할 경우 새로운 JSON-RPC id로 재시도할 수 있습니다.

### 알림 및 구독

최신 목록 및 리소스 변경은 클라이언트가 연 `subscriptions/listen` 스트림에서만 도착합니다. 클라이언트는 알림 필터를 보내고, `notifications/subscriptions/acknowledged`를 기다리며, 알림 메타데이터의 listen 요청 id와 이벤트를 상관관계 지어야 합니다.

연결이 끊어지면, 새로운 listen 요청을 열고 관련 목록이나 리소스를 다시 가져오세요. 최신 스트림은 `Last-Event-ID`로 재개되지 않습니다.

### 서버 주도 요청 없음

최신 서버는 샘플링, 유도, 루트와 같은 요청에 대해 독립적인 JSON-RPC 요청으로 클라이언트를 호출하지 않습니다. `input_required`을 반환하며, 클라이언트는 내장된 입력 요청을 처리한 후 원래 요청을 재시도합니다.

입력을 처리하는 동안 피어의 응답 리더를 차단하지 마세요. 상관관계를 유지하고 재시도를 위해 새로운 JSON-RPC id를 생성하세요.

```figure
tp-client-merge
```

## 사용하기

`code/main.py`은 프로토콜 결정이 가시적으로 유지되도록 프로세스 내 피어 함수를 사용합니다. 두 개의 최신 피어와 의도적으로 허용 목록에 포함된 하나의 레거시 피어에 연결한 후, 그들의 도구를 병합하고 라우팅합니다. 트랜스포트 호출 함수는 시간 제한 예산을 받으므로, 호환성 분기가 무제한 프로브를 숨길 수 없습니다.

```bash
cd code
python3 main.py
python3 -m unittest discover tests -v
```

테스트는 일반적인 데모가 놓치는 경계를 증명합니다:

- 최신 요청은 메타데이터를 반복합니다;
- `-32022`은 초기화 없이 최신 발견을 재시도합니다;
- 인식된 최신 오류는 허용 목록에 포함된 피어에 대해서도 격하되지 않습니다;
- 시간 초과, 연결 종료, 빈 응답, 인식되지 않은 오류는 허용 목록이 없으면 `initialize`을 트리거하지 않습니다;
- 허용 목록에 포함된 피어는 유효하고 지원되는 `initialize` 결과 후에만 레거시가 됩니다;
- 잘못된 형식 및 지원되지 않는 레거시 결과는 피어를 사용 불가능하게 만듭니다;
- 성공적으로 선택된 시대는 트랜스포트 수명 동안 캐시됩니다.

## 연습 문제

1. 가짜 서버가 상호 지원되는 버전 없이 `-32022`을 반환하도록 만드세요. 클라이언트가 `initialize`을 보내는 대신 실패하는지 확인하세요.
2. 가짜 레거시 서버를 허용 목록에 추가하고, 그 제한된 `initialize` 프로브가 시간 초과되도록 한 후, 피어가 `unknown` 상태로 유지되고 사용 불가능함을 증명하세요.
3. 두 개의 인증 컨텍스트에 대해 `cacheScope: "private"` 도구 목록을 추가하세요. 클라이언트가 한 컨텍스트의 캐시된 결과를 다른 컨텍스트와 공유하지 않는지 확인하세요.
4. 충돌 정책을 거절로 변경하고, 두 피어 이름이 포함된 오류로 시작이 실패하도록 만드세요.
5. 유한한 `subscriptions/listen` 시뮬레이터를 추가하세요. 스트림 손실 시, 새로운 요청 id로 다시 리스닝하고 도구를 다시 가져오세요.

## 핵심 용어

| 용어 | 의미 |
|------|---------|
| 피어 | 하나의 서버 전송 및 그 발견된 데이터에 대한 클라이언트 측 기록 |
| 프로토콜 시대 | 현대의 요청별 메타데이터 또는 레거시 초기화 의미론 |
| 발견 프로브 | stdio 시대를 식별하는 데 사용되는 초기 `server/discover` |
| 인식된 현대적 오류 | 현대적 동작을 증명하고 레거시 폴백을 금지하는 오류 |
| 레거시 허용 목록 | 고정된 피어에 대해 하나의 제한된 호환성 프로브를 허용하는 운영자 구성 |
| 긍정적 레거시 증거 | 명시적으로 지원되는 레거시 개정판에 대한 유효하고 상관된 `initialize` 결과 |
| 병합된 네임스페이스 | 모든 활성 피어에 걸친 표준화된 도구 이름 |
| 충돌 정책 | 중복된 도구 이름에 대한 접두사 또는 거부 규칙 |
| 시대 캐시 | 하나의 전송 피어에 대해 저장된 현대적 또는 레거시 동작 |
| 전송 복구 | 새로운 id로 안전하게 재시작 또는 재연결, 재발견, 재목록화 및 재시도 |
