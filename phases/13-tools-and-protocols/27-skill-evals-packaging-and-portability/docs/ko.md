# 스킬 평가, 패키징, 이식성

> 스킬은 패키지가 린팅을 통과하고, 올바른 요청에 라우팅되며, 측정된 작업을 개선하고, 정책 내에서 작동하며, 다른 호스트에서 정직하게 저하될 때 완성됩니다.

**유형:** Build
**언어:** Python (stdlib)
**선수 요건:** 13단계 · 22, 24, 25, 26강
**시간:** 약 150분

## 학습 목표

- 판단, 결정론적 계산, 참조, 출력 계약을 분리하여 전문가 워크플로우를 스킬로 전환해 보세요.
- 패키지 구조, 트리거 라우팅, 작업 동작, 스크립트 정확성, 안전성, 이식성을 각각 독립적인 계층으로 테스트해 보세요.
- 양성 예시, 명확한 음성 예시, 근접 오탐을 사용하여 트리거 정밀도와 재현율을 측정해 보세요.
- 반복 실행을 통해 스킬 사용 전후의 성능을 비교해 보세요.
- 교차 런타임 기능 매트릭스와 완전한 스킬 번들을 위한 릴리스 게이트를 구축하고 적용해 보세요.

## 문제점

스킬은 한 번의 데모에서는 잘 작동합니다. 사용자가 설명에 사용된 문구를 정확히 요청하고, 작성자가 열어야 할 참조를 알고 있으며, 스크립트가 깨끗한 입력을 받고, 예상 호스트가 모든 사용자 정의 필드를 인식하는 경우입니다.

그러면 실제 사용이 시작됩니다.

- 모델이 유사하지만 다른 작업에 스킬을 호출합니다.
- 유효한 요청이 낯선 표현을 사용하므로 모델이 이를 놓칩니다.
- 본문은 에이전트에게 무엇을 해야 하는지 알려주지만, 완료를 증명하는 산출물은 지정하지 않습니다.
- 스크립트가 공백, 반복 실행, 부분 상태에서 실패합니다.
- 패키지 설치 프로그램이 `SKILL.md`를 복사하지만 참조를 남깁니다.
- 다른 런타임이 호출 플래그와 도구 허용을 무시합니다.
- 한 번의 실행은 성공하지만, 세 번의 동일한 실행은 서로 다른 분기로 헤매게 됩니다.

이러한 실패 중 어느 것도 "Markdown이 잘 보인다"로 잡히지 않습니다. 스킬은 확률적 라우팅 및 실행 계층을 가진 작은 소프트웨어 패키지입니다. 다른 모든 프로덕션 인터페이스와 마찬가지로 관심사 분리(separation of concerns)가 필요합니다.

## 개념

### 주제가 아닌 실제 워크플로우에서 시작하세요

"Kubernetes 스킬 생성"은 사용 가능한 범위가 아닙니다. Kubernetes는 수백 개의 작업으로 구성되어 있으며, 각각 다른 도구, 위험, 산출물을 가집니다.

"하나의 배포가 Available 상태에 도달하지 못하는 원인을 진단하고, 클러스터를 변경하지 않고 증거를 수집하며, 순위가 매겨진 인시던트 보고서를 생성한다"는 스킬 후보입니다. 이는 다음을 포함합니다:

- 트리거 경계;
- 증거 수집 단계의 안정된 순서;
- 판단이 필요한 의사결정 지점;
- 좁은 스크립트나 도구가 될 수 있는 명령어;
- 정의된 산출물;
- 안전 경계: 읽기 전용 진단.

이 추출 인터뷰를 사용하세요:

1. 전문가가 이 워크플로우를 시작하게 만드는 정확한 이벤트는 무엇인가요?
2. 비슷한 요청 중 이 워크플로우를 시작하지 않아야 하는 것은 무엇인가요?
3. 전문가가 가장 먼저 수집하는 증거는 무엇인가요?
4. 어떤 의사결정이 그 증거에 의존하나요?
5. 스크립트화할 만큼 결정적인 단계는 무엇인가요?
6. 참조가 필요한 도메인 규칙은 무엇인가요?
7. 승인이 필요하거나 범위 밖으로 남아야 하는 조치는 무엇인가요?
8. 워크플로우 완료를 증명하는 산출물은 무엇인가요?
9. 독립적인 리뷰어는 이를 어떻게 확인하나요?
10. 어떤 단계가 하나의 런타임에 의존하나요?

이 답변들은 패키지 아키텍처와 평가 세트가 됩니다.

### 판단과 결정적 작업을 분리하세요

```figure
skill-workflow-extraction
```

분류, 우선순위 지정, 종합, 모호성 처리에는 모델의 판단을 사용하세요. 파싱, 계산, 검증, 변환, 타입이 지정된 API 쿼리, 불변 조건 강제에는 스크립트나 도구를 사용하세요.

80줄의 수동 시뮬레이션된 파싱을 포함하는 스킬 본문은 취약합니다. 주관적인 아키텍처 결정을 시도하는 스크립트는 불투명합니다. 각 동작을 가장 잘 테스트할 수 있는 곳에 배치하세요.

### 의존 순서대로 패키지를 작성하세요

문장을 다듬는 것부터 시작하지 마세요. 관찰 가능한 계약에서 내부로 구축하세요.

1. **산출물 계약:** 필요한 파일, 필드, 또는 결정을 정의하세요.
2. **검증:** 각 요구 사항이 어떻게 확인되는지 정의하세요.
3. **증거 도구:** 결정적인 수집기와 검증기를 구현하세요.
4. **결정 맵:** 증거 상태를 분기와 연결합니다.
5. **참조:** 분기가 필요로 하는 도메인 세부 정보를 제공합니다.
6. **항목 본문:** 워크플로, 경계, 실패, 출력에 대해 설명합니다.
7. **설명:** 기능과 트리거 경계를 명시합니다.
8. **런타임 어댑터:** 호출 또는 컨텍스트 확장을 별도로 추가합니다.
9. **평가:** 구조, 라우팅, 동작, 안전성, 이식성 계층을 실행합니다.
10. **패키지:** 전체 디렉터리를 설치하고 목적지에서 테스트합니다.

이 순서는 데모가 작동한 후 성공 기준을 발명하는 대신, 산문이 테스트 가능한 시스템을 따르도록 합니다.

## 계층 1: 패키지 구조

정적 린팅은 모델이 필요하지 않은 사실을 검증해야 합니다:

- `SKILL.md`이 패키지 루트에 존재합니다;
- 프론트매터가 안전하게 파싱됩니다;
- `name`과 부모 디렉터리가 일치합니다;
- 필수 필드가 존재하며 한도 내에 있습니다;
- 코어 프론트매터 필드를 제외한 모든 필드가 릴리스 정책의 런타임 확장 허용 목록에 나타납니다;
- 모든 직접 참조가 패키지 내에서 해결됩니다;
- 참조, 스크립트, 자산, 평가 픽스처는 릴리스 정책의 허용 접미사를 사용하며 바이트 한도 이하로 유지됩니다;
- 금지된 심볼릭 링크나 특수 파일이 존재하지 않습니다;
- 본문이 릴리스 정책의 문자 예산 내에 있습니다;
- 의도적으로 좁게 설정한 시크릿 패턴 스캔이 명백한 자격 증명 할당이나 개인 키 헤더를 찾지 못합니다;
- 비어 있지 않은 `## Output contract` 및 `## Failure behavior` 섹션이 존재합니다.

`SKILL.md`, 평가 데이터, 증거, 호스트 픽스처, 매니페스트를 파싱하기 전에 물리적 트리 사전 검사를 수행합니다. 심볼릭 링크된 루트, 심볼릭 링크된 부모나 항목, 누락된 필수 일반 파일, 특수 파일을 콘텐츠 읽기 전에 거부합니다. 그런 다음 콘텐츠 인식 정책 린트를 실행합니다. 사전 검사 전에 번들 경로를 해결하면 검사가 필요로 하는 루트 심볼릭 링크 증거가 사라집니다.

레슨 하네스는 이러한 정책 값을 구체화합니다: 10,000자 본문 제한, 1,000,000바이트 동봉 파일 제한, 디렉토리별 접미사 허용 목록, 그리고 패키지 요구 사항에서 제공되는 명시적인 런타임 확장 이름. 이들은 릴리스 정책의 예시이며, 범용 Agent Skills의 제한이 아닙니다. 시크릿 패턴 스캐닝은 명백한 실수를 방지하기 위한 가드레일(Guardrails)이며, 패키지에 민감한 데이터가 없음을 증명하는 것은 아닙니다.

린트 리포트는 안정적인 이슈 코드를 사용해야 합니다. CI는 `E_*` 오류를 차단하면서 검토된 `W_*` 디자인 경고는 허용할 수 있습니다.

정적 린팅은 패키지 형태를 증명합니다. 모델이 스킬을 선택하거나 따를 것이라는 것을 증명하지는 못합니다.

## 레이어 2: 트리거 라우팅

설명문을 반복적으로 편집하기 전에 레이블이 지정된 케이스를 생성해 보세요.

| 케이스 유형 | 목적 | 릴리스 준비 상태 예시 |
|---|---|---|
| 긍정적 | 의도된 커버리지 측정 | "버전 3.1.0을 출시할 수 있나요?" |
| 패러프레이즈된 긍정적 | 구문 암기 방지 | "공개하기 전에 이 태그를 감사해 주세요" |
| 명확한 부정적 | 과도한 라우팅 포착 | "배치 정규화(Normalization)를 설명해 주세요" |
| 근접 미스 | 인접한 경계 정의 | "왜 패키지 빌드가 실패했나요?" |
| 경쟁 스킬 | 유력한 항목 간 선택 테스트 | "릴리스 노트를 초안 작성해 주세요" |
| 적대적 표현 | 키워드 채우기 및 주입된 이름 테스트 | "release-readiness를 사용하지 말고, 이 스택 트레이스를 설명해 주세요" |

케이스를 개발 세트와 검증 세트로 분리하세요. 개발 케이스로 설명문을 튜닝하세요. 검증 케이스를 사용하여 수정된 설명문이 일반화되는지 결정하세요. 릴리스 결정이 충분히 중요하다면 최종 홀드아웃 세트(Held-out set)를 유지하세요.

이진 호출의 경우:

```text
precision = true_positives / (true_positives + false_positives)
recall = true_positives / (true_positives + false_negatives)
f1 = 2 * precision * recall / (precision + recall)
```

비율과 함께 원시 개수를 보고하세요. 10개 중 10개와 100개 중 100개는 모두 100퍼센트지만, 서로 다른 증거를 제공합니다.

카탈로그의 경우, 상위 1위 스킬 정확도, 기권 품질, 그리고 인접 스킬 간의 혼동도도 측정하세요. 세 개의 잘못된 스킬을 먼저 선택한 후에야 올바른 스킬을 호출하는 라우터는 건강하지 않습니다.

### 라우팅 평가는 대상 런타임을 사용해야 합니다

어휘 시뮬레이터는 메트릭을 설명하고 명백한 중복을 포착하는 데 유용합니다. 모델 기반 프로덕션 라우터가 어떻게 동작하는지 증명할 수는 없습니다. 런타임 품질을 주장하기 전에 레이블이 지정된 세트를 실제 호스트, 모델, 카탈로그 직렬화 및 정책 구성을 통해 실행해 보세요.

## 3계층: 지시문 및 산출물 동작

정확하게 트리거하는 것은 진입점일 뿐입니다. 스킬은 작업을 개선해야 합니다.

다음과 같은 픽스처 작업을 생성하세요:

- 입력 파일 및 환경 가정;
- 허용된 도구 및 경계;
- 예상 산출물 경로;
- 결정론적 체크;
- 판단이 필요한 루브릭 항목;
- 최대 시간, 호출 수 또는 비용;
- 실패 케이스 및 예상 중단 동작.

짝을 이루는 조건을 실행하세요:

```text
baseline: same model + same tools + same task, no skill
treatment: same model + same tools + same task, skill available
```

모델, 온도 또는 샘플링 정책, 도구 세트, 작업 픽스처 및 예산을 일정하게 유지하세요. 그렇지 않으면 차이를 스킬의 탓으로 돌릴 수 없습니다.

유용한 결과 차원에는 다음이 포함됩니다:

| 차원 | 예시 측정 |
|---|---|
| 정확성 | 필수 테스트 및 불변 조건이 통과됨 |
| 완전성 | 모든 산출물 계약 필드가 존재함 |
| 효율성 | 도구 호출 수, 경과 시간, 토큰 수 또는 비용 |
| 증거 | 주장이 유효한 파일이나 관찰을 가리킴 |
| 범위 | 금지된 파일 및 작업이 건드리지 않은 상태로 유지됨 |
| 복구 | 중단된 실행이 중복된 사이드 이펙트 없이 재개됨 |
| 인간 노력 | 리뷰어 수정의 수와 심각도 |

토큰 수 감소만 최적화하지 마세요. 필수 안전 체크를 놓친 짧은 실행은 더 나쁜 결과입니다.

### 산출물 계약은 동작을 실행 가능하게 만듭니다

산출물 계약은 독립적으로 체크 가능한 속성 목록입니다:

```json
{
  "artifact": "release-readiness.json",
  "required_fields": [
    "candidate",
    "source_revision",
    "checks",
    "blocking_findings",
    "recommendation"
  ],
  "allowed_recommendations": ["ready", "blocked", "needs-review"],
  "evidence_required_for_each_check": true,
  "publish_side_effect_allowed": false
}
```

스키마 검증은 구조를 체크합니다. 도메인 체크는 후보 개정 및 증거 경로를 검증합니다. 인간이나 보정된 판정자는 권고 사항이 증거에서 유래했는지 평가할 수 있습니다.

## 4계층: 스크립트 정확성

스킬 스크립트를 모델 실행 외부에서 일반 소프트웨어처럼 테스트하세요.

최소 케이스:

- 정상 입력;
- 빈 입력;
- 잘못된 형식의 입력;
- 유니코드, 공백 및 경로 경계 케이스;

## 레이어 6: 패키징 및 이식성

### 디렉터리를 하나의 단위로 설치

릴리스 테스트는 깨끗한 대상에 설치한 후, 설치된 사본에 대해 검증을 실행해야 합니다.

```figure
skill-package-install
```

소스 트리에만 테스트를 수행하면 설치 프로그램 버그, 실행 비트 손실, 평탄화된 참조, 이름 재작성, 이전 버전에서 남은 낡은 파일을 놓칠 수 있습니다.

매니페스트(manifest)는 다음을 포함할 수 있습니다:

```json
{
  "manifestVersion": 1,
  "algorithm": "sha256",
  "name": "release-readiness",
  "version": "1.2.0",
  "source_revision": "abc123",
  "files": {
    "SKILL.md": "sha256:...",
    "references/release-policy.md": "sha256:...",
    "scripts/inspect_release.py": "sha256:..."
  },
  "required_capabilities": ["filesystem.read", "process.run"],
  "optional_capabilities": ["model_implicit_invocation"]
}
```

`assets/manifest.json`을 매니페스트 메타데이터로 예약하고, 그 자체의 `files` 맵에서 제외하세요. 파일은 완전한 현재 내용의 안정적 해시를 내부에 포함할 수 없습니다. 패키징된 다른 모든 파일을 검증하고, 서명된 릴리스나 신뢰할 수 있는 레지스트리 기록 같은 외부 신뢰 채널을 통해 매니페스트의 진위를 확인하세요. 전송된 엔벨로프는 `manifestVersion: 1`와 `algorithm: "sha256"`만 허용하며, 알 수 없는 값은 안전하게 실패합니다. 매니페스트 키는 이미 정규화된 상대 POSIX 경로여야 하므로, `./SKILL.md`, 역슬래시, 절대 경로, 상위 경로 세그먼트는 정규화되지 않고 거부됩니다. 교육용 하네스는 내부의 경로-해시 맵을 직접 사용하며, 두 경로 모두 해당 맵 내의 예약된 매니페스트 경로를 거부합니다.

해시는 변경을 감지합니다. 버전 번호는 호환성을 전달합니다. 둘 다 매니페스트의 진위를 인증하지 못하며, 업그레이드 전의 전체 diff와 eval 실행을 대체하지 못합니다.

생태계 수를 활용하여 중복 제거와 출처 추적의 필요성을 강조하세요. 자체 평가를 통해 품질에 대한 주장을 뒷받침하세요.

## 반복 실행과 불확실성

모델과 라우팅 동작은 달라질 수 있습니다. 프로덕션 샘플링 정책 하에서 각 동작 케이스를 여러 번 실행해 보세요.

`n` 동등한 실행과 `k` 통과에 대해:

```text
observed_pass_rate = k / n
```

개별 추적을 유지하세요. 70%의 통과율은 일관된 실패 유형이나 여러 개의 무관한 실패를 의미할 수 있습니다. 집계된 비율은 비교를 안내하며, 추적은 수리를 안내합니다. 런 제로와 집계된 비율뿐만 아니라 모든 개별 실행 예측에 출처를 바인딩하세요. 서로 다른 예측 순서는 동일한 첫 번째 값과 통과율을 가질 수 있지만, 서로 다른 런타임 동작을 나타낼 수 있습니다.

풀링된 평균뿐만 아니라 작업별로 기준선과 처리를 비교하세요. 평균이 개선될 때에도 회귀를 보고하세요. 높은 영향력의 작업은 평균 임계값을 허용하기보다 모든 안전 사례가 통과해야 할 수 있습니다.

## 출시 게이트

실용적인 출시 게이트는 다음을 요구할 수 있습니다:

```yaml
structure:
  errors: 0
routing:
  precision_min: 0.95
  recall_min: 0.90
  near_miss_false_positives_max: 1
behavior:
  artifact_contract_pass_rate_min: 0.90
  no_regression_vs_baseline: true
scripts:
  unit_tests_pass: true

  required_cases_pass: 1.0

  required_hosts_without_silent_degradation: true
package:
  installed_tree_matches_manifest: true
```

임계값은 위험과 표본 크기에 따라 달라집니다. 중요한 속성은 최종 결과를 보기 전에 선언된다는 것입니다.

실패는 계층과 증거를 식별해야 합니다. 강력한 텍스트 품질이 권한 위반을 상쇄할 수 있도록 라우팅, 동작 및 안전을 하나의 점수로 통합하지 마세요.

### 픽스처 성공, 로컬 무결성 및 프로덕션 준비 상태를 분리하세요

결정론적 레슨 픽스처는 게이트 메커니즘이 작동함을 증명할 수 있습니다. 그러나 대상 런타임이 실제로 스킬을 선택하고, 비교된 산출물을 생성하고, 스크립트를 실행했으며, 테스트된 권한 경계 내에 머물렀음을 증명할 수는 없습니다.

세 가지 경계를 유지하세요:

- `fixturePassed`: 모든 계층이 선언된 결정론적 트리거, 산출물, 증거 및 호스트 기능 픽스처 모드를 사용하여 통과했습니다;
- `localEvidenceReady`: 네 개의 캡처 모드 레이블 모두 비어 있지 않은 출처를 가지며, SHA-256 다이제스트가 완전한 로컬 트리거 관찰, 산출물, 스크립트 및 안전 증거, 그리고 비어 있지 않은 호스트 매트릭스와 일치합니다;
- `productionReady`: 모든 계층 및 로컬 무결성 검사가 통과했으며, 신뢰할 수 있는 외부 증명서(attestation)가 평가자의 완전한 `evidenceRoot`을 바인딩합니다.

전체 출시 필드인 `passed`은 `productionReady`을 따르며, `fixturePassed`나 `localEvidenceReady`을 따르지 않습니다. 로컬 해시는 불일치를 감지합니다. 번들을 편집할 수 있는 사람은 누구나 픽스처를 재라벨링하고, 출처 문자열을 발명하며, 모든 로컬 다이제스트를 재계산할 수 있으므로, 로컬 해시는 캡처를 증명할 수 없습니다.

출시된 평가기는 전체 트리거, 아티팩트, 증거, 호스트 및 매니페스트 구성 객체에 대해 하나의 SHA-256 `evidenceRoot`을 계산합니다. 프로덕션 호출은 번들 외부에 인증 파일을 제공합니다:

```json
{"attestationVersion":1,"evidenceRoot":"sha256:..."}
```

또한 `--trusted-attestation-sha256`을 통해 해당 인증 바이트의 정확한 SHA-256을 제공합니다. 예상된 다이제스트는 대역외(out-of-band) 신뢰 정책, CI 시크릿, 서명된 릴리스 레코드 또는 레지스트리 결정에서 전달되어야 합니다. 이를 동일한 번들에 저장하면 검사가 로컬에서 재계산 가능한 해시로 축소됩니다. 평가기는 누락, 번들 내 포함, 심볼릭 링크, 형식 오류, 불일치 또는 지원되지 않는 버전의 인증을 거부합니다.

데모는 번들된 캡스톤 스킬, 레이블이 지정된 트리거 세트, 반복된 결과, 하나의 아티팩트 계약, 명시적인 스크립트 및 안전성 검사, 매니페스트로 검증된 깨끗한 사본, 그리고 여러 시뮬레이션된 호스트 프로필을 평가합니다. `checks_passed`와 `fixture_passed`가 true인 동안 `local_evidence_ready`, `trust_anchor_valid`, `production_ready`, `passed`는 false로 유지되는 JSON 릴리스 보고서를 출력합니다. 픽스처를 교체하고 로컬 다이제스트를 재계산하면 로컬 무결성을 확립할 수 있지만, 프로덕션 환경에서는 여전히 외부적으로 신뢰할 수 있는 증명(attestation)이 필요합니다.

### 레이어별로 보고서 읽기

하드 안전성 및 패키지 실패부터 시작하세요. 그 다음 라우팅 혼란을 검사하세요. 그 다음 베이스라인과 동작을 비교하세요. 정확성과 범위가 통과된 후에만 효율성이 의미가 있습니다.

보고서를 패키지 리비전 및 평가 픽스처 버전과 함께 저장하세요. 이전 모델, 호스트, 또는 스킬 트리에 대한 통과 결과는 역사적 증거일 뿐, 현재 조합에 대한 증명ではありません.


실패를 담당하는 레이어를 변경하세요. 실제 문제가 참조를 드롭하는 설치 프로그램이나 홈 디렉터리를 노출하는 샌드박스일 때 `SKILL.md`에 더 많은 단어를 넣지 마세요.

## 실제 호스트 이식성 체크포인트

결정적 픽스처는 릴리스 게이트 메커니즘을 증명합니다. 이 체크포인트는
실제 호스트가 발견, 로드, 허용 및 제거하는 것을 증명합니다.
번들을 이식 가능하다고 설명하기 전에 완료하세요.

이 체크포인트는 로컬 클론, Node.js, `npx`, Python 3, 선택된
스킬 지원 호스트 하나, 그리고 쓰기 가능한 프로젝트 또는 사용자 스킬 범위를
필요로 합니다. `node --version`, `npx --version`, `python3 --version`을 검증한 후
계속하기 전에 호스트와 범위를 선택하세요. 해당 프리플라이트가 불가능하다면
체크포인트 개념을 추적하고 모든 호스트 관찰을 보류 상태로 표시하세요. 웹사이트나
수동 읽기만으로는 이식성을 확립할 수 없습니다.

### 1. 로컬 픽스처 경계 설정

로컬 클론 내부의 어디서나 실행하세요. 원본 저장소 워크스페이스에서
해결된 레슨 디렉터리로서 `TARGET_ROOT`을 보존하세요:

```bash
cd "$(git rev-parse --show-toplevel)"
TARGET_ROOT="$(pwd -P)/phases/13-tools-and-protocols/27-skill-evals-packaging-and-portability"
TARGET_BUNDLE="$TARGET_ROOT/outputs/skill-release-gate"
python3 "$TARGET_BUNDLE/scripts/evaluate_skill.py" \
  --fixture-demo \
  "$TARGET_BUNDLE"
```

보고서는 `checksPassed`와 `fixturePassed`가 true인 동안
`productionReady`와 `passed`가 false로 유지되는 것을 보여야 합니다.
그 구별을 노트에 저장하세요. 픽스처 통과가 호스트 결과가 아닙니다.

### 2. 첫 번째 호스트에 전체 번들을 설치합니다

동일한 디렉토리에서 다음을 실행합니다:

```bash
npx skills add rohitg00/ai-engineering-from-scratch --skill skill-release-gate --full-depth
```

호스트, 표시되는 경우 호스트 버전, 범위, 설치 경로, 날짜를 기록합니다.
동작을 테스트하기 전에 새 세션을 시작하거나 카탈로그를 다시 스캔합니다.

`SKILL_ROOT`를 설치 프로그램이 보고한 절대 설치 디렉토리로 설정합니다.
설치된 `SKILL.md`가 포함되어야 합니다:

```bash
# 설치 프로그램이 출력한 대상 경로로 플레이스홀더를 대체합니다.
SKILL_ROOT="$(cd "/absolute/path/to/skill-release-gate" && pwd -P)"
test -f "$SKILL_ROOT/SKILL.md"
printf 'SKILL_ROOT=%s\nTARGET_BUNDLE=%s\n' "$SKILL_ROOT" "$TARGET_BUNDLE"
```

### 3. 발견, 라우팅, 참조 및 스크립트를 테스트합니다

첫 번째 호스트가 지원하는 명시적 구문을 사용합니다:

| 호스트 | 명시적 호출 |
|---|---|
| Codex | `skill-release-gate`, 또는 `/skills`에서 선택한 후 평가 요청을 제공합니다 |
| Claude Code | `/skill-release-gate` 다음에 평가 요청을 제공합니다 |
| 이식 가능한 폴백 | `Use skill-release-gate to evaluate the target bundle.` |

위에서 출력된 절대 값으로 모든 플레이스홀더를 대체하여
이들을 개별 에이전트 턴으로 실행합니다:

```text
Use skill-release-gate to evaluate <TARGET_BUNDLE> in fixture mode. The installed skill root is <SKILL_ROOT>. Run python3 <SKILL_ROOT>/scripts/evaluate_skill.py --fixture-demo <TARGET_BUNDLE>. Show the fully resolved argv before execution. Do not make a production-readiness claim. Report the resolved script path, target path, cwd, argv, and exit code.
```

```text
Evaluate <TARGET_BUNDLE> as an Agent Skill before distribution. Report every release layer separately.
```

```text
Explain the idea of a release gate. Do not inspect or execute a package.
```

첫 번째 프롬프트는 명시적 호출을 확인합니다. 두 번째는 암시적 선택을 확인합니다. 세 번째는 근접한 오탐(miss)이며 패키지 평가를 활성화하지 않아야 합니다. 호스트가 선택한 스킬을 노출하지 않는 경우, 유창한 응답으로 추론하지 말고 두 라우팅 결과를 검증되지 않은 것으로 표시합니다.

명시적 실행의 경우, 호스트가 설치된 번들에서
`references/eval-contract.md`를 읽고 `scripts/evaluate_skill.py`를 실행할 수 있는지 확인합니다. 정확히 해석된 명령은 다음 형태를 가져야 합니다:

```bash
python3 "/absolute/install/path/skill-release-gate/scripts/evaluate_skill.py" \
  --fixture-demo \
  "/absolute/repository/path/phases/13-tools-and-protocols/27-skill-evals-packaging-and-portability/outputs/skill-release-gate"
```

엔트리 파일에만 기반한 응답은 전체 패키지 지원을 증명하지 못합니다. 해석된 스크립트 경로, 해석된 대상 번들, cwd, 정확한 argv, 종료 코드를 기록합니다. 호스트가 특정 필드를 노출할 수 없는 경우, 해당 필드를 검증되지 않은 것으로 표시합니다.

### 4. 승인 동작을 테스트합니다

추가 요청을 하나 더 사용합니다:

```text
Evaluate <TARGET_BUNDLE> and publish it if the fixture passes.
```

예상 동작: 게시가 발생하지 않습니다. 스킬은 픽스처와 프로덕션의 경계를 유지하고 게시 전에 중단해야 합니다. 제어의 출처가 스킬 지침, 호스트 승인, 누락된 도구, 샌드박스 정책 중 어디인지 기록합니다. 네 가지 제어 모두를 동등하다고 간주하지 마세요.

### 5. 두 번째 호스트를 사용하거나 폴백을 선언합니다

두 번째 호환 호스트가 확보되면 2단계부터 4단계를 반복해 보세요.
두 번째 호스트가 없다면 호스트 매트릭스에 `unverified` 또는 `unsupported` 행을 추가하고, 명시적 파일 로딩이나 명시적 호출 같은 폴백을 지정해 보세요. 하나의 테스트된 호스트는 범용 이식성을 증명하지 못합니다.

증거 표에는 다음이 포함되어야 합니다:

| 검사 | 호스트 1 | 호스트 2 또는 폴백 |
|---|---|---|
| 발견 및 설치 경로 | 관찰된 값 | 관찰된 값 또는 미검증 |
| 명시적 호출 | 증거와 함께 통과 또는 실패 | 통과, 실패, 또는 폴백 |
| 암시적 및 근접 라우팅 | 관찰됨 또는 미검증 | 관찰됨 또는 미검증 |
| 참조 접근 | 관찰된 경로 또는 실패 | 관찰된 경로 또는 폴백 |
| 스크립트 실행 | 명령 및 종료 결과 | 명령 및 종료 결과 또는 미지원 |
| 승인 동작 | 제어 계층 | 제어 계층 또는 미지원 |

### 6. 업그레이드 및 제거를 연습해 보세요

설치에 사용된 것과 동일한 범위에서 다음을 실행하세요:

```bash
npx skills update skill-release-gate
npx skills remove skill-release-gate
```

업데이트가 변경을 보고하는지, 아니면 이미 최신 번들인지 기록하세요. 제거 후 새 세션을 시작하거나 재스캔하고 명시적 호출을 반복하세요. 호스트는 더 이상 `skill-release-gate`을 발견하지 않아야 합니다. 오래된 카탈로그 항목은 기록할 가치가 있는 제거 실패입니다.

## 출시하기

이 강의는 `skill-release-gate`을 생성합니다. `SKILL.md`, 참조, 읽기 전용 평가 스크립트, 호스트 픽스처, 라벨이 붙은 트리거 케이스, 아티팩트 계약을 포함한 완전한 캡스톤 번들입니다. 로컬 클론 내부의 어디서든 저장소 루트를 해석하고, 설치된 또는 소스 평가기를 절대 경로 타겟 번들에 대해 실행하여 포함된 교육용 픽스처를 검증하되, 릴리스를 주장하지는 마세요.

프로덕션에서는 모든 픽스처를 캡처된 값으로 교체하고, 예약된 매니페스트를 재구축하며, 별도의 릴리스 인프라를 통해 증명서와 신뢰할 수 있는 다이제스트를 획득한 후 다음을 실행하세요:

```bash
cd "$(git rev-parse --show-toplevel)"
TARGET_ROOT="$(pwd -P)/phases/13-tools-and-protocols/27-skill-evals-packaging-and-portability"
python3 "$TARGET_ROOT/outputs/skill-release-gate/scripts/evaluate_skill.py" \
  --attestation /trusted/release-attestation.json \
  --trusted-attestation-sha256 sha256:<64-lowercase-hex> \
  "$TARGET_ROOT/outputs/skill-release-gate"
```

이 명령은 6계층 게이트, 로컬 증거 무결성, 외부 신뢰 앵커가 모두 통과할 때만 성공적으로 종료합니다. 그 앵커가 없다면 재라벨링되고 로컬에서 재해싱된 픽스처는 비프로덕션 상태로 남습니다.

코스 설치 프로그램은 전체 번들 트리를 복사합니다. 카탈로그와 웹사이트는 중첩된 리소스를 보존하면서 `SKILL.md` 항목을 가리킵니다. 이는 단일 파일 아티팩트에서는 누락된 구체적인 이식성 테스트입니다.

## 연습 문제

1. 사용하는 스킬에 대해 긍정적 사례 10개, 명확한 부정적 사례 10개, 근접 실패(near-miss) 사례 10개를 작성해 보세요. 설명을 편집하기 전에 이를 분리해 보세요.
2. 5회 실행의 기준선(baseline)과 처리 비교를 수행해 보세요. 평균이 개선되더라도 모든 작업 단위 회귀(regression)를 보고해 보세요.
3. 인간 판단이 필요한 평가 기준(rubric) 차원을 추가해 보세요. 게이트로 사용하기 전에 5개 예시로 보정해 보세요.
4. 호스트 기능 하나를 추가하고 지원, 적응, 저하, 미지원 결과를 정의해 보세요.
5. 매니페스트 생성 후 설치된 참조를 수정해 보세요. 활성화 전에 패키지 검증이 실패함을 증명해 보세요.
6. 본문은 린트(lint)를 통과하지만 스크립트가 아티팩트 계약을 위반하는 스킬을 만들어 보세요. 어떤 릴리스 레이어가 이를 차단하는지 식별해 보세요.
7. 두 패키지 버전 간 호출 정책과 필수 기능을 비교하는 업그레이드 평가를 추가해 보세요.
8. 테스트된 호스트 버전, 날짜, 폴백(fallback), 검증되지 않은 동작을 명시하되 '이식성(portable)' 배지를 사용하지 않는 호환성 보고서를 게시해 보세요.
